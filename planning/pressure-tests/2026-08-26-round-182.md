# ISS-006 Windows state-root sharing review — round 182

## Disposition

`PASS_TO_REPAIR`.

This is a fresh independent blocker/removal review of the current uncommitted
Windows native profile-custody implementation against pushed HEAD
`7e06766b389c24f2d878480f996633bb2525d8ce`, Rounds 175 and 179–181, the
local Windows SDK, Microsoft filesystem API documentation, and the sole ISS-006
authority.

The complete real two-cycle profile diagnostic now succeeds only when the
retained state-root handle uses
`FILE_SHARE_READ|FILE_SHARE_WRITE|FILE_SHARE_DELETE`. The tracked production
arm opens the same directory with `FILE_SHARE_READ` alone. Every canonical USED
pending record is written, file-flushed, directory-flushed, security/identity
read back, and root-rechecked successfully; then both relative-root
`FileRenameInfo` and full-path `FileRenameInfoEx` fail with
`ERROR_SHARING_VIOLATION` 32. No ATTEMPTED phase or AppContainer mutation
occurs.

This is a share-contract conflict, not evidence that the root is untrusted.
The retained directory handle requests `GENERIC_WRITE` so it can flush directory
metadata. Windows share modes remain attached to that handle for its lifetime;
an incompatible later delete/rename access fails with sharing violation, and
`FILE_SHARE_DELETE` specifically admits later delete access, which includes
rename. Share flags grant no filesystem access: the owner/DACL/SACL and desired
access on each later open still authorize or deny the caller.

The smallest trust-preserving repair is therefore one retained state-root
handle with all three share flags in production and diagnostics, plus stronger
handle-and-path custody at every mutation boundary and exclusive journal-leaf
handles. Closing the root around rename would create a substitution window;
writing directly to the final phase name would add partial-final recovery
states. Both alternatives are larger and less safe.

No human decision or authority-document change is required.

## Exact reviewed implementation fact

`retain_root` currently requests:

```text
FILE_LIST_DIRECTORY | FILE_READ_ATTRIBUTES | READ_CONTROL | GENERIC_WRITE
```

and selects `FILE_SHARE_READ` in production while a diagnostic conditional
adds WRITE and DELETE sharing. The same retained handle is then passed to
`FlushFileBuffers` around journal publication. `persist_phase` opens the pending
leaf with DELETE access and ultimately invokes
`SetFileInformationByHandle(...FileRenameInfoEx...)` to publish it. The real
error occurs only at that rename.

The SDK and Microsoft documentation establish:

- an open request conflicts when its desired access is not admitted by every
  existing handle's share mask;
- `FILE_SHARE_WRITE` admits later write-access opens;
- `FILE_SHARE_DELETE` admits later delete-access opens; delete access includes
  rename; and
- `SetFileInformationByHandle` requires the leaf handle to carry the access
  appropriate to its rename/delete information class.

Changing `FileRenameInfo` structure variants cannot repair an incompatible
directory-handle share contract, as the two real attempted variants confirmed.

## Exact retained-root repair

Production and every diagnostic/fake arm must use exactly:

```text
desired access =
  FILE_LIST_DIRECTORY | FILE_READ_ATTRIBUTES | READ_CONTROL | GENERIC_WRITE

share mode =
  FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE

flags =
  FILE_FLAG_BACKUP_SEMANTICS | FILE_FLAG_OPEN_REPARSE_POINT
```

Delete the compile-time diagnostic share-mode difference. The tracked PE and
test fixture must exercise the same root-open arguments.

The broader share mask is not an authority grant. Before and after every
journal create, write, file flush, directory flush, rename, disposition delete,
and profile API call, native custody must prove all of these independently:

1. the retained root handle still has the captured volume serial, 128-bit file
   ID, directory type, attributes, link count, owner, protected exact DACL,
   exact mandatory-label SACL, and complete self-relative security bytes;
2. `GetFinalPathNameByHandleW` for that retained handle is byte-equal to the
   canonical requested root path;
3. a fresh no-follow open of the current canonical pathname, using the same
   three share flags but only read-attribute/control desired access, has the
   same volume/file ID, type, attributes, link, owner, DACL/SACL/label, security
   bytes, and final path as the retained handle;
4. the fresh probe is closed successfully; and
5. the state-root binding digest remains unchanged.

A moved retained object, same-path replacement, rename-away-and-replace,
reparse substitution, security change, path disagreement, probe denial, or
close ambiguity refuses before further mutation and returns
RECOVERY_REQUIRED whenever a durable nonterminal group may exist. File-ID-only
or final-path-only equality is insufficient.

Future TypeScript custody must independently retain and recheck the ancestor
chain and root topology under Round 175. That later caller does not replace
these native mutation-boundary checks.

## Exclusive journal-leaf publication

Every pending/final journal leaf remains stable/SYSTEM-only and opens with share
mode zero. Strengthen publication so one leaf handle is retained continuously
through the authority-changing portion:

1. create-exclusively open `<final>.pending` with
   `GENERIC_READ|GENERIC_WRITE|DELETE|SYNCHRONIZE`, share zero,
   `CREATE_NEW`, `FILE_FLAG_WRITE_THROUGH|FILE_FLAG_OPEN_REPARSE_POINT`, and the
   exact stable/SYSTEM-only security descriptor;
2. write all canonical bytes, flush the leaf, rewind/read the same handle, and
   verify exact bytes, size, one link, non-reparse regular type, owner/security,
   and captured file ID without closing it;
3. run the complete retained-root/current-path custody check;
4. rename that same retained leaf handle, without replacement, from the exact
   pending basename to the exact final basename under the retained root;
5. while still holding the leaf handle, require its final handle path, volume/
   file ID, type/link/security, and bytes unchanged, require the pending pathname
   absent, flush the retained state-root directory, and recheck root custody;
6. close the leaf handle successfully;
7. reopen the exact final path no-follow with share zero, require the same
   captured file ID and all exact bytes/profile facts, close successfully, and
   recheck root custody again; and
8. only then treat the phase as durable and authorize the next profile API
   mutation.

This removes the current close/readback/reopen-for-delete gap before rename.
If a platform limitation prevents same-handle readback or rename, the slice
refuses; it does not close the retained root, widen a leaf share mask, replace an
existing final record, or downgrade the durability barrier.

Journal loading, pending cleanup, and final-record verification likewise use
share-zero child handles. A root share mask cannot launder a competing leaf
writer because the stable-only DACL and exclusive leaf handle remain exact.

## Rename and retry semantics

Use one reviewed rename arm only. Prefer retained-root-relative
`FileRenameInfo` with the exact final basename and `ReplaceIfExists=FALSE` if it
passes the real diagnostic under the corrected sharing; otherwise the already-
reviewed full canonical final path with `FileRenameInfoEx`, POSIX semantics, and
no replacement is acceptable only after a fresh exact-tree review proves its
buffer/flag/path closure. Do not keep two fallback rename arms in production.

Any rename false return, close failure, root flush ambiguity, final readback
failure, pending residue, or identity disagreement leaves the pending/final
facts for recovery and never advances the in-memory phase. Recovery probes both
fixed names by retained identity, never trusts the return code, and follows the
Round-179/181 conservative prior-final-phase cleanup rules.

`ERROR_SHARING_VIOLATION` remains refusal if observed after the corrected exact
open masks; it cannot be normalized to success or retried by closing custody.

## Proportionality and alternatives

- Share READ|WRITE|DELETE is required compatibility for the broker's own
  retained writable directory and child rename/delete operations. It adds no
  ACE, desired right, principal, path, or candidate capability.
- Retained-handle plus current-path identity/security checks close the path-
  movement risk created by allowing rename-compatible opens.
- Exclusive leaf handles are smaller and stronger than global root exclusivity:
  they serialize the exact record while allowing the required directory
  metadata operations.
- Closing/reopening the root around rename is deleted because it abandons
  custody at the authority boundary.
- Direct final-file writes are deleted because a crash creates a malformed
  final phase indistinguishable from a committed filename and expands recovery.
- Transactions, kernel-native `NtCreateFile`, a service, lock file, alternate
  helper, or generalized journal library are unnecessary.
