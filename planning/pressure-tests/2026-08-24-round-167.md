## OP-R167-1 — hosted executable and artifact byte identity is not exact

The workflow is treated as immutable because `workflowRevision` is pinned to
the protected default-branch SHA. That pins the YAML text, but the packet does
not require each executable `uses:` dependency—checkout, Node setup, artifact
upload/download, or any other action—to be referenced by a reviewed full commit
SHA. A stable YAML file containing `actions/upload-artifact@v7`, another tag, or
a branch still satisfies every written event/ref/permission/root rule while
executing bytes that can move after independent review. Those transitive action
bytes are outside both stable bundle manifests.

This omission also leaves the provider-record artifact equality ambiguous. The
post-terminal verifier currently requires provider API SHA-256/length to equal
“downloaded canonical bytes”. With the default artifact upload mode, the API
identity and download are the artifact ZIP/archive bytes, not the contained
canonical provider-record JSON. A current upload action can instead use an
explicit single-file non-archive mode, but the packet does not select that mode,
pin an action revision that supports it, or bind the required file name. Two
reasonable implementations therefore hash different bytes while both claim the
same relation.

The observation and aggregate artifacts may legitimately remain multi-file
archives, but then their `artifactDigest`/`byteLength` must be explicitly the
provider archive identity and the reviewed workflow must define the exact
inner file census needed to recompute `Draw`, receipts, and `Daggregate`. For
the single provider record, the smallest alternative is either:

1. pin an immutable upload action and require a supported exact single-file
   non-archive mode whose provider digest/length cover the canonical record
   bytes; or
2. keep the archive, bind API digest/length to the downloaded ZIP bytes, require
   an exact one-file inner path/census, and separately parse/recompute the
   canonical provider-record identity from the extracted bytes.

The post-job time rule also needs literal provider fields and comparisons.
“Creation during the record-job interval” does not state whether the relation
is inclusive, and `recordedAt` is only called provider-observed without naming
the response timestamp used. Retention authority changes if one implementation
uses runner wall clock, an artifact `created_at`, or an arbitrary API response
`Date` header.

Smallest repair:

- require every remote action/reference to be a reviewed full commit SHA and
  add a mutable-tag/branch deletion mutant;
- select and pin one upload/download byte mode, define archive versus inner
  record digests/lengths and exact contained paths, and kill cross-mode
  substitution;
- define `recordedAt` as one exact provider timestamp available before upload;
  and
- require the exact inclusive relation
  `recordJob.startedAt <= artifact.createdAt <= recordJob.completedAt` plus the
  existing `artifact.expiresAt >= recordedAt + 30 complete days`.

No additional record, signature, attestation, status authority, or post-record
receipt is necessary.

## OP-R167-2 — the portable candidate digest omits the exact Git-mode projection

`conformance-candidate-subject/v1` now correctly commits the complete candidate
regular-file tree and refuses symlinks, submodules, partial trees, and
checkout-only files. Its public row contains only an `executable` boolean, which
keeps Git vocabulary out of the core. The adapter rule, however, says that
boolean is derived from “the only admitted regular-file modes” without naming
the modes or the mapping.

The provider exposes exact values `100644` and `100755`. One implementation can
admit only those and map them to false/true; another can treat any blob mode
other than `100755` as false or normalize a mode before hashing. Those choices
change both accepted candidates and `Dsubject`, so this is not an internal code
style.

Smallest repair: state exactly that an adapter tree row must be
`type=blob,mode=100644` and maps to `executable:false`, or
`type=blob,mode=100755` and maps to `executable:true`; `120000`, `160000`, every
other mode/type, a truncated tree response, missing blob, duplicate path, or
nonportable path refuses. Add one mutation for each crossed/unknown mode. The
portable record remains provider-neutral.
