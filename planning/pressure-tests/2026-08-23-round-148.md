## Blocking finding

### OP-R148-1 — empty position cannot construct the registered reservation `Dp`

The registered reservation path is:

```text
installation/activation-recovery-launches/<transaction>/<source>/reservations/<predecessor-key>.json
```

The proposed position is exactly:

```json
{ "mode": "VALUE", "parts": {} }
```

The current ordinary identity implementation computes `Dp` through
`computePointerInstanceDigest(identity)`. Its path-binding helper obtains every
non-transaction/non-source placeholder from
`identity.positionEvidence.parts`. For `RECOVERY_ATTEMPT_RESERVATION`, that
means it looks for `parts.predecessorKey`. Empty parts supply no key, so the
registered path constructor receives an incomplete binding and refuses.

This is not isolated to a convenience API:

- `computeMutationId` calls that same ordinary instance-digest function;
- `validateLocatedSelectedPointerEvidence` calls it before checking proposal,
  tip, value, position, and recomputed mutation identity; and
- later ISS-004 selection must use those common contracts rather than invent a
  reservation-only CAS identity.

Consequently, the ledger's own exact path and position cannot currently reach
the common mutation or selected-read graph. Adding `Kreservation` to position
would make the current route work, but it contradicts the packet's explicit
nonredundancy decision and would duplicate the key in both `Dp` and the
position digest.

An existing `computePointerInstanceDigestFromCanonicalPath` helper demonstrates
the smallest viable alternative. It validates and parses the registered
canonical path directly, including transaction, source, and lowercase key,
then computes the same `Dp` identity. It is already used for common commit
target identities. However, merely noticing that helper does not repair the
packet:

1. the sole authority does not select it for reservation identity;
2. the authorized footprint does not say whether the ordinary instance,
   mutation-ID, and selected-locator routes change or gain a reservation branch;
3. no named later family equality requires selected reservation predecessor
   facts to recompute the same key/path; and
4. the acceptance matrix omits end-to-end `path -> Dp -> mutation -> selected
   locator` constructibility.

The smallest planning repair should say, exactly:

- parse the five-input predecessor record and recompute `Kreservation`;
- construct the one canonical reservation path from that same parsed input;
- derive reservation `Dp` from that canonical path, transaction, source, and
  the remaining ordinary identity scalars, without reading the key from empty
  position;
- make common mutation-ID and selected-object validation use that exact
  reservation `Dp` route; and
- assign the future reservation family composition the equality from selected
  predecessor facts to recomputed key and exact canonical path, while the
  generic locator continues to prove only path/`Dp` structure; and
- add focused identity tests for valid constructibility plus malformed,
  uppercase, cross-source, and cross-transaction paths. The later value ledger
  must add predecessor-to-key/path substitution tests.

This adds no key field, index, head, lookup, schema, callback, or runtime
mechanism. It closes the public-contract seam where the key is actually
consumed.

## Five-input census, framing, and scalar attack

The proposed pure input is otherwise exact and closed, with five members in
ascending canonical member order:

```text
predecessorReceiptDigest: nullable SHA-256
predecessorTipDigest: nullable SHA-256
predecessorValueDigest: nullable SHA-256
sourceToken: cleanup-gate-pre-fence | recovery-fence
transactionId: UUIDv7
```

The branch rule is unambiguous: all three digests null selects genesis; all
three non-null selects one predecessor; every partial combination refuses.
Swapping `Dt`, `Dv`, or `Dr` changes the selected key because each occupies a
distinct ordered raw-32 frame part. Invalid/case-changed digests, unknown or
case-changed sources, non-v7 UUIDs, extras, missing fields, and hostile
reflective inputs refuse.

The key framing is stable and acyclic:

```text
domain: recovery-attempt-reservation-predecessor/v1
transactionId: text
sourceToken: text
branch: raw fixed 00 | 01
selected only: Dt raw32, Dv raw32, Dr raw32
```

The tag is not enum text, JSON, or a caller-provided number. Genesis has no
nullable digest frame ambiguity because it has only the fixed `00` branch.
Selected uses `01` and exactly three raw digests. Deleting the tag collapses
branch structure; deleting or reordering any selected part changes a committed
golden. No attempt UUID, time scalar, ordinal, array, length, or random path
component enters the key. UUIDv7 transaction text is validated identity, not
attempt ordering; future random attempt UUID time grants uniqueness only.

The predecessor triple is an upstream selected terminal attempt-log node, so a
new reservation depends only on completed earlier evidence. The reservation
does not enter its own key, its position, or its predecessor log. Future value,
descriptor, and log facts remain downstream. There is therefore no digest or
path recursion cycle.

## Transaction/source binding and proportionality

Transaction and source appear both in `Kreservation` and in its parent path.
The smallest byte-level alternative would hash only branch plus predecessor
triple and rely on the parent path/`Dp` for namespace separation. That
alternative is smaller, but the retained shape is still proportionate because
the proposed public key function is an opaque context identity, not merely an
untyped filename suffix. Binding the two scalars prevents detached keys from
being equal across two valid recovery contexts, while adding no new input—the
path constructor already requires both fields.

The deletion test is exact: change transaction or switch between the two
registered source tokens while keeping branch/triple fixed; both the key and
constructed path must change. This prevents a future map, retry comparison, or
diagnostic from treating a detached key as globally interchangeable. The key
still grants no authority without the full constructed path, `Dp`, selected
tip, and stable mutation path.

This justification is bounded enough to retain the two frame parts. It does
not authorize caller-supplied keys, a global reservation index, key lookup,
directory enumeration, or caching as authority.

## Path, source vocabulary, and collision attack

The two exact sources already exist in the closed eleven-kind pointer registry:

```text
cleanup-gate-pre-fence
recovery-fence
```

The reservation, recovery launch, and attempt log share that recovery-source
vocabulary; every other pointer uses `none`. Adapter or repository vocabulary
does not enter the engine contract.

The proposed path constructor consumes the same parsed five-input record and
recomputes its key. It accepts no key parameter, so a caller cannot combine one
trusted triple with another key. Changing transaction, source, branch, or any
selected predecessor digest changes the recomputed path. Raw predecessor
digests, UUID ordering, directory enumeration, latest-file selection, alternate
source spelling, and random UUID path components grant nothing.

Competing random attempt IDs for the same exact context/predecessor deliberately
share the same bucket and later compete through common CAS. That is the required
single-winner behavior, not a path collision. Different predecessor triples
have different framed keys under ordinary SHA-256 collision resistance.

The unresolved OP-R148-1 seam is distinct: once the correct path is constructed,
the packet must still choose how the existing generic identity and mutation
contracts consume it.

For a later selected read, family composition is the sufficient and correct
place to recompute the key/path from parsed reservation value predecessor facts.
The generic selected-object locator has no predecessor-key input and should not
gain one; it should validate only the registered canonical path and derived
`Dp`. Until the value ledger exists, the identity slice can honestly prove only
that its own five-input constructor produces a path whose `Dp`, mutation ID,
and generic locator are constructible. Naming the later equality avoids both a
trust gap and premature value fields.

## Position and downstream deferrals

Empty VALUE position is the smallest nonredundant position:

```json
{ "mode": "VALUE", "parts": {} }
```

The future reservation value/`Dv` should bind the selected attempt and
descriptor inputs. The constructed canonical path/`Dp` should bind transaction,
source, and predecessor key. Copying attempt ID or key into position would add
no independent fact.

The specialized parser and common dispatch must accept only this closed VALUE
shape for reservation identity. Missing/extra outer members, nonempty or
extended parts, TOMBSTONE, and cross-family evidence refuse. The common route
must use the already registered `attempt-reservation-position/v1` domain;
untagged canonical hashes or another family's domain are not substitutes.
Reservation TOMBSTONE position remains correctly deferred until the archive/
tombstone ledger fixes its terminal evidence.

The ledger correctly does not authorize reservation value bytes, attempt-ID
allocation, descriptor, launch, attempt-log records, terminal selection,
archive/tombstone bytes, full history/currentness, persistence, filesystem IO,
proposal/CAS, capability, process start, broker call, command, or runtime
behavior. Those facts cannot be inferred from a valid key, path, position, or
structural `Dp`.

Candidate-created key/path bytes and pure validator success are not a selected
tip, live handle, independent review, release verdict, or promotion authority.
Only ISS-004 stable external mutation authority may select the future value; a
candidate never certifies itself.

## Dependency-order finding

Reservation identity is the true next reservation dependency. A reservation
value cannot have a stable common `Dp` until its competition bucket is fixed.
Descriptor and attempt log depend on the selected reservation, while archive
and tombstone depend on later lifecycle/terminal facts. Defining those first
would either guess the bucket identity or copy it redundantly.

The correct order is therefore:

```text
repaired reservation identity/path/Dp composition
  -> reservation value and selection semantics
  -> descriptor and attempt-log ledgers
  -> reservation archive/tombstone ledger
  -> ISS-004/ISS-030 runtime composition
```

This dependency-order conclusion does not clear the current head; OP-R148-1
must be repaired before identity implementation.
