## Blocking findings

### `OP-R75-001` — prior selector `Dp` is neither cross-bound nor derived

`validateCommitCheckpointEvidenceSequence` extracts only the prior selector
`Dt`, `Dv`, `Dr`, and `Dpost`. It discards the parsed prior proposal's
`pathInstanceDigest`. Checkpoint zero is then checked against only those four
stored predecessor fields. The current checkpoint selector
`pathInstanceDigest` is also never recomputed from the exact
`POINTER_MUTATION_RUN_CURRENT` target/mutation path identity and is not
required to equal either the prior selector `Dp` or the selector `Dp` of the
other checkpoints.

Consequently a caller can move the prior selected graph or any current
selected graph to another caller-chosen selector `Dp`, recompute its value,
proposal, receipt, tip, observation, downstream predecessor digests, current
cores, run ID, and `Dcommit`, and retain a structurally selected composition.
The validator observes internally consistent hashes but has no derivation or
equality that names the required run-current pointer instance. This is the
coordinated-copy attack that rounds 71–72 explicitly required to refuse; the
canonical union bytes merely co-hash the substituted siblings.

Repair the composition so the prior selector `Dp/Dt/Dv/Dr` and `Dpost`, not
only `Dt/Dv/Dr` and `Dpost`, initialize checkpoint zero. Independently derive
the current run-current selector `Dp` from its canonical target/mutation path
and platform identity, and require every checkpoint selector graph to use that
same derived instance. Add independent and coordinated mutants for the prior
selector `Dp`, each current selector `Dp`, and all dependent hashes.

### `OP-R75-002` — target `Dp` recomputation does not cover the closed registry

Both target-identity checks call `computePointerInstanceDigest` with
`positionEvidence: null`. That helper uses position evidence to expand path
placeholders before applying the reviewed `Dp` formula. Null happens to work
for the two fixtures in this test file and for rows whose placeholders are
recoverable from transaction/source, but it cannot validate legitimate rows
whose path carries another binding. In particular,
`RECOVERY_ATTEMPT_RESERVATION` needs `<predecessor-key>`, and
`POINTER_MUTATION_RUN_CURRENT` needs `<target-instance-digest>` and
`<target-mutation-id>`.

The commit schema admits every non-rotation registry kind for ORDINARY, while
the implementation reports `targetPathInstanceDigest:inputs-invalid` for
those valid dynamic target identities. This is not an acceptable fail-closed
security choice: it silently narrows the public eleven-kind contract and
makes registered ordinary mutations unrepresentable. Derive the exact path
bindings from the canonical target path/existing evidence, or add a reviewed
closed derivation that preserves the existing field census. Exercise every
registry row, including both non-transaction placeholder families, and reject
independent and coordinated changes to kind/path/installation/project/state/
transaction/source/`Dp`.

### `OP-R75-003` — the legacy resolution-binding helper remains a partial escape

The exported `validateCommitResolutionBinding` now accepts a full
`priorCheckpointEvidence` value, but for a positive run it consumes only the
recomputed prior `Dcore` when rebuilding the run ID. It does not require the
prior core ordinal to be exactly one less; does not equal-bind prior target,
platform identity, `G`, or selected epoch; and does not consume the prior
selector tuple or `Dpost` at all. A structurally valid unrelated checkpoint
therefore passes this public helper when the caller recomputes `runId` from its
core digest and keeps the resolution/common fields mutually equal.

This is the digest-only semantic escape under a full-record spelling that the
review request explicitly called out. Either make the helper validate the
same complete positive-run lineage as the authoritative commit parser, change
its closed input so it has the current checkpoint-zero evidence needed to do
so, or make it refuse the positive branch and route callers through the full
commit validator. Add a mutant with an unrelated but valid prior checkpoint
whose `Dcore` is copied into the run ID; the helper must refuse it.

## Test adequacy

The new tests prove one positive retry using checkpoint 6, null-at-positive,
one prior-core ordinal mutation, one copied target `Dp`, one copied run ID,
rotation positive/non-null rejection, and digest goldens. They do not execute
the ISS-002 acceptance matrix they claim:

- no prior or current selector-`Dp` substitution;
- no coordinated selector graph/observation/predecessor/core/run-ID/`Dcommit`
  substitution;
- no prior `Dpost`, selector `Dt/Dv/Dr`, target tuple, `G`, or selected-epoch
  mutant in the positive branch;
- no positive-run attack against `validateCommitResolutionBinding`; and
- no target-identity fixture beyond `ACTIVE_RELEASE` and authority rotation,
  leaving the other nine registry rows and dynamic path bindings uncovered.

The passing goldens pin the implementation's current framing but do not prove
the missing semantic equalities. The acceptance suite must contain the
coordinated mutants above before a later exact-head review can pass.
