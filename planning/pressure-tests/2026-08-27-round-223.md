# ISS-006 Windows TypeScript adapter implementation review — round 223

## Disposition

`BLOCK_REPLAN`.

The adapter is private and the successful real diagnostic is useful, but this
exact slice may not land. It is production-authority-bearing: `createPrincipal`
runs native recovery and starts `SERVE`; `prepare` creates the profile and
execution root; `launch` resumes candidate code. It is not a refusal-only or
inert partial boundary. Round 222's native live-image custody is therefore a
pre-land requirement, not work that can safely follow this adapter.

Independent static review also found four concrete TypeScript lifecycle and
resource defects that survive the current three-test evidence.

## Blocking findings

### 1. The live native image is invoked before required custody exists

`windows-isolation-authority.ts:588-613` starts the fixed pathname directly.
The TypeScript preflight at lines 101–218 proves retained/current bytes, basic
Node file identity, digest, X64 magic, a few directory values, and forbidden
strings. It does not prove the Win32 owner, DACL, SACL/mandatory label, complete
stream/import relation, reparse/ancestor security, or bind the image mapped by
`CreateProcessW` to the retained file.

The native source and PE are unchanged from Round 220. Their sole live-module
use remains `windows-isolation-broker.c:2728-2730`: after a candidate process is
already suspended, `GetModuleFileNameW` supplies one path for a candidate-token
negative read-open. There is no pre-PREPARE retained live-module profile,
ancestor/path identity check, or lifecycle recheck.

That is exactly the gap Round 222 kept inside its implementation fence. The
real test demonstrates that the unproved image can create, execute, and delete
an AppContainer; it does not turn the missing observation into an inert future
hardening.

Smallest repair: add the fixed native live-image/ancestor custody check before
the broker reads PREPARE or mutates recovery/profile state, retain/recheck it
through terminal cleanup, and extend the candidate-token negative-access matrix
to the exact image and protected ancestors. Rebuild/re-pin the PE and exercise
the exact-source mutations. If this cannot run on the hosted stable bundle
profile, Round 222's direct-invocation replan must be reconsidered; TypeScript
must not normalize that incompatibility away.

### 2. Failed PREPARE can still enter LAUNCH, and overlapping lifecycles are open

At `windows-isolation-authority.ts:688-689`, `state.prepared` is assigned before
bundle verification, frame write, native response, OPWR validation, diagnostics,
and post-use verification. The catch at lines 704–706 sets `failed`, but
`launch` at lines 710–716 tests only `prepared` and `launched`; it never tests
`failed`. A caller that catches a failed PREPARE can invoke LAUNCH against a
partially consumed or terminal broker.

The same mutable booleans provide no per-principal operation exclusion. LAUNCH
can overlap the first PREPARE after the early assignment and race two
`BoundedReader.read` calls over one stream. TEARDOWN can overlap PREPARE or
LAUNCH. Two TEARDOWN calls can write/recover concurrently. More seriously,
`createPrincipal` has no factory-wide active lease: a second concurrent creation
runs `RECOVER` over the shared state root while the first principal is live.

Smallest repair: use one closed state machine and one stable-owned operation
lease. A factory permits only one active principal for its state root. PREPARE
stores the request binding only after exact success; any attempt/failure enters
a terminal recovery-only state. LAUNCH requires exact PREPARED and not failed.
TEARDOWN atomically owns the state and is retryable only through a defined
recovery state. No two method bodies may own a broker reader/writer or recovery
root concurrently.

### 3. RECOVER and broker terminality are not proved on failure

`startBroker` at lines 588–613 resolves its terminal promise on the ChildProcess
`exit` event and rejects immediately on `error`; it does not latch those facts
until trusted `close`. `requireExit` at lines 615–624 waits for stdout EOF but
calls synchronous `stderr.requireEmpty()` without waiting for stderr end/error.
Late stderr after the check can therefore be accepted.

On any `runRecovery` failure, lines 626–636 call `child.kill()` and immediately
rethrow. They neither require the kill result nor await process terminality,
stdout/stderr drain, or handle close. The failed RECOVER process may still own
and mutate the state root after `createPrincipal` or teardown has returned its
refusal. `terminate` similarly treats `exit`, not close-bound terminal/control
resource completion, as sufficient.

`writeAll` also calls `stdin.end()` without an end callback or a retained stdin
error/close owner. A post-write/end error is not part of the returned promise
and can become an unhandled stream error.

Smallest repair: one close-bound native-command owner must latch spawn error,
exit, close, stdin completion/error, stdout EOF/error/overflow, stderr
EOF/error/overflow, and every owned listener/buffer/handle. Failure initiates
bounded hard abort but cannot settle until close and complete pipe drain. RECOVER
failure remains recovery-required and never returns before the exact broker root
is terminal. Add transient, persistent, late, and simultaneous error/close
mutants for `SERVE` and `RECOVER`.

### 4. Teardown launders cleanup ambiguity and destroys retry custody

The teardown catch at `windows-isolation-authority.ts:751-758` records only the
first error, runs broker termination plus a fresh RECOVER under
`Promise.allSettled`, discards both cleanup results, then closes both retained
bundle handles under another discarded `allSettled`. It throws the original
error at line 759 regardless of whether recovery succeeded, failed, remained
live, or a handle close was ambiguous.

Because the WeakMap entry is retained on failure while its custody handles are
unconditionally closed, a nominal teardown retry sees an active principal with
destroyed bundle custody and cannot establish the Round-222 post-use relation.
Conversely, a successful native recovery followed by one ambiguous close is
indistinguishable from total recovery failure. The coordinator receives a
refusal, but stable cleanup authority is lost rather than durably retained for
the next attempt.

Smallest repair: teardown must accumulate and classify every terminal,
recovery, pipe, verification, and close result; attempt all independent cleanup
steps in the required order; and never discard recovery failure. Keep the opaque
entry and every still-valid retained handle in an exact RECOVERY_REQUIRED state
until a retry proves native recovery and post-use image custody. If handle close
itself is ambiguous, refuse permanently without pretending the entry is safely
retryable; factory reconstruction must still perform native state recovery
before new work.

## Parser and executable-evidence gap

The current OPWR parser (`windows-isolation-authority.ts:508-560`) checks useful
bounds but does not prove binary SID/text equality or bind the returned folder
and execution root to the prepared profile/parent. The runtime PE parser
(`:101-135`) does not implement the exact closed import census required by
Round 222; a Latin-1 forbidden-string scan is not equivalent. These should be
closed while adding the required fake broker matrix, but they are secondary to
the four blockers above.

`test/conformance/windows-isolation-authority.test.ts` contains only:

1. one source-text/private-export assertion;
2. one off-Windows guard test; and
3. one opt-in Windows happy lifecycle.

There is no executable non-hosted broker/client fixture for framing, hostile
responses, partial writes/reads, resource ownership, lifecycle ordering,
concurrency, recovery failure, or retry. The current green tests therefore do
not delete any of the production bugs above. Static source-string assertions
cannot substitute for those paths.

Before landing, add a private fake-process/control-stream fixture that executes
the real adapter core. It must cover every OPWB/OPWE/OPWR/terminal byte and
bound; partial/zero/duplicate/trailing frames; fatal UTF-8; 1-byte and 4-MiB
challenge limits; response/status confusion; request mutation/reflection;
failed PREPARE then LAUNCH; concurrent method calls and second principal;
spawn/error/exit/close permutations; stdin callback/end failure; late and
oversize stdout/stderr; watchdog hard abort; RECOVER status/failure/terminality;
teardown cleanup ordering; bundle read/path/identity/close ambiguity; and exact
retry retention. Production paths/platform dependencies remain fixed.

## Scope, authority, and planning impact

The package-root privacy and exact bundle census changes are correct. The
adapter exposes no receipt, workflow, provider, PASS, or promotion route, and
the stable coordinator still owns expected values, timing, semantic parse, and
three-cycle result release. None of those facts remove native mutation and
resource ownership from this slice.

No draft, board, roadmap, or sole-ledger amendment is warranted. Round 222's
direct-invocation design remains viable if the bounded native live-image check
and adapter repairs succeed. ISS-006 remains incomplete and all required OS and
hosted/provider evidence remains outstanding.

This record authorizes repair only. It is not a landing disposition, hosted
PASS, public contract, receipt, aggregate, provider authority, certification,
installation, promotion, workflow dispatch, issue completion, or Chase Sets
access.
