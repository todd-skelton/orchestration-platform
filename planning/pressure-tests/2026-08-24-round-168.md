## OP-R168-1 — the non-archive provider record has two incompatible exact names

The ledger requires both of these properties:

1. the `archive:false` upload binds canonical bytes at exact file name
   `provider-record.json`, and a different file name refuses; and
2. the uploaded provider artifact has exact attempt-qualified name
   `conformance-<runId>-<runAttempt>-provider-record`, with the post-terminal
   verifier requiring exactly that name.

Those requirements cannot both be implemented with the selected provider
action. Under `archive:false`, the reviewed action ignores its `name` input and
uses the uploaded file's name as the artifact name. Uploading
`provider-record.json` therefore produces artifact name `provider-record.json`,
which fails the required attempt-qualified name. Renaming the file to the
attempt-qualified artifact name makes the artifact join succeed but fails the
ledger's exact `provider-record.json` file-name rule. A workflow cannot repair
this by setting both `path` and `name`; the action explicitly ignores `name` in
this mode.

This is authority-relevant rather than presentation drift. The attempt-qualified
name is part of the acyclic post-job association and prior-attempt refusal, while
the exact non-archive file name is declared part of the byte/mode admission
rule. Two reasonable implementations necessarily violate different normative
sentences, so no deletion-grade workflow fixture can prove the current packet.

Smallest repair: choose one exact ASCII filename that is also the provider
artifact name under `archive:false`. The smaller shape preserves the existing
attempt-qualified join by serializing the canonical provider-record bytes to an
attempt-qualified `.json` filename and requiring that exact same filename from
the provider API. Delete the contradictory fixed `provider-record.json` name;
the canonical record identity remains its bytes and domain, not an inner
archive path. Alternatively, choosing fixed `provider-record.json` would require
deleting the attempt-qualified artifact-name rule and specifying an equally
strong current-attempt uniqueness/refusal join. No second record, ZIP wrapper,
signature, attestation, or receipt is needed.

Add one executable structure mutation proving that changing the non-archive
source filename changes the provider artifact name and refuses, and one proving
that a `name:` input cannot override it. Re-sync issue #12 from the repaired
draft and return the exact clean pushed head for independent review.

## Round 167 repairs otherwise verified

### Frozen executable boundary

Every remote `uses:` dependency, including checkout, Node setup, and artifact
upload/download, must be a reviewed full 40-hex commit SHA. Tags, branches,
short hashes, unpinned remote executable downloads, and installs outside the
reviewed lockfile/integrity graph refuse. The protected workflow revision binds
those literal references, so movement of a remote tag cannot substitute action
bytes after review. The draft and deletion matrix explicitly require mutable-
reference and unpinned-download mutations. This adds no action manifest record
or engine vocabulary.

### Exact archive byte layers and layouts

Observation and aggregate `artifactDigest`/`byteLength` now mean the provider
API's outer ZIP digest and archive byte length. Safe extraction rejects
traversal, absolute/backslash paths, symlinks, duplicates, encryption,
unsupported compression, and over-bound entries. The observation archive has
exactly the four `Draw` bytes plus canonical environment/raw-manifest JSON at
the six fixed root paths. The aggregate has exactly canonical `aggregate.json`
and one `receipts/<jobId>.json` per registry row. Exact regular-file censuses,
inner bytes, receipt order/mapping, outer API identity, and cross-role mode are
revalidated. No archive digest is mistaken for a canonical inner-record digest.

The single provider record correctly selects direct non-archive bytes, so its
API digest and length can equal the canonical JSON bytes without a second inner
digest. OP-R168-1 concerns only the impossible pair of exact names, not the
selected byte layer.

### Provider time and post-terminal association

`recordedAt` is now the canonical millisecond projection of the provider `Date`
header on the final current-attempt jobs API response immediately before
serialization; missing, repeated, malformed, or non-UTC headers refuse. The
post-terminal verifier requires the exact inclusive relation
`recordJob.startedAt <= recordedAt <= artifact.createdAt <=
recordJob.completedAt`, all from provider fields/projections, and requires the
provider-record artifact to expire at least 30 complete days after
`recordedAt`. Listed observation/aggregate artifacts already have the same
remaining-retention requirement. Ambiguous, duplicate, expired, nonterminal,
or cross-run evidence refuses.

The provider record still does not claim its own writer job or artifact. The
independent post-job verifier observes the successful record job and artifact
after the entire run is terminal and emits only PASS/refusal, preserving the
acyclic direction and avoiding self-attestation. Once the filename contradiction
is removed, the immutable workflow's unique upload step, exact run/attempt,
unique artifact, provider digest/length/time, and live revalidation form the
bounded association the provider API itself cannot express as an uploader-job
field.

### Exact Git projection

The adapter mapping is now literal: only `type=blob,mode=100644` maps to
`executable:false`, and only `type=blob,mode=100755` maps to
`executable:true`. Modes `120000` and `160000`, every other mode/type,
truncated or unterminated tree responses, duplicate/unlisted rows, missing
blobs, checkout-only files, and nonportable paths refuse. The portable
candidate record retains only the boolean, so Git vocabulary remains adapter-
local while `Dsubject` is deterministic.
