## Repairs verified

### Native direct-image custody now exists

Production `broker_entry` retains the actual module's immediate protected
parent, sibling reviewed C source, and mapped-image pathname before dispatching
`SERVE` or `RECOVER`. The existing retained-object machinery requires a fixed
drive, canonical final path, regular/directory type, no reparse point, one link,
exact unnamed-stream census, stable owner, protected exact DACL and mandatory
label, complete self-relative security bytes, volume/file ID, size, content
digest, and retained/path probe equality. Handles remain open with restrictive
sharing.

The broker rechecks custody before and after its first frame, before candidate
admission, and through `broker_exit`. Release failures convert exit to recovery
required. The native source and tracked PE were rebuilt and the TypeScript
expected hashes match them.

### TypeScript lifecycle ownership is closed

The adapter now permits one principal per factory/state root and rejects a
second creation or overlapping method before it can own the stream. PREPARE
stores its request only after exact response/post-use success. The closed
lifecycle union forces every attempted failure into `RECOVERY_REQUIRED` and
LAUNCH requires exact `PREPARED` state. TEARDOWN retains the active entry and
bundle custody when native recovery fails, and marks an ambiguous bundle close
as permanent failure instead of advertising a retry.

`BrokerCommand` now binds success to ChildProcess `close`, awaits stdout and
stderr end on normal settlement, owns stdin write/end errors, and makes a failed
RECOVER hard-abort before returning refusal. The real three-walk diagnostic also
drives failed PREPARE, second-principal refusal, overlapping PREPARE, overlapping
TEARDOWN, and production recovery.

### Runtime PE census and response parser improved

The adapter now parses the exact six-library named import census, rejects
ordinal/delay drift through the fixed image layout, and retains the existing
machine/mitigation/relocation/hash checks. The latest OPWR parser independently
canonicalizes the binary SID and requires exact SID-text equality, and rejects
an execution root outside the configured execution parent. Package-root privacy
and exact bundle rows remain correct.

## Blocking findings

### 1. Module-custody candidate denial is only a subset of the authorized matrix

At `windows-isolation-broker.c:2713-2724`, the AppContainer-token `AccessCheck`
arm proves only:

- image `GENERIC_READ`, `GENERIC_EXECUTE`, and `DELETE` denied;
- source `GENERIC_READ` denied; and
- protected parent `FILE_LIST_DIRECTORY` denied.

The impersonated actual-open arm at `:2768-2772` is narrower still: image read
and execute, source read, and parent list.

Round 222 required the direct-invocation repair to deny read, write, execute,
delete, owner, DACL, and SACL access to the exact live image and protected
stable relation. The broker already defines the exact denied-right set at
`:509-512` as `GENERIC_WRITE`, `FILE_APPEND_DATA`, `DELETE`, `WRITE_DAC`,
`WRITE_OWNER`, and `ACCESS_SYSTEM_SECURITY`; it applies all six through both
AccessCheck and actual opens to execution targets/root. Deleting those rows for
module image/source/parent currently survives because they are never called.

Exact protected ACL capture makes a grant unlikely, but it does not replace the
required kernel-token access relation or its deletion evidence. This slice was
introduced specifically so direct invocation would not infer candidate denial
from bytes/mode alone.

Smallest repair: use one closed object/right/expected table for module image,
source, and protected parent. Exercise every applicable read/traverse and all
six denial rights through both AccessCheck and impersonated actual open, with
exact object/path/right ordering and independent per-row failure mutants. No
candidate-visible path or new privilege surface is needed.

### 2. Production module custody is compiled out of the exact-source fake-OS fixture

`OP_WINDOWS_MODULE_CUSTODY_PRODUCTION` is defined only when none of the three
fixture macros is present (`windows-isolation-broker.c:496-502`). Consequently,
the large exact-source C fixture never executes `retain_module_custody`,
`verify_module_custody`, `release_module_custody`, or the production module
candidate-access branch. `rg` finds no module-custody case in
`windows-isolation-broker-fixture.c`.

The changed TS broker test supplies four useful real-process cases: unprotected
source bytes, hard-linked image, source alternate stream, and widened parent
ACL. The happy adapter diagnostic exercises the unmutated production branch.
Neither can inject or observe:

- image/source/parent retain ordering and partial-retain cleanup;
- initial or later file-ID/path/security/link/stream/content substitutions;
- drift between startup, first-frame reads, PREPARE mutation, candidate proof,
  cleanup response, and `broker_exit`;
- probe, crypto, security-buffer, FindClose, HeapFree, retained-handle close, or
  token/context release failures, including simultaneous failures; or
- response-success followed by module-release ambiguity changing terminal exit
  to 70.

Those are authority-bearing branches newly added in this diff. The reported
13/13 suite validates the ordinary native lifecycle but does not delete these
mutants.

Smallest repair: add a compiled exact-source module-custody fixture that replaces
only OS observations, not the production custody functions. It must execute
retain/verify/release and `broker_exit` for parent/source/image success, each
partial prefix, each identity/security/stream/hash/path drift at every recheck,
every resource failure, and simultaneous cleanup failures. It must also execute
the complete candidate AccessCheck/actual-open table from finding 1. Confirm the
fixture macros do not remove the code under test and that the production PE
remains the separately repinned no-fixture image.

### 3. Hard-abort still launders output-resource ambiguity

`windows-isolation-authority.ts:720-728` waits for ChildProcess `close` but then
uses `Promise.allSettled` for `reader.requireEnd()` and
`stderr.requireEnd()`, discarding both results. Thus stdout truncation/overflow/
error and stderr error/nonempty/overflow after a hard abort all produce the same
successful `hardAbort` result as exact empty closed control pipes.

This affects failed `SERVE` and `RECOVER` cleanup. For a CREATED or
RECOVERY_REQUIRED principal, TEARDOWN can accept hard abort, run a clean native
RECOVER, close bundle custody, and return without ever surfacing the broker
control-resource ambiguity. The process root is terminal, but the stable
resource fact is still being normalized away. The adapter test has no fake
process/stream fixture, so every transient, persistent, late, and simultaneous
stdout/stderr/close branch survives.

The similar `Promise.allSettled` at `windows-isolation-authority.ts:946` also
discards source/image close ambiguity when principal creation fails before an
active entry exists. A refusal is returned, but the same factory is immediately
allowed to create again without a permanent lost-custody state.

Smallest repair: hard abort must attempt both drains but throw an AggregateError
when either is ambiguous; callers may still run independent native RECOVER, but
must not turn that stream/resource failure into a clean teardown. Creation must
either prove both bundle handles closed or permanently poison that factory.
Add a fake close-bound `BrokerCommand` fixture covering every stdin/stdout/
stderr/error/close ordering, one and simultaneous drain failures, failed
RECOVER, and creation-close ambiguity. The fixture must execute the production
command/state core, not source-string assertions.

## Remaining strict-parser deletion

promotion route was added. The opaque four-method interface, stable expected
