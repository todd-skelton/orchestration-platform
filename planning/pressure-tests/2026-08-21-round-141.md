## Round-140 removal verification

### OP-R140-1 — proposal family and trusted position are now equal-bound

The validator now requires both exact equalities that were absent at round 140:

```text
proposal.pointerKind = expectedIdentity.pointerKind
proposal.positionDigest =
  computePointerPositionDigest(expectedIdentity.pointerKind,
                               expectedIdentity.positionEvidence)
```

It also recomputes `Dp` from the closed expected identity and registered path
rules, requires the tip kind and `Dp` to equal that trusted identity, and
computes `Dv` under `expectedIdentity.pointerKind`, not an attacker-selected
proposal kind. The proposal successor and `Dp`, and tip `Dv` and `Dr`, must
equal the independently recomputed values before `Dt` is returned.

This closes both previously demonstrated attacks. A cleanup-gate or recovery-
fence position mutation can leave its static-path `Dp` unchanged, but it now
changes the required position digest. A proposal cannot declare another
registered family while a separately formed tip declares the expected family.
Independent deletion mutants are explicitly required for the proposal-kind and
proposal-position comparisons.

### OP-R140-2 — the exact API is one-node-only

The pure validator still has exactly four non-persisted inputs:

```text
expectedIdentity
proposal
tip
value
```

It validates only that current supplied node. It returns exact recomputed
`Dp/Dv/Dr/Dt`, detached parsed records, and an exact prior `Dt/Dv/Dr` triple
that must be either wholly null or wholly present. The contract expressly says
that null does not prove an authorized family genesis and a non-null tuple does
not prove that an ancestor exists.

ISS-004 now owns the iterative walk: construct the prior three paths, read
canonical bytes, invoke the same one-node validator, reject path/digest
mismatch and cycles, and continue until family composition proves an authorized
terminal. Missing, forked, reordered, falsely terminated, or otherwise
incomplete histories are `UNKNOWN`. Structural ISS-002 tests may repeat the
one-node call only to prove tuple handoff and path constructibility; they make
no completeness or terminal claim. The impossible four-input recursive-walk
obligation and deletion mutant are gone.

### OP-R140-3 — canonical persistence is assigned to the byte reader

The record-only validator now makes no source-byte claim. ISS-004 owns exact
canonical byte reads for both current and historical aliases and must reject
reordered JSON, whitespace, invalid UTF-8, missing LF termination, and every
other noncanonical persisted representation before using a record. Those tests
and their deletion mutants are explicitly in the ISS-004 matrix.

This is observable at the correct boundary: once JSON bytes have become the
same detached record, the pure validator cannot recover their former encoding.
The repair therefore preserves the canonical persistence rule without adding
three byte inputs or a hidden reader callback to ISS-002.

## Identity, graph, and prior-tuple attack

The expected identity remains the existing closed eight-member contract:

```text
canonicalPointerPath
installationId
pointerKind
positionEvidence
projectId
sourceToken
stateRootDigest
transactionId
```

The registered path constructor validates kind-specific transaction, source,
and position bindings; `Dp` commits the canonical path and all identity scalars.
The separate position digest commits position evidence that is intentionally
not a direct `Dp` part. Closing and snapshotting all four inputs before semantic
use keeps the public validator total over proxies, accessors, symbols, inherited
fields, exotics, and other hostile reflective values.

For a successful node, the required graph is exactly:

```text
Dp = pointer instance(expectedIdentity)
Dv = pointer value(expectedIdentity.pointerKind, Dp, value)
Dr = proposal(proposal)
Dt = tip(tip)

proposal.pointerKind       = expectedIdentity.pointerKind
proposal.positionDigest    = trusted recomputed position digest
proposal.pathInstanceDigest = Dp
proposal.successorValueDigest = Dv
tip.pointerKind            = expectedIdentity.pointerKind
tip.pathInstanceDigest     = Dp
tip.valueDigest            = Dv
tip.proposalReceiptDigest  = Dr
```

Changing any expected-identity or graph member independently refuses. A
coordinated attacker may recompute proposal and tip digests, but cannot bypass
the trusted identity, position, `Dp`, or family equalities. The proposal parser
already admits only an all-null or all-SHA-256 prior tuple, and the new result
returns that exact mapping as prior `Dt/Dv/Dr`; no partial prior tuple is
accepted or silently normalized.

Generic location deliberately does not parse an open value as family authority.
After structural success, family composition must invoke the exact value schema
registered for the trusted pointer kind. This prevents cross-family or merely
hash-consistent open objects from acquiring semantic authority.

## Alias, path-collision, crash, idempotence, and orphan attack

The retained paths are exact and class-separated:

```text
installation/pointer-cas/<Dp>/objects/values/<Dv>.json
installation/pointer-cas/<Dp>/objects/proposals/<Dr>.json
installation/pointer-cas/<Dp>/objects/tips/<Dt>.json
```

All four variable components are lowercase SHA-256 text. `Dp` separates pointer
instances, while the three literal class directories prevent cross-class
filename collisions. `Dv` commits trusted pointer kind, `Dp`, and value bytes;
`Dr` commits the closed proposal; and `Dt` commits the closed tip. Removing or
crossing any component becomes observable in the focused path and graph tests.

Runtime ordering remains acyclic:

```text
create/read-back exact value alias
  -> create/read-back exact proposal alias
  -> create/read-back exact candidate-tip alias
  -> stable external current-tip CAS and read-back
```

Same-path exact-byte retry is idempotent. Different existing bytes refuse
rather than choosing by writer, time, directory order, or mutation ID. A crash
or losing CAS before selection may leave complete or partial orphan aliases,
but alias presence grants no authority. A coherent losing candidate graph may
be structurally validated when supplied; it is not thereby current. In this
packet, rejection of an "orphan current node" means rejection of supplied
value/proposal/tip members that are not connected by the required current-node
digest graph. Authenticated current-tip origin and selected currentness remain
explicitly outside the pure validator and are ISS-004 obligations.

Because every selected dependency is written and read back before CAS, a crash
after CAS does not require a new candidate write. The selected `Dt/Dv/Dr` plus
trusted `Dp` constructs the exact aliases. Missing or conflicting required
aliases are `FULL_REQUIRED UNKNOWN`; mutation-addressed originals, enumeration,
and a caller-provided mutation ID are not fallbacks. No alias is deleted or
compacted.

## Family, terminal, and trust boundaries

The common locator does not construct cleanup, fence, authorization, or other
family root/archive paths. Family composition derives those paths from
independently trusted identity and semantically parsed selected values, then
equal-binds required roots, archives, and family terminals. The generic null
prior tuple is never promoted into a genesis rule by itself.

Candidate-created aliases remain upstream content, not a producer epoch,
capability, review receipt, promotion verdict, or CAS handle. Only the stable
external mutation path may select the canonical current tip. A candidate never
routes its own structural verdict into its promotion, and knowledge of a valid
object tuple cannot certify or activate that candidate.

The implementation footprint remains limited to the existing pointer contract
module and focused pointer tests: three pure path constructors and one total
pure current-node validator. The repaired ledger authorizes no IO, alias
materializer, current-tip reader, history reader, family root/archive locator,
proposal/CAS operation, conflict mutation, filesystem feature, capability,
command, broker call, runtime service, deletion, or compaction.
