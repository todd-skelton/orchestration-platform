## Dependency comparison

### Selected: private native isolated-walk composition

Linux and Windows now each implement the same four-method
`Iss002StableIsolationAuthority` boundary. `isolated-walk.ts` already owns the
fixed 1,000-record challenge, stable monotonic interval, expected values,
hostile terminal parse, selected-head semantics, three fresh cycles, and
teardown-before-result rule. No production function yet selects one of the two
real authorities and consumes them through that coordinator. Leaving them only
as independent test fixtures postpones the first composition fault until the
larger hosted runner.

This composer establishes one necessary dependency without duplicating any OS
lifecycle, semantic parser, clock, receipt, or provider vocabulary. It is also
the cheapest place to prove that the Linux factory's extra retained custody is
closed on every result and that Darwin cannot silently fall back.

### Portable aggregate and receipt: already implemented, not next

`contracts.ts` and `reducer.ts` already contain the closed portable records,
job-evidence constructor, environment-family relation, and aggregate reducer.
Adding another receipt/aggregate layer would duplicate landed contracts and
still lack a real observation producer. Connecting the reducer before native
composition would invert the data dependency and risk treating simulation as
hosted evidence.

### Provider authority: downstream

The pure GitHub protection, run, artifact, and terminal validators already
exist behind the adapter subpath. A live provider writer/verifier needs exact
current-attempt observation and aggregate artifacts plus the reviewed workflow
topology. It cannot make an OS observation authoritative and is not a substitute
for the missing composer or macOS authority.

### Workflow mutation gate: downstream of the runner packet

There is no `.github/workflows/conformance.yml`; the registered
`test:harness-workflow-mutations` slot remains intentionally unimplemented.
The mutation gate must kill concrete workflow job, command, root, artifact,
and ordering relations. Authoring it against a speculative runner command and
artifact layout would create a second provisional contract and require a
rewrite. The exact observation CLI/serialization packet and workflow should be
pressure-tested together immediately after the stable observation producer is
fixed, with the mutation gate landing in that same workflow slice.

### macOS helper custody: insufficient for composition

`macos-helper-custody.ts` and `macos-principal-helper.c` authenticate/build a
narrow native helper, but they do not compose account/profile allocation,
artifact DAC, process terminality, cleanup, and the four-method isolation
interface. Adapting them as if they were a complete authority would falsely
claim isolation. Same-principal `walk.ts` remains local advisory evidence only.

### Closed production input

The production function captures `process.platform` at module initialization
and has no caller-supplied platform, factory, authority, clock, parser, runner,
profile reader, token generator, syscall, or cleanup seam. It accepts two
hostile-detached exact data objects:

1. the existing absolute `candidateArtifactPath` and `rpcRunnerPath` run input;
2. one platform-specific stable path configuration selected by the captured
   platform.

The Linux configuration is a flat closed record containing only:

```text
accountHelperPath
accountStateRoot
cleanupHelperPath
dacHelperPath
dacStateRoot
executionParent
executionStateRoot
pidfdHelperPath
runtimePath
```

The composer reconstructs fresh nested production options itself:

- account, process, and execution account state all receive the one exact
  `accountStateRoot`;
- DAC and execution receive only their own distinct state roots;
- execution receives the exact parent and cleanup helper; and
- every optional custody `commandRunner`, `profileReader`, `principalToken`,
  and `token` member is absent.

The Windows configuration is the exact closed
`executionParent`, `runtimePath`, and `stateRoot` path record already consumed
by its factory. Supported-platform options and input are copied from own
enumerable data descriptors, reject proxies/accessors/symbols/extra keys and
noncanonical members, and cannot be changed after detachment. Existing OS
factories remain the sole canonicalizers and custody owners for their paths.

On `darwin` and every unknown platform, selection occurs before touching either
caller object. The function returns one frozen existing `ok:false` result with
an exact stable issue such as `native-isolated-walk:macos-authority-unavailable`
or `native-isolated-walk:unsupported-platform`. It must not import/call a macOS
helper as an authority, invoke `runIss002CrossRootWalk`, or inspect a caller
option to decide whether to fall back.

### One stable coordinator owner

On Linux the composer creates exactly one production Linux authority, invokes
the unmodified `runIss002IsolatedWalk` once, and calls `close()` exactly once
after all coordinator work on every success, refusal, or throw arm. Close
failure can only produce a fixed stable refusal and must override an `ok:true`
result; if both the coordinator and close refuse, retain both fixed/detached
issue classes in deterministic order. No caller receives the authority,
principal, UID/GID, lease, helper profile, or custody object.

On Windows it creates exactly one production Windows authority and invokes the
same coordinator. The authority's three per-principal teardowns and native
RECOVER own complete cleanup; the composer must not invent a no-op global close
or infer cleanup from candidate output. A coordinator refusal/throw is a fixed
refusal and never a partial observation.

The successful return is exactly the existing private coordinator result:
three stable-owned duration strings and their maximum. It is not renamed PASS,
serialized as a portable record, or accepted from candidate output. Candidate
stdout remains hostile data parsed only inside the coordinator. The composer
does not accept or return expected values, timing, selected head, raw custody,
principal identity, receipt authority, or promotion state.
