## OP-R166-1 — literal record/digest authority is incomplete and internally miscounted

The seven hosted portable record shapes are mostly well closed and ordered, but
several identities that their receipts and provider record depend on have no
formula or literal source:

- `candidateSubjectDigest` is described as a canonical candidate source-
  manifest digest, but no source-manifest schema, file census, canonical bytes,
  adapter projection, or digest domain exists. The stable plan job therefore
  cannot deterministically derive the portable subject from the payload's Git
  revision without inventing whether it hashes a tree, archive, checkout, or
  selected file set.
- `contractVersionsDigest` appears in every job receipt and aggregate but has no
  record, member census, ordering, source registry, domain, or formula. If the
  already-bound stable test bundle/vector registry makes it redundant, it must
  be deleted; otherwise its exact stable derivation must be fixed.
- A `GENERATOR` vector's `fixtureDigest` “hashes” source plus a canonical
  parameter record, but the parameter record and framed part/domain order are
  not defined. Different reasonable implementations produce different
  `Dvector`.
- `protectionSnapshotDigest` names
  `github-conformance-protection-snapshot/v1`, but that projection has no digest
  formula/domain and no exact rule for reducing multiple applicable rulesets
  and branch-protection layers into one snapshot. Current provider rules can
  layer, so singular “the ruleset API” is not a deterministic projection.
- `conformance-local-result/v1` is introduced as another closed portable record
  after the ledger/draft claim exactly seven portable records. Its exact members,
  nested per-suite row, scalar types, order, bounds, and parser refusal are not
  stated. It cannot yet prove structural non-interchangeability with hosted
  records.

The bundle `purpose` enum is also not a literal two-value table row. The raw
Markdown line contains an unescaped table delimiter between `HARNESS` and
`TEST_BUNDLE`; Prettier has widened it as an extra table cell. A generated
schema/test cannot safely copy that malformed authority.

Other declared bounds are missing despite the preamble saying over-bound input
refuses: vector entries and registry suite/job arrays have no maximum, so the
future-suite public parsers have no literal hostile-input ceiling. The initial
22/one/three censuses are exact, but they do not define the extensible parser's
bound.

The closed dispatch payload likewise names “one revision” without naming its
sole JSON member. An implementation must guess `candidateRevision`, another
spelling, or a scalar payload, while the workflow mutation test claims to pin
the exact payload.

Smallest repair:

1. fix the two-value purpose enum and exact dispatch payload member;
2. define one adapter-owned canonical candidate-source projection and digest;
3. either delete `contractVersionsDigest` as redundant or define its exact
   stable registry/formula;
4. define the GENERATOR digest and parameter record;
5. define the protection projection's single/multiple-ruleset reduction and
   canonical-frame identity;
6. either count and literally define the local advisory record or replace it
   with fixed non-contract advisory output that hosted parsers reject; and
7. add bounded vector/registry array ceilings.

No deployed migration exists.

## OP-R166-2 — the future-suite rule cannot compose with the current registry/aggregate

The registry is explicitly per suite: every suite row binds its own
`vectorCensusDigest`, and AC5 requires a future package-local vector/handler/
registry row. The job receipt likewise carries its suite's vector digest. The
aggregate, however, has one `vectorCensusDigest` and the reducer requires vector
identity equality across every receipt. Two suites with different reviewed
vector censuses cannot produce one aggregate. Requiring all future suites to
reuse the ISS-002 22-row `Dvector` would contradict the package-local vector row
and provides no place for the future suite's cases.

The same registry cannot enforce environment nullability as written. Suite rows
have only `ownerPackage`, `runnerToken`, `suiteId`, and `vectorCensusDigest`, but
the environment ledger and AC9 say null helper/custody digests are legal only
when the registry row declares those dimensions unused. No such declaration
exists. The handler catalog is mentioned but no exact requirement metadata is
part of the authenticated registry.

Finally, `maximumWalkDurationNanoseconds` is mandatory and non-null in every job
receipt. That is correct for the initial ISS-002 suite, whose census contains
`walk-1000-records`, but the future-suite rule does not require that row. A
future suite with no walk has no honest value and cannot parse a receipt.

Smallest repair:

- remove the aggregate's single `vectorCensusDigest` because `Dregistry`
  already commits the per-suite mapping, and require each receipt's vector
  digest to equal its own suite row; or explicitly choose and define a global
  census instead of the current per-suite model;
- add exact `REQUIRED|UNUSED` helper/custody requirement members to suite rows
  (and any ABI/profile requirement actually used by composition); and
- make walk timing a closed suite/census-dependent arm, non-null only for the
  suite that executes the required MEASURE row, or declare the walk as a
  separately authenticated global job rather than inventing a value.

The per-suite repair is smaller and preserves AC5 without workflow logic
changes.

## OP-R166-3 — raw environment and provider-record retention joins are not constructible

The raw manifest requires entries named `environment`, `report`, `stderr`, and
`stdout`, but does not fix each entry's media type or require
`environment.sha256Digest = conformance-environment.osImageDigest` (or another
named raw-inventory member). `Denv` and `Draw` can therefore be recomputed from
mutually inconsistent environment claims and bytes. Changing the raw inventory
changes `Draw`, as AC6 says, but the stable writer can issue a fresh receipt
whose portable `osImageDigest` still names different bytes. Exact raw binding
needs one direct equality and exact four-row media/name census.

The final provider record has a second constructibility gap. Its `jobs` census
contains PLAN, OBSERVATION, and AGGREGATE jobs, omitting the RECORD job that
writes it. Its `artifacts` census contains observations and the aggregate,
omitting the provider record itself. This exclusion avoids an obvious self-
digest cycle, but the packet then merely says retrieval of the provider record
is verified against the run. It gives no provider-record artifact name/path,
artifact ID/digest/expiry, completed record-job condition, or external review
input that performs that join. The retention section nevertheless requires the
provider record itself to be retained for 30 days.

The provider artifact API can authenticate run association, digest, bytes, and
expiry, but not the uploader job. Thus `artifact.logicalJobId` must be justified
by the exact reviewed workflow/upload step and current-attempt name, while the
provider record's own post-write job/artifact observation must remain an
explicit downstream independent-review condition rather than a self-asserted
field.

Smallest repair: define the exact four raw rows and image equality; define one
attempt-qualified provider-record artifact and state that an independent
reviewer, after the record job completes, requires that job SUCCESS plus the
artifact's exact run/repository/workflow/attempt/name/digest/length/expiry.
Keep that downstream observation outside the provider record to avoid a cycle,
but name it as required evidence and include it in the 30-day operator/retention
procedure. No second provider-record schema is required.

## OP-R166-4 — `triggeringActorId` has no authority or deletion test

The provider record and `DproviderRun` bind `triggeringActorId`, but no accepted
actor census, expected operator equality, or reducer/refusal rule uses it. Any
positive actor ID passes. The run ID/attempt/repository/candidate already
distinguish the run, and dispatch only initiates non-promotional evidence.
Raw provider metadata is retained for audit.

Deleting `triggeringActorId` therefore admits no mixed-run, candidate,
workflow, artifact, protection, capability, or promotion substitution. Keeping
it as an authority member defends only advisory attribution, contrary to the
work-model proportionality rule.

Smallest repair: remove it from the provider record and `DproviderRun`. If the
user intends an actor allowlist to grant dispatch authority, that is a new
outward-facing operator-authority decision and must be stated explicitly; the
current approved topology does not require it.

## Trust-topology attacks that passed

The selected provider mechanism itself is sound and bounded. Official GitHub
event semantics support the premise that `repository_dispatch` executes the
workflow on the default branch with default-branch `GITHUB_REF` and `GITHUB_SHA`.
The plan job additionally refuses unless protected `main`, exact workflow path/
ref, and `GITHUB_WORKFLOW_SHA = GITHUB_SHA = workflowRevision` hold. A moved
default branch after dispatch cannot change the immutable revision already
bound to the run.

The payload is restricted to a commit resolvable in this repository; forks,
symbolic refs, unresolved commits, and extras refuse. Stable and candidate roots
are separate, checkout credentials are not persisted, workflow permissions are
only `contents:read` and `actions:read`, and candidate children receive an
allowlist without tokens, secrets, provider metadata, environments, caches,
OIDC, status writes, or aggregate authority. Stable bundle bytes are checked
before and after candidate execution.

Candidate jobs can emit only untrusted attempt-qualified observations. A fresh
stable-only job re-reads raw bytes/provider context and writes portable receipts
plus at most one derived aggregate. A later stable-only job re-queries jobs,
artifacts, rules, and retention before writing the provider record. Candidate
output is never executed after observation. Prior-attempt, mixed-run,
mixed-repository, moved workflow, extra/missing job/artifact, non-success job,
expired artifact, and candidate registry/aggregate paths are all assigned exact
fail-closed mutations.

The digest direction is acyclic:

```text
protected provider context -> DproviderRun
stable observations + DproviderRun -> Djob set -> Daggregate
Daggregate + provider API/rules projection -> provider record
independent post-record retrieval -> reviewed bounded evidence
```

The aggregate does not contain its downstream provider-record digest. Aggregate
bytes alone grant no hosted authority. The provider record remains adapter-only;
the core sees `providerRunDigest` as opaque SHA-256 and exports no GitHub, Git,
repository, workflow, run, job, artifact, check, or ruleset vocabulary.

The protection snapshot's intended accepted values are appropriately strict:
protected `refs/heads/main`, active enforcement, pull requests required,
deletion and non-fast-forward blocked, and zero bypass actors. Ruleset movement
between plan and record refuses. Status-check names are presentation only and
grant no provenance.

The stable initial registry has one ISS-002 suite and exactly Linux, macOS, and
Windows required jobs. Candidate discovery cannot add, remove, rename, exclude,
or downgrade a row. The 22 named vector IDs cover framing, bounded decimals,
all pointer families/domains, external ledgers, authorization, reservation,
descriptor, attempt log, archives/tombstones, linear history, rotation,
single-epoch commit/crash behavior, FULL_REQUIRED loss, reflection, and the
1,000-record walk. The stable generator/fixture census, not candidate code, owns
expected behavior. OP-R166-1 is about literal row identities, not missing broad
coverage.

Raw stdout, stderr, report, and environment bytes are intentionally not newline,
encoding, locale, path, order, or diagnostic-normalized. The normalized result
is only PASS/FAIL/UNSUPPORTED; diagnostics remain advisory but missing or moved
required raw bytes block reuse. Reflective rules cover same-realm mutable,
sealed, and frozen values and reject proxies, cross-realm arrays, subclasses,
holes, symbols, extras, accessors, custom iterators, malformed descriptors, and
exotic prototypes.

The timing rule is otherwise exact and proportional: one fixed 1,000-record
vector, three fresh Node processes per OS, bytes read before timing,
`process.hrtime.bigint()` around JSON parse plus full genesis-to-head validation
plus selected-head equality, each interval at most 5,000,000,000 ns, and no
warmup, average, best-of, retry, checkpoint, or index. Startup, installation,
and file IO are excluded. A slow/refused/overflowed interval makes the required
job non-PASS.

Requested and provider-observed retention are at least 30 days, and evidence is
usable only before the earliest bound expiry. Local results are intended to be
fixed `authority:ADVISORY` and rejected by hosted parsers; OP-R166-1 requires
only their literal structural closure.

The implementation footprint correctly owns `packages/conformance/`, the new
conformance workflow, fixtures/tests/capability slots, the two root ISS-006
commands, the package-local test command, and every ISS-000 bootstrap census
restating those slots, including `scripts/verify/bootstrap-contracts.mjs`.
It forbids contract-package changes and runtime state in the checkout. The
three current placeholders and conformance package skeleton match that
amendment boundary.

No ISS-006 output certifies a release, selects/install/mutates authority, issues
a live capability, or promotes a candidate. ISS-019 owns complete
certification, ISS-029 owns later authenticated bootstrap provenance, ISS-022
owns the independently reviewed capability decision, and ISS-004 owns
production helper/lock authority. First hosted evidence is explicitly
post-merge on protected `main`, never candidate-branch self-test evidence.
