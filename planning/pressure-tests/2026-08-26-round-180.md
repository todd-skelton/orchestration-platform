The clean bounded repair is to tolerate only exact duplicate identities for
unrelated rows while retaining raw exact uniqueness and pairing for every
target/burned `orch6` moniker or SID. No authority, draft, ledger, or public
contract changes.

## Exact reduced census rule

Every successful enumeration still must satisfy all of these facts before any
reduction:

- API result is exact success;
- `count <= 4096`, and count/pointer nullability agrees;
- every row has non-null terminated bounded name and valid bounded SID;
- every pointer/count relation used by the row, including target capability
  inspection, is structurally valid;
- every row is visited, and the API allocation is freed exactly once with exact
  free success; and
- no malformed, truncated, over-bound, unreadable, or unfreed row is ignored
  merely because it appears unrelated.

After structural validation, classify raw rows relative to each canonical
profile identity, without first requiring global uniqueness:

```text
nameMatch = row.name == exact moniker
sidMatch  = row.sid  == exact derived binary SID
```

The target rules remain exact:

1. `nameMatch != sidMatch` always refuses. A name-only or SID-only row is an
   inconsistent target relation, even if another correct pair exists.
2. An absence census requires zero raw rows with either match.
3. A presence census requires exactly one raw row with both matches and zero
   other target-related rows. That one row must have exact zero capability
   count and pointer.
4. Two byte-identical target rows are still two raw target observations and
   refuse. Canonicalization must never collapse a duplicate target into one.
5. Complete recovery census permits an `orch6-` row only when its name and SID
   pair one and the same canonical nonterminal journal group. A second raw row
   for that group, cross-group name/SID match, unjournaled `orch6-` name, or row
   for an ABSENCE_PROVED group refuses.

For rows that match neither any burned/target moniker nor any burned/target SID:

- an exact identity duplicate—same complete UTF-16 name and `EqualSid` binary
  SID—may be canonicalized to one unrelated identity for comparison/storage;
- the duplicate is nevertheless structurally validated and freed as a raw row;
- differing diagnostic/display/binary metadata is ignored because no unrelated
  field contributes to the target absence or ownership fact; and
- same name with a different SID, or same SID with a different name, remains an
  inconsistent identity relation and refuses. This review does not generalize
  the observed exact duplicate into permission for conflicting unrelated
  identities.

No sorting or canonicalized unrelated digest becomes authority. The reduction
answers only whether an exact stable-generated moniker/SID relation is absent,
present exactly once, or inconsistent. Complete raw traversal preserves that
answer even when Windows repeats an unrelated identity.

## Response-status correction

`RECOVERY_REQUIRED` is reserved for a canonical durable nonterminal group,
active in-memory profile, attempted profile mutation, ambiguous handle close,
or residue whose cleanup ownership is established by such a group.

If the state root is empty and no profile mutation or durable USED/ATTEMPTED
record exists, an API/census/environment preflight failure returns ordinary
`REFUSED` status/exit 65. It must not return status 70: there is no recovery
state to process. This distinction is deletion-tested independently of the
duplicate-row repair.

An unjournaled `orch6-` row remains fail-closed residue. Because the broker
cannot establish ownership, it neither deletes the row nor reports clean
refusal; it reports recovery-required/lost custody exactly as Round 179 fixed.
Unrelated duplicates never create cleanup authority.

## Concrete implementation repair

In both `census_profile` and `complete_profile_census`:

1. remove the pairwise global `same name OR same SID` rejection;
2. retain complete per-row structural validation;
3. perform target name/SID classification on every raw row before unrelated
   deduplication;
4. count raw exact target pairs and refuse every split or repeated target
   relation;
5. in the complete census, retain a per-journal-group raw match count and
   require at most one row for every nonterminal group and zero for terminal
   groups;
6. permit only unrelated rows whose duplicate predecessor has both the same
   name and SID; retain refusal for name-only or SID-only unrelated conflicts;
   and
7. preserve the exact enumeration-free and allocation cleanup checks on every
   return path.

The fix does not change the OPWB/OPWP/OPWR bytes, journal bytes or filenames,
token/moniker derivation, zero-capability create call, folder proof, create/
delete ordering, durable barriers, in-memory lifecycle, modes, opcodes, PE
surface, package exports, or candidate boundary.
