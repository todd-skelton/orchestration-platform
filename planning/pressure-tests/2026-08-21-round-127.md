The authority says the state has no standalone digest and that the common
`Dv = pointer-value/v1(kind, Dp, canonical state bytes)` is its sole value
identity. The current public `serializeContract` parses a supported schema and,
except for the already repaired recovery core, returns
`canonicalDigest(parsed.value)`. Adding the new state parser to public dispatch
therefore deterministically makes
`serializeContract("recovery-authorization-state/v1", state)` return an
untagged second identity.

Unlike the round-125 core defect, this cannot be repaired by routing to a
schema-specific no-context helper. State `Dv` requires the exact common `Dp`,
which depends on installation/project/state-root/path/transaction/source facts
not present in the state record or the serializer signature. Returning the
untagged digest violates the ledger; pretending it is `Dv` is impossible; and
silently choosing a `Dp` would invent authority.

The smallest repair is to state in the authority and draft that generic public
serialization of `recovery-authorization-state/v1` refuses with one exact
context-required issue and returns no digest. Canonical state bytes remain
constructible from the successfully parsed detached value, and the existing
common `computePointerValueDigest("RECOVERY_AUTHORIZATION_STATE", Dp, value)`
computes the only `Dv` once the caller supplies authenticated pointer context.
Focused evidence must prove:

- generic state serialization returns the exact refusal and never the untagged
  canonical digest;
- canonical bytes for CREATED, CONSUMED, and all three REVOKED cells remain
  exact after parsing;
- common `Dv` equals the registered formula for each cell and changes when
  `Dp` changes; and
- no state-specific standalone digest helper, registry identity, or serializer
  fallback is publicly reachable.

This is one schema-specific fail-closed branch plus focused evidence. A new
digest registry, a broad serializer redesign, or a second state identity is
larger and unsupported.

## Lifecycle, substitution, and impossible-branch attacks

The pure graph is exactly null-to-CREATED plus CREATED-to-CONSUMED,
CREATED-to-REVOKED, and CONSUMED-to-REVOKED. Every non-genesis edge preserves
core, prebound consume operation, mode, and transaction. Time is inclusive:
equal `recordedAt` values are valid and reversal refuses. CONSUMED-to-REVOKED
also preserves exact gate and native-consume digests. Direct CREATED revocation
requires the null consume pair and permits precisely R0 or R1. Self-loops,
reverse edges, skips, a second CREATED, null to another lifecycle, and every
REMOVED state edge refuse.

Coordinating the same wrong core/transaction/mode/consume operation across two
otherwise valid values necessarily passes this pure validator: it is a valid
different structural history, not proof of the selected transaction.
Likewise, coordinating a wrong gate/native receipt across both CONSUMED and R2,
or placing an arbitrary gate digest in R1, remains structurally valid. The
ledger explicitly withholds selected-history/currentness and upstream equality,
and acceptance criterion 8 assigns independent and all-field coordinated
mutants to the later closed composition matrices. Treating these pure passes as
authority would be a caller defect, not a reason to add proof bags to the state.
