## Round-193 repair 2 has one surviving handle-identity mutant

The new `SetFileInformationByHandle` wrapper compares the disposition handle
only with:

```text
fixture_execution_observed->targets[0].handle
fixture_execution_observed->targets[1].handle
fixture_execution_observed->targets[2].handle
fixture_execution_observed->root.handle
```

Recognized handles append roles 1–4. If no comparison matches, `role` remains
zero and the wrapper simply forwards the disposition. It does not set
`fixture_execution_unidentified_delete`. That flag is set only when a fifth
recognized disposition overflows the four-byte order array.

This creates two concrete blind spots:

- `delete_partial_target` retains a fixed child into a local `observed`
  object. Its handle never appears in `execution->targets`. In the short-write
  PARTIAL case the child disposition is ignored, the root is recorded as the
  sole role, and `fixture_execution_children_before_root` accepts the one-byte
  sequence `{4}` because the root is last and its loop has no child element to
  validate.
- A mutant that calls `delete_retained_object` on any retained stable source
  before normal target/root cleanup is also ignored. The product can then
  finish exact execution-root absence; fixture teardown merely removes the
  source temporary directory and never verifies that stable source bytes
  survived. This mutant violates the core source-custody boundary and can pass
  the current compiled and TypeScript assertions.

Raw handle reuse does not invalidate the recognized COMPLETE assertions:
target/root handles are simultaneously live at their disposition boundary,
and a journal pending handle cannot share the same live numeric value. The
problem is omission, not a false positive from reuse.

### Smallest repair

Do not change production or the record/protocol. In the exact-production
execution fixture:

1. Exclude the currently known journal-pending handle when its disposal is the
   publication rollback being modeled.
2. For every other disposition, resolve the live handle's exact final path or
   maintain a create/open-time handle-to-path role table through close. Admit
   only fixed target roles 1–3 and the execution root role 4. Set
   `fixture_execution_unidentified_delete` for any other handle, including a
   source, parent, state-root, stale, or unknown handle.
3. Require the short-write PARTIAL cleanup to record exactly `{1,4}`. Retain
   the existing exact COMPLETE `{1,2,3,4}` and retry `{2,3,4}` assertions.
4. Independently reread and compare the three stable source files after each
   destructive fixture case, before test teardown. This directly kills the
   source-deletion mutant even if a future observation seam regresses.

This is one bounded test-evidence repair. No new production mechanism or PE
rebuild is required unless the build process intentionally tracks fixture-only
bytes elsewhere.
