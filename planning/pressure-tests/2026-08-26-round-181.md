reconciled profile is never returned as prepared authority.

## Exact reviewed facts

The local SDK `userenv.h` states only that
`GetAppContainerFolderPath(pszAppContainerSid, &path)` retrieves the local app
data folder for the specified AppContainer and uses the thread or process user.
Microsoft Learn likewise says its successful output is the same folder obtained
through `SHGetKnownFolderPath(FOLDERID_LocalAppData)` in that AppContainer
context. Neither source defines a pre-profile path formula or promises success
for a SID whose profile has not been created.

`CreateAppContainerProfile` is the API that creates the per-user/per-app data
store and folders. It returns `ERROR_ALREADY_EXISTS` for an existing store.
`DeleteAppContainerProfile` deletes that store, may return success for an
already absent profile, and requires independent absence proof. These facts
support create-or-reconcile cleanup under an already-durable ATTEMPTED record;
they do not support guessing a folder pathname.

## Exact journal framing repair

Keep the existing OPWJ version `1`, kinds, filenames, token, moniker, SID,
state-root digest, prior-digest chain, pending/final durability, and permanent
USED tombstone. Change only the closed folder arm:

- USED `1` and PROFILE_ATTEMPTED `2` require
  `folderPathUnits == 0`, contain zero folder-path bytes, and contain no
  `folderBindingDigest`;
- PROFILE_CREATED `3`, PROFILE_DELETE_ATTEMPTED `4`, and
  PROFILE_ABSENCE_PROVED `5` require `folderPathUnits` in `1..1024`, the exact
  broker-observed canonical UTF-16LE folder path, and the existing exact
  32-byte `folderBindingDigest`; and
- a kind 3–5 zero folder, a kind 1–2 nonzero folder, padding, optional inferred
  folder, or record/path disagreement refuses.

The common record remains:

```text
OPWJ | version:1 | kind | reserved:0 | totalLength |
token | priorDigest | Dstate | moniker |
sidLength | binarySid | sidTextLength | canonicalSidText |
folderPathUnits | [folderPath] | [folderBindingDigest for kinds 3..5]
```

`identity_for_token` derives only token, moniker, binary SID, and canonical SID
text. It must not call `GetAppContainerFolderPath`. Parsing kinds 1 and 2 proves
the exact zero-folder arm. Parsing kind 3 obtains the folder only from canonical
record bytes, then requires a live post-create API query and retained-handle
profile to agree before the value can authorize cleanup. Kinds 4 and 5 repeat
the exact kind-3 folder and binding.

The previous direct ATTEMPTED-to-DELETE branch with a zero folder binding is
removed. Cleanup first establishes and persists PROFILE_CREATED, then persists
DELETE_ATTEMPTED. This restores one exact linear predecessor chain:

```text
USED -> PROFILE_ATTEMPTED -> PROFILE_CREATED
     -> PROFILE_DELETE_ATTEMPTED -> PROFILE_ABSENCE_PROVED
```

## PREPARE ordering

PREPARE now performs:

1. authenticate/retain state-root custody and preflight journals/census under
   Round 180;
2. generate token/moniker, derive and validate binary SID and canonical SID
   text, and prove name/SID census absence;
3. durably write USED and PROFILE_ATTEMPTED with the exact zero-folder arm;
4. call `CreateAppContainerProfile(moniker, moniker, moniker, NULL, 0, &sid)`;
5. require exact success, returned/derived SID equality, stable/SYSTEM
   inequality, one exact zero-capability target census row, and exact allocation
   cleanup;
6. only now call `GetAppContainerFolderPath`, canonicalize its returned path,
   reopen/bind it no-follow, and require the exact OS-created owner/DACL/SACL/
   label/type/link/identity profile;
7. durably append PROFILE_CREATED with the observed path/binding; and
8. only after all of those facts return PREPARE/OK and enter PREPARED.

There is no pre-create folder open or absence probe. Freshness comes from the
fresh burned token/moniker/SID, complete pre-create target census absence, and
the exact `CreateAppContainerProfile` success arm. `ERROR_ALREADY_EXISTS` in
ordinary PREPARE is never adopted and enters cleanup.

The profile folder remains hostile non-evidence storage. This slice grants no
candidate access and may not infer authority from folder contents.

## Crash reconciliation and cleanup

A durable PROFILE_ATTEMPTED owns the exact stable-generated moniker/SID cleanup
namespace because it predates the only authorized create call. Recovery from
that phase performs no candidate launch and returns no profile authority:

1. run a complete target census;
2. call `CreateAppContainerProfile` with the exact same moniker/display/
   description and `NULL,0` capabilities solely to reconcile cleanup;
3. admit only:
   - exact success with returned SID equal the journal SID, meaning recovery
     created the cleanup profile; or
   - `ERROR_ALREADY_EXISTS` plus exactly one correctly paired target census row,
     meaning the attempted profile already exists;
4. for any other create result, rerun the census. If exactly one correct target
   exists, continue cleanup without trusting the create result; if absent or
   inconsistent, retain ATTEMPTED and return RECOVERY_REQUIRED for a later
   retry;
5. require `GetAppContainerFolderPath` success now that the exact profile is
   established, canonicalize/reopen/bind the folder, require zero capabilities
   and exact target pairing again, and durably append PROFILE_CREATED;
6. close every SID/folder allocation and folder handle, durably append
   PROFILE_DELETE_ATTEMPTED, call delete, and independently prove zero raw name
   or SID rows plus exact folder-path absence; and
7. clean pending records and durably append PROFILE_ABSENCE_PROVED.

This create-or-reconcile operation is permitted only for an exact canonical
ATTEMPTED group under retained state-root custody. USED-only recovery performs
no create: USED proves the external mutation was never authorized. A caller
moniker/SID, unjournaled `orch6-` row, malformed phase, or guessed folder can
never enter reconciliation.

If the original create succeeded but the broker crashed before folder capture,
recovery observes `ERROR_ALREADY_EXISTS` or the exact target row, obtains the
folder through the documented API, and deletes it. If the original create never
ran, recovery creates the exact profile only long enough to obtain and bind its
folder, then deletes it. Thus every ATTEMPTED prefix reaches an exact final
folder absence proof without relying on an undocumented path.

Get-folder failure after create/reconcile remains RECOVERY_REQUIRED with the
durable ATTEMPTED or CREATED record retained. Enumeration absence alone cannot
stand in for folder absence, and Delete success alone remains insufficient.

  it cannot return PREPARE success or reach LAUNCH.
