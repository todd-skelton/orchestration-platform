## OP-R150-1 — path input relations are not deletion-discriminated

The implementation correctly parses the same five-input predecessor record,
recomputes `Kreservation`, and passes exactly these bindings to the registered
reservation path constructor:

```text
transactionId = parsed transactionId
sourceToken = parsed sourceToken
predecessorKey = recomputed Kreservation
```

The focused suite pins only one exact path, for the selected fixture:

```text
installation/activation-recovery-launches/
  018f0f4d-7b2d-7a11-8a2b-123456789abc/
  recovery-fence/reservations/
  b6aac024b9bad1cc639279bb5a48aff11ba01a0f635e927f2aa57e3f89569754.json
```

It separately proves that the **key function** changes when transaction,
source, or each predecessor digest changes. It does not call
`recoveryAttemptReservationPath` with any changed valid predecessor input and
compare the whole returned path to the expected parent context and recomputed
key.

That distinction is observable. Even with a fixed wrong parent transaction or
source, changing one of those inputs still changes `Kreservation`, so a weak
`pathA != pathB` assertion would pass while the record is stored under the
wrong parent namespace. Likewise, a fixed predecessor-key suffix can preserve
the one happy-path golden while every other valid predecessor is routed to that
same stale bucket.

The three exact mutants and outcomes were:

| Deleted relation | In-memory replacement | Focused result |
| --- | --- | --- |
| Transaction path input | `transactionId` fixed to the selected fixture UUID | 5/5 PASS — mutant survived |
| Source path input | `sourceToken` fixed to `recovery-fence` | 5/5 PASS — mutant survived |
| Recomputed-key path input | `predecessorKey` fixed to the selected fixture key | 5/5 PASS — mutant survived |

These are not artificial alternate algorithms. Each is the direct deletion
test named by the authority: stop consuming one parsed input while retaining a
well-formed path. The first two would move a reservation away from its trusted
recovery context. The third would merge distinct predecessor competition
buckets. All three remain structurally well-formed and therefore need exact
relation evidence rather than malformed-input checks.

The smallest discriminating additions are:

1. construct a record with `otherTransactionId`, recompute its key, and require
   the exact path to contain that transaction, the unchanged source, and that
   recomputed key;
2. switch the record to `cleanup-gate-pre-fence`, recompute its key, and require
   the exact path to contain that source, the unchanged transaction, and that
   recomputed key; and
3. change one predecessor digest or use the tagged-genesis record, recompute
   its key, and require the exact path suffix to contain that new key.

Each assertion must be independent enough that fixing a sibling relation does
not hide deletion of the target relation. Exact equality is preferable to
mere inequality because transaction/source are deliberately also key parts.

## Five-input closure, branch, and key framing

The production key input is the exact closed five-member record in ascending
canonical member order:

```text
predecessorReceiptDigest
predecessorTipDigest
predecessorValueDigest
sourceToken
transactionId
```

The parser snapshots before semantic reads, requires UUIDv7 transaction,
admits exactly `cleanup-gate-pre-fence|recovery-fence`, and permits only an
all-null genesis triple or all-SHA-256 selected predecessor triple. Partial,
invalid, extra, caller-key, and hostile reflective inputs refuse. Neither key
nor path helper accepts a supplied predecessor-key member.

The exact domain and frame are implemented as authorized:

```text
recovery-attempt-reservation-predecessor/v1
transactionId text
sourceToken text
00 raw fixed byte for genesis | 01 raw fixed byte for selected
selected only: predecessor Dt raw32, Dv raw32, Dr raw32
```

Both genesis and selected key goldens are pinned. Transaction and source
sensitivity, swapping `Dt/Dv`, and changing each of the three predecessor
digests all change the key. Partial triples refuse before they can select a
valid key.

Deletion-grade attacks confirm every framed component is independently
observable. Removing transaction text, source text, the fixed branch tag,
selected `Dt`, selected `Dv`, or selected `Dr` caused the focused key golden to
fail. Thus the `00/01` raw tag, selected branch part count, and exact
`Dt/Dv/Dr` order are not protected merely by prose. The evidence block is
limited to the later path relation, not key identity.

The key remains acyclic. It contains only an upstream predecessor triple and
recovery context; no reservation value, proposal, tip, attempt identifier,
descriptor, log, archive, or tombstone digest enters its own preimage.

## VALUE position and common dispatch

The specialized reservation position parser admits exactly:

```json
{ "mode": "VALUE", "parts": {} }
```

It snapshots the closed outer record and empty nested parts. Missing/extra
outer members, nonempty parts, cleanup-head-shaped parts, and TOMBSTONE refuse.
The specialized digest and common pointer route both return the pinned
`attempt-reservation-position/v1` golden. No key or attempt ID is duplicated in
position.

Three isolated position mutations were killed:

1. disabling nested empty-parts closure made a nonempty input parse and failed
   the specialized refusal assertion;
2. disabling the VALUE-mode comparison made TOMBSTONE parse and failed the
   specialized refusal assertion; and
3. disabling the reservation branch in common position dispatch made malformed
   reservation parts hash under the generic route and failed the common
   `toThrow` assertion.

The reservation branch intentionally refuses TOMBSTONE even though the common
registry can derive a tombstone domain for tombstone-capable rows. The later
reservation archive ledger must first fix terminal evidence. This slice adds no
tombstone parser or removal authority.

## Canonical-path-derived `Dp` and common identity consumers

The Round 148 integration gap is correctly repaired in production.
`computePointerInstanceDigest` contains one internal family dispatch:

```text
RECOVERY_ATTEMPT_RESERVATION
  -> computePointerInstanceDigestFromCanonicalPath
```

The canonical-path helper parses the registered template, requires path
transaction and source equal the closed identity members, validates the key as
lowercase SHA-256, reconstructs the exact path, and then applies the unchanged
`pointer-instance/v1` formula. The public identity census and digest preimage
remain unchanged.

Because `computeMutationId` and `validateLocatedSelectedPointerEvidence` both
call public `computePointerInstanceDigest`, the same reservation-only dispatch
produces one identical `Dp` through identity, mutation, and selected-object
location while position remains empty. The focused positive constructs a
valid mutation/proposal/tip graph and the locator returns the same `Dp`.

Deleting the reservation family dispatch was killed: the positive identity and
locator cases fell back to position-derived placeholder extraction and refused
with `predecessorKey:missing`. There is no public flag, overload, alternate
identity type, or caller choice between two formulas.

Malformed key text, moved transaction, and moved source paths refuse. A
different well-formed lowercase SHA-256 key is correctly accepted as another
structural identity and produces a different `Dp`. That is not lineage
authority. Later reservation family composition, once actual predecessor and
value evidence exist, must recompute the key and whole path and equal-bind them
to the independently trusted identity. The generic locator has no predecessor
input and correctly does not invent one.
