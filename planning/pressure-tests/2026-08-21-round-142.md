## Blocking findings and smallest repairs

### OP-R142-1 — deletion of the locator's tip identity equality survives

The implementation correctly contains this required comparison:

```text
tip.pointerKind = expectedIdentity.pointerKind
tip.pathInstanceDigest = recomputed Dp
```

It is implemented as one combined `tip:identity-mismatch` branch. The new
focused test never supplies a valid closed tip with a different registered
`pointerKind`, and never supplies a valid closed tip with a different SHA-256
`pathInstanceDigest`. Repository search confirms that the new public validator
is invoked only by `selected-object-locator.test.ts`; older pointer tests attack
the different `validateSelectedPointerEvidence` function and cannot kill
deletion of this new branch.

The existing expected-identity mutation loop is not discriminating evidence
for this comparison. Those cases fail while recomputing the trusted identity or
before reading the unchanged tip. The wrong-kind proposal case kills the
proposal-kind equality while leaving the tip kind unchanged. The selected-
graph loop mutates tip `Dv` and `Dr`, but not tip kind or `Dp`.

Consequently, deleting the complete combined tip identity branch leaves all 35
files and 394 tests green. This directly violates the round-141 requirement
that deletion of every current-node identity equality fail the ISS-002 suite.

The smallest repair adds two focused inputs while keeping every other record
and recomputed digest valid:

1. set `tip.pointerKind` to another registered kind and require refusal; and
2. set `tip.pathInstanceDigest` to another lowercase SHA-256 and require
   refusal.

These should be independent cases so either half of a split future comparison
also remains deletion-discriminated. No new production mechanism is needed.

### OP-R142-2 — malformed alias-digest evidence is not argument-complete

All three constructors correctly call the shared lowercase-SHA-256 validator
for both dynamic path inputs. The focused negative matrix, however, covers only
these calls:

| Constructor | `Dp` malformed | Object digest malformed |
| --- | --- | --- |
| selected value | yes | no |
| selected proposal | no | yes |
| selected tip | no | yes |

The valid exact-path assertions pin literal path/class components, but they do
not distinguish a mutation that removes only one untested `storageDigest(...)`
call and interpolates that argument directly. For example, accepting a
malformed `valueDigest` in `selectedValue`, or a malformed `Dp` in
`selectedProposal`, leaves every current test green.

The smallest repair is the remaining three negative calls, using malformed or
uppercase digest text in each missing cell. That proves every public argument
of every constructor refuses before producing a path. It adds no path type,
schema, or alternative validation layer.

### OP-R142-3 — the new entry point does not test hostile nested slots

The implementation is total by inspection: expected identity is closed-
snapshotted, proposal/tip/value parsing is inside the refusal boundary, and the
called closed-record helpers reject proxies, accessors, symbols, inherited
members, and exotic records. The focused hostile case nevertheless supplies a
throwing proxy only as the outer input. It does not place hostile values in
`expectedIdentity`, nested `positionEvidence`, `proposal`, `tip`, or `value`.

Because totality is a public-entry-point property, relying only on helper tests
does not prove that future refactoring preserves the try/refusal boundary at
each nested read. The smallest repair reuses one throwing proxy in each of the
five nested positions and requires a nonthrowing `{ ok:false }` result. This is
a bounded evidence repair and does not justify deep cloning, a new wrapper, or
any production change unless a new case actually fails.

OP-R142-1 and OP-R142-2 are independently definite blockers under the explicit
deletion matrix. OP-R142-3 should be repaired in the same focused test slice
because it closes a named acceptance boundary at negligible additional cost.

## Semantic implementation attack

Apart from the evidence gaps above, the implementation matches the reviewed
contract:

- the outer input is an exact closed four-slot composition of
  `expectedIdentity`, `proposal`, `tip`, and `value`;
- expected identity is the exact existing closed eight-member record;
- `Dp` is recomputed from that identity and registered canonical path rules;
- proposal and tip are parsed through their existing closed v1 parsers;
- the trusted expected kind, rather than proposal vocabulary, selects the `Dv`
  family;
- proposal kind and recomputed trusted position are equal-bound explicitly;
- proposal `Dp`/successor `Dv` and tip kind/`Dp`/`Dv`/`Dr` are compared to the
  recomputed graph;
- `Dr` and `Dt` are computed by the existing domain-separated proposal and tip
  functions;
- the proposal parser enforces an all-null or all-SHA-256 prior tuple;
- success returns exact `Dp/Dv/Dr/Dt`, exact prior `Dt/Dv/Dr`, and detached
  proposal/tip/value records without extra authority state; and
- generic structural success deliberately admits a hash-consistent open value,
  while the focused test proves the registered active-release family parser
  still refuses it.

Independent scalar mutations cover all eight expected-identity members,
including a valid alternate position branch whose static active-release path
leaves `Dp` unchanged but changes the required position digest. Proposal kind,
proposal position, proposal `Dp`, proposal successor `Dv`, tip `Dv`, tip `Dr`,
value bytes, and partial prior tuples all refuse in the implementation. The
complete and null prior branches return the exact expected tuple.

The returned success object introduces no schema or serializer. `index.ts`
already exports the pointer module generically, while the schema registries and
generic canonical serializer remain unchanged. The eleven-kind/FULL_REQUIRED
registry tests and ISS-002 compatibility slot remain green.

`.json` suffix.

A coherent losing candidate can still pass this structural validator when
supplied; the result does not claim it is selected or current. Only ISS-004's
stable external current-tip read and CAS path may grant selection. The function
returns no capability, producer epoch, review verdict, release admission, or
