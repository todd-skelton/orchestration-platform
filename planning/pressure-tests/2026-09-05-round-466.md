### (d) Native-lock digest reasoning and the CRLF-literal grep

Per the ledger paragraph, the censused bundle rows for the four trees feed
`harnessPaths` and `testPaths` in `scripts/conformance/hosted-native-lock-plan.mts`,
which in turn feed `computeConformanceRecordDigest` (`packages/conformance/src/manifest.ts`)
to produce `harnessBundleDigest` and `testBundleDigest`, and
`computeGithubProviderRunDigest` (`packages/conformance/src/github-actions.ts`)
to produce `providerRunDigest`. Before this slice, a Windows checkout of any
file in the four trees checked out CRLF (no `eol=lf` attribute, `core.autocrlf=true`
on `windows-latest`) while a Linux or macOS checkout of the same commit checked
out LF, so the per-file byte length and SHA-256 read into those digests
differed by OS for reasons of checkout normalization alone. After this slice
lands, every file in the four trees checks out LF on every OS (part (b)
above), so that source of cross-OS digest divergence for these 37 files is
closed. This is a bundle-input change: no digest *value* changed by this
commit (the tracked bytes are unchanged, part (c) above); only what a future
Windows checkout of those bytes will produce changes.

A grep of `test/conformance/**` and `test/native-lock-experiment/**` for any
committed digest literal that encodes a CRLF byte sequence — patterns `crlf`,
`CRLF`, `0d0a`, `0D0A`, and the literal two-character escape sequence `\r\n` —
found no digest literal built from or asserting a CRLF byte sequence. The lone
match for `autocrlf` (`test/conformance/hosted-review-api.test.ts:477`,
`git("config", "core.autocrlf", "false")`) sets a git config value in an
unrelated authenticated-review test fixture and is not a digest literal.

**Tooling note, recorded because it nearly produced a false report.** This
host's Git-Bash/MSYS shell pipes (`git show | grep`, `git cat-file -p | grep`,
plain Bash `grep -c $'\r'`) silently reintroduce CR bytes into LF-only content
that merely passes through them, because several MSYS-built tools default to
text-mode stdio. A first pass using `grep -c $'\r'` over `git show HEAD:<path>`
falsely reported CR bytes in all 37 blobs and a plain Bash `grep '\r\n'`
falsely reported the literal escape sequence in dozens of unrelated files. Both
were re-verified and refuted: the blob byte check was redone with
`git cat-file -p <path> > file; [System.IO.File]::ReadAllBytes(file)` in
PowerShell (binary-safe, no MSYS pipe), which found zero CR bytes across all 37
blobs; the literal-escape check was redone with the ripgrep-backed Grep tool,
which found zero matches. All acceptance evidence above was produced or
re-verified through one of these two binary-safe paths, not through a Bash
pipe carrying git or file output.

## Review attack surface

A fifth attribute line added beyond the four named trees; an existing
`.gitattributes` line changed; a renormalization commit (`git add
--renormalize` or equivalent) that rewrites any blob, in the four trees or
elsewhere; one of the four trees left uncovered or covered by a wrong glob
(for example a glob that fails to match a `.d.mts` or `.c` file); a committed
digest literal, anywhere in `test/conformance/**` or
`test/native-lock-experiment/**`, that depended on a CRLF byte sequence and was
missed by the grep above; and the tooling hazard itself — a reviewer
re-running the CR/CRLF checks through a Bash/MSYS pipe on Windows and getting
the same false positives this packet hit and then discarded, rather than using
a binary-safe read.
