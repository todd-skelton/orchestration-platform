# ISS-006 Windows AppContainer token-criterion repair — round 199

## Disposition

`PASS_TO_REPAIR_PACKET`.

The Round-175/197 requirement that the suspended AppContainer child satisfy
`IsTokenRestricted(token) == TRUE` is mis-specified and must be deleted. It is
not an AppContainer sandbox predicate. Microsoft documents that
`IsTokenRestricted` answers only whether the token contains a restricting-SID
list and returns false when that list is absent, even for a token produced by
other filtering operations.

The real suspended child observation—`TokenIsAppContainer == TRUE`, exact
`TokenAppContainerSid`, and `IsTokenRestricted == FALSE`—is therefore
consistent with the documented APIs. It does not weaken the AppContainer
boundary or authorize fallback.

Do not replace the check with `TokenHasRestrictions`, reserved
`TokenIsRestricted`, or a requirement on `TokenRestrictedSids`. Those values
describe filtering history or a restricting-SID list, not whether the kernel
token is an AppContainer. The exact replacement evidence is the already
required AppContainer-specific token fields plus complete token-shape, atomic
creation, actual effective-access, and job-membership proofs below.

Round 197's no-resume rule, exact package grant, zero capabilities, stable-
owned expected access, atomic startup attributes, Job Object containment,
durable Round-198 reversal union, and full cleanup remain unchanged.
Implementation may continue after deleting the false criterion and must receive
a fresh exact-tree review.

## Primary-source finding

Microsoft's
[`IsTokenRestricted` documentation](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-istokenrestricted)
states that the function indicates whether a token contains a list of
restricting SIDs. Its remarks explicitly say the function checks only that
list and can return false even for a token created by `CreateRestrictedToken`.
False also shares the API's error return, making “require false” an invalid
replacement criterion.

Microsoft's
[`TOKEN_INFORMATION_CLASS` documentation](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ne-winnt-token_information_class)
defines separate AppContainer-specific observations:

- `TokenIsAppContainer` returns nonzero for an AppContainer token;
- `TokenCapabilities` returns its capability rows; and
- `TokenAppContainerSid` returns the AppContainer SID or NULL for a token not
  associated with an AppContainer.

The
[`SECURITY_CAPABILITIES` documentation](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-security_capabilities)
separately defines the AppContainer SID and capability list supplied at process
creation. These are the APIs the design already uses in the atomic suspended
creation and token proof.

Inference from those primary contracts and the real observation: an
AppContainer token need not contain a restricting-SID list. The false
`IsTokenRestricted` result says nothing contrary about `TokenIsAppContainer`,
the exact package SID, capabilities, low integrity, effective access, or job
membership.

Before any `ResumeThread` can ever be added, the stable broker must continue to
require all of the following on the actual primary token opened from the exact
suspended child:

1. `GetTokenInformation(TokenIsAppContainer)` succeeds with exact returned
   size and value 1.
2. `GetTokenInformation(TokenAppContainerSid)` returns one structurally valid,
   in-buffer SID exactly equal to the independently derived and profile-returned
   package SID and unequal to stable, SYSTEM, Administrators, and every
   authority SID.
3. `GetTokenInformation(TokenUser)` returns the exact stable-user relation
   expected for this AppContainer construction. The ordinary user SID is not
   misrepresented as the package principal.
4. `GetTokenInformation(TokenCapabilities)` returns a structurally closed
   `TOKEN_GROUPS` value with `GroupCount == 0`, matching the exact
   `SECURITY_CAPABILITIES` input (`Capabilities == NULL`,
   `CapabilityCount == 0`, reserved zero).
5. `TokenIntegrityLevel` is the exact low mandatory SID;
   `TokenElevation.TokenIsElevated == 0`; and `TokenUIAccess == 0`.
6. The complete detached `TokenGroups` census has valid bounded rows/SIDs,
   no holes, duplicates, truncation, aliasing, or malformed attributes, and no
   enabled stable-authority, SYSTEM, or Administrators SID. Expected ordinary
   AppContainer/package groups are not mislabeled as a restricting-SID list.
7. The process is the exact suspended root and is atomically a member of the
   authenticated nonbreakaway kill-on-close job. Exact job accounting and the
   completely sized process-ID list agree on that one root.
8. A minimum duplicated impersonation token from that actual child passes the

   root/files read/execute; write/append/delete/owner/DACL/SACL denied; scratch

   and state/helper/source/stable paths denied.
9. The exact `SECURITY_CAPABILITIES`, `JOB_LIST`, and three-handle `HANDLE_LIST`
   were supplied in the same `CREATE_SUSPENDED` call; the candidate thread has
   not run and cannot self-certify any field.
