## Finding 1: cached bindings are not live custody rechecks

`retained_object_binding` hashes the retained handle's current content for a
nonempty file, but every identity, path, attributes, link count, size, and
security field in its material comes from the `RETAINED_OBJECT` snapshot. It
does not fstat the retained handle, re-read current security, ask for its current
final path, reopen the pathname no-follow, or compare a pathname probe's file ID
with the retained handle.

Consequently these apparent rechecks are tautological for directories and only
content rechecks for files:

- the final parent comparison before CREATED;
- final source/target comparisons;
- target comparisons before and during COMPLETE cleanup; and
- the parent comparison after root deletion.

A parent renamed/replaced after initial retention still recomputes its old
binding. A target pathname can be replaced while the original target handle
remains open; the final content hash reads the original handle while the root
census sees only the replacement's fixed name. Path-based stream enumeration
can likewise inspect a different pathname object than the retained file. The
broker can therefore append CREATED without proving that the three current
pathnames still identify its retained targets. PARTIAL cleanup can resolve its
fixed names under a replaced parent because the retained parent binding is not
live-reproved.

### Required bounded repair

Add one private live retained-object verifier and use it at every authority
boundary. It must:

1. re-read the retained handle's file ID, basic attributes, link count, size,
   final path, exact owner/DACL/label descriptor, and file content/stream census;
2. reopen the current pathname with no-follow and non-widened sharing, capture
   the same live facts, and require exact identity/profile equality to the
   retained handle and persisted binding;
3. close/free every probe with ambiguity latching; and
4. refuse path absence except in the explicitly durable post-DELETE retry arms.

Use it after source retention, before and after each copy, for all
parent/source/root/targets before CREATED, before the first COMPLETE DELETE
publication, at each child/root delete boundary, and for the parent after root
absence. PARTIAL reconstruction has no root/target persisted identity, but it
still must live-prove the persisted parent binding and retain/probe equality for
each admitted current root/child before deletion.

Deleting the pathname reopen, current security read, final-path read, file-ID
comparison, or any one call site must fail an executable substitution mutant.

## Finding 2: directory alternate streams escape the census

`exact_unnamed_stream` is called only for nondirectories. Both
`directory_empty` and the fixed/subset directory censuses enumerate children
with `FindFirstFileW`; they do not enumerate streams on the directory itself.
An execution parent can therefore appear empty while retaining a named stream,
and an execution root can present exactly three children while carrying an
additional named stream. Cleanup deletes such a root rather than refusing.

Round 175 and Round 189 explicitly exclude alternate streams from the execution
namespace. The parent is required to contain no stable bytes, and the future
package grant must not expose an unbound directory stream.

### Required bounded repair

Give retained directories their exact host-supported unnamed-stream/no-named-
stream formula and bind it into live verification. Apply it to the execution
parent and root at initial capture, before CREATED, before first DELETE, on
retry, and immediately before root deletion. `FindFirstStreamW` failure,
additional stream, wrong unnamed-stream name/size, enumeration error, and
`FindClose` ambiguity must refuse. A named stream on a source, target, partial
child, parent, or root must each have a compiled deletion test.

The stream census must be identity-bound by Finding 1; enumerating only a path
that may name a replacement is insufficient.
