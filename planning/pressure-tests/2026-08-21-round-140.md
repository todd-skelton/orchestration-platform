## Disposition

`BLOCK_REPLAN` for the authenticated common-CAS selected-object locator ledger
at exact reviewed head `19013ad598329b37f45af0fa2452b5c7dae2b99a`.

The three aliases, pre-CAS create-once/read-back order, orphan treatment,
content/path digest binding, root/archive separation, FULL_REQUIRED loss rule,
and stable external CAS fence are coherent. No digest cycle is introduced, and
the candidate tip can be content-addressed before selection without becoming
selection authority.

Three definite contract gaps remain:

1. the selected graph never binds the proposal's pointer kind or
   `positionDigest` to the independently trusted expected identity;
2. the exact four record inputs cannot perform the promised recursive prior-
   history walk or prove its missing/forked/reordered/terminal properties; and
3. a validator receiving records rather than persisted bytes cannot distinguish
   canonical bytes from reordered or otherwise noncanonical encodings, despite
   canonical-byte rejection and a deletion mutant being assigned to this pure
   slice.

All three are planning defects, not implementation choices. Implementing around
them would either omit required trust bindings or invent a larger API not
authorized by the sole contract document.

## Blocking findings and smallest repairs

### OP-R140-1 — expected position and proposal family are not equal-bound

The proposed input census deliberately includes the closed eight-member
`expectedIdentity`, including `pointerKind` and `positionEvidence`. The stated
validator recomputes expected `Dp`, checks only the tip's pointer kind and
`Dp`, then checks proposal successor/`Dp` and tip `Dv`/`Dr`. It never requires:

```text
proposal.pointerKind = expectedIdentity.pointerKind = tip.pointerKind
proposal.positionDigest =
  computePointerPositionDigest(expectedIdentity.pointerKind,
                               expectedIdentity.positionEvidence)
```

This is observable with existing contracts. `Dp` binds the canonical pointer
path and identity scalars, but it does not hash `positionEvidence` as a separate
part. Position evidence supplies only placeholders needed to reconstruct some
registered paths. In particular, cleanup-gate and recovery-fence current paths
are static, while their position evidence carries authoritative
`ordinal+rootDigest`. Mutating either position member leaves their `Dp`
unchanged. A proposal with an arbitrary well-formed `positionDigest` can
therefore satisfy every listed locator equality.

There is also no listed equality from `proposal.pointerKind` to the expected
kind. A proposal may carry the expected `Dp` but declare a different registered
kind; `Dr` authenticates those proposal bytes, and a tip can name that `Dr`
while independently declaring the expected kind. Checking the tip alone does
not close the cross-family graph.

The compatibility prose itself requires mutation of every expected-identity
member and rejection of wrong-family inputs, so the missing equalities make
the acceptance matrix non-executable as written. Computing `Dv` under a
proposal-selected kind would compound the problem; it must be computed under
the kind already equal-bound to the trusted identity.

The smallest repair adds the two explicit equalities above to the authority and
mirrored ISS-002 evidence matrix. It adds no schema, input, digest, index, head,
or runtime mechanism. Deletion mutants should independently remove the proposal
kind equality and the proposal-position equality; cleanup-gate and recovery-
fence position mutations must then refuse even when all attacker-controlled
proposal/tip digests are recomputed.

### OP-R140-2 — four current-node inputs cannot walk full prior history

The pure validator has exactly four inputs:

```text
expectedIdentity
proposal
tip
value
```

Those inputs contain one current node. The proposal contains only nullable
prior `Dt/Dv/Dr` digests, not the prior value/proposal/tip records. The function
can validate that the prior triple is all-null or all-non-null and can return a
non-null prior tuple for a caller to locate. It cannot inspect even one prior
record, much less prove a multi-record history is complete, ordered, unforked,
nonmissing, or terminated at an authorized null genesis.

The authority nevertheless assigns all of the following to this structural
slice:

- the predicted footprint says the one four-input validator includes
  recursive prior-triple walking;
- compatibility evidence walks null-genesis and multi-record histories and
  rejects partial, forked, reordered, and missing objects; and
- deleting the full-prior recursion check must leave a committed mutant.

Repeated calls made only inside a test helper would not implement a public
contract that owns those properties. Adding an implicit reader callback would
violate the exact four inputs and the no-filesystem/no-runtime boundary. Adding
a fifth dense history input would also widen the authorized API and requires an
exact terminal and length model not currently specified.

The smallest repair is to keep the four-input validator as a **single selected
node** validator and have it return the exact nullable prior triple. State that
ISS-004 iteratively constructs, canonically reads, and validates prior objects,
with family composition deciding whether the terminal null is authorized.
Structural tests may compose multiple single-node invocations to demonstrate
path constructibility, but must not claim full-history completeness. Move the
missing/forked/reordered/terminal walk and its deletion mutants to the ISS-004
read/composition matrix. This is smaller than adding a history container,
reader callback, common head, index, length field, or second digest.

If a pure full-history validator is instead intended, the packet must replace
the exact four-input census with a closed finite history input and specify
dense ordering, maximum/termination behavior, duplicate/cycle handling, and
the exact returned result before another review. The current packet authorizes
neither design.

### OP-R140-3 — a record-only validator cannot prove canonical persisted bytes

Canonical persistence is a necessary runtime rule. A reordered JSON object and
the canonical JSON bytes parse to the same detached record and therefore
produce the same `Dp/Dv/Dr/Dt`. Once the pure four-input API receives records,
the original byte ordering, whitespace, encoding, and LF termination are gone.
No record snapshot or digest recomputation can distinguish those encodings.

The authority correctly says each later content-path read must first be
canonical bytes, but the same packet then requires the pure structural locator
evidence to reject reordered/noncanonical objects and requires deletion of a
canonical-byte check to make a mutant survive. No one of the three path
constructors or the record-only validator can own that test honestly.

The smallest repair keeps canonical byte comparison in ISS-004, which already
owns filesystem read, byte-identical create-once retry/read-back, and the
authenticated current-tip read. The pure ISS-002 validator should accept only
detached records and make no source-byte claim. Move noncanonical persisted-
byte cases and the canonical-byte deletion mutant to the ISS-004 matrix. If
ISS-002 is meant to own byte validation, then value/proposal/tip canonical
bytes must become explicit closed inputs and their parsing/result contract must
be decided; that is a larger replacement, not an implementation inference.

## Alias construction, crash order, and path collision attack

The three proposed paths are exact and mutually separated:

```text
installation/pointer-cas/<Dp>/objects/values/<Dv>.json
installation/pointer-cas/<Dp>/objects/proposals/<Dr>.json
installation/pointer-cas/<Dp>/objects/tips/<Dt>.json
```

`Dv` already commits pointer kind, `Dp`, and canonical value record; `Dr`
commits the closed proposal including pointer kind, `Dp`, successor `Dv`,
prior triple, position, mutation, producer, and time; `Dt` commits the closed
tip including pointer kind, `Dp`, `Dv`, and `Dr`. Prefixing all three by `Dp`
is redundant for content identity but necessary bounded namespace separation
and makes wrong-instance paths observable. Cross-class subdirectories prevent
a value/proposal/tip filename collision.

Under ordinary SHA-256 collision resistance, the same `Dp+digest` denotes one
canonical byte string. If pre-existing bytes at that path differ, exact-byte
create-once comparison refuses; it must not choose either by age, writer, or
directory order. Concurrent identical writers are idempotent. Concurrent
different candidates normally address different digests and leave harmless
orphan aliases. No mutation ID, index, journal, alias head, or latest-file
convention is needed.

The crash order is acyclic and recoverable:

```text
write/read-back value alias
  -> write/read-back proposal alias
  -> write/read-back candidate tip alias
  -> stable external current-tip CAS/read-back
```

A crash before CAS leaves only non-authoritative content. A losing CAS leaves
orphan aliases. Because all three exact read-backs precede CAS, a selected tip
does not depend on a planned post-CAS alias write. A crash after CAS can locate
the already-verified tuple. Retrying exact bytes is idempotent; any conflict is
`UNKNOWN`. The current tip is safe to alias before CAS because its `Dt` is a
content identity, while only the registered current-tip path and stable
external CAS grant selection.

Candidate-written aliases do not certify the candidate and never enter a
producer epoch, capability, or promotion verdict. The runtime implementation
must still preserve the stated stable-release mutation boundary: knowledge of
bytes or ability to present an orphan object is not a CAS handle. No alias may
delete, compact, resurrect, or replace selected history.

## Family root/archive ownership and FULL_REQUIRED behavior

The common locator correctly stops at value/proposal/tip objects. Cleanup-gate
and recovery-fence root paths require independently trusted transaction
identity, while parsed selected heads supply the root digest that family
composition must equal-bind. Recovery authorization has its separately
reviewed transaction archive path and tombstone composition. A generic locator
must not infer any root/archive from a value digest, enumerate a directory, or
accept a caller-selected fallback.

Missing, unreadable, conflicting, digest-mismatched, path-mismatched, or
semantically invalid selected objects and required family records remain
`FULL_REQUIRED UNKNOWN` and block mutation. Mutation-addressed originals are
not a fallback for a missing authenticated alias. Bare absence is authoritative
only where a separately reviewed genesis rule proves it; a null prior triple
inside the generic proposal does not by itself prove family genesis.

## Acceptance and predicted-footprint executability

After repair, the smallest implementable structural slice remains within the
existing pointer module and focused pointer tests: three path constructors plus
one total pure current-node validator. The validator can snapshot all four
records, parse closed proposal/tip, validate exact expected identity, bind
proposal kind and position, recompute `Dp/Dv/Dr/Dt`, check every current graph
equality, and return detached records plus the exact tuple and nullable prior
triple. It can reject partial prior triples and hostile reflective inputs
without throwing. Generic success still cannot semantically admit the value;
the registered family parser remains required.

It cannot prove filesystem origin, canonical source bytes, alias presence,
read-back, whole-history completeness, family root/archive validity,
current-tip source authentication, conflict resolution, proposal/CAS,
capability, command, broker behavior, deletion, compaction, or runtime
mutation. Those deferrals preserve the engine/adapter boundary and candidate
non-self-certification.
