## Disposition

`BLOCK_REPLAN` for `ISS-006` at exact reviewed head
`d792cbbeb75fc9272251aa7a9a527453b5df58fe`.

The draft has the correct high-level trust rule: trusted default-branch harness
bytes evaluate a candidate subject; a candidate cannot choose required jobs,
author the aggregate, normalize an unsupported capability to pass, or route its
own verdict into promotion. The packet does not define enough authority to
implement that rule without guessing.

Four coupled blockers remain:

1. there are no literal job-receipt, raw-artifact manifest, environment
   inventory, or aggregate schemas and no exact digest/canonicalization rules;
2. there is no executable workflow topology identifying which trusted bytes
   choose the candidate, required jobs, receipt writer, and aggregate writer;
3. there is no authenticated same-run/artifact join that distinguishes a
   stable aggregate from candidate-authored byte-identical JSON or mixed-run
   artifacts; and
4. the stable suite/job registry, future package-registration rule, retention,
   local-versus-authoritative output, performance measurement, and shared
   scaffold footprint are not closed.

These are authority decisions rather than implementation details. Different
reasonable choices change the trust root, public contract bytes, workflow
permissions, provenance, and downstream ISS-022 evidence. A human decision is
required on the pre-ISS-029 CI trust topology and provenance mechanism before
implementation.

The smallest repair is a bounded ISS-006 authority ledger plus a mirrored
draft update. It need not add production release certification, signatures, a
general workflow engine, or runtime primitives. It must fix the exact schemas,
stable/candidate execution topology, same-run provenance join, required-job
registry ownership, and evidence/deletion matrices described below, then
return to fresh exact-head removal review.

## OP-R165-1 — receipt and aggregate contracts are not defined

The draft says receipts bind test-bundle digest, source subject, OS image,
architecture, Node version, contract versions, and capability result. It does
not state a schema name, exact ordered member census, scalar types, nullability,
closed enums, canonical byte encoding, digest domain, result lattice, or
compatibility policy.

The same gap exists for:

- the “exact environment inventory” named in scope;
- raw per-job artifacts and platform diagnostics;
- the required-job/suite census;
- the aggregate and its outcome;
- artifact retention evidence; and
- the local entrypoint result.

The glossary defines “conformance receipt” only as versioned evidence on a
named environment. Repository search finds no conformance receipt or aggregate
contract implementation. `contract-decisions.md` incorporates no ISS-006
literal ledger. `state-machines.md` states only that all OS receipts bind the
candidate and test bundle at the later release `CONFORMED` state. Those
statements do not select public bytes.

An implementer would have to invent whether result is `PASS|FAIL|UNSUPPORTED`,
whether a required unsupported capability is a receipt plus aggregate refusal
or an invalid receipt, whether diagnostics are embedded or digest-bound, how
contract versions are ordered, whether image facts are scalar or a nested
closed record, and what prevents one receipt from another workflow from being
joined.

The authority ledger must define, at minimum:

1. an exact environment-inventory record;
2. an exact per-required-job receipt binding one candidate subject, stable
   harness/test bundle, suite/job identity, environment inventory, normalized
   result, raw artifact manifest/digest, and run provenance;
3. an exact aggregate binding the same subject/harness/run, the trusted
   required-job census, and the complete ordered receipt set; and
4. domain-separated digests and canonical serialization for each persisted
   record.

The aggregate outcome must be derived, never supplied: success requires one
valid receipt for every exact required job and no extras, with every required
capability passed. Missing, duplicate, skipped, cancelled, unsupported,
unreadable, mixed-subject, mixed-harness, mixed-run, or unknown evidence must
refuse.

These public evidence contracts belong either in the ISS-006 conformance
package with an explicit compatibility contract or in `packages/contracts`
under an amended ISS-002 authority. The current ownership statement merely
says ISS-006 produces infrastructure and ISS-002 owns schemas/vectors; it does
not say who owns these new schemas. That ownership must be resolved explicitly.

## OP-R165-2 — trusted workflow bytes and candidate subject are not composed

“Harness definition and aggregation execute from trusted default-branch bytes”
is necessary but not executable as written.

The existing `.github/workflows/bootstrap.yml` uses `pull_request` and an
unqualified `actions/checkout`. For a pull request, that workflow and checkout
are candidate/merge-context behavior. It does not provide the planned
separation and cannot be used as evidence that default-branch harness bytes
selected or aggregated the suite.

The ISS-006 packet does not choose:

- the workflow event/dispatch mechanism that guarantees workflow bytes come
  from the trusted default branch;
- the exact trusted default-branch SHA and harness-tree digest;
- the exact candidate subject supplied by trusted event context;
- whether the subject is head revision, merge revision, tree digest, source
  bundle, or candidate artifact;
- two separate checkout roots and the permitted direction of access;
- `persist-credentials`, token permissions, secrets, environments, and artifact
  permissions for jobs that execute candidate code;
- the stable wrapper/child-process boundary that prevents candidate code from
  writing the authoritative receipt; or
- the stable aggregation job checkout and its refusal if stable bytes move
  during the run.

This is not solved by hashing the harness after the fact if candidate code ran
with write access to that same harness tree. Nor is it solved by checking out
main inside a candidate-authored workflow: the candidate still selected the
matrix, steps, permissions, and aggregator.

The smallest topology decision should identify one protected default-branch
entry workflow whose immutable bytes:

1. derive an exact immutable candidate subject from trusted event/API context;
2. materialize stable harness and candidate source in separate roots;
3. select the complete required job matrix from the stable registry;
4. run stable test definitions against candidate modules/artifacts;
5. keep candidate execution without secrets, write token, aggregate
   credential, or job-selection input;
6. have a stable wrapper write each receipt only after candidate execution;
7. have a separate stable aggregation job re-check stable harness bytes and
   consume only expected same-run artifacts; and
8. emit no promotion, installation, review, or capability handle.

Whether that entry is a protected dispatch, a base-context pull-request
workflow, a ruleset-required workflow, or another CI authority is a security-
sensitive outward-facing choice. In particular, executing untrusted candidate
code under a base-context workflow has known permission consequences. The
repository must select the mechanism and required repository configuration;
the reviewer cannot choose it from the current prose.

## OP-R165-3 — candidate-authored and mixed-run artifacts cannot be detected

Acceptance criterion 3 requires candidate-authored aggregate and mixed-run
receipt mutations to fail. JSON fields such as `workflowRunId` or
`aggregateAuthor: stable` are self-assertions unless independently joined to
trusted workflow provenance.

The draft does not state which provenance is authoritative before ISS-029.
ISS-029 later probes GitHub OIDC/artifact attestations for bootstrap release
authority and is itself blocked by the trusted OS harness. ISS-006 therefore
cannot silently assume the passed result of ISS-029 or add that dependency
without changing the graph.

A smaller pre-release harness can use provider-authenticated run/job/artifact
metadata plus independent review rather than production attestation, but the
authority must say so exactly. It must bind and verify at least the repository,
trusted workflow identity/ref/SHA, numeric run ID, run attempt, exact candidate
subject, stable harness digest, required job/matrix identity, artifact ID/name,
raw artifact digest/length, and aggregation job provenance. Every receipt and
raw artifact must be drawn from the same expected run/attempt; replay from a
prior retry or another candidate refuses.

The aggregate must not trust receipt-declared provenance alone. Its stable
writer must obtain the expected artifact set from the provider/run context,
verify raw bytes, and recompute receipt and aggregate digests. Candidate jobs
must not possess the authority used to author or publish the final aggregate.

If provider metadata without portable attestation is only review evidence, the
aggregate must be explicitly non-promotional and its downstream ISS-022 use
must require an independent reviewed capability decision. Local outputs must be
marked advisory/untrusted or be structurally distinct; otherwise a candidate
can run the local entrypoint and manufacture byte-identical “hosted” receipts.

## OP-R165-4 — required-job and future-suite ownership are ambiguous

The draft correctly says a candidate cannot select required tests and a future
package can register a suite without editing shared workflow logic. It does not
say where that registration lives or when it becomes trusted.

If the harness dynamically discovers candidate packages or reads a candidate
registry, the candidate can remove, rename, skip, or downgrade its own required
suite. If the workflow hard-codes matrix jobs, acceptance criterion 4 fails and
workflow changes are required for every package. If both exist, precedence is
undefined.

The smallest closed rule is a release/default-branch stable suite registry
owned by the conformance package. It defines exact suite IDs, owning package,
command/entrypoint, required environments/capabilities, expected vector census,
and required/advisory disposition. The trusted harness derives jobs only from
that registry. A package adds its suite by changing its package registration
and the stable registry/census through normal review; that registration becomes
required only after landing in the stable harness revision, never merely
because the candidate declares it.

The registry, workflow matrix, receipts, and aggregate must be cross-checked so
deleting a suite row, excluding a matrix cell, changing required to advisory,
or adding `continue-on-error` fails a structural workflow/census test.

The current predicted footprint does not mention the root command/capability
slot replacements, conformance package manifest/test placeholder, bootstrap
package/workflow census, or shared ISS-000 scaffold checks that must change.
Under the work model, a shared scaffold amendment must update every restating
census in one reviewed change. The footprint must enumerate these paths or
name an explicit ISS-000 amendment.

## OP-R165-5 — raw bytes, diagnostics, reflection, and cross-OS vectors need an owner

The draft requires canonical receipts that normalize semantic results without
hiding platform-specific diagnostics. It does not define the split between
authority and diagnostics.

The smallest design keeps the normalized closed result in the receipt and
binds raw stdout/stderr/report bytes through an exact artifact manifest with
byte length and digest. Diagnostics remain non-authoritative but cannot be
silently substituted or discarded. Line endings, encoding, file order, path
redaction, and platform-native text must be specified before cross-OS “same
hash” claims are made. Semantic receipt equality cannot replace raw artifact
identity.

The cross-OS vector list is broad and appropriate, but it has no exact vector
census or stable owner. The harness should consume an ISS-002-published vector
registry/digest rather than hand-copying expected values into candidate code.
That registry must cover every currently shipped digest/schema branch named by
acceptance criteria 5, 8, and 9, including raw32/NUL/tag/count/type/length
framing, safe decimal boundaries, full authority chains, crash prefixes,
rotation refusal, pointer registry, reservation/descriptor/log/archive paths,
and FULL_REQUIRED loss.

Likewise, the reflective corpus needs exact fixture IDs and expected result for
mutable, sealed, frozen, proxy, cross-realm, subclass, hole, symbol, extra,
accessor, custom iterator, and malformed descriptor cases. The stable harness,
not candidate code, owns those bytes and expected outcomes. Mutation evidence
must delete each corpus row or change its expected disposition and fail the
census.

## OP-R165-6 — environment inventory and 1,000-chain budget are underspecified

The draft alternates between a general environment inventory and epoch-lock
receipts binding OS image, filesystem, helper/profile/ABI, and custody inputs.
It does not define which facts are required for every job, which are capability-
specific, or how an unavailable fact becomes `UNSUPPORTED` rather than null or
omission.

The environment ledger must distinguish stable platform identity from observed
runner image/build, OS/version, architecture, Node/pnpm versions, filesystem
case/Unicode/atomicity profile, helper/profile/ABI/custody observations, and
capability-specific evidence. Exact values may differ across OS; the normalized
result joins only facts the suite declares comparable. ISS-022 must not combine
receipts whose required profile dimensions differ.

The 1,000-record chain target is a useful falsifiable prediction, but “within
five seconds per walk” lacks a measurement contract. The ledger should specify
the exact vector bytes/head, clean-process or warmup policy, monotonic timer,
number of walks, measured interval, timeout/refusal rule, and receipt field.
Hosted runner provisioning and dependency installation must be excluded from
the walk interval. Exceeding the bound is a failed/unsupported required result,
not a retry-until-pass policy.

No dedicated checkpoint or optimized index is justified by this budget. The
deletion/proportionality test should first run the full linear walk. Performance
machinery may be added only if a measured clean-run failure demonstrates the
need.

## Artifact retention and operator actions

“Artifact retention” is named in scope but absent from decisions and acceptance
criteria. The packet must state which raw artifacts, receipts, aggregate,
stable registry/harness bundle, provider metadata, and mutation outputs are
retained; the minimum retention or immutable publication rule; and how missing
or expired evidence affects downstream use. Loss must never normalize to pass.

The operator action “Enable the three harness checks” is also not executable.
The packet must name exact stable check/job identities, required ruleset or
branch-protection configuration, who may change it, and evidence that matrix
exclusion, check renaming, admin bypass, or `continue-on-error` cannot satisfy
the requirement. A matrix with three OS cells may appear as one check or three
checks depending on CI naming; the authority cannot rely on an informal count.

These are outward-facing repository changes. Human approval is required for
the selected protected workflow/ruleset configuration after the authority
ledger is explicit.

## Self-hosting trust attack

ISS-006 must evaluate candidate behavior without certifying a release. The
correct authority flow is:

```text
trusted stable/default harness bytes
  -> fixed required registry and three-OS jobs
  -> stable wrappers evaluate exact candidate subject
  -> stable same-run receipt writers
  -> stable aggregator derives complete aggregate
  -> independently reviewed conformance evidence only
```

The candidate may provide the code/artifact under test. It may not provide the
required registry, expected vectors, workflow/matrix, receipt writer,
aggregation logic, normalized verdict, or promotion decision.

The current draft states this invariant but lacks the bytes/provenance graph
that enforces it. A candidate-authored workflow could check out main tests yet
omit a job or emit its own aggregate. A stable workflow could execute candidate
code in the same mutable harness directory and accept overwritten report
files. An aggregate could accept byte-identical candidate JSON without trusted
run provenance. All satisfy portions of the prose while violating the trust
model.

ISS-006 output must never be accepted directly by release promotion. ISS-019
owns complete candidate certification; ISS-029 owns the later authenticated
bootstrap workflow/grant probe. The ISS-006 aggregate should state its bounded
purpose/capability census and carry no promotion, review, installation, or
mutation handle.
