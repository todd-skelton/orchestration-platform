# Pressure round 430 — ISS-048 unavailable-control result contract

Status: bounded definition repair before stage-two source. No workflow trigger,
native build/run, artifact upload, provider record, selection, or operator
authority is activated.

## Measured blocker and disposition

Stage-two audit found that the registered report requires twelve
`{controlId,refused}` rows with Boolean `refused`, treats `false` as
`VIOLATED`, and treats a missing row as `UNKNOWN`. The first three controls need
the real stable witness. When compiler, SDK, Node distribution input, candidate
binding, or custody evidence is unavailable, those controls cannot safely run.
`true` would fabricate a refusal, `false` would invent a failed guard, and
omission would break the fixed census.

Disposition: amend the private inline diagnostic record before implementation.
Every control row becomes exactly `{controlId,refused,result}` with four valid
arms: `{true,"REFUSED"}`, `{false,"VIOLATED"}`,
`{null,"UNSUPPORTED"}`, or `{null,"UNKNOWN"}` for the last two fields.
The nullable arms mean the control did not run. They require stable prerequisite
evidence and cannot contribute refusal evidence.

## Scope and acceptance evidence

This definition round changes only the native-lock decision ledger, ISS-048
draft, and this pressure record. It closes the build, case, control, and per-OS
result vocabularies; maps control results into the existing report precedence;
and defines retained-file presence. Executed controls require both fixed files
and replayable stable evidence. Unavailable controls require canonical
`observation.json`, forbid `input.json`, and must agree with independently
validated prerequisite facts. Each control is reduced independently so an
unavailable real witness does not erase later stable guard results that can
still execute.

Acceptance evidence is exact issue/draft parity, planning validation, focused
format and diff checks, independent review, and green Linux, macOS, and Windows
bootstrap verification. Review must show that no invalid field pairing can be
read as a refusal and that only all four cases `OBSERVED` plus all twelve
controls `REFUSED` can produce an `OBSERVED` per-OS report.
