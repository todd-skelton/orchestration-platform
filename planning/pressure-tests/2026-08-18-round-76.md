## Blocking finding

### `OP-R76-001` — round 75's required mutant matrix remains incomplete

Round 75 required the subsequent acceptance suite to contain discriminating
mutants for every repaired derivation and equality. The exact repair adds:

- one all-current-checkpoints selector-`Dp` substitution;
- one prior selector-`Dp` substitution copied into otherwise closed prior
  evidence;
- one assertion that positive input to `validateCommitResolutionBinding`
  returns `positive-lineage:full-commit-required`;
- one accepted checkpoint sequence for each non-rotation ordinary target; and
- one all-eleven-row equivalence test between position-derived and
  canonical-path-derived `Dp`, plus one malformed reservation predecessor.

It still has no positive-lineage mutant that substitutes the prior selector
`Dt`, `Dv`, or `Dr`; substitutes `Dpost`; changes prior target kind/path,
installation, project, state, transaction, source, `G`, mutation, or selected
old epoch; or recomputes every dependent prior core, current checkpoint-zero
predecessor, run ID, selector graph, observation, and `Dcommit`. The existing
single-field checkpoint-chain tests are run-zero sequence tests, not attacks on
the new prior-evidence hop.

The registry loop proves only that valid examples are accepted. It does not
reject independent or coordinated changes to kind, path, installation,
project, state, transaction, source, and copied target `Dp` for the registry
census, as ISS-002 acceptance criterion 10 and round 75 require. In particular,
there is no negative commit-level case for the reservation predecessor key or
for a target that is itself the nested `POINTER_MUTATION_RUN_CURRENT` path.

The new canonical-path parser also lacks executable attacks for:

- placeholder prefix/suffix confusion and a suffix embedded inside a token;
- transaction text that is valid but disagrees with the identity field;
- a valid alternate recovery source that disagrees with `sourceToken`;
- fixed-segment, separator, dot-segment, backslash, drive, scheme, percent/
  Unicode, or other alias spellings that must not bypass exact canonical-path
  equality;
- extra/missing segments, empty placeholder values, and unsupported kinds; and
- hostile or malformed runtime inputs through the commit parsers, proving
  refusal rather than an uncaught exception.

The implementation reads soundly for the fixed current templates: each
template segment has at most one recognized placeholder; literal segments are
exact; dynamic transaction/source values are equal-bound; digest placeholders
are lowercase SHA-256; `pointerPath` reconstructs the only accepted spelling;
and commit callers catch derivation failures. But those facts are precisely the
new parser behavior under review and need executable compatibility evidence.
The sole malformed-predecessor test is not a substitute for this matrix.

Until these mutants execute, the suite cannot show that the complete prior
tuple/`Dpost`/run-ID/target semantics survive independent and coordinated
substitution. The removal criterion is therefore unmet even though no direct
accepting path was found in the repaired code during this review.

### `OP-R75-003` — removed

`validateCommitResolutionBinding` unconditionally returns
`positive-lineage:full-commit-required` whenever the ordinal is nonzero or
prior evidence is non-null. It computes only the ordinal-zero/null run ID and
therefore cannot return an empty issue set for positive lineage. The full
ordinary commit parser remains the only implemented validator that consumes
positive prior evidence, checks the predecessor ordinal and target/platform/
`G`/mutation equalities, checks the selected old epoch, binds prior selector
state into checkpoint zero, and derives the current run ID. The new test
directly proves the public helper refusal.
