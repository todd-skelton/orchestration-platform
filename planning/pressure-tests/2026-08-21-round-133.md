## Blocking finding and smallest bounded repair

### OP-R133-1 — `Dv` and `Dr` repeat facts already authenticated through `Dt`

The proposed receipt carries all four selected-evidence digests:

```text
selectedStatePathInstanceDigest = Dp
selectedStateProposalReceiptDigest = Dr
selectedStateTipDigest = Dt
selectedStateValueDigest = Dv
```

The sole authority already fixes `Dt` as the digest of the selected tip that
contains exactly `Dv+Dr`. This ledger additionally requires ISS-004 later to
parse the actual selected value, proposal receipt, and tip and recompute
`Dp/Dv/Dr/Dt`. ISS-032 must authenticate that the exact tip was read back before
creating the post-selection receipt. Once that actual tip is parsed and its
`Dt` equal-bound to the post-selection receipt, the tip itself supplies the
only authoritative `Dv` and `Dr`; the actual value and proposal receipt then
recompute and verify them. Receipt-local copies cannot catch a substitution
that the `Dt` and full graph checks do not already catch. An attacker can copy
the same expected `Dv/Dr/Dt` consistently, so the extra fields add no
independent provenance.

This is the same proportionality class removed from the native receipts in
round 131: an aggregate authenticated record remains the sole source for its
members, while copied member digests only expand the public census and later
equality matrix. Requiring remove/null/cross-type mutants for copied proof does
not establish a semantic deletion threat.

`Dp` is different and remains justified. `Dt` does not directly encode the
receipt's selected pointer instance, and the transaction-relative receipt path
alone is not the installation/project/state/path-instance binding. Retaining
and later recomputing `Dp` prevents an otherwise valid selected tip from being
replayed as an observation of another pointer instance. `Dt` remains the
smallest direct digest of the exact selected-tip read-back. The other four
members each have a separate role: transaction and operation construct the
receipt's own path and bind later state operations, `recordedAt` records the
new durable observation event, and the branch-local schema distinguishes
CONSUMED from REVOKED and selects the digest domain.

The smallest repaired census for each branch is therefore exactly six members
in ascending canonical JSON member order:

```text

schemaVersion:recovery-authorization-consume-receipt/v1|recovery-authorization-revoke-receipt/v1
selectedStatePathInstanceDigest:sha256
selectedStateTipDigest:sha256

```

equal-bind receipt `selectedStatePathInstanceDigest = Dp`; authenticate and
parse the exact selected tip and equal-bind
`selectedStateTipDigest = Dt`; take `Dv/Dr` from that tip; parse the actual
selected state value and proposal receipt; recompute their `Dv/Dr`; and then
perform the existing branch lifecycle, transaction, operation, path, native
receipt, currentness, and time composition. A caller-supplied expected tuple is
never a source. ISS-032 remains the owner of the selected-tip read-back,

## Acyclicity and the later REVOKED edge

The exact order is acyclic:

```text
native consume Dnc -> selected CONSUMED Dv/Dr/Dt -> consume post receipt Drcp
prior state/native removal Dnr -> selected REVOKED Dv/Dr/Dt -> revoke post receipt Drrp
```

No native receipt, core, gate, state value, selecting proposal, or selected tip
contains its downstream post-selection receipt digest. On the later
CONSUMED-to-REVOKED edge, selected REVOKED may contain the already-fixed
`Drcp`; consequently its `Dv`, selecting `Dr`, and `Dt` are downstream of
`Drcp`. `Drrp` is computed only after that REVOKED tip is selected and never
enters the REVOKED preimage. The graph is therefore a strict chain, not
`Drcp -> REVOKED -> Drrp -> REVOKED`.

Deleting copied `Dv/Dr` from each post receipt preserves that order. The
receipt's `Dt` still commits the selected tip's embedded `Dv/Dr`; it does not
make either post receipt an upstream state member. No digest cycle or missing
read-back relation was found.
