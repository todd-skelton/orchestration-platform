## Blocking finding 1: active control failure bypasses cleanup

`write_all` exits the process directly on a write failure. `read_frame` and
`protocol_refused` likewise exit directly on a malformed, truncated, unknown,
oversized, or short frame. These helpers are reused after PREPARE/OK, when a
live profile, folder handle, CREATED phase, and cleanup obligation exist.

Consequences include:

- a broken stdout while writing PREPARE/OK or LAUNCH/NOT_IMPLEMENTED exits 64
  without `cleanup_profile`;
- a malformed/truncated second frame exits 65 without cleanup;
- a partial frame after PREPARE is not treated like parent-pipe loss; and
- a canonical but wrong-order second request calls cleanup but discards its
  result and always returns REFUSED/65, even when profile deletion or absence
  proof failed.

Durable recovery makes those residues recoverable later, but it does not permit
the active process to report ordinary protocol refusal or skip its required
bounded reversal. Round 179 explicitly requires control-pipe loss and every
post-mutation failure to run the same cleanup and return/exit
RECOVERY_REQUIRED on ambiguity.

### Required repair

- No low-level parser or writer may call `ExitProcess` after an active profile
  can exist. Make reads, writes, frame validation, and response serialization
  return a closed result to the lifecycle owner.
- Track an explicit `EMPTY|PREPARED|TERMINAL` state. Every input/output error,
  short/oversize/malformed second frame, unknown second opcode, response short
  write, and EOF in PREPARED first attempts `cleanup_profile`.
- If cleanup is exact, terminal exit may be 65 with no response when the pipe is
  unusable. If cleanup is ambiguous, exit 70; send status 70 only when a
  complete response remains possible.
- Never treat partial response bytes as evidence; stable caller already refuses
  them. The broker still must clean.
- Capture and propagate the cleanup result on the current wrong-order branch;
  remove the `(void)cleanup_profile` laundering.

The fake fixture must execute malformed header/body, oversize, broken input,
broken PREPARE/LAUNCH response, wrong-order request, EOF, cleanup success, and
cleanup failure after PREPARED. Source-text assertions are insufficient.

## Blocking finding 2: durable recovery state can return ordinary REFUSED

`recover_groups` returns the raw zero result from `complete_profile_census`
without considering whether canonical nonterminal groups already exist.
`preflight_and_recover` propagates that zero. Thus an enumeration/free/system
failure with ATTEMPTED, CREATED, or DELETE_ATTEMPTED records maps to status/exit
65 instead of 70.

Similarly, `scan_journals` has only boolean success. A malformed, forked,
unknown, substituted, or unreadable journal in a nonempty state root is reduced
to the same zero used for a clean empty pre-mutation environmental refusal.
The caller cannot distinguish “no cleanup authority ever existed” from “durable
cleanup ownership exists but cannot be parsed.”

### Required repair

- Make journal scan, complete census, recovery, and preflight a closed tri-state:
  `CLEAN`, `REFUSED_BEFORE_MUTATION`, or `RECOVERY_REQUIRED`.
- Only an exact empty root with no USED/pending/final record and no active
  mutation may return pre-mutation REFUSED for an API/environment failure.
- Any canonical USED or later group, any recognized profile filename/pending
  residue, malformed/noncanonical state-root entry, scan ambiguity, or target
  `orch6` residue returns RECOVERY_REQUIRED/lost custody until exact absence is
  durably established.
- With `group_count > 0`, enumeration, free, root recheck, parse, pending,
  allocation, or cleanup failure cannot return zero/65.
- Tests must independently delete each mapping and cover mixed sorted groups
  where a later malformed/nonterminal group prevents all earlier mutation.

This repair preserves Round 180: an exact empty root plus unrelated-census API
failure still returns ordinary REFUSED and writes nothing.

## Blocking finding 3: handle/allocation ambiguity is discarded

`release_root` is `void` and ignores `CloseHandle` for the retained state-root
and process-token handles. Every successful SERVE/RECOVER response calls it
without a result. This directly contradicts Round 179's rule that every handle
close is checked and close ambiguity changes the result.

Folder failure paths are also not closed:

- `bind_folder` can open a folder handle and then return failure without closing
  and nulling it;
- ATTEMPTED reconciliation can call `bind_folder` again and overwrite an
  earlier failed handle;
- some error cleanups close a folder handle but ignore close failure; and
- many returning allocation APIs (`HeapFree`, `LocalFree`, `FreeSid`, BCrypt
  destroy/close) discard their status even on authority-bearing paths.

A leaked folder handle can itself prevent `DeleteAppContainerProfile` from
removing storage. Process exit eventually closes handles, but the broker may
already have emitted OK or ordinary REFUSED, and the same attempt has not proved
cleanup.

### Required repair

- Replace `release_root` with an accumulating checked close routine. Attempt
  every remaining close/free, but refuse success if any reporting operation is
  ambiguous. A void API such as `CoTaskMemFree` is invoked exactly once but
  cannot supply a status.
- `bind_folder` must leave either one fully validated retained handle or null.
  On every partial failure, close it, record close failure, and never overwrite
  an existing handle.
- Cleanup must attempt folder, record, token, root, find, BCrypt, SID, security,
  and heap releases independently; one failure cannot skip later reversal.
- No SERVE/RECOVER OK may be written until all required non-process-lifetime
  handles are closed successfully. Where response failure itself occurs, exit
  state follows finding 1.
- Add fake deletion mutants for each close/free arm, including bind failure
  after open, failed close before delete, root close after ABSENCE_PROVED, and
  multiple simultaneous failures proving all releases were attempted.
