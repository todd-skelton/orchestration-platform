## Why this is the next complete boundary

The landed LAUNCH path already creates the exact candidate process suspended,
proves its actual AppContainer token, Job membership, handle list, access
relation, argv/cwd/environment, and stable-root denial, then reverses everything
without executing one candidate instruction. The next unresolved fact is
whether the same broker can safely run the copied Node/RPC/candidate process
and return only a stable-framed terminal observation while retaining complete
cleanup authority.

The following operations are one indivisible security unit:

1. durably prove pre-resume admission;
2. establish all three stable I/O workers;
3. resume exactly once;
4. send the stable challenge and close candidate stdin;
5. drain stdout and stderr concurrently under independent hard bounds;
6. prove the root handle, both output pipes, and the complete Job terminal;
7. expose candidate bytes only inside one broker-authenticated response frame;
8. retain the empty Job and durable custody until TEARDOWN; and
9. terminate/reprove, revoke, remove roots/profile, and prove absence.

A resume-only slice would create live hostile code without terminal or cleanup
evidence. A protocol-only mock would not exercise the actual Job and inherited
pipes. Performing teardown before returning LAUNCH would put revocation/profile
deletion inside the coordinator's measured interval and erase the existing
teardown-before-result boundary. Adding the later TypeScript adapter now would
mix native execution correctness with broker-image custody and process-client
composition, increasing the attack surface before the native contract is
closed.

## Reuse the existing durable OPWL owner

No new journal magic, version, kind, path, or digest is authorized.

`ADMISSION_PROVED` (OPWL kind 5) is already durable before any possible resume.
It binds the exact profile/execution predecessors, package SID, Dgrant,
Dlaunch, named Job, security descriptor, limit bytes, application, argv, cwd,
environment, creation flags, and suspended process cleanup authority. Recovery
from phase 5 already opens or reconciles the named Job, terminates it when
present, restores all four descriptors, and completes OPWL 6/7 before OPWX/
OPWJ cleanup.

The resumed/suspended distinction does not change the required recovery action:
terminate the exact durably named nonbreakaway Job and prove it empty before
revocation. Adding `RUN_ATTEMPTED` would duplicate phase 5 and introduce a new
publication gap between admission and resume. Candidate output is never durable
authority; a crash after terminal output but before the stable response simply
loses that attempt and enters the same phase-5 cleanup.

Normal TEARDOWN uses the existing chain:

```text
ADMISSION_PROVED (5)
  -> exact Job/root/pipe terminal reproof
  -> REVOKE_ATTEMPTED (6)
  -> root-first DACL restoration and exact original proof
  -> scratch absence
  -> ADMISSION_ABSENCE_PROVED (7)
  -> OPWX execution cleanup/absence
  -> OPWJ profile cleanup/absence
```

An old phase-5 record from the refusal-only version and a new phase-5 record
after resume therefore have the same safe recovery semantics.

## Closed native protocol

The broker retains exactly the existing `SERVE` and `RECOVER` modes, protocol
version 1, and PREPARE/LAUNCH/TEARDOWN opcodes. No general command or new mode is
added.

### Request sequence

- PREPARE is unchanged and remains outside the future coordinator interval.
- The first LAUNCH after PREPARE carries exactly one opaque challenge byte
  string of length `1..4,194,304`. The global request ceiling may increase from
  1 MiB to 4 MiB; PREPARE retains its much smaller canonical five-path parser.
- The challenge is stable input, not candidate authority. The broker does not
  parse, normalize, hash as evidence, or accept a candidate replacement. It
  writes the exact bytes through the candidate stdin worker and closes stdin
  after the complete one-message write.
- After a terminal LAUNCH response, exactly one zero-payload TEARDOWN is legal.
  Duplicate LAUNCH, PREPARE reuse, nonzero TEARDOWN, trailing input, malformed
  framing, control EOF, or parent-pipe loss enters the same cleanup path and
  cannot preserve a live candidate.

### Terminal response

The existing broker response envelope remains `OPWB`, version 1, response kind
2, operation LAUNCH. `STATUS_OK` has one exact binary payload:

```text
terminalKind:u8  # 0=EXITED, 1=TIMEOUT
reserved:u24=0
exitCode:u32le   # exact DWORD only for EXITED; zero for TIMEOUT
stdoutLength:u32le
stderrLength:u32le
stdout:bytes[stdoutLength]
stderr:bytes[stderrLength]
```

Total length is exactly `16 + stdoutLength + stderrLength`; each stream is at
most 4,194,304 bytes and integer addition is checked before allocation/write.
No trailing, alternate order, duplicate frame, textual PID, duration, PASS,
issue list, signal, candidate status, or optional field is admitted.

`EXITED` requires a signalled exact root process handle and detached exit DWORD.
`TIMEOUT` has no exit code and exposes empty stdout/stderr, matching the current
Linux authority's stable timeout observation. Nonzero exit, stderr, malformed
JSON, noncanonical JSON, or semantic issues still use `STATUS_OK`: they are
hostile candidate observations for the stable coordinator, not broker protocol
errors. Invalid UTF-8 remains raw bytes; the later stable adapter must use fatal
UTF-8 decoding before returning strings to the coordinator.

Output overflow, I/O ambiguity, wrong pipe, resource failure, or incomplete Job
terminal proof never truncates into a successful payload. A cleanly terminal
over-limit attempt may return `STATUS_REFUSED` with no payload and still
requires TEARDOWN. Lost custody returns `STATUS_RECOVERY_REQUIRED` and retains
journals for RECOVER.

The candidate inherits only its stdin/stdout/stderr handles. Broker control
stdout is never a candidate handle, so candidate bytes cannot forge `OPWB`.

## Exact resume, concurrent I/O, and watchdog

Use three fixed stable-broker worker threads, not named pipes, a thread pool,
shell, service, or candidate callback:

- one writer owns the stable candidate-stdin end and exact challenge extent;
- one reader owns candidate stdout;
- one reader owns candidate stderr.

All three contexts and handles are stable allocations, noninheritable, created
and authenticated before resume. Partial worker creation terminates the still-
suspended Job, closes/unblocks every created worker, joins them, and enters
ordinary reversal. Reader threads loop until exact EOF, copy at most their
independent 4 MiB bound, latch overflow/error, and continue draining/discarding
until terminal so a hostile writer cannot deadlock cleanup. The writer handles
partial writes, refuses zero progress, sends every challenge byte exactly once,
and closes stdin on every terminal path.

Only after all workers exist does the broker call `ResumeThread` exactly once.
The return must prove the prior suspend count was exactly one. Failure, zero,
greater-than-one, a second call, or thread-handle substitution terminates the
Job and refuses. The primary thread handle is then closed; the exact process
handle remains the root terminal authority.

A fixed stable watchdog begins immediately before resume and uses an
authenticated monotonic Windows source plus bounded wait arithmetic. At five
seconds it calls `TerminateJobObject`, then still joins root and all workers and
reproves Job zero before emitting TIMEOUT. This watchdog is liveness authority
inside the native broker, not the portable duration: the existing stable
coordinator remains sole owner of the broader launch-to-response/parse interval
and will independently reject anything over 5,000,000,000 nanoseconds after the
later adapter is wired.

## Terminal root and descendant proof

Normal EXITED is permitted only after all of the following are simultaneously
true:

1. the exact root process handle is signalled;
2. `GetExitCodeProcess` succeeds and is not `STILL_ACTIVE`;
3. the stdin writer has terminally closed;
4. stdout and stderr workers reached exact EOF without an unreported error;
5. both worker thread handles are signalled and joined;
6. Job accounting and the completely sized PID-list observation agree; and
7. the exact nonbreakaway Job contains zero processes.

If the root exits while a descendant remains or holds a pipe, the broker waits
only within the same fixed deadline, then terminates the whole Job and returns
TIMEOUT/refusal after terminal proof. A PID, parent-process tree, completion
port message, root exit alone, pipe EOF alone, or candidate claim is never
terminality. Assigned/list disagreement, over-64 census, zero/duplicate/
over-DWORD PID, returned-length ambiguity, query denial, or surviving process
refuses and retains cleanup custody.

After a clean LAUNCH response, close root/thread/pipe worker resources but
retain the exact empty Job handle and the already authenticated candidate token
needed for post-revocation denial. Candidate output buffers are zeroed/freed
after the broker response is written. The broker state becomes terminal-await-
TEARDOWN; it cannot launch again.

## TEARDOWN, control loss, and recovery

TEARDOWN first calls `TerminateJobObject` even after observed zero, rechecks
complete accounting/PID-list zero, and closes the last Job handle. It then
persists OPWL kind 6, restores the execution root before all three files,
requires the retained exact AppContainer token to fail read/execute/write/
delete/security access and actual opens, closes every token/process/thread/
pipe/worker handle, proves scratch absence, and persists kind 7. Existing OPWX
and OPWJ cleanup then removes execution/profile state and independently proves
moniker/SID/folder/job/ACE/root absence before `TEARDOWN/STATUS_OK` and exit 0.

Control EOF or malformed input after LAUNCH performs the same cleanup without
trusting or waiting for another command. If the broker dies, its last
kill-on-close handle terminates the Job; existing RECOVER phase-5 handling then
proves or reconciles Job absence and completes 6/7 plus execution/profile
cleanup. Recovery never signals a numeric PID and never reconstructs candidate
output.

No terminal observation becomes usable until live LAUNCH terminality is proved;
no semantic result becomes usable until the future coordinator's parse and
subsequent successful TEARDOWN. A teardown failure therefore still overrides a
candidate-success observation.

## Proportionality and removal table

| Retained mechanism | Concrete in-scope threat | Required deletion test | Smaller alternative and conclusion |
| --- | --- | --- | --- |
