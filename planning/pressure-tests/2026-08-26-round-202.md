# ISS-006 Windows admission executable-evidence review — round 202

## Disposition

`PASS_TO_REPAIR`.

This is a fresh independent exact-tree removal review of the current
uncommitted Windows pre-execution admission slice against pushed HEAD
`c3de3212ddb616ceafb7508917a43bf62c414e96`, the sole ISS-006 authority, and
Rounds 175 and 197–201.

The new `OP_WINDOWS_ADMISSION_OS_FIXTURE` is a material improvement. It
includes the exact production C source, directly executes the real descriptor
reducer, grant/restore, suspended-launch, token proof, Job, lifecycle, and
recovery functions, and leaves the production PE byte-identical to Round 201.
It closes the broad Round-201 finding that those functions had no compiled
fake-OS execution at all.

It does not yet close the removal round. Several specific deletion mutants
survive because the fake observations count calls without authenticating their
semantic tuple, partial launch results never enter the real cleanup function,
restore failures are not driven, token/Job hostile cases remain incomplete,
and lifecycle/recovery tests do not observe the complete durable ordering or
retry state. These are bounded fixture/evidence repairs within the existing
packet; no production design, protocol, phase, mode, helper, public contract,
or human decision is required. A landing disposition would be premature.

## Finding 1: access/open cardinality does not prove the right-object tuple

`fixture_admission_access` accepts any non-null object, any nonzero desired
mask, and either Boolean expectation. `fixture_admission_open` likewise accepts
any nonempty path, any nonzero mask, and either directory/expectation Boolean.
They increment counters and fail at a selected ordinal, but they do not bind an
ordinal to the expected object role, exact path, access mask, directory flag,
and expected result.

The 30/34 happy counts and one-failure-per-ordinal loops therefore do not prove
the claimed distinct checks. For example, each of these mutants remains green:

- use `denied_execution_rights[0]` for all six iterations;
- probe one target handle/path for all three target roles;
- substitute a source, parent, stable root, or unrelated nonempty path;
- use a file probe where the execution root requires directory semantics; or
- pass the wrong expected-allow Boolean while retaining the same call count.

The separate pure fixture proves only that the six-member constant array has
the expected values. It cannot prove how either production loop consumes the
array. The real host happy path observes denial, but a repeated stronger or
different denial can still pass it.

### Smallest repair

Have both seams append the complete detached observation tuple. Assert the
exact ordered 30-row AccessCheck census and 34-row impersonated-open census:
token, object role or exact canonical path, access mask, directory flag, and
expected allowance. Retain each ordinal failure case. Add direct mutants for a
repeated right, wrong target role, wrong boundary/source path, and directory/
file substitution.

## Finding 2: hostile token/Job and resource observations remain incomplete

The production token/Job parsers remain accepted as fail-closed code, but the
new fixture exercises only part of their attack surface.

For tokens, the OS fixture covers scalar false/size, elevation/UIAccess,
wrong user/package/low SID value, header-only nonzero capability/group count,
Job-membership failure, token duplication, impersonation, scratch, revert, and
leftover thread token. The older pure helper adds a few SID offset/truncation
and duplicate-group cases. Neither fixture drives:

- first-query failure, zero/over-bound requirement, second-query failure, or
  returned-length drift for each variable token class;
- null, before-buffer, after-buffer, unaligned, overlapping, bad-revision,
  excessive-subauthority, or incomplete SID pointers;
- group count over 128, row-array overflow, noncontiguous/overlapping/hole/
  trailing SID layouts, forbidden/conflicting attributes, or independently
  enabled stable, SYSTEM, and Administrators groups; or
- close/free ambiguity while token proof is unwinding.

Those omissions allow deletion of several bounds, pointer, attribute, and
forbidden-enabled-group checks while both compiled fixtures remain green.

For Jobs, the OS fixture covers limit/accounting/PID returned-size faults,
one count mismatch, accounting mismatch, security mismatch, preexisting/
create/already-exists/set-limit/verify failure, and happy termination. The pure
helper covers wrong child and duplicate PID. It does not drive zero PID,
over-`DWORD` PID, assigned count over 64, every assigned/list/returned-length
arm through `verify_admission_job`, or resource ambiguity. Most concretely,
`fixture_admission_TerminateJobObject` defines fault 24, but
`fixture_admission_job_matrix` loops create faults only through 23 and never
sets 24. Deleting termination-failure propagation survives.

### Smallest repair

Extend the existing hostile matrices to every listed token shape and Job
boundary. Exercise Job fault 24, Job close/reopen ambiguity, and exact final
name absence. Track every allocated/returned token, SID, security, Job, process,
thread, and pipe resource so each close/free failure—including simultaneous
failures—causes refusal without hiding remaining cleanup attempts.

## Finding 3: partial launch and restore cleanup are not executed

The launch matrix calls real `create_suspended_admission` for all 22 call-site
failures, but after failure it only directly frees `runtime.attributes` when
non-null. It never calls real `cleanup_admission_runtime`. The higher-level
lifecycle matrix substitutes `fixture_admission_create_suspended` and
`fixture_admission_cleanup_runtime`, so it cannot compose real partial launch
state with real cleanup either.

As a result, deleting cleanup of a pipe endpoint, sentinel, attribute list,
process/thread/token, suspended child, or Job after a particular launch prefix
does not fail the fixture. The current close seam also treats any non-null
handle as valid and does not detect an unknown, repeated, stale, or leaked
handle. Real `WaitForSingleObject` and pipe draining are not substituted in
this fixture mode, which is why real cleanup cannot yet safely run over its
synthetic handles.

The grant-order matrix injects failures in each of four grant calls, but it
does not inspect each failure prefix. More importantly, it never injects a
failure into real `restore_admission_grant`. A mutant that stops restoration
after the first failed object instead of independently attempting the remaining
authenticated objects passes. That violates the bounded Round-200 recovery
requirement.

### Smallest repair

- Track every synthetic runtime handle and attribute allocation exactly.
  Substitute wait, pipe-read/drain, terminate, attribute-delete, close, and
  free observations, then pass every one of the 22 partial launch states
  through real `cleanup_admission_runtime`. Assert all resources are attempted,
  the suspended process/Job reach terminal absence, no pipe data is accepted,
  and ambiguity is retained.
- For every grant and restore call failure, assert the exact call prefix or
  complete best-effort restore trace. In particular, restore must always
  attempt root then all three targets, suppress final success verification on
  any failure, and cleanly retry to four exact originals.

## Finding 4: lifecycle/recovery tests do not prove the durable destructive order

The lifecycle happy case asserts the exact seven phases. Its component-failure
cases, however, assert only a nonpositive result and—on a subset—one cleanup
and one restore call. They do not assert the predecessor-specific OPWL sequence.
A mutant can record the wrong cancellation/absence kind while preserving the
same result and component counts.

The outer recovery matrix checks that its first four recorded calls are root
then targets. It does not place Job termination, durable kind 6, all restore
calls, final object verification, fixed census, scratch absence, durable kind
7, and retained-handle release into one observable sequence. The set-security
seam records calls but does not change `fixture_admission_profiles`; the verify
object, census, and verify-original seams return success without checking the
modeled post-restore state. Deleting final-original verification can therefore
pass. A Job-after-DAC reorder can also pass because the fake recovery-Job seam
does not share the order log.

Finally, the kind-6 and kind-7 persistence failures are each tested only as one
failed call on newly initialized state. The matrix does not retain the exact
durable predecessor, reconstruct, retry, and prove final kind 6/7 plus OPWL
absence. It does not prove that OPWX/profile cleanup remains barred throughout
the failed prefix.

### Smallest repair

Use one exact event log for durable record publication, Job proof/termination,
root/target restoration, final object/census/scratch proof, kind 7, release,
and outer cleanup eligibility. Make security mutation update the modeled object
profile and make verification read that state. For every lifecycle component
and phase-publication failure, assert the exact allowed Round-198 branch.
For kind-6 and kind-7 ambiguity, retain the same modeled durable records and
objects across reconstruction, prove no downstream cleanup, then cleanly retry
to exact absence.

## Trust and project impact

The production trust boundary remains intact:

- stable N owns Dgrant, Dlaunch, token/Job/access expectations, durable OPWL,
  reversal, and result status;
- package read/execute grant and stable/SYSTEM custody remain exact;
- Job assignment, security capabilities, and closed handle inheritance remain
  one atomic `CreateProcessW` call with `CREATE_SUSPENDED`;
- production and tracked PE contain no `ResumeThread`, so candidate/RPC bytes
  do not execute in this slice;
- candidate output is required empty and supplies no verdict or authority;
- OPWL absence remains required before OPWX/profile cleanup; and
- LAUNCH remains private refusal-only NOT_IMPLEMENTED with no receipt,
  aggregate, provider result, installation, certification, or promotion path.

The broker and tracked PE remain outside the package-root exports and are only
in the exact stable bundle census. Fixture seams are compile-time test seams;
the unchanged tracked PE proves they are absent from production bytes.

No ISS-006 draft, sole ledger, roadmap, or board amendment is warranted. These
are executable-evidence gaps inside the already authorized private Windows
slice. Windows/Linux private progress may continue before macOS, but macOS
remains required for ISS-006 completion and hosted PASS.
