## Blocking findings

### 1. The new 3×8+2 candidate-denial relation has no deletion oracle

The production relation is guarded by
`OP_WINDOWS_MODULE_CUSTODY_PRODUCTION`. That macro remains disabled whenever
the lifecycle, admission, or admission-OS fixture macro is defined. Therefore
the existing exhaustive fake admission tests still compile the legacy
single-module-read fallback and never execute the new broker-object loops.

The new `windows-module-custody-fixture.c` is only 30 lines and calls
`retain_module_custody`, `verify_module_custody`, and
`release_module_custody`. It never calls `prove_child_token`, AccessCheck, or
the impersonated-open arm. The four real custody refusals and happy production
diagnostic likewise cannot distinguish deletion of any one denied row because
the unchanged exact protected ACL continues denying all remaining probes.

Deleting image `WRITE_DAC`, source append, parent `WRITE_OWNER`, one
`ACCESS_SYSTEM_SECURITY` actual-open, parent traverse, or any other individual
row leaves all current tests green. This is not cosmetic coverage: the direct
invocation replan depends on kernel-observed candidate exclusion from the
stable broker bundle.

Smallest repair: execute the real production broker-object loops inside an
exact-source admission fixture with prebound module image/source/parent objects.
Assert the exact ordered 3 objects × 8 rights plus parent list/traverse sequence
separately for AccessCheck and actual open. Inject failure at each ordinal and
require candidate proof refusal, complete cleanup, and no resume. Do not replace
the loops with a test-owned duplicate table.

### 2. Close-bound hard abort can still hang before RECOVER

`windows-isolation-authority.ts:732-740` bounds the wait for ChildProcess
`close`, then directly awaits:

```text
Promise.all([reader.requireEnd(), stderr.requireEnd()])
```

Unlike normal `settle`, neither drain is wrapped in `bounded`. A child stream
can close or be destroyed without emitting this model's observed `end` or
`error`; ChildProcess `close` may already have resolved while the corresponding
`BoundedReader`/`BoundedDiagnostic` remains `ended=false` and failure-free.
`hardAbort` then waits forever.

In TEARDOWN's CREATED/RECOVERY_REQUIRED arm this occurs before `runRecovery`, so
the durable native recovery chain is never attempted. The catch cannot help
because the awaited abort never settles. `runRecovery` has the same unbounded
abort path after a malformed/failed RECOVER response. This violates bounded
cleanup even though the process root itself is terminal.

The fake child always emits `end` or `error` before `close`; it has no
close-without-end/error, never-close, stderr-drain failure, simultaneous-drain,
kill-false race, or RECOVER composition case.

Smallest repair: apply the same fixed watchdog to both hard-abort drains, attempt
both, and aggregate their failures. TEARDOWN must still start independent native
RECOVER once root `close` is proved, even if a control drain times out; it then
returns refusal after recovery rather than hanging. Add exact fake-process cases
for each and simultaneous stdout/stderr missing-end/error, kill failure/race,
late close, and failed hard-abort plus successful/failed RECOVER.
