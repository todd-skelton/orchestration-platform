## Blocking finding and smallest bounded repair

### OP-R134-1 — receipt-local `Dp` repeats the pointer context already committed by `Dt`

The repaired authority says both that `Dt` commits the exact `Dp/Dv/Dr` and
that `Dp` remains explicit as pointer-instance context. Those statements do not
establish two independent observations. Under the incorporated common pointer
formula, `pointer-tip/v1` frames pointer-kind text, raw `Dp`, raw `Dv`, raw
`Dr`, and the canonical closed current-tip bytes. The state `Dv` and proposal
`Dr` also bind `Dp`. Consequently the receipt's `Dt` is already specific to
the exact pointer instance before any transitive argument through `Dv` or `Dr`
is needed.

Later ISS-004 is already required to:

- derive the authorization-state path from authenticated installation context
  and the receipt/state transaction;
- reconstruct the empty VALUE position and recompute actual `Dp`;
- parse the actual selected value, proposal receipt, and current tip;
- recompute actual `Dv`, `Dr`, and `Dt` under that `Dp`; and
- equal-bind receipt `selectedStateTipDigest` to that recomputed `Dt` before
  accepting any lifecycle, operation, time, core, gate, or native evidence.

Deleting the receipt-local `Dp` loses none of those checks. Moving a valid tip
to another pointer instance changes recomputed `Dp` and therefore changes
recomputed `Dt`; the unchanged receipt `Dt` then fails. Coordinately copying an
expected `Dp` into the receipt never establishes provenance because an
attacker can copy `Dp` and `Dt` together. The explicit digest is not a path
locator: it cannot be inverted to a path, while the receipt's own
`transactionId` already constructs the state and receipt transaction roots.
It is also not needed to construct the post-selection receipt's path, which
uses only its own transaction and operation IDs.

The smallest branch-local census is exactly five members in ascending
canonical JSON member order:

```text
operationId:uuid-v7
recordedAt:timestamp
schemaVersion:recovery-authorization-consume-receipt/v1|recovery-authorization-revoke-receipt/v1
selectedStateTipDigest:sha256
transactionId:uuid-v7
```

The authority and draft should reject
`selectedStatePathInstanceDigest`, `selectedStateValueDigest`, and
`selectedStateProposalReceiptDigest` as unknown extras. Later ISS-004 should
still recompute `Dp/Dv/Dr/Dt` from actual graph and context and bind receipt
`Dt` to actual `Dt`; it simply has no second receipt-local `Dp` equality.
ISS-032 remains the owner of selected-tip read-back, create-once persistence,
byte-identical retry/read-back, conflict refusal, and receipt time.

## What remains sound

### Branch closure, scalar types, and canonical bytes

The two schema literals remain a proportional branch discriminator. Consume
and revoke later impose different lifecycle and operation equalities; merging
them would require another branch member or unauthenticated caller selection.
The remaining five fields have closed scalar grammars and exact ascending
canonical order. Missing, extra, renamed, null, wrong-type, reordered,
cross-schema, unknown/future-schema, proxy, accessor, symbol, inherited,
non-enumerable, exotic-instance, and descriptor-trap inputs have a bounded
total refusal route under the global closed-record rules.

`operationId` and `transactionId` remain necessary receipt-own path inputs.
The receipt digest does not frame its filesystem path, so deleting either
would remove the self-contained equality that detects moved receipt bytes.
`recordedAt` is the distinct durable observation event, not selected-state or
proposal time. `schemaVersion` closes and branches the record and selects its
digest domain. `Dt` is the minimum direct identity of the exact selected-tip
read-back. None of those roles is replaced by deleting copied `Dp`.

### Receipt-own path, digest domains, and serialization

The canonical path remains complete and branch-neutral:

```text
installation/recovery-authorizations/<transactionId>/receipts/<operationId>.json
```

Both own UUIDv7 inputs must remain path-sensitive, while any otherwise valid
pair is structurally acceptable. ISS-004 later binds consume operation to the
selected state's prebound `consumeOperationId`, revoke operation to REVOKED
`removalOperationId`, transaction/path identity to the actual selected state,
and the two operations as distinct. Those are correctly excluded from the
structural parser.

The digest identities remain closed and acyclic:

```text
Drcp = SHA256(frame("recovery-authorization-consume-receipt/v1", canonical consume receipt bytes))
Drrp = SHA256(frame("recovery-authorization-revoke-receipt/v1", canonical revoke receipt bytes))
```

Each has one canonical-record part. The existing exact
`{ ok: true, bytes, digest }` result is sufficient. Raw JSON, untagged
canonical hashing, swapped domains, field-wise framing, common pointer `Dv`, a
helper identity, a common receipt domain, or a third domain must refuse. The
five-member repair changes canonical goldens but requires no new route or
envelope.

### Time, persistence, `FULL_REQUIRED`, and trust

`recordedAt` has one coherent future-production meaning: durable receipt
creation after ISS-032 reads back the exact selected tip. Structural parsing
proves only timestamp grammar. ISS-004 later requires actual selected state
`recordedAt <= post-selection recordedAt`; ISS-032 establishes exact read-back,
create-once write, byte-identical retry/read-back, conflicting-byte refusal,
and receipt-time production.

The receipts remain immutable `FULL_REQUIRED` evidence only when their actual
selected branch requires them. Missing, conflicting, noncanonical, truncated,
or unreadable required evidence becomes `UNKNOWN` in the later ISS-004/ISS-032
flow. Bare absence does not prove completion, and archive/tombstone treatment
remains independently gated. Parser, serializer, path, digest, timestamp,
worker, candidate, broker assertion, or this review cannot authenticate a
provider outcome, select state, manufacture an epoch, issue a capability, or
promote a candidate. Stable composition and independently reviewed production
remain the only future consumers.

### Acyclicity, including the later REVOKED edge

The intended order remains a strict chain:

```text
native consume Dnc -> selected CONSUMED Dp/Dv/Dr/Dt -> consume post Drcp
consume post Drcp -> selected REVOKED Dp/Dv/Dr/Dt -> revoke post Drrp
native removal Dnr ------------------------------^ 
```

No native receipt, core, gate, state value, selecting proposal, or selected tip
contains its downstream post-selection receipt. A later REVOKED value may
contain the already-fixed consume post receipt digest `Drcp`; its selected
`Dv/Dr/Dt` are then downstream of `Drcp`. The revoke post receipt `Drrp` is
created only after selection and never enters the REVOKED preimage. Deleting
the duplicate receipt-local `Dp` neither reverses nor weakens this order.
