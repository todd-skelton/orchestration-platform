## Finding 1: the 34th open oracle accepts any nonempty path

`expected_access = GENERIC_READ`; `expected_path` remains null. Its final check
intentionally skips path equality when the expected pointer is null.

Deleting the production `GetModuleFileNameW` relation and passing any nonempty
candidate, source, execution, state, or unrelated path at row 34 leaves the
34-row count, all right/directory/allow assertions, and every ordinal failure
green. This is not the exact ordered 34-row path oracle required by Round 202.

### Smallest repair

Capture the independently modeled broker-module path through a fixture-only
`GetModuleFileNameW` observation, then require row 34 to equal that exact path.
Add a same-right/nonempty wrong-path mutant. Do not weaken the production
negative module-read probe.

## Finding 2: several bound/error tests do not kill their own clause

The token query cases correctly produce refusal, but two important cases have
the same result after deleting the production check they are intended to
protect:

- Query fault 1 returns `ERROR_ACCESS_DENIED` and leaves the initialized
  required length at zero. Deleting the exact
  `ERROR_INSUFFICIENT_BUFFER` check still refuses through `required == 0`.
- Query fault 3 reports 65,537 bytes. If the
  `required > TOKEN_BUFFER_MAXIMUM` clause is deleted, the broker allocates
  65,537 bytes; the fake second query then refuses because capacity differs
  from its canonical small `needed` value. The outward test remains green, so
  deletion of the allocation bound is not observed.

The same masking pattern affects two count maxima:

- capability count 129 is supplied in a header-only buffer, so deleting
  `GroupCount > 128` still refuses through row-array extent; and
- Job assigned/list count 65 is paired with a returned length of eight, so
  deleting the `JOB_PROCESS_MAXIMUM` clause still refuses through the exact
  length relation.

These cases show compound refusal, not deletion evidence for the independent
resource/loop bounds.

### Smallest repair

- For wrong first-query error, return a plausible nonzero canonical length so
  deletion of the error-code check would otherwise reach and accept the second
  result.
- Add a fixture-only allocation oracle and prove zero allocation for zero and
  over-limit required sizes. Make the over-limit second result otherwise

- Call the real group/PID-list closed parsers with safe, sufficiently large

## Finding 3: launch evidence proves forwarding of a toy plan, not canonical Dlaunch

The direct launch matrix fabricates:

```text
application = X
command line = "X"
cwd = Y
environment = A=B
flags = CREATE_SUSPENDED | EXTENDED_STARTUPINFO_PRESENT |
        CREATE_UNICODE_ENVIRONMENT
```

It omits production's required `CREATE_NO_WINDOW`. The lifecycle/recovery
matrix replaces `OP_ADMISSION_PLAN_DIGEST` with
`fixture_admission_plan_digest`, which constructs only dummy security pointers
and digests. Thus no fake-OS case executes the real canonical Dlaunch builder
for the retained runtime/RPC/candidate paths, candidate file URL, scratch cwd,
fixed five-key environment, and exact four flags.

The CreateProcess seam also compares command-line bytes but does not require
the mutable command pointer to differ from `plan->command_line` or prove the
stable plan bytes unchanged afterward. Deleting the Heap allocation/copy and
passing the plan buffer directly survives.

Concrete surviving mutants include removing `CREATE_NO_WINDOW`, deleting or
substituting an environment member, changing the RPC/candidate argument
relation, or deleting the command-line copy while retaining equal bytes.

### Smallest repair

Drive the real plan builder from modeled retained profile/execution inputs and
assert an independent exact Dlaunch projection before calling the real launch
function. Require all four flags, exact application/argv/cwd/environment bytes,
and a distinct mutable command buffer; mutate that buffer in the CreateProcess
seam and prove the retained plan remains unchanged.

## Finding 4: cleanup and outer failure composition still have silent deletions

Real partial-runtime cleanup is now executed and close/free failures propagate,
but two cleanup operations have no observation:

- `fixture_admission_DeleteProcThreadAttributeList` is a no-op with no counter
  or active-list state. Deleting the production call still frees and nulls the
  allocation and passes every case.
- `fixture_admission_ReadFile` returns a canonical broken pipe but records no
  stdout/stderr drain calls. Deleting either drain, accepting nonempty data, or
  swapping a pipe can pass while all handle fields later become null.

More importantly, the outer lifecycle fixture still implements
`fixture_run_admission` as an unconditional success. It never returns `-1`.
The production branch uses `int clean = admission >= 0` to bar execution and
profile cleanup on unresolved OPWL recovery. Deleting either `if (clean)` guard
or changing the comparison to admit `-1` is therefore untested. Direct
`recover_admission` kind-6/kind-7 retry does not execute this outer composition
or prove OPWX/profile cleanup was skipped during the failed attempt.

### Smallest repair

- Track initialized/deleted attribute-list identity and require exactly one
  delete before freeing it.
- Track exact stdout and stderr pipe handles, drive broken, nonempty, wrong-
  handle, and read-failure results, and require both drains before closure.
- Add one outer lifecycle case where the admission seam returns `-1`. Prove
  zero execution/profile cleanup calls, recovery-required status, retained
  durable records, and release-only behavior. Retain the existing `0` clean-
  refusal and `1` NOT_IMPLEMENTED cases to kill comparison widening.
