### `OP-R59-001` — the embedded host capability census has no exact public contract

The governing ledger now says:

- the host artifact contains a closed static host contract and capability
  census;
- release installation validates that census;
- ISS-012 recomputes each identity from the installed artifact, validates the
  census, and admits the requested action capability;
- step 7 validates the same census again before rendering and ownership.

But the ledger, routine cycle, module ABI, ISS-002, and the named producer/
consumer drafts define none of the following:

- a schema/version literal, exact member census, canonical member order, or
  closed nested record/array shape for the embedded host contract/census;
- the exact static location/export/projection inside the package artifact from
  which the common parser obtains those bytes;
- whether a capability row is a name, action/capability pair, role-qualified
  entry, or another projection, and its grammar, bounds, uniqueness, and exact
  membership comparison;
- the total relation that turns every row of the complete installed active-
  release mapping plus exact installed artifact bytes into the step-5 census
  and the identical step-7 read-back.

A scoped search outside pressure history finds the phrase only in the repaired
decision/routine prose and ISS-008/012/014/020/021/026/045. There is no existing
contract schema, parser, test, manifest member, or host-static-registry contract
that supplies the missing definition. The current contracts code and tests
likewise contain no dispatch-brief, worker-host identity, renderer mapping, or
host capability-census implementation, which is expected at this pre-
implementation gate but means no executable authority silently fills the gap.

Consequently two host implementations can put different closed records in
their exact package artifacts, two release implementations can validate
different projections, and two routing implementations can use different
capability membership rules while all satisfy the new identity formula. Hashing
the entire artifact distinguishes those byte sets but does not define their
semantics. A route can therefore be SHA-256-correct and mapping-selected without
an executable proof that the selected artifact supports the exact action
capability under one public contract.

Bounded repair: define exactly one provider-neutral embedded static host-
contract/capability-census record in the decision ledger and ISS-002 packet.
Fix its schema literal, exact member and nested-array censuses, canonical order,
capability projection and grammar, bounds, uniqueness, exact membership rule,
and deterministic static extraction from the already hashed package artifact.
Define one total admission relation over the reviewed active-release mapping,
installed artifact bytes, recomputed host identity, and parsed census, and
require ISS-012 and step 7 to use that identical relation. Assign ISS-021 and
ISS-045 to emit it, ISS-020/ISS-014 to install/read it back, ISS-012 to consume
the complete mapped set, and ISS-008/ISS-026 to revalidate the selected row.
Add missing/extra/future/wrong-family fields, dense-array bounds, duplicate and
case-substituted capabilities, moved static record, catalog/capability mismatch,
cross-host, manifest/read-back, and coordinated artifact/census mutants. Reuse
`hostRendererArtifactDigest`; add no subordinate digest, provider field,
dynamic resolver, filesystem scan, network lookup, or second registry.

## Direct contract attack results

- **Two-member identity:** `worker-host-identity/v1` is exactly
  `hostRendererArtifactDigest` then `schemaVersion` in canonical member order.
  The literal and domain are both `worker-host-identity/v1`; the two framed
  parts are text schema version then raw-32 artifact digest. The digest itself,
  direct provider/model/selector/path/executable/credential/runtime/route/
  dispatch/launch/output fields, and mutable evidence are excluded. Any exact
  artifact change changes the artifact digest and identity. ISS-002 and both
  host issues require byte/domain/order/substitution goldens. This closes
  `OP-R57-001` for identity shape and derivation.
- **Artifact binding versus census semantics:** the exact package artifact
  contains renderer and template bytes and is SHA-256-bound. The new prose also
  says it contains the static contract/census, so changes are identity-changing.
  The blocker is not binding strength; it is the absence of one defined
  embedded record and shared parser/membership relation.
- **Release mapping:** `release-manifest/v1` retains a dense closed 1–16 array
  of exact three-member renderer rows, unique by opaque host identity. Every row
  recomputes identity from installed artifact bytes, is read back, and is bound
  to the selected active release. ISS-020 owns N0 and ISS-014 successors; a
  candidate, host, or worker cannot add, choose, or attest a row. This mapping
  authority is sound once the separately validated embedded census is exact.
- **Step 5 and route ownership:** routine step 5 now takes action capability,
  evidence, and the complete installed active-release host census and emits one
  admitted opaque identity. ISS-012 alone owns that field and first-/two-host,
  missing/duplicate/unknown/stale/moved/capability/cross-host/coordinated/
  route-manifest mutants. This closes `OP-R57-002` structurally, but its
  capability test cannot be implemented consistently until `OP-R59-001` is
  repaired.
- **Step 7 cross-bindings:** ISS-008 and ISS-026 select exactly one route-keyed
  manifest row, prove executing artifact equality, recompute identity, validate
  the embedded census separately, prove requested/module/brief role equality,
  and bind unchanged host identity, artifact, action core, subject, descriptor,
  and rendered bytes before ownership. Candidate, self-reported, coordinated,
  cross-host, manifest/read-back, and moved substitutions refuse. No second plan
  or template-registry digest was introduced.
- **First-/two-host portability:** ISS-021 and ISS-045 each own a distinct exact
  package artifact, identity, templates, three-OS rendering/identity goldens,
  credential isolation, and host-specific conformance. ISS-012 owns generic
  first- and two-host routing goldens. Provider names remain confined to
  concrete integration drafts and the documented first-host section, not
  engine contract fields or opaque route identity.
- **Action core and catalog:** `dispatch-action-core/v1` remains one exact six-
  member projection and one six-part framed digest, with role included and
  brief/render/dispatch/launch/host-artifact fields excluded. Step 4 equal-
  binds action, capability, subject, descriptor, role, and core digest. The
  release-reviewed catalog remains dense 1–256, exact six-member rows, unique by
  `(actionKind,capabilityName,directiveKind,code)`, with one accessor/template
  result and exact duplicate-free worker-required pair projection. ISS-011 owns
  executable producer mutants.
- **Cardinality, no prose, and rendering:** the envelope plus exactly three
  nested dispatch-brief schemas remain closed. All eight non-operator directive
  kinds require one or more present rows; operator action remains the exhaustive
  one-or-more-present versus exactly-one-absent XOR. Present rendering uses a
  nonempty selected scalar and fixed reviewed 1–8192-byte template; raw catalog
  keys and resource values do not render. Directive/resource arrays and
  uniqueness rules remain bounded and exact.
- **Removal and vocabulary:** scoped search found no restored `resourceKind`,
  `referenceSchemaVersion`, `referenceDigest`, old `actionPlanDigest`, or
  `templateRegistryDigest`. No dynamic renderer, arbitrary schema reference,
  resource path/class, superseded authority generation, sparse membership
  proof, node inventory, materialization coordinator, retention/compaction
  pointer kind, or diagnostic namespace was restored. Existing vocabulary
  lint remains green.
- **Self-certification:** a host build supplies bytes and a deterministic
  identity input only. Reviewed release-manifest ownership, installed-byte
  recomputation/read-back, active-release selection, route admission, external
  review, and stable promotion remain separate. The repair does not let a
  candidate, host, worker, or receipt certify itself.
