## Clean implementation findings

### Platform and option authority remain stable-owned

`nativeHostPlatform` is captured at module initialization. `runCore` returns
the exact Darwin-unavailable or unknown-platform refusal before touching either
caller object or factory. There is no production platform/factory/runner/clock/
parser argument.

Supported input and configuration records reject proxies, exotic prototypes,
symbols, accessors, extra fields, and relative paths, then copy only string
values into frozen records before an asynchronous factory call. The Linux
composer reconstructs fresh nested options with one shared
`accountStateRoot`; no `commandRunner`, `profileReader`, `principalToken`, or
`token` member is forwarded. Windows receives only its existing three exact
path fields.

### Cleanup and result ownership are narrow

Linux factory failure returns a fixed refusal. After successful construction,
the code attempts `close()` exactly once after coordinator success, refusal, or
throw. Close ambiguity overrides success; simultaneous coordinator/close
refusal is retained in deterministic fixed order. Windows invents no global
close and delegates all per-principal cleanup to the existing coordinator and
native authority.

The returned union remains the existing private
`Iss002IsolatedWalkRunResult`. The defensive copy rejects extra fields,
malformed issue arrays, wrong duration count/canonical decimal, and an
incorrect maximum. No receipt, aggregate, provider, workflow, PASS string,
principal, custody handle, or promotion value is added. The module is absent
from the package root and appears only in the exact private harness census.

### macOS remains an honest completion gap

Darwin gets only `native-isolated-walk:macos-authority-unavailable` before
caller inspection. The code does not adapt helper custody into a false
four-method authority and does not invoke same-principal `walk.ts`. This is the
required behavior for the authorized Windows/Linux-first private increment.
It neither blocks this slice on macOS nor changes the fact that ISS-006 cannot
complete or produce a hosted PASS without real macOS authority/evidence.

## Blocking findings

### 1. The exported production dependency binding is deletion-invisible

Production lines 298–307 are the authority-bearing bridge:

```text
runNativeIss002IsolatedWalk(...)
  -> platform: nativeHostPlatform
  -> linuxFactory: createLinuxIsolationAuthority
  -> run: runIss002IsolatedWalk
  -> windowsFactory: createWindowsIsolationAuthority
```

Every focused behavioral test instead bundles the module with a footer that
exports private `runCore` and calls only `runCore` with caller-supplied fake
dependencies. `runNativeIss002IsolatedWalk` is mentioned only to assert that it
is absent from the package root. Consequently these production mutations all
survive the 13 focused tests:

- return a constant `ok:true` result from the exported wrapper;
- bind a caller/fixed wrong platform;
- swap, omit, or duplicate the Linux/Windows factory;
- replace `runIss002IsolatedWalk` with a shortcut that never creates or tears
  down three principals; or
- return before coordinator teardown or Linux close.

The Windows unit explicitly expects its fake authority's
`teardownPrincipal` not to have been called because its fake `run` returns a
constant success object. That is valid for testing `runCore`'s boundary, but it
does not establish the required production coordinator composition.

Smallest repair: execute the exact exported wrapper in transformed Linux and
Win32 modules while substituting only the fixed imported dependencies at the
module boundary. Assert the selected production factory, exact reconstructed
options/input, one real coordinator call, three ordered
create/prepare/launch/teardown cycles, result only after the third teardown,
and Linux close after that result. The transformed Darwin/unknown arms must
still prove zero imported dependency calls. Also make the fixed dependency
object itself deletion-visible so replacing the exported wrapper with a
constant or different function fails.

This can remain a compiled/test-only transform. It must not add production
factory/platform/run seams or call a real privileged authority in the default
cross-platform suite. Existing opt-in lower-layer Linux and Windows diagnostics
remain complementary; a future supported-host diagnostic may call the exact
exported composer, but no hosted PASS is required or authorized here.

### 2. The new test-bundle row has no exact deletion oracle

`iss002TestBundlePaths` correctly adds
`test/conformance/native-isolated-walk.test.ts`, and manifest construction will
copy whatever rows the list currently contains. But
`stable-bundles.test.ts` asserts only:

- the exact `packages/conformance/src` partition;
- the exact `test/contracts` census; and
- equality between a manifest and the same source path list.

It never independently expects the new `test/conformance` row. Deleting that
one row from `iss002-bundle-paths.mts` therefore still lets manifest creation,
source partitioning, contract-test census, and the composer tests pass. This is
the exact missing-bundle-row mutant Round 229 required to die.

Smallest repair: add an independent exact assertion that the owned
`test/conformance` subset is precisely
`["test/conformance/native-isolated-walk.test.ts"]` for this slice (or include
that row in another independent fixed expected census). Test adding, deleting,
renaming, or duplicating it. Do not broaden the test bundle to unrelated
conformance tests.
