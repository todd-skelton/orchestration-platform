## Acceptance evidence

The added row:

```ts
{
  relation: "triggering BUILD conclusion is the SUCCESS literal",
  input: () => sealedReceipt({ triggering: { conclusion: "FAILURE" } }),
  issues: ["apiObservations.8.triggeringBuild.conclusion:mismatch"],
},
```

The exact issue array was computed outside the repository: `repository-protection-parse.ts`
and `repository-protection.ts` were bundled with the repository's own `esbuild`
(0.28.2) into a scratch `.cjs` file, and a Node script reconstructed the same
receipt shape the test file's `fixture()`/`sealedReceipt()` helpers build,
then set `apiObservations[8].triggeringBuild.conclusion = "FAILURE"`. Both
`parseRepositoryProtectionStructure` (structural layer) and
`parseRepositoryProtectionReceipt` (the function the test table calls) returned
`{ ok: false, issues: ["apiObservations.8.triggeringBuild.conclusion:mismatch"] }`
— a single path-prefixed code. This differs in shape from the sibling
triggering-BUILD relation rows (which read
`apiObservations.WORKFLOW_RUN.triggeringBuild.<field>:mismatch`): those three
sibling checks are cross-record equality relations evaluated by
`relateRepositoryProtectionStructure` after structural parsing succeeds (hence
the readable `WORKFLOW_RUN` name chosen by that function), whereas the
`conclusion` literal is enforced inside `parseTriggeringBuild` itself, at
structural-parse time, before any relation check runs; the array-index
prefix (`8`, not `WORKFLOW_RUN`) is `parseTypedArray`'s numeric child prefix,
composed through `parseHistoricalApiObservation`'s
`child(parseTriggeringBuild(...), "triggeringBuild", closure)` call and the
outer `child(parseHistoricalApiObservations(...), "apiObservations", issues)`
call in `parseRepositoryProtectionStructure`. `parseRepositoryProtectionReceipt`
returns the structural result unchanged because it short-circuits on
structural failure before calling `relateRepositoryProtectionStructure`.

The mutant reaches the literal gate: a baseline receipt (same construction,
`conclusion` left at `"SUCCESS"`) parses with `ok: true` at the structural
layer; changing only `conclusion` to `"FAILURE"` is the sole difference
between that accepted receipt and the refused mutant.

A scratch-copy deletion of the gate makes the mutant survive: the same
`repository-protection-parse.ts` source was copied (with its sibling module
files, to keep relative imports resolvable) into the scratchpad, the line
`const conclusion = literal(record.conclusion, "SUCCESS", "conclusion:mismatch", issues);`
was replaced with `const conclusion = record.conclusion as string;` (removing
the literal gate while leaving every other field's validation untouched), and
the patched copy was bundled and required separately. Against the identical
mutant input, the real (gated) bundle returned `ok: false` with the issue
above; the de-gated bundle returned `ok: true`. This was executed with Node,
not reasoned only.
