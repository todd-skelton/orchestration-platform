## Existing outer transport retained

Every message retains the existing 16-byte `OPWB` outer frame:

| Offset | Bytes | Rule |
| ---: | ---: | --- |
| 0 | 4 | ASCII `OPWB` |
| 4 | 1 | protocol version `1` |
| 5 | 1 | request `1` or response `2` |
| 6 | 1 | PREPARE `1`, LAUNCH `2`, or TEARDOWN `3` |
| 7 | 1 | request `0`; response status below |
| 8 | 4 | little-endian payload byte length, at most 1 MiB |
| 12 | 4 | zero |

The only response statuses are `0` `OK`, `65` `REFUSED`, `70`
`RECOVERY_REQUIRED`, and `78` `NOT_IMPLEMENTED`. Unknown status, kind, version,
opcode, reserved byte, oversize, truncated header/body, trailing frame bytes,
or payload-shape disagreement is protocol refusal: no response and terminal
exit 65. Semantic refusal after one canonical frame returns the same opcode,
status 65 or 70, and zero payload. No OS error text, SID, folder content,
candidate field, PASS, or duration appears in a refusal.

`SERVE` is a sequential one-profile process, not the current one-frame process.
It accepts at most PREPARE, any number of LAUNCH probes, and one TEARDOWN. The
only admitted state transitions are:

```text
EMPTY --PREPARE/OK--> PREPARED
PREPARED --LAUNCH/NOT_IMPLEMENTED--> PREPARED
PREPARED --TEARDOWN/OK--> TERMINAL
```

PREPARE twice, LAUNCH/TEARDOWN before PREPARE, any request after TEARDOWN, or a
second profile refuses. LAUNCH has exactly zero payload, performs no OS mutation
or candidate execution, returns status 78 with zero payload, and leaves the
profile prepared so TEARDOWN remains mandatory. EOF/control loss while PREPARED
executes the same cleanup as TEARDOWN before terminal refusal; cleanup ambiguity
exits 70.

| Offset | Bytes | Rule |

| 0 | 4 | ASCII `OPWP` |
| 4 | 1 | payload version `1` |
| 5 | 1 | profile-scope arm `1` |
| 6 | 2 | zero |
| 8 | 2 | little-endian state-root UTF-16 code-unit count, `1..1024` |
| 10 | 2 | zero |
| 12 | `2*n` | exact UTF-16LE state-root path, no NUL, surrogate, or trailing bytes |

The path is already-normalized absolute extended DOS form
`\\?\C:\...`, uses backslashes, names a non-volume-root directory, and contains
no empty, dot, dot-dot, UNC, volume-GUID, device, alternate-stream, wildcard, or
trailing separator arm. PREPARE is the only SERVE operation carrying this
payload. SERVE TEARDOWN and LAUNCH payloads are empty. `RECOVER` accepts exactly
one TEARDOWN frame carrying this profile-scope payload; every other RECOVER
frame refuses without mutation.

A successful PREPARE response payload is:

OPWR | version:1 | arm:1 | reserved:u16=0 |
token:32 | moniker:64 ASCII |

The outer length must equal the exact concatenation. SID length is `8..68`, SID

## State-root authentication responsibility

The native broker owns the mutation-side authentication; a later TypeScript
caller must independently repeat it but cannot replace it. Before parsing an
existing journal or generating a token, the broker:

1. captures the actual process token's stable user SID and integrity SID and
   proves it is X64 Windows, not AppContainer, not restricted, and not
   impersonating;
2. opens the requested state root with no delete/write sharing and
   `FILE_FLAG_BACKUP_SEMANTICS|FILE_FLAG_OPEN_REPARSE_POINT`, retains the handle,
   and requires the final handle path byte-equal to the request;
3. requires one directory link, no reparse point, local fixed volume, exact
   volume serial/file ID/type/attributes, and unchanged retained/path identity;
4. requires owner equal the stable SID, one protected DACL containing only
   stable SID and `SYSTEM` full-control allows, no deny/inherited/broad/package/
   capability ACE, and one mandatory-label SACL equal the actual stable token's
   integrity label with no audit or extra ACE; and
5. retains the complete self-relative security descriptor and rechecks all
   facts before and after each record or profile operation.

Round 175's later TypeScript custody remains responsible for pairwise root
equality/nesting, checkout/provider exclusion, broker/source/runtime custody,
and caller-side handle retention. This native slice receives no such path and
therefore claims none of those later relations.

Define:

```text
Dstate = SHA256(
  "op.windows-profile-state-root/v1\0" ||
  u32le(pathBytes) || canonicalPathUtf16LE ||
  u64le(volumeSerial) || fileId128 ||
  u32le(attributes) || u32le(linkCount) ||
  u32le(securityBytes) || selfRelativeSecurityDescriptor
)
```

This is a private native journal domain, not a portable conformance contract.

## Token, moniker, journal bytes, and paths

The broker obtains exactly 32 bytes from system-preferred `BCryptGenRandom`.
The token is never accepted from a request. Its lowercase 64-hex form is
`Htoken`. The moniker is exactly `orch6-` plus the lowercase hex encoding of
the first 29 token bytes: 64 ASCII characters. Before use, both token and
moniker must be absent from every canonical journal group and the complete
AppContainer census. A collision burns the token and retries with a new one; it
never adopts or deletes the colliding profile.

All durable files are flat children of the retained state root:

```text
windows-profile-<Htoken>-00-used.opwj
windows-profile-<Htoken>-01-profile-attempted.opwj
windows-profile-<Htoken>-02-profile-created.opwj
windows-profile-<Htoken>-03-profile-delete-attempted.opwj
windows-profile-<Htoken>-04-profile-absence-proved.opwj
```

Final files are append-only and remain for the hosted job. The `00-used`
tombstone is never removed, including when no profile mutation followed. This
deletes state-record unlink/reuse machinery from the slice.

Each final file is one canonical closed record:

```text
magic:"OPWJ" | version:u8=1 | kind:u8 | reserved:u16=0 |
totalLength:u32le |
token:32 | priorDigest:32 | Dstate:32 | moniker:64 ASCII |
sidLength:u16le | binarySid |
sidTextLength:u16le | canonicalSidASCII |
folderPathUnits:u16le | canonicalFolderPathUtf16LE |
[folderBindingDigest:32 only for kinds 3..5]
```

Kinds are USED `1`, PROFILE_ATTEMPTED `2`, PROFILE_CREATED `3`,
PROFILE_DELETE_ATTEMPTED `4`, and PROFILE_ABSENCE_PROVED `5`. Every length is
inclusive and exact; there is no padding, NUL, optional field, duplicate arm,
or trailing byte. The SID and folder facts are independently derived before
USED is persisted, so kinds 1 and 2 contain them. `priorDigest` is all zero only
for USED; otherwise it is SHA-256 of the exact previous canonical record.
DELETE may point to CREATED or directly to ATTEMPTED after ambiguous creation;
all other predecessor kinds are exact and linear. Kinds 3..5 repeat the exact
created folder binding. A DELETE reached directly from ATTEMPTED uses 32 zero
bytes there and can never later claim a created folder identity.

`folderBindingDigest` uses the same closed path/volume/file-ID/attributes/link/
security framing as `Dstate` under domain
`op.windows-profile-folder/v1`. It is authority only for identifying and
closing the OS-created folder during cleanup, never for its hostile contents.

## Durable write and ambiguous-prefix semantics

Every phase first uses the matching final filename plus suffix `.pending`.
The broker create-exclusively opens it with `FILE_FLAG_WRITE_THROUGH` and an
exact stable/SYSTEM-only descriptor, writes all canonical bytes, calls
`FlushFileBuffers`, closes it, flushes the retained state-directory handle,
reopens it no-follow, and compares bytes, security, and file identity. It then
renames by retained handle without replacement to the final name, flushes the
state directory, reopens the final path, proves pending absence, and compares
the exact bytes/profile again. Only then is the phase durable.

The USED final file must be durable before ATTEMPTED; ATTEMPTED must be durable
before `CreateAppContainerProfile`; DELETE_ATTEMPTED must be durable before
`DeleteAppContainerProfile`. A failed/ambiguous pending write or rename never
authorizes the next OS mutation.

A crash can leave an exact `.pending` file after a profile mutation while the
prior final phase remains authoritative. Recovery groups pending names only
under an already-canonical USED token, never trusts pending contents, and uses
the last complete final phase to perform conservative deletion. After exact
profile/folder absence, it deletes each retained pending file, flushes the
directory, proves its path absent, and then durably appends ABSENCE_PROVED.
An orphan, substituted, hard-linked, reparse, wrongly secured, or unexpected
pending file blocks new authority but cannot cause deletion outside the fixed
token filenames. If its identity cannot be removed safely, recovery remains
refused with the durable cleanup record intact.

Factory/recovery scans the complete state-root census, parses every group before
any OS mutation, rejects duplicate/forked/missing/out-of-order phases, unknown
files or suffixes, malformed bytes, mismatched filename/token/moniker/SID/path/
state binding, and sorts groups by raw token bytes. A USED-only group needs no
profile mutation and remains burned. ABSENCE_PROVED is terminal. Every other
canonical prefix enters deletion recovery.

## Exact AppContainer ordering

PREPARE performs this order and no other mutation:

1. authenticate/retain the state root and preflight every journal group;
2. generate and burn a fresh token/moniker, derive the binary SID independently,
   convert it to canonical SID text, and derive the canonical folder path;
3. run one complete bounded
   `NetworkIsolationEnumAppContainers(NETISO_FLAG_FORCE_COMPUTE_BINARIES)`;
   admit at most 4,096 well-formed rows, unique by moniker and SID, and require
   neither the exact moniker nor SID in any row;
4. open-probe the exact folder path and require exact not-found, not access
   denial or unknown error;
5. durably persist USED and PROFILE_ATTEMPTED;
6. call `CreateAppContainerProfile(moniker, moniker, moniker, NULL, 0, &sid)`;
   `ERROR_ALREADY_EXISTS`, any non-success, or lost response is never adopted;
7. require the returned SID byte-equal to the independently derived SID and
   different from stable user, `SYSTEM`, and every authority SID; free every
   returned allocation exactly once;
8. repeat the complete enumeration and require exactly one row pairing this
   moniker and SID, zero capability entries, no duplicate name/SID, and no
   disagreement;
9. rederive the folder path, open it no-follow, require one directory link and
   its exact OS-created package/stable/SYSTEM owner/DACL/SACL/label profile,
   capture its folder binding, and retain the handle; and
10. durably append PROFILE_CREATED, return the one PREPARE OK response, and
    enter PREPARED.

Any result after ATTEMPTED is ambiguous until independent absence. The broker
must not report PREPARE refusal and exit while a profile may remain. It closes
returned/folder handles, durably appends DELETE_ATTEMPTED referencing CREATED
when available or ATTEMPTED otherwise, calls delete, proves absence, appends
ABSENCE_PROVED, and only then returns REFUSED. Cleanup ambiguity returns
RECOVERY_REQUIRED.

TEARDOWN, control loss, and RECOVER close all profile/folder handles first,
append DELETE_ATTEMPTED if absent, and call `DeleteAppContainerProfile` exactly
once per cleanup attempt. Its return code is never absence. Whether it reports
success, not-found, or error, success requires a new complete enumeration with
no row matching either moniker or SID, exact-not-found for the canonical folder,
no live profile handle, unchanged state-root custody, pending-file cleanup, and
durable ABSENCE_PROVED. Delete error plus those independent absence facts may
succeed; delete success with either residue refuses. No unrelated AppContainer
row or folder is deleted.

An unjournaled `orch6-` enumeration row or folder is residue and blocks all new
authority; this slice cannot guess ownership or delete it. Existing unrelated
non-`orch6-` profiles are validated as well-formed census rows but otherwise
left untouched.

## In-memory and recovery authority

The broker retains exactly one token, SID, moniker, folder path/handle, state-
root handle, and last durable phase. None is supplied to a candidate. It cannot
prepare twice, adopt an existing profile, recover an active in-memory profile,
or return OK until the corresponding durable phase and readback are complete.
Every close is checked; close ambiguity changes the result to
RECOVERY_REQUIRED even if subsequent absence appears clean.

RECOVER has no create arm. It preflights the complete state root before deleting
anything, processes groups in token order, stops on the first failure, and
returns TEARDOWN/OK only when every nonterminal group is durably
ABSENCE_PROVED. It never accepts a caller SID, moniker, folder, phase, PID,
command, or arbitrary deletion path.
