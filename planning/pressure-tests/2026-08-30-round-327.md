## Findings

1. **P1 — malformed OS scalars escape the closed failure boundary.**
   `packages/config/src/loader.ts:628` calls
   `String(invocation.operatingSystem)` before checking its scalar type.
   `validateInvocation` runs at `:687`, outside the `try` beginning at `:707`.
   An otherwise exact invocation whose OS is
   `{toString(){throw Error("OS_CANARY")}}` therefore rejects with that canary,
   rather than resolving to the fixed `ARGV_REFUSED` row. An OS value of
   `Object.create(null)` likewise rejects with a conversion exception. Both
   reproduced with zero adapter calls. Construction repeats the coercion at
   `:206`: the analogous malformed adapter throws `FACTORY_CANARY` directly.
   This contradicts the draft's wrong-scalar/throw classification at `:66-73`
   and never-reject promise at `:113-115`. Use non-coercing closed enum checks
   and keep malformed-input handling within its promised boundary; add these
   discriminating mutants, not just the existing extra-key mutant
   (`test/config/loader.test.ts:107-133`).

2. **P1 — the reverse census accepts changed source bytes.**
   `loader.ts:788-795` hashes the retained configuration handle before starting
   the census. The fresh handle at `:544` is only statted; `:545-557` compares
   identity, kind, mode and path, never its source bytes. A focused Windows
   mutant rewrote the same regular file, without replacing its inode, during
   the config path's second adapter observation (the final census). It returned
   accurate BigInt device/inode facts using the same observational shape as the
   committed tests. Result: `ok:true`, returned `adapterId:"fixture.adapter"`,
   actual file `adapterId:"altered.adapter"`, two config observations. Thus
   success is emitted despite a persistent write during the operation, contrary
   to draft `:109-111`. Bind a fresh-handle source digest to the final census
   and test this same-inode write; the current replace/restore mutants only
   change identity (`loader.test.ts:223-250,396-425`). This finding does not ask
   for an impossible atomic guarantee after the operation has returned.

3. **P2 — shadowed environment paths override CLI precedence by refusing.**
   `loader.ts:697-702` admits all three environment paths before selecting
   their precedence arms at `:708-724,748-750`. An exact invocation with
   absolute CLI project/config/state paths and only
   `ORCHESTRATION_STATE_ROOT:"relative-shadowed-value"` returns `PATH_REFUSED`
   before any adapter call. The draft explicitly limits this path check to
   the selected environment value (`:71-73`) and places CLI above environment
   (`:84-90`). Validate all environment scalar shapes, but physically/path-
   validate only the selected arm. The existing precedence row uses absolute
   lower-priority values and cannot discriminate this defect
   (`loader.test.ts:301-334`).
