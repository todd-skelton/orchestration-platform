## Blocking findings and smallest bounded repair

### OP-R130-1 — serializer success contract contradicts its exclusion

The ledger says generic `serializeContract` for either native receipt returns
its domain-tagged digest and canonical bytes. The current public serializer can
do exactly that only through its established success arm:

```text
{ ok: true, bytes: Uint8Array, digest: string }
```

The same authority sentence then says “there is no ... generic success
envelope.” Read literally, implementation must both return and not return the
existing generic success envelope. The predicted footprint admits
schema-specific serializer routes, not a redesign or removal of the public
`SerializationResult` union. A worker cannot choose which half of this public
contract is authoritative.

The smallest repair is to replace the exclusion with an exact statement that
both schemas use the existing `SerializationResult` success arm, whose `digest`
is respectively `Dnc` or `Dnr`, and that there is no additional receipt-specific
envelope, helper identity, untagged digest, or third native-receipt domain.
Acceptance must pin the exact public result shape for both schemas and prove a
schema-specific route cannot fall through to the generic untagged canonical
digest. No serializer framework or result-type change is needed.

### OP-R130-2 — duplicated core fields have no independent source or deletion test

Both records carry `authorizationCoreDigest` and later composition must parse
the actual immutable core and recompute that digest. They then repeat these
seven core fields:

```text
capabilityDigest
capabilityReferenceDigest
hostIdentityDigest
installationId
projectId
stateRootDigest
userIdentityDigest
```

The ledger calls them “core/custody identities needed for later equality,” but
does not say which are independently observed in authenticated native-provider
read-back, which are asserted by the broker request, or which are merely copied
from the core. If they are copied context, deleting any one loses no binding:
the recomputed `Dac` already commits to the actual parsed field. If they are
independent read-back, the ledger has not named the authenticated producer or
adapter output that makes a mismatch meaningful. A caller can otherwise copy
the same values into a structurally valid receipt, so the extra comparisons do
not prevent self-certification.

`transactionId`, `operationId`, generation, time, schema, disposition, and the
nullable prior-consume digest have direct path, ordering, branch, or outcome
roles. The seven fields above do not yet have a comparable deletion
discriminator. Freezing them into a public 13/16 schema before provenance is
decided violates the work-model proportionality rule and increases the later
composition matrix without an evidenced threat.

The smallest repair is a field-by-field provenance/deletion table in the sole
authority and mirrored draft. Remove every field that is only copied core
context because authenticated `Dac` plus the parsed core is the smaller source.
Retain a duplicate only if the ledger names its independent authenticated
read-back source, the exact substitution threat its equality catches, and the
later owning composition dependency. If deciding that source would define the
deferred provider/IPC contract, park the field until that ledger rather than
guessing it now. The repaired exact census, whatever remains after deletion,
must return to independent review.

This finding does not request signatures, a nested proof bag, provider names,
secret material, or adapter vocabulary.

### OP-R130-3 — structural tests cannot refuse deferred operation/path relations

The structural parser can prove that a receipt-local `transactionId` and
`operationId` are canonical UUIDv7 values. The generic native path constructor
can deterministically place any such pair at
`installation/recovery-authorizations/<transactionId>/native/<operationId>.json`.
Swapping two valid consume/removal operation IDs therefore creates two other
valid structural records and paths. Only later composition can prove that the
consume ID equals selected prior state `consumeOperationId`, the removal ID
equals later REVOKED `removalOperationId`, and the two IDs are distinct.

The ledger correctly assigns those equalities and duplicate-operation refusal
to later composition, but its structural compatibility paragraph and draft
criterion 8 also require the native-receipt tests to cross paths and operation
IDs and kill the path relation. Without an exact distinction, an implementer
must either accept crossed valid IDs, failing the apparent refusal obligation,
or add state/receipt composition that the scope fence forbids.

The same boundary problem affects the operational prose. `FULL_REQUIRED`,
create-once immutability, byte-identical retry, conflict on changed bytes, and
missing/truncated/unreadable-as-`UNKNOWN` are sound fail-closed requirements,
but the admitted slice has no persistent lookup, provider call, filesystem
mutation, or retry coordinator. Likewise, `ABSENT|DISABLED` is only a closed
structural literal here; parser success cannot authenticate a provider outcome
or prevent restoration. `recordedAt` is a closed timestamp, but whether it is
provider-operation, read-back, or receipt-creation time is not fixed, so the
later inclusive state/receipt ordering is not yet an executable semantic
comparison.

The smallest repair is to split evidence explicitly:

- structural tests pin each receipt's own canonical path, show transaction and
  operation sensitivity, and accept any otherwise valid UUIDv7 pair; they make
  no cross-operation refusal claim;
- the later closed composition matrix owns consume/removal state equality,
  cross-operation distinctness, schema-at-path collision, time ordering, and
  authenticated adapter disposition;
- the named provider/persistence owner or parked unpark condition owns
  create-once write, idempotent read-back, `FULL_REQUIRED` loss, and `UNKNOWN`
  behavior; and
- the authority says explicitly that structurally parseable bytes, including a
  caller-asserted disposition, are not yet an authenticated native receipt.

This preserves every fail-closed property without granting the deferred
surfaces implementation authority in the structural slice.

## Literal census, types, and nullable arms

The proposed lists are unique and in exact ascending canonical JSON member
order:

| Schema | Count | Structural result |
| --- | ---: | --- |
| `native-consume-receipt/v1` | 13 | Nine core identities plus operation, time, schema, and aggregate core binding. |
| `native-removal-receipt/v1` | 16 | Core identities plus nullable consume digest, operation, prior/successor generation, time, disposition, and schema. |

All digest members use the closed lowercase SHA-256 grammar; installation,
operation, project, and transaction IDs use canonical UUIDv7; generations use
canonical safe-decimal; timestamps and schema literals are closed. The
removal disposition is exactly `ABSENT|DISABLED`. Missing, extra, renamed,
duplicate, null-at-required, wrong-type, unknown/future-schema, and hostile
reflective shapes can be refused totally by the bounded parser.

The removal nullable arms are structurally unambiguous: null
`nativeConsumeReceiptDigest` represents the proposed direct-CREATED arm and
non-null represents the proposed post-CONSUMED arm. The parser must not infer a
prior lifecycle from either arm. Later composition must bind the arm to the
actual selected prior state and bind a non-null digest to the actual parsed
consume receipt. No nullable partial group or third arm exists.

`successorNativeGeneration = priorNativeGeneration + 1` is exact under the
safe-integer grammar. Zero, maximum-as-successor, overflow from maximum prior,
noncanonical decimal, and non-adjacent values are discriminating structural
cases. Adjacency prevents a receipt from silently blessing the same generation,
but it does not authenticate which provider generation was current; that
source remains later composition/provider evidence.

## Path, schema collision, framing, and replay

The shared transaction/operation path is deterministic and collision-free when
consume and removal operation IDs are authenticated as distinct. Before that
later equality, the common directory is fail closed rather than authoritative:
a wrong schema at the same path, a moved transaction, or duplicate ID cannot
be selected merely because bytes parse. The structural constructor alone
cannot decide any of those relations and must not enumerate or choose a latest
file.

The digest formulas are closed and acyclic:

```text
Dnc = SHA256(frame("native-consume-receipt/v1", canonical consume bytes))
Dnr = SHA256(frame("native-removal-receipt/v1", canonical removal bytes))
```

Each frame has one canonical-record part. Domain deletion, domain swap, raw
JSON, field-wise framing, untagged canonical digest, or common pointer `Dv`
substitution changes identity and is directly testable. The serializer must
route each exact schema to its own function after total parsing.

Replay of byte-identical evidence at its authenticated same path is not a new
operation result. Different bytes, another schema, another path, or a copied
receipt under a different selected transaction must not regain authority. The
structural digest and path goldens distinguish those values, while actual
same-path read-back, collision handling, and restoration prevention remain
provider/persistence/composition responsibilities. Missing live bytes remain
`UNKNOWN`; the ledger grants no bare-absence success.

## Time, graph order, and trust

The intended order is acyclic:

```text
core/CREATED -> native consume Dnc -> selected CONSUMED -> consume post receipt
prior state  -> native removal Dnr -> selected REVOKED  -> revoke post receipt -> archive
```

Neither native receipt contains its selecting state proposal/tip, a downstream
post-selection receipt, or the archive. A nullable `Dnc` may enter `Dnr` only
after consume, and `Dnr` enters REVOKED only afterward. There is no digest
cycle.

The proposed inclusive time windows are also acyclic: CREATED time is at or
before consume receipt time, which is at or before CONSUMED time; prior-state
time is at or before removal receipt time, which is at or before REVOKED time.
Equality at one canonical instant is coherent. The structural parser proves
only timestamp grammar. The later validator must first fix and authenticate
the producer meaning of receipt `recordedAt`; otherwise ordered strings compare
caller assertions rather than operation evidence.

A parsed record, canonical bytes, `Dnc`, `Dnr`, path, serializer success,
worker, candidate, copied core fields, disposition literal, or this review does
not certify a provider result or select state. Only later authenticated
composition and the stable mutation path may consume the records as authority.
The current producer/consumer section names `ISS-002` as schema producer and
`ISS-041` as the first runtime parser consumer, but does not yet name the owner
that authenticates and produces each native receipt. That ownership must be
made explicit with the OP-R130-2/3 repair; it cannot be inferred from the word
“reviewed.”

generation adjacency, structural acceptance, and bounded footprint. The
footprint over the existing recovery module, serializer/export/compatibility

not sufficient—and must not be widened—to implement provider truth,
same-path persistence, retry conflict, selected-state equality, operation-ID

No registered dependency or board topology changed, and no topology repair is
required. The smallest replan is confined to the authority and mirrored
`ISS-002` draft: clarify the existing serializer success arm, remove or source
the redundant fields, split structural path sensitivity from later
cross-operation refusal, and assign operational receipt admission/read-back to
