## Definite blockers

### OP-R159-1 — a pure supplied-array validator cannot detect a valid truncated suffix

The ledger says the total full-chain validator receives only a dense supplied
array, performs no lookup, takes no expected current value or final digest, and
makes no currentness claim. It also requires this slice's compatibility
fixtures to cover truncation and says a truncated history is `UNKNOWN`.

Those statements cannot all be true. Given a valid selected history
`[I0, T1, I2, T3]`, the supplied prefix `[I0, T1]` is byte-for-byte a valid
complete history at an earlier instant. Genesis, adjacency, predecessor digest,
ordinal, lifecycle, identity preservation, and time all validate. No pure
function receiving only that prefix can know that `I2` and `T3` exist.

The later ISS-004 composition already owns the missing fact: it locates the
selected current pointer graph and requires the supplied final record to equal
that current selected value. That composition, not the bounded array validator,
can honestly turn a missing suffix into `UNKNOWN`.

Smallest repair: define this slice's function as a supplied-chain structural
validator that accepts every nonempty valid prefix, remove the pure-validator
truncation claim and mutant, and retain truncation/current-tail refusal in the
later selected-current composition evidence. If the function must itself claim
fullness, add one independently trusted expected final `Dt`/value/digest input
and prove equality; that is larger and duplicates the already assigned ISS-004
boundary.

### OP-R159-2 — non-adjacent attempt-ID reuse passes every stated edge rule

The pure transition rules require only that a `TERMINAL -> IN_PROGRESS` edge use
an attempt ID different from the immediately prior TERMINAL record. The
full-chain validator is specified to apply those edge rules and adds no global
attempt-ID census. Therefore this chain satisfies every written relation:

```text
IN_PROGRESS(A) -> TERMINAL(A) -> IN_PROGRESS(B) -> TERMINAL(B)
               -> IN_PROGRESS(A)
```

The final `A` differs from adjacent `B`, may use a newly digesting descriptor,
has the correct predecessor digest/ordinal/time, and is accepted even though it
reuses a completed attempt identity. This contradicts the ledger's statement
that reused attempt IDs refuse, ISS-002's UUID-uniqueness evidence, and ISS-030
AC1's ID-collision refusal. Random UUID generation is uniqueness advice, not a
proof, and a create-once descriptor-path conflict is later persistence behavior
outside this pure validator's claimed evidence.

Smallest repair: keep the adjacent edge validator unchanged, but require the
supplied-chain validator to maintain the set of prior attempt IDs and reject a
new IN_PROGRESS whose attempt ID has appeared anywhere earlier in the chain.
Add the non-adjacent `A/B/A` mutant. Alternatively, explicitly remove global
reuse refusal from this validator and assign it to later descriptor create-once
composition, but then the current ledger, ISS-002, and ISS-030 evidence must all
say so consistently.

### OP-R159-3 — the tagged digest repeats fields already committed by canonical bytes

The proposed digest frames the full canonical record bytes and additionally
frames:

- a genesis/later byte selected from the record's exact
  `ordinal`/`predecessorRecordDigest` arm;
- `ordinal`, which is already an exact canonical record member; and
- for later records, `predecessorRecordDigest`, also already an exact canonical
  record member.

The closed parser makes the two arms disjoint: genesis is exactly ordinal `"0"`
with a null predecessor, while every later record has a positive ordinal and
SHA-256 predecessor. Canonical bytes already commit those values and their
types. The platform frame already commits the `attempt-log/v1` domain, part
types, lengths, and count. Deleting the extra tag, predecessor, and ordinal
parts therefore admits no record substitution, cross-domain value, ambiguous
concatenation, fork, gap, or reorder that hashing the one canonical record part
would not already distinguish.

The packet requires mutants for every duplicate frame part but gives no
concrete in-scope threat for them. Under the work model, complexity defending
only against a parser/canonicalizer failure excluded by the same contract is a
finding.

Smallest repair: use one `attempt-log/v1` canonical-record frame, matching the
already reviewed descriptor shape. If a separate tag or repeated field is
retained, record the concrete substitution that survives the canonical-record
digest without it and why a smaller frame cannot kill that substitution. Update
the supervisor digest census and draft/goldens together; no deployed digest
migration exists because this record family is not implemented.

## Attacks that did not produce blockers

The IN_PROGRESS census is exactly nine sorted members and TERMINAL is exactly
the same nine plus six branch-only members at the correct canonical positions.
Branch-only terminal fields are absent from IN_PROGRESS. Scalars, nullable
predecessor arms, safe-integer decimal ordinals, exact source/lifecycle/
disposition enums, and inclusive adjacent time are unambiguous. The first value
is IN_PROGRESS at ordinal `"0"`; the only local graph is
`null -> IN_PROGRESS -> TERMINAL -> IN_PROGRESS`, and same-attempt
terminalization preserves transaction, source, attempt, and descriptor.

The record path is constructible from each parsed record and moving
transaction, source, attempt, ordinal, or lifecycle changes it. The common
`RECOVERY_ATTEMPT_LOG` pointer remains the transaction/source current path;
selected-object aliases and prior triples, not directory enumeration or a new
head/index, supply predecessor graphs. The exact VALUE position
`{mode:"VALUE",parts:{}}` needs no additional discriminator. Archive and common
tombstone composition remain deferred; this slice introduces no delete,
retention, compaction, accumulator, checkpoint, rolling digest, or terminal
summary.

`descriptorDigest` is sufficient without a directly copied reservation key or
tip. The parsed log transaction/source/attempt constructs the immutable
descriptor path; exact descriptor bytes recompute the digest; and the descriptor
itself directly carries `reservationPredecessorKey` and selected RESERVED
`reservationTipDigest`. Later family composition can therefore reconstruct and
validate the selected reservation graph. Copying reservation siblings into
each log record adds no locator or replay discriminator.

The dependency order is acyclic:

```text
selected RESERVED reservation
  -> immutable LIVE descriptor
  -> selected IN_PROGRESS log
  -> selected CONSUMED reservation
  -> selected TERMINAL log
  -> selected TERMINAL reservation
  -> later archive/common tombstone
```

The IN_PROGRESS record does not contain the reservation value that later names
its selected tip, and the TERMINAL record does not contain the later reservation
TERMINAL tip. A next attempt binds the prior selected TERMINAL log before its
new reservation and descriptor. No digest cycle is introduced.

The terminal fold keeps distinct structural identities for the selected
attachment, process terminal observation, denied channels, applicable
revocation, and disposition-specific outcome. Attachment and revocation are
independently nullable structural cells; no upstream structural fact in this
slice establishes an iff relation between them. Exact applicability and
cross-record chronology remain assigned to ISS-005/ISS-030/ISS-032
composition. A SHA-shaped field, parser success, or candidate report grants no
terminal fact. The stable external mutation handle and selected common pointer
graph remain necessary; the candidate never certifies or promotes itself.

Engine contracts contain only opaque identities, lifecycle/disposition/source
tokens, timestamps, and constructed platform paths. No Git, GitHub, provider,
native process, argv, endpoint, package, or project-policy vocabulary enters the
record. Opaque process/channel/outcome evidence is not accepted semantically by
this parser; later independently reviewed source contracts and composition own
that proof.
