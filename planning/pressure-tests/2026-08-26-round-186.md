## Round-185 production repair confirmed

`forbidden_profile_sid` now accepts mutable `ROOT_CUSTODY *`. A non-null
`FreeSid(system_sid)` result sets `root->resource_ambiguous` before the helper
refuses. Fresh create and ATTEMPTED reconciliation therefore cannot reduce this
returning-resource ambiguity to ordinary refusal.

The fault fixture directly stages `FAULT_SID_FREE` at this exact helper after a
complete terminal journal exists. It proves the helper returns forbidden, the
resource latch is set, later root/token/heap releases are still attempted, and
the intact durable chain is readable by a clean retry. This kills the precise
Round-185 mutant rather than consuming the fault only in `exact_acl`.

## Remaining finding 1: exact Windows call shapes are not deletion-tested

The profile fixture returns modeled success without authenticating several
inputs that Rounds 179 and 181 fixed exactly:

- `fixture_CreateAppContainerProfile` discards `display` and `description`.
  A production mutant no longer passing
  `(moniker, moniker, moniker, NULL, 0, &sid)` survives.
- `fixture_GetAppContainerFolderPath` explicitly discards `sid_text`. A mutant
  asking Windows for a different principal's folder survives.
- `fixture_profile_CreateFileW` discards access, sharing, creation disposition,
  flags, attributes, and template for the profile folder. Removing
  `FILE_FLAG_OPEN_REPARSE_POINT`, adding delete/write sharing, requesting write
  authority, or changing `OPEN_EXISTING` survives. The returned “reparse” case
  cannot kill removal of no-follow because the fixture reports the same object
  regardless of the open flags.
- `fixture_profile_GetSecurityInfo` does not require `SE_FILE_OBJECT` and exact
  `OWNER | DACL | LABEL` information. Deleting the label request can still
  receive a modeled SACL and pass.

These are not cosmetic assertions. Exact SID-to-folder binding, no-follow open,
delete-denying retained sharing, read-only access, and requested label custody
are part of the authority boundary.

### Required repair

Make each fixture seam reject any noncanonical argument before returning a
modeled observation. Add direct deletion cases for each argument, including a
nofollow mutant whose modeled result differs when the flag is absent. Require
the exact moniker in all three create strings, zero capabilities, canonical SID
text, folder read-attributes/read-control access, `FILE_SHARE_READ` only,
`OPEN_EXISTING`, exact backup/no-follow flags, null security/template inputs,
and exact security-information mask.

## Remaining finding 2: reconciliation failures are not exercised

The TypeScript driver runs profile cases `4..34` only with mode zero, the fresh
`create_profile` path. Modes one and two run only the canonical case: successful
create from absent ATTEMPTED and `ALREADY_EXISTS` from present ATTEMPTED.

Consequently the failure matrix does not prove ATTEMPTED reconciliation for:

- API failure or invalid/wrong/forbidden returned SID;
- the Round-185 SYSTEM-SID release ambiguity at its actual reconciliation call
  site;
- census, folder path/open/security/binding, and CREATED persistence failures;
  or
- close/delete/absence retry behavior after reconciliation adopted an existing
  profile.

The direct helper test proves the latch implementation but does not kill removal
of the helper call from reconciliation.

### Required repair

Run every applicable post-create case through both absent and already-existing
ATTEMPTED modes, or use a reduced table that independently kills each distinct
reconciliation branch. Assert exact operation result class, create/delete call
counts, retained-handle state, durable phase, resource latch, and terminal
`65`/`70` reduction. Do not accept merely “nonpositive.”

## Remaining finding 3: two delete-truth retries erase residue in the fixture

For profile cases 30 and 31, the first production cleanup correctly refuses
because either the target row or folder remains. Before the clean retry, however,
the fixture driver sets both modeled presence bits to zero. The second production
cleanup therefore does not prove it can remove the exact residue that caused the
first refusal.

### Required repair

Keep the surviving row or folder present, switch only the modeled API behavior
to the canonical retry arm, and require the second production cleanup to call
delete and establish both absence facts. Assert the first durable
DELETE_ATTEMPTED state and final ABSENCE_PROVED state. External disappearance is
not an authorized substitute for broker retry.

## Remaining finding 4: package and label ACE flags are not exact

`exact_profile_folder_security` currently requires the package and mandatory
label ACEs to contain `OBJECT_INHERIT_ACE | CONTAINER_INHERIT_ACE`, and rejects
an inherited package ACE, but it does not reject other flag bits. It therefore
admits package or label ACEs additionally marked `INHERIT_ONLY_ACE`,
`NO_PROPAGATE_INHERIT_ACE`, inherited-label, or audit-only bits.

That is not the exact Windows-created package/full-control and low/no-write-up
profile required by Rounds 179 and 181. In particular, `INHERIT_ONLY_ACE` changes
whether the package right applies to the retained folder itself.

### Required repair

Require the package ACE and low mandatory-label ACE flags to equal exactly
`OBJECT_INHERIT_ACE | CONTAINER_INHERIT_ACE`. Add independent extra-flag mutants,
including `INHERIT_ONLY`, `NO_PROPAGATE`, and inherited label. Preserve the
existing complete descriptor binding and dangerous-right checks for other
inherited ACEs.
