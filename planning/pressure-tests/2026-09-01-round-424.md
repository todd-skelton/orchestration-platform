# Pressure round 424 — worker-result review preflight extraction

Status: bounded implementation packet; independent review and host execution pending.
No mutation, review authority, command publication or ISS-013 completion claim.

## Proportionality decision

The landed project-mutation request/plan/apply contracts do not yet make a
two-fixture mutation runtime safe. Current ISS-041 consumers produce COMPLETE,
FOLLOW_UP or UNKNOWN dispositions and explicit no-mutation skips, never the
required APPLY/PROJECT disposition. Branch and queue fixtures expose no reviewed
action-to-resource/effect mapping, stable transaction owner, fresh dry/before/
after resource observations, allocation claims or idempotent progress source.
The existing `project plan --request` and `project apply --plan --plan-id`
arguments also omit the full binding preimages required by the public relations.
Starting plan/apply or `adapters:conformance` here would therefore invent an
owner or overstate mutation transcripts.

The smaller live consumer is the worker-result REVIEW arm already executed by
`consumeReview`. It currently rereads the fixed retained review seed and builds
the public step-6 observation inline. This packet moves only that read/bind logic
to the existing SDK preflight source and leaves the complete final-cycle copy
for a later bounded migration.

## Scope, evidence and attack surface

- Admit the complete module/action/SELECTED route and detached mapping before
  the fixed current-subject callback. PROJECT and release-candidate contexts
  refuse without a callback.
- Retain a concrete worker-result subject. Exact identity is ELIGIBLE; a valid
  changed identity is TARGET_CHANGED; thrown, rejected, malformed or thenable
  sources become SOURCE_UNKNOWN. None grants review authority.
- Bind fresh observation ID/time, configuration, action, route, mapping and the
  full subject through the existing project-preflight/v1 relation.
- Migrate `consumeReview` without changing its canonical evidence files,
  allocation boundary, worker execution, review reduction or cleanup behavior.

Removal attacks cover pre-admission callback invocation, substituted route or
subject, mapping/input mutation across the await, project/policy observation-ID
reuse, digest-only target comparison, changed-target-to-unavailable conversion,
thenable assimilation, malformed source output and an added authority field.
Existing review-consumer tests must continue to prove the positive tuple,
changed-target refusal before allocation, canonical retained records and
unchanged outside manifest.

## Non-goals, footprint and verification

Non-goals are final-cycle migration, release-candidate preflight, mutation
request/plan/apply, allocation/reclaim, project commands, adapter conformance,
recovery, providers, credentials, journal changes and effective review or
release authority. No roadmap or board state changes.

Predicted implementation footprint is SDK preflight source/tests, the existing
review consumer, this pressure record and the ISS-013 implementation note.
Focused SDK and review-consumer tests, typecheck, format, planning and clean-diff
checks are host evidence only; three-OS CI and independent exact-head review
