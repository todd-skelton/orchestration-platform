## Round-192 finding 1 is removed

Production now has one exact close reducer:

```text
close_find_handle(root, find)
  FindClose failure -> root->resource_ambiguous = 1 -> false
```

`directory_empty`, `directory_fixed_census`, `exact_unnamed_stream`, and
`execution_subset_census` all route every acquired enumeration handle through
that reducer, including early invalid-entry and enumeration-error arms. Callers
cannot clear the latch. SERVE and recovery already reduce any retained resource
ambiguity to recovery-required.

The 40-case compiled execution fixture supplies returning failures at:

- initial execution-parent emptiness and the next retained stream census;
- root census after mkdir and target stream census after a target write;
- the first PARTIAL and COMPLETE cleanup census; and
- an enumeration close combined with a later ordinary retained-handle close.

The fixture calls the real Windows close before returning the modeled failure,
then verifies the ambiguity remains latched even where the underlying resource
was actually released. This is proportionate executable evidence for the
shared reducer. No relevant raw execution `FindClose` remains outside it.

## Round-192 finding 2 is only partially removed

### Accepted cleanup and retry evidence

Cases 10–33 create a real ATTEMPTED partial root, invoke production
`cleanup_execution`, and inject all twelve publication failures for PARTIAL
DELETE and PARTIAL ABSENCE. Cases 34–35 construct COMPLETE and inject first-
publication failures for DELETE and ABSENCE. Each failed run retains its exact
durable prefix, releases/reloads the production execution record, retries
cleanup, reaches `EXECUTION_ABSENCE_PROVED`, and reparses the resulting chain.

The fixture's `SetFileInformationByHandle` seam proves:

- a DELETE publication failure observes zero child/root disposition calls;
- an ABSENCE publication failure occurs only after product deletion calls;
- pending files do not escape the publication reducers; and
- clean reconstruction can consume a durable publication that the first call
  could not acknowledge.

PARTIAL and COMPLETE cleanup census-close failures also refuse before a delete,
latch ambiguity, and admit a later clean recovery attempt. The COMPLETE record
serializer independently rejects a zero binding for each of the three targets,
and production rechecks exact fixed cardinality and all three target/root
bindings before its first DELETE publication.

### Remaining finding: composition and exact deletion order are modeled, not observed

In `fixture_execution_expected`, `profile_cleanup_calls` is initialized to
zero, checked after the execution failure, and incremented manually only after
the fixture has already decided execution cleanup succeeded. It is not a seam
around production `cleanup_profile` and does not execute `recover_groups` or
the SERVE teardown reducer. Consequently the assertion that profile cleanup
did not run is tautological with respect to the product.

The separate lifecycle fixture does exercise outer SERVE cleanup, but
`fixture_cleanup_execution` always changes the phase to
`EXECUTION_ABSENCE_PROVED` and returns success. It has no execution-cleanup
failure arm, much less one caused by a durable publication/census failure. A
deletion that ignores the return from production execution cleanup and enters
profile cleanup is therefore not killed by either fixture.

The disposition seam similarly increments only
`fixture_execution_product_deletes`. It never records which retained target or
root handle was offered. Final filesystem absence can catch many root-first
mistakes because Windows refuses removal of a nonempty directory, but it is not
the direct child-before-root observation explicitly required by the reviewed
packet.

Finally, COMPLETE case 35 fails ABSENCE only after all targets and the root are
already absent. No current case durably publishes COMPLETE DELETE, deletes
exactly one identified target, reconstructs custody with the other two targets
present, injects a retry census/publication failure, and then proves only the
remaining exact targets are deleted. The serializer's three nonzero mutants do
not execute this retry branch.

### Smallest repair

Keep the production broker and all protocol/schema bytes unchanged. Extend the
compiled fixtures only as follows:

1. Make the lifecycle cleanup fixture able to return execution-cleanup failure
   while recording whether `fixture_cleanup_profile` was called. Run the outer
   SERVE/EOF or recovery reducer and require zero profile cleanup and
   recovery-required. Bind one case to a real execution publication/census
   failure, or invoke the exact composition function with that failed result;
   a manually incremented local counter is not sufficient.
2. Record disposition identities or fixed roles in the execution fixture and
   assert the successful sequence is target 0/1/2 before root, with no profile
   cleanup before execution ABSENCE.
3. Add one COMPLETE durable-DELETE retry with exactly one named target already
   absence-proved, the other two exact and present, then inject a subset-census
   or ABSENCE-publication failure. Reconstruct and prove the absent target is
   not reopened/deleted, each remaining target is checked against its own
   nonzero persisted binding, children precede root, and profile cleanup waits
   for durable execution ABSENCE.

This is a deletion-evidence repair, not a request for another broad fault
matrix or implementation redesign.

## Regression and trust-boundary review

- COMPLETE serialization computes `complete` only when the root binding and
  each individual target binding are nonzero. The compiled serializer mutants
  independently zero all three target roles.
- First COMPLETE cleanup admits no subset: it reopens the exact root, requires
  the fixed three-file census, verifies every target and the root digest, and
  only then publishes DELETE. Subset absence is admitted only after a durable
  COMPLETE DELETE predecessor.
- Pending publication cleanup uses the existing exclusive pending handle and
  absence proof. The 48 persist-only faults plus cleanup-integrated DELETE/
  ABSENCE faults cover pending/final cleanup and durable retry.
- PARTIAL remains a closed zero-root/zero-target-binding arm and deletes only a
  stable-owned fixed-name subset under the durable ATTEMPTED predecessor.
- Cleanup remains execution-before-profile in production source. Failure stops
  the loop. The remaining issue is executable deletion evidence for that exact
  composition, not a discovered production inversion.
- LAUNCH remains NOT_IMPLEMENTED. No package SID grant, process, token, Job
  Object, candidate input, authority verdict, receipt, provider result,
  aggregate, certification, or promotion path is added. The broker and records
  remain private and unwired.
