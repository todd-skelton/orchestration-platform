## Finding 1: best-effort reversal creates an unrecoverable exact state

Round 198 explicitly permits the earlier active intent to authorize best-effort
reversal if REVOKE_ATTEMPTED publication fails. Production follows that rule:
`run_admission_lifecycle` marks cleanup unclean but still terminates the runtime
and calls `restore_admission_grant` even when kind 6 is not durable.

If the latest durable phase is GRANTED, JOB_ATTEMPTED, LAUNCH_ATTEMPTED, or
ADMISSION_PROVED, and kind-6 publication fails before becoming durable, the
latest final remains phase 2–5 while all four descriptors may now be exact
original. Recovery then calls `admission_recovery_descriptor_state`. That
function sets:

```text
require_grant = phase >= GRANTED && phase <= ADMISSION_PROVED
```

and refuses every exact-original descriptor for phases 2–5. The broker cannot
publish kind 6/7 or reach OPWX/OPWJ cleanup, despite observing the state created
by its own authorized reversal.

The same prefix arises when a later active-phase publication becomes durable
but its acknowledgement is lost: in-memory cleanup restores originals, then
reconstruction discovers the later durable phase.

### Smallest repair

For every active/revoke phase 1–6, recovery must admit each of the four mutable
objects independently as exactly original or exactly grant. A third profile,
wrong identity/path, mixed bytes within one descriptor, or any other security
value refuses. The reducer then authenticates every object, terminates/proves
the exact job absent, restores root first then all files, and proves all four
exact original before kind 7.

Do not weaken GRANTED's historical meaning: its publication still requires all
four exact grants at that boundary. Recovery's two-profile admission exists
only because later unrecorded best-effort reversal is authorized by the same
durable intent.

Required tests must inject every kind-6 publication fault after each predecessor
1–5, let best-effort restoration succeed, reconstruct from whichever final was
actually durable, and finish kind6/7 plus OPWX/OPWJ cleanup. Each third-profile
object and each partial mixture must refuse while other authenticated objects
are still independently restored and records retained.

`fixture_run_admission`, which only emits `fixture:admission` and returns
success. It does not execute `admission_record`,
`persist_admission_phase`, `apply_admission_grant`, job creation/query,
`CreateProcessW`, token parsing, access probes, runtime cleanup, or
`recover_admission`.

The TypeScript test additionally asserts the fixture source contains no
`CreateProcess` text. Repository search finds no compiled fake-OS seam for the
new APIs and no deterministic OPWL serializer/parser/publication matrix. The
only production admission execution is the real host diagnostic.

Real happy/crash tests cannot inject malformed returned lengths/pointers,
partial security transitions, false-success resource results, every OPWL
publication fault, startup attribute deletion, token field mutation, job-list
truncation, or simultaneous close ambiguity. Nearly every Round-197/198/199
deletion mutant therefore survives.

Extend the existing exact-source C fixture with a separate
`OP_WINDOWS_ADMISSION_FIXTURE` mode that macro-substitutes only OS observations
before including production source and directly invokes the real static
admission functions. Keep the outer lifecycle fixture small; do not duplicate
production logic in TypeScript.

## Finding 3: token and Job results are not hostile-safe

`query_token_buffer` trusts a successful second `GetTokenInformation` call and
stores its output length. `prove_child_token` then casts the returned bytes to
`TOKEN_USER`, `TOKEN_APPCONTAINER_INFORMATION`, `TOKEN_MANDATORY_LABEL`, and
`TOKEN_GROUPS` without first proving minimum structure size, pointer extent and
alignment inside the allocation, SID revision/subauthority/length bounds, or
`GroupCount` multiplication within the returned bytes. Capabilities can claim
zero through an undersized buffer; groups can drive out-of-bounds row/SID
reads; token SID pointers can escape the captured allocation.

`verify_admission_job` uses a fixed eight-PID buffer but does not check the
returned byte count, prove `NumberOfProcessIdsInList` fits the buffer, or detach
and validate the complete variable-length relation. Its “any count” recovery
arm can accept attacker-shaped equal counts that exceed captured storage. The
one-process arm combines `IsProcessInJob` with count one, but malformed/truncated
rows still are not closed input.

### Smallest repair

Add shared bounded parsers over `(base,length)`:

- scalar token queries require exact returned size;
- every SID-bearing pointer must be aligned, start within the detached buffer,
  have a complete in-buffer SID header/subauthority array, and pass exact
  length/revision/count bounds before `EqualSid`;
- TOKEN_GROUPS requires a bounded count whose descriptor array fits exactly
  within returned bytes, every SID extent is in-buffer, and no duplicate row or
  malformed attributes are admitted; zero capabilities still requires a valid
  canonical group header;
- Job PID-list queries must size/retry to a fixed hard ceiling, require returned
  bytes exactly cover the reported in-list count, reject truncation/count
  disagreement/duplicates/zero or over-bound IDs, and compare the one admitted
  PID with the exact child process ID. Cleanup/recovery requires a completely
  observed zero list before absence.

All native buffers are OS data, not candidate data, but authority still fails
closed on malformed or ambiguous observations. The fake-OS matrix must execute
every boundary.

## Finding 4: required denied rights are not probed

The exact DACL formula excludes dangerous rights, but the actual child-token
proof checks only `GENERIC_WRITE` denial for execution files/root. It does not
independently `AccessCheck` and attempt actual opens for:

```text
FILE_APPEND_DATA
DELETE
WRITE_DAC
WRITE_OWNER
ACCESS_SYSTEM_SECURITY
```

Rounds 175, 197, and 199 require concrete write/append/delete/owner/DACL/SACL
denial before candidate execution. Relying only on descriptor construction is
not the required composite-token/effective-access proof.

### Smallest repair

Use the same actual impersonation token and fixed paths. For every execution
file and the execution root where meaningful, require independent AccessCheck
denial for each dangerous right and actual no-follow open denial for rights
accepted by `CreateFileW`. `ACCESS_SYSTEM_SECURITY` failure must distinguish
expected access denial from privilege/query ambiguity. Retain positive exact
read/execute/traverse and scratch rights. Add one deletion mutant per right and
per object class; do not collapse them into one `GENERIC_WRITE` aggregate.
