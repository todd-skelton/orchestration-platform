## Blocking finding

The contention PASS oracle contradicts the authoritative ledger. The ledger
requires both contenders to start behind one barrier, then requires exactly one
`SELECTED(42)` and one `PREDECESSOR_MISMATCH(41)`. `cas.ts` has no barrier; it
only launches two child promises. The worker's persistent `O_EXCL` `cas-lock`
lets one child enter CAS and makes the other return `ERROR/EEXIST` before any
predecessor read. The reducer nevertheless defines `SELECTED + EEXIST + final
42` as PASS. Thus a failed lock admission is promoted to proof that two
contenders executed locked CAS, and scheduling may let the winner finish before
the alleged contender starts. The existing nominal test freezes this false
positive.

The same worker closes its only lock handle before the `SELECTED` readback.
Parent final readback cannot repair that ordering: it occurs after both children
close and proves only final bytes, not the ledger's locked exact readback. An
`EEXIST` event also carries no operation/stage, so the reducer cannot prove it
came from lock admission rather than proposal creation.

## Bounded remedy

Add one provider-owned start barrier and require PASS evidence from two coherent
fresh-child terminal rows: one exact `SELECTED(42)` and one exact predecessor
mismatch for request `41 -> 42`, with readback performed while the admitted
lock remains held. `EEXIST` must never be the CAS contender-success arm. If the
exact Node/O_EXCL candidate cannot produce that sequence without deletion,
retry, a sequencer, or a helper, reduce the row to UNSUPPORTED; do not manufacture
PASS. Regression mutants must cover missing/released lock, no barrier,
`SELECTED + EEXIST`, request substitution (`42 -> 42` versus `41 -> 42`), and
post-close/final-only readback.
