## Disposition

`PASS_TO_REWRITE`.

This is a fresh independent cold planning/removal review of the Windows
per-job principal-isolation design against exact clean and pushed HEAD
`2fcc13853231e8cf646d4a68b865ef100d547a44`, the sole ISS-006 authority ledger

composition only for interface and ownership constraints. It does not inherit
an earlier disposition and does not authorize a Windows simulation to stand in

The smallest constructible design for the current required
`windows-2025`/X64 hosted environment is one fresh journal-burned AppContainer
profile with zero capabilities, exact protected DACL grants, and one private
stable native broker that atomically launches the candidate into a fresh named
non-breakaway `KILL_ON_JOB_CLOSE` Job Object. The broker owns only the bounded
profile/DACL/process lifecycle, inherits no candidate authority, and exposes no
general command, shell, service, installation, network, or promotion surface.

The directed sequencing change permits the reviewed Windows and Linux private
infrastructure to support the initial self-hosting path without waiting for the
macOS implementation. It changes no acceptance relation: the three required OS
jobs remain in the stable registry, macOS remains required before ISS-006 can
complete, missing macOS evidence cannot normalize to PASS, and neither Windows
simulation nor candidate output can certify or promote a candidate.

This review did not read or touch any consumer repository or consumer system.

## Windows facts that constrain the design

- The current stable environment vector names `windows-2025`; the current
  GitHub-hosted Windows X64 runner is an administrator with UAC disabled. That
  stable identity can perform the bounded profile, DACL, Job Object, and
  cleanup operations, but the AppContainer SID receives none of that authority.
- `CreateAppContainerProfile` creates a per-user profile and reports
  `ERROR_ALREADY_EXISTS` for a pre-existing moniker. The caller can independently
  derive and compare the package SID. `DeleteAppContainerProfile` reports
  success even when the profile does not exist, so its return code alone is not
  an absence proof.
- `NetworkIsolationEnumAppContainers` documents enumeration of all created
  AppContainers. One complete successful enumeration can therefore prove the
  exact burned moniker/SID absent independently of profile-delete status; the
  profile folder must also be absent.
- `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES` creates the AppContainer token;
  a zero-length capability list requests no network/device capability.
  `PROC_THREAD_ATTRIBUTE_JOB_LIST` assigns the new process to the supplied job
  at process creation. `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` limits inherited
  handles when every listed handle is inheritable and `bInheritHandles` is
  true.
- Nested Job Objects are supported on the target Windows generation. A child
  placed in the inner job cannot break away when neither breakaway flag is set,
  and `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` terminates every associated process
  when the last job handle closes. Completion-port notifications are advisory;
  authoritative terminality comes from exact process waits, pipe EOF, and job
  accounting.
- An AppContainer token is a restricted token associated with the stable user
  plus the package SID. Stable-user inequality cannot be guessed from
  `TokenUser`; authority instead requires exact `TokenIsAppContainer`,
  `TokenAppContainerSid`, restrictions, low integrity, zero supplied
  capabilities, and access checks that require the package SID. Stable roots
  must deny this exact token even though they admit the stable user.
- The recently documented `CreateProcessInSandbox` surface is experimental and
  adds a separate specification/BFS/job mechanism. It is not the established
  Round-172 AppContainer-plus-Job design and is deleted from this rewrite.

## Authorized reduced Windows design

The rewrite may implement only the following bounded design.

1. **Hard platform and package boundary.** The production factory captures the
   native platform at module initialization and refuses before option parsing,
   helper lookup, state access, or mutation unless it is exactly `win32`.
   Private fixtures may inject syscall results into a core, but no caller seam
   can make the production factory authoritative off Windows. The adapter,
   broker, journals, SIDs, ACLs, and Job Object vocabulary remain private
   package files; no symbol enters the package root or any of the nine portable
   records.

2. **One reviewed stable native broker, not a service.** Add one tracked narrow
   native source and one reviewed reproducible X64 PE image to the exact stable
   harness bundle. The stable adapter opens the PE and source from protected
   stable bytes, captures byte hash, volume/file identity, link count, size,
   owner, complete protected DACL/SACL/mandatory-label profile, PE machine, and
   a closed system-DLL import census, then copies the PE by retained handles to
   a stable-only external helper root. The copy is independently hashed,
   profiled, and kept inaccessible to the candidate before and after every use.
   A PE/source mismatch, mutable import/tool path, alias, reparse point, hard
   link, architecture change, moved ancestor, widened ACE, or substituted byte
   refuses. Reproducible compilation is executable review evidence; no hosted
   compiler, PATH, `cmd.exe`, PowerShell, shell, download, or mutable SDK is in
   the runtime authority chain.

   The helper has exactly two process modes: one job-private `SERVE` lifecycle
   and one journal-bound `RECOVER`. `SERVE` accepts only closed framed
   `PREPARE`, `LAUNCH`, and `TEARDOWN` transitions over stable-owned anonymous
   control pipes. `RECOVER` accepts only canonical records under the retained
   state root. It has no arbitrary executable, path-discovery, command,
   registry-write, network, daemon, install, receipt, or promotion mode. One
   broker exists only for one principal and terminates after teardown; it is
   not a machine service or cross-job authority.

3. **Stable roots, handles, and durable burned state.** Capture the stable user
   SID from the actual non-AppContainer process token, require the hosted X64
   environment, and retain opened handles for the volume root, stable authority
   root, state root, helper root, execution parent, stable runtime/artifact/RPC
   sources, and every ancestor. Roots are absolute, normalized, pairwise
   distinct and nonnested; none lies in either checkout or provider/evidence
   storage. Stable roots have exact protected DACLs admitting only the stable
   SID and `SYSTEM`, an exact owner and mandatory label, no reparse/mount point,
   one link, and captured volume serial/file ID/type/attributes/security bytes.
   The execution parent contains no stable bytes and is initially empty.

   Before every OS mutation, write a create-exclusive canonical cleanup phase
   under the state root with `FILE_FLAG_WRITE_THROUGH`, flush the record and
   retained state-directory metadata, close and reopen it, and compare exact
   bytes/security/identity. Append-only phase files bind one cryptographic
   token, profile moniker, derived SID, named-job nonce, roots, object IDs,
   hashes, DACLs, and prior phase. Every attempted moniker/job/root remains
   burned for the hosted job even after successful cleanup. An ambiguous write,
   flush, rename, unlink, directory flush, or absence proof retains the record
   and refuses; a retry must complete a fresh successful durability barrier.

4. **Fresh profile and independent absence.** Derive a lowercase ASCII moniker
   of bounded documented length from the burned nonce and derive its package SID
   before creation. Require one complete bounded
   `NetworkIsolationEnumAppContainers(NETISO_FLAG_FORCE_COMPUTE_BINARIES)`
   result with no malformed, duplicate, aliased, over-bound, or exact
   moniker/SID row, plus absence of the canonical profile folder. Persist and
   sync `PROFILE_ATTEMPTED`, then call `CreateAppContainerProfile` with zero
   capabilities. `ERROR_ALREADY_EXISTS`, an unexpected SID, unexpected profile
   path, second matching row, or any partial/unknown result refuses and enters
   recovery; an existing profile is never adopted.

   Capture the returned SID as binary and canonical string, require it differs
   from the stable user and every stable/authority SID, obtain the exact profile
   folder through `GetAppContainerFolderPath`, and retain its identity/security
   handle. This OS-created folder is the only candidate-writable scratch root.
   Its bytes are hostile and never evidence.

5. **Exact execution copy and DACL relation.** Before `LAUNCH`, create one fresh
   execution root beneath the authenticated empty execution parent and copy
   through retained source handles exactly three stable-selected files: the
   X64 Node 24 runtime, the candidate artifact, and the Windows-capable RPC
   runner. Independently read every destination through retained no-follow
   handles and require exact size/hash, regular-file type, one link, volume/file
   identity, and fixed three-file root census. Creation is complete and
   directory-synced before any package grant.

   Atomically install exact protected security descriptors: stable SID and
   `SYSTEM` retain full control; the exact package SID receives only directory
   traverse/read/execute and file read/execute; no `Everyone`, `Users`,
   `ALL APPLICATION PACKAGES`, capability, inherited, deny-conflict, write,
   delete, owner, DACL, SACL, alternate-stream, reparse, or extra-path grant is
   admitted. The AppContainer profile folder retains only its exact OS-created
   package write relation. A suspended-token `AccessCheck` plus actual
   impersonated opens must prove runtime/artifact/RPC read and execute, their
   write/delete/security denial, scratch create/write/delete, stable/state/
   helper/source root denial, and no unlisted inherited handle before any
   candidate instruction executes. Missing Node dependencies yield
   `UNSUPPORTED`/refusal, never a wider DACL or same-principal fallback.

6. **Atomic closed launch and pre-execution token proof.** The stable broker
   creates one fresh named Job Object with an exact stable-only security
   descriptor, persists `JOB_ATTEMPTED`, and sets and re-reads exactly
   `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`; neither
   `JOB_OBJECT_LIMIT_BREAKAWAY_OK` nor
   `JOB_OBJECT_LIMIT_SILENT_BREAKAWAY_OK` is ever set. It creates the candidate
   suspended with exact non-null application path to the copied runtime, exact
   Windows quoting/argv for the copied RPC runner and artifact, exact scratch
   cwd, and a closed allowlisted UTF-16 environment. The environment contains
   only hosted-probed Node necessities and the AppContainer-rerouted
   `LOCALAPPDATA`, `TEMP`, and `TMP`; it contains no PATH, checkout, provider,
   token, cache, credential, helper, job name, or stable-root value.

   One `STARTUPINFOEXW` call supplies exactly the fresh job through
   `PROC_THREAD_ATTRIBUTE_JOB_LIST`, the exact package SID and zero capabilities
   through `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES`, and only candidate
   stdin/stdout/stderr through `PROC_THREAD_ATTRIBUTE_HANDLE_LIST`. The three
   child pipe ends are the only inheritable broker handles;
   `bInheritHandles=TRUE`, stable pipe ends and every control/state/helper/job
   handle are noninheritable, and the child starts with `CREATE_SUSPENDED`.
   Before `ResumeThread`, open its token and require exact AppContainer SID,
   `TokenIsAppContainer`, restricted-token status, low integrity, no elevation
   or UI access, zero capability entries, no enabled Administrators/authority
   group, stable-token inequality in the package-principal dimension, the
   DACL/access probes above, and membership in the exact inner job. Any token,
   handle, job, environment, argv, cwd, or probe ambiguity terminates the job
   without candidate import.

7. **Stable-only protocol, timing, and terminal root.** The existing private
   coordinator remains the sole owner of the canonical challenge, expected
   values, selected-head equality, hostile parse, monotonic interval,
   normalization, three fresh cycles, and teardown-before-result order.
   Profile/root preparation occurs in `prepare` outside the interval. The
   interval begins immediately before the broker's closed `LAUNCH` transition
   and contains process creation, token/job validation, resume, Node/module
   load, IPC, complete response read, parse/full semantic validation, and exact
   candidate-root wait status.

   The broker drains candidate stdout and stderr concurrently into independent
   bounded byte buffers, writes input once then closes candidate stdin, and
   exposes candidate bytes only as length-bound fields in one canonical broker
   frame. Candidate handles never include broker control stdout/stderr, so a
   candidate cannot forge the stable frame. Success requires the exact root
   process handle signalled, a detached numeric exit code, candidate stdout and
   stderr EOF, no truncation/duplicate frame/output-limit/spawn error, and the
   stable parent accepting the response. EOF, candidate PASS/duration, PID
   text, a broker `error` event, kill request, or root exit without both pipe
   closures is not terminality. A stable five-second watchdog instructs the
   broker to terminate the job; the observation is then TIMEOUT/refusal and
   still waits for root and pipe terminality.

8. **Descendant containment and exact job quiescence.** The broker retains the
   only live inner-job handle across `LAUNCH` and into `TEARDOWN`; it never
   duplicates or names that handle to candidate code. Candidate descendants,
   including nested process groups and detached pipe holders, remain in the
   immediate nonbreakaway job. Teardown and timeout call
   `TerminateJobObject`, wait every retained candidate process/pipe handle
   terminal, and repeatedly query both
   `JobObjectBasicAccountingInformation.ActiveProcesses` and a completely
   sized `JobObjectBasicProcessIdList` until both prove zero within a fixed
   deadline. Count disagreement, list truncation, a survivor, query denial,
   close failure, or nonterminal broker refuses; completion-port messages and
   PIDs are diagnostics only.

   On parent-pipe loss the broker performs the same kill/query sequence and
   closes its job handle. On broker failure, the kernel's last-handle
   kill-on-close rule applies. Recovery opens the cryptographically named job
   with the retained stable descriptor when it still exists, terminates and
   empties it, closes all handles, and requires `OpenJobObject` exact-not-found
   after zero accounting. Because the candidate never inherits a job handle,
   a missing named object after a durably proved kill-on-close configuration is
   not replaceable by candidate self-report. Recovery never signals a numeric
   PID or trusts a parent-process tree.

9. **Revocation and handle-bound root cleanup.** Only after candidate root,
   pipes, broker transition, and inner job are terminal/empty, replace each
   execution security descriptor with the exact stable/SYSTEM-only descriptor
   and prove the exact AppContainer token is denied. Close candidate token,
   process, thread, pipe, and job handles before filesystem/profile deletion.
   If a handle close is ambiguous, keep custody and refuse.

   Quiescent scratch cleanup enumerates each retained directory handle, opens
   each child without following reparse points, rejects mount/device crossing,
   deletes reparse entries themselves rather than traversing them, and deletes
   the exact opened object with `SetFileInformationByHandle`. It treats hard
   links, alternate namespaces/streams, malformed names, replacement IDs,
   unexpected fixed-root entries, or a nonempty retry as refusal. Candidate
   quiescence removes the concurrent-renaming actor; stable code nevertheless
   rechecks every ancestor and parent/child volume/file identity and security
   profile at each deletion boundary. It deletes only the captured profile
   scratch and fixed execution objects, syncs the execution parent, and proves
   both paths absent while all stable roots retain identity.

10. **Profile deletion and independent final absence.** Persist and sync
    `PROFILE_DELETE_ATTEMPTED` only after job absence, access revocation, handle
    closure, and root absence. Call `DeleteAppContainerProfile`; whether it
    reports success, not-found, timeout, or an error, independently rerun the
    complete AppContainer enumeration and exact profile-folder probe. Success
    requires no row with either burned moniker or SID, no folder, no named job,
    no package ACE on any retained root, and stable/helper/state identities
    unchanged. A delete return code, folder absence alone, or enumeration row
    absence alone is insufficient. Unknown/partial output retains state and
    retries cleanup; the burned moniker/SID/job/root token is never reused.

11. **Crash recovery and composition order.** Factory construction authenticates
    platform, helper, state and all roots, closes any in-memory active lifecycle,
    loads every canonical phase hostile-safe, preflights all records before any
    mutation, and sorts by burned token. For each incomplete record it opens or
    reconciles the named job, proves root/pipes/job terminal, revokes package
    access, performs handle-bound scratch/execution cleanup, closes every
    profile/object handle, deletes the profile, and proves complete
    moniker/SID/folder/job/ACE absence before permitting another principal.
    Failures stop later phases and retain the journal. No active principal can
    be recovered or closed twice, preparation cannot retry after an attempt,
    and no record is removed until a successful unlink plus state-directory
    durability/absence retry barrier.

12. **Opaque adapter and unchanged evidence authority.** The Windows adapter
    implements only `createPrincipal`, `prepare`, `launch`, and
    `teardownPrincipal` behind opaque handles. It does not choose expected
    semantics, timing, result, receipt, aggregate, provider record, capability,
    certification, or promotion. Candidate stdout/stderr/scratch, helper
    diagnostics, SID/job/PID text, and all simulations are non-authoritative
    data. No Git, GitHub, repository, workflow, run, job, or artifact vocabulary
    enters the coordinator/engine surface.

## Trust and removal sweep

- Stable protected-main bytes alone select the helper PE/source, runtime,
  candidate artifact, RPC runner, challenge, expected values, DACLs, job
  policy, parser, timing, and cleanup. The candidate cannot invoke the helper,
  write a journal, select a capability, or produce a PASS/receipt.
- AppContainer is the Windows principal boundary, not a candidate assertion.
  Suspended native token inspection plus exact access probes precede candidate
  execution; the RPC runner's Windows arm may corroborate closed argv/protocol
  shape but cannot certify its own SID or authority.
- The exact package-SID DACL grants only three immutable read/execute files and
  one non-evidence writable profile folder. Capability SIDs, broad package
  groups, inherited ACEs, a shared checkout, and candidate access to stable
  roots are deleted.
- Atomic `JOB_LIST` association removes the pre-assignment execution window.
  Nonbreakaway policy, kill-on-close, retained job ownership, exact root/pipe
  waits, complete job accounting, and named-job recovery close descendants,
  inherited writers, broker crashes, and PID-reuse attacks without a service or
  numeric-PID signal.
- Complete AppContainer enumeration is retained because profile deletion
  deliberately has success-on-absence semantics. Enumeration plus folder/job/
  ACE absence is the smallest independent final principal proof.
- The experimental sandbox API, Windows Sandbox/VM/container, service account,
  scheduled task, durable daemon, named shared pipe, registry policy, network
  capability, generalized ACL broker, compiler-at-runtime, shell, and public OS
  schema are all unnecessary and removed.
- Linux composition is not refactored into a speculative cross-OS abstraction.
  The existing four-method private interface is sufficient; Windows lifecycle
  nouns remain inside the adapter.
- Advancing Windows/Linux implementation before macOS creates no authority
  shortcut. Until exact Linux, macOS, and Windows required jobs all produce
  protected stable evidence, ISS-006 remains incomplete and no hosted PASS
  aggregate, capability, certification, promotion, or installation follows.
