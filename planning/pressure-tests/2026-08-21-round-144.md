## Disposition

`BLOCK_REPLAN` for the selected-object locator at exact reviewed head
`1a0342a14052637f4ef2404181fcd64e726b68bc`.

The locator accepts a selected proposal whose `mutationId` is not the
deterministic mutation identity derived from the independently trusted pointer
identity, trusted position, returned prior triple, recomputed successor `Dv`,
and proposal outcome. Recomputing attacker-controlled `Dr`, the tip's
`proposalReceiptDigest`, and `Dt` does not cause refusal. This directly defeats
the authority's statement that a caller-supplied mutation ID is not authority
and acceptance item 11's coordinated selected-graph attack.

The adjacent proposal semantics are also incomplete. Under trusted VALUE
position evidence the locator accepts `TOMBSTONE_PROPOSED/SELECT`,
`VALUE_PROPOSED/REMOVE`, and `TOMBSTONE_PROPOSED/REMOVE`, provided the attacker
recomputes the self-consistent proposal/tip graph. Those combinations contradict
the existing ordinary/tombstone contract mapping.

A source-only fix cannot be selected safely from current authority because the
incorporated exact mutation-ID table ends in `outcome/intent`, while the
surrounding normative prose and current public helper specify and frame only
`outcome`. The packet must resolve that formula and the trusted position-to-
intent/outcome mapping before implementation. No producer authentication,
current-tip IO, or family composition needs to move into this slice.

## Reproduced coordinated attack

```text

  22c19415c110a5cbf8c1217821ba246e459f5082f61bc8cdbbbc4515ec832492
```

The proposal instead carried:

```text

  9999999999999999999999999999999999999999999999999999999999999999
```

The attack then recomputed exact `Dr` from that altered closed proposal, placed
the new `Dr` in an otherwise valid tip, and recomputed `Dt`. The public result
was:

```text

attacker Dr =
  e78636eccc8c106d7e65e9eb1e98f2cec8c75faccac387cd677de31817302847

  27b5ffec42374afdb05eac4000834c6b687c185b3c8d03a0ca2697485b34c783
```

No malformed scalar, family substitution, partial prior, position mismatch, or
digest mismatch is involved. `requireProposal` proves only that `mutationId`
is lowercase SHA-256. `computeProposalReceiptDigest` and
`computeCurrentTipDigest` prove that the altered bytes are self-consistent; they
do not prove that the mutation identity is correct.

The checked-in focused happy path already uses an arbitrary `d("c")` mutation
ID rather than `computeMutationId(...)`, so the current green baseline itself
does not represent the deterministic mutation identified by its other facts.
Neither the round-142 evidence repair nor round-143 removal mutations exercise

## OP-R144-1 — deterministic proposal mutation identity is not recomputed

The exact recomputation inputs are already present at the bounded locator
boundary:

```text
expectedIdentity.pointerKind
expectedIdentity.canonicalPointerPath
recomputed Dp
expectedIdentity.transactionId
expectedIdentity.sourceToken
trusted recomputed position digest
proposal prior Dt/Dv/Dr
recomputed successor Dv
proposal outcome
```

Those are the parts consumed by the current `computeMutationId` helper. The
locator already snapshots the trusted identity, parses the complete-or-null
prior tuple, recomputes position, `Dp`, and successor `Dv`, and parses the
proposal outcome. No fifth input, mutation-addressed read, producer expectation,
or caller-supplied expected digest is needed.

The missing equality is therefore structurally derivable:

```text
proposal.mutationId = computeMutationId(
  expectedIdentity,
  proposal prior Dt/Dv/Dr,
  recomputed successor Dv,
  admitted outcome-or-intent formula
)
```

The exact final formula is subject to OP-R144-2. Once decided, a coordinated
test must replace only the proposal mutation ID, recompute `Dr` and tip `Dr/Dt`,
and still refuse. Deleting only the locator's mutation-ID equality must make
that committed mutant survive and fail the focused suite.

This is not redundant with stable current-tip authentication. A trusted tip
authenticates the selected proposal digest, but a stable writer/reader must
first validate that the proposal is a well-formed deterministic mutation. A
self-consistent wrong mutation ID can otherwise disagree with the canonical
mutation-addressed value/proposal paths, conflict evidence, run-current target,
and commit evidence. Treating that copied member as authoritative is precisely
the caller-selected mutation-ID behavior the locator ledger excludes.

## OP-R144-2 — the exact mutation-ID formula is internally ambiguous

The incorporated exact digest table in `supervisor-contract.md` says:

```text
mutation ID / pointer-mutation-id/v1 / ... successor Dv raw32,
outcome/intent
```

The adjacent `Dr` row separately says `intent/outcome text`, and the production
`Dr` function frames two text parts in that order. For mutation ID, however,
the normative prose immediately below the table says only that it additionally
binds the "proposed outcome." The public `computeMutationId` closed input has an
`outcome` member, has no `intent` member, frames one final outcome text part,
and rejects an otherwise valid input containing `intent` as
`intent:unknown-field`.

The slash therefore cannot safely be interpreted during implementation. It
might be shorthand for both record fields, as the `Dr` row demonstrates, or it
might mean the one semantic choice redundantly expressed by intent/outcome.
Those choices produce different mutation IDs and different public goldens.

The smallest proportional repair is to retain the deployed pre-release helper
shape and make the formula explicitly end in one `outcome` text part. State
that `intent` is excluded because it is exactly derived from trusted position
mode plus outcome, then enforce OP-R144-3's mapping. This avoids hashing the
same VALUE-versus-TOMBSTONE choice twice and avoids changing every existing
mutation-ID caller and golden.

If the table intended both fields, the repair must instead specify their exact
order, add `intent` to the closed mutation-ID input, update every caller and
golden, and explain why the duplicate semantic part is necessary. The reviewer
does not select that larger alternative. Either choice requires an explicit
authority repair before OP-R144-1 can be implemented without guessing.

## OP-R144-3 — trusted position mode is not bound to proposal intent/outcome

The ordinary/tombstone contract is already exact:

```text
VALUE position     -> VALUE_PROPOSED / SELECT
TOMBSTONE position -> TOMBSTONE_PROPOSED / REMOVE
```

`expectedIdentity.positionEvidence` is independently trusted. The locator
already parses it through the exact kind-specific position route and requires
the proposal's `positionDigest` to equal its recomputed digest. The proposal
parser, however, admits the Cartesian product of the two intent literals and
two outcome literals for selected-epoch proposals.

Three coordinated attacks were executed with valid mutation IDs under the
current outcome-only helper and recomputed `Dr`/tip/`Dt`:

| Trusted position | Proposal intent | Proposal outcome | Locator result |
| --- | --- | --- | --- |
| VALUE | `TOMBSTONE_PROPOSED` | `SELECT` | `ok:true` |
| VALUE | `VALUE_PROPOSED` | `REMOVE` | `ok:true` |
| VALUE | `TOMBSTONE_PROPOSED` | `REMOVE` | `ok:true` |

The smallest bounded repair requires the exact two-row mapping in the locator
from trusted position mode. A central proposal-parser pair check may also be
appropriate so contradictory intent/outcome records are never structurally
valid, but it does not replace the locator's trusted position-mode equality: a
consistent `TOMBSTONE_PROPOSED/REMOVE` proposal is still wrong under trusted
VALUE position.

Tests must independently change intent, outcome, and both together, recompute
every attacker-controlled downstream digest, and require refusal. Independent
deletion mutants must remove each trusted mode-to-proposal comparison. This adds
no record member, input, digest domain, producer proof, or runtime mechanism.

## Other proposal semantics and scope boundary

The bounded locator can and should recompute only facts available from its four
inputs:

- pointer kind, `Dp`, position digest, successor `Dv`, mutation ID, and
  position-mode intent/outcome mapping;
- proposal `Dr`, tip identity/`Dv/Dr`, `Dt`; and
- complete-or-null prior tuple return.

It cannot independently authenticate `producerDigest`, the selected authority-
epoch `Dt/Dv/Dr`, `producerKind`, or `proposedAt` from the current four inputs.
Those members are closed and committed by `Dr`, but their equality to actual
producer authority and time remains later composed evidence. The repair must
not add caller-supplied expected producer/time fields, authenticate current-tip
origin, parse family values, walk history, or perform IO/CAS.

Acceptance item 11 should distinguish these categories. "Mutate every selected-
graph member ... through coordinated rehashes" must require refusal for every
member derivable at the locator boundary, including mutation ID and
intent/outcome. For self-committed producer/time members, coordinated mutation
should prove only that `Dr/Dt` change until the later composition supplies an
independent expectation. Otherwise the acceptance text invites either the
current under-validation or an unauthorized proof-bag widening.

## Alias, trust, and authority reconfirmation

The selected alias constructors and the other reviewed graph equalities remain
correct. The paths are exact and class-separated under trusted `Dp`, with
lowercase SHA-256 validation for all six dynamic arguments. Proposal kind,
trusted position digest, proposal `Dp/Dv`, and tip kind/`Dp/Dv/Dr` are
equal-bound; complete and null prior tuples return exactly; partial tuples and
hostile nested inputs refuse; and generic success still does not semantically
admit an invalid family value.

The locator remains a record-only one-node validator. It performs no canonical
persisted-byte check, recursive history walk, current-tip acquisition,
root/archive lookup, conflict mutation, proposal/CAS, capability issuance,
broker call, filesystem action, deletion, compaction, runtime mutation,
release review, or promotion. Those boundaries do not explain the reproduced
gap because mutation ID and position mode are already derivable in memory.

Candidate or worker bytes still cannot certify themselves merely by passing a
structural validator. Only stable external authority may select the canonical
tip. Conversely, stable selection does not make an internally contradictory
proposal valid; malformed selected evidence must fail closed as `UNKNOWN`.
