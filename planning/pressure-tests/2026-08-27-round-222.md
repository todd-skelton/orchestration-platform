# ISS-006 Windows broker-custody replan — round 222

## Disposition

`PASS_TO_REWRITE` for one reduced private Windows adapter slice that invokes the
authenticated tracked broker directly from the protected stable bundle.

This round explicitly replaces only Round 175 item 2's stable-to-helper broker
copy. It does not add a materializer, bootstrap handoff, process mode, opcode,
public surface, or authority claim. The broker retains exactly `SERVE` and
`RECOVER`.

Round 221 correctly blocked a TypeScript implementation that claimed to prove
Win32 helper-copy security using Node filesystem facts. Removing that copy is
the smaller trust-preserving repair. The sole ISS-006 authority requires the
stable checkout/bundle to remain protected and inaccessible to the candidate;
it does not require duplicating the stable broker into a second executable
root. The existing native admission proof already denies the actual
AppContainer token read access to the running broker image. A direct stable
invocation keeps the executable inside the reviewed stable root of trust and
deletes an otherwise circular copy/publication/cleanup lifecycle.

## Alternatives removed

### Separate fixed native materializer — rejected

A second native executable would add another source/PE pair, import census,
runtime authentication path, crash journal, recovery owner, deterministic
build, and hosted evidence matrix. It has the same initial question—why the
stable parent may execute the materializer before authenticating it—and leaves
two native authority artifacts where Round 175 chose one. It is not
proportional.

### Broker bootstrap handoff — rejected

Making the tracked broker copy and re-exec itself would require either a third
mode or a new pre-PREPARE protocol/state machine inside `SERVE`/`RECOVER`.
Handoff must transfer exact control handles, bind the mapped source image to the
copy, terminally prove the source process, durably recover every copy prefix,
and ensure only the copy mutates lifecycle state. That machinery does not
improve candidate isolation over executing the same authenticated PE directly.
It also contradicts the already closed two-mode framing unless separately
re-authorized.

### Stable-before-candidate direct invocation — selected

The stable release already executes reviewed TypeScript and native bundle
bytes. Before any candidate or other untrusted same-principal process exists,
the adapter can retain and hash the fixed tracked PE and source from its own
bundle, parse the PE structure, and start that exact stable program. The native
broker then authenticates the live module path/security relation before its
first lifecycle mutation and later proves that the exact admitted AppContainer
token cannot read it. Candidate code never receives the module path and cannot
modify or replace it.

Executing a byte-for-byte tracked stable helper is not candidate
self-certification. Expected PE/source hashes, protocol values, request values,
timing, terminal parsing, and result meaning remain owned by stable TypeScript
and the stable coordinator. The native helper may report/refuse kernel
observations; it never produces PASS, a receipt, or promotion authority.

## Exact implementation fence

The rewrite may add only:

- private `packages/conformance/src/windows-isolation-authority.ts`;
- its focused TypeScript test;
- any fixture-local types/helpers needed by that test; and
- the exact harness/stable-bundle census rows.

If the current native broker lacks one of the live-image/ancestor checks below,
the same slice may add only that fixed startup/admission check to
`windows-isolation-broker.c`, its exact-source compiled fixture, tracked PE,
build/import census, and real diagnostic. It may not add another executable,
mode, opcode, journal family, general path operation, compiler/runtime
dependency, or caller seam.

The production factory remains package-private and captures `process.platform`
at module initialization. It refuses before option parsing or path/state access
unless the value is exactly `win32`. Production options are paths only:

- one external stable-owned state root;
- one external stable-owned empty execution parent; and
- one authenticated stable runtime path.

The broker PE/source paths are fixed relative to the reviewed module bundle,
not caller inputs. RPC and candidate paths come only from the closed coordinator
request. No runner, clock, parser, profile, digest, syscall, spawn, command,
security, or platform seam is caller-supplied. A private test constructor may
model these dependencies but must be unreachable from the package root and
exact harness bundle.

## Direct broker-image custody

Before state access or process creation, stable TypeScript must:

1. resolve the fixed source and PE paths from the module URL without PATH,
   shell, registry, search, environment, or caller input;
2. open both as regular non-directory files, retain the handles, require one
   link and closed size bounds, and capture detached bigint device/inode/size/
   time facts;
3. read all bytes through the retained handles, require exact reviewed
   SHA-256 values, and parse the PE bytes for exact X64 machine, image/section
   bounds, mitigations/relocations, and the closed reviewed import census;
4. re-open the current paths, compare exact detached identity and bytes to the
   retained handles, and retain both handles through broker terminal exit;
5. recheck the retained and current source/PE facts after every native use and
   before closing them; and
6. refuse every read, close, path, identity, link, size, hash, PE, or movement
   ambiguity.

Source-to-PE deterministic reproduction remains executable build evidence; the
runtime never invokes a compiler or trusts the C source to bless the PE.

Before reading PREPARE or mutating profile/execution/admission state, the native
broker must authenticate its actual `GetModuleFileNameW` path as a canonical
non-reparse regular one-link file, retain its identity/security handle, require
that it is owned/protected by the stable authority relation, and recheck the
path/handle relation through lifecycle terminality. It must refuse writable or
executable alternate streams, writable non-authority ACEs, unexpected
mandatory-label/security drift, aliases, substitutions, or ancestor movement.
The exact profile must be deletion-tested and confirmed on the target hosted
Windows image; it must not be guessed from Unix mode bits.

Immediately before resume, the existing impersonated candidate-token proof
must deny read/write/execute/delete/owner/DACL/SACL access to the exact live
broker image and deny traversal/list/read of its protected stable bundle
ancestors. No stable path is put in candidate argv, environment, challenge,
terminal response, adapter result, or diagnostics consumed as evidence.

The stable bundle is the root of trust for this direct invocation. This design
does not claim protection from replacement of already trusted stable code by a
kernel or stable-principal compromise; those could replace the TypeScript
authority itself and are outside the stated hosted-OS boundary.

## Closed four-method adapter

The production object implements only the existing
`Iss002StableIsolationAuthority` vocabulary.

### `createPrincipal()`

- First run one exact broker `RECOVER` process for the authenticated state root
  and require canonical zero-payload TEARDOWN success, control EOF, empty
  diagnostics, terminal process exit, and post-use image custody.
- Start one exact direct broker `SERVE` process with `shell:false`, hidden
  window, stable-owned anonymous stdin/stdout/stderr, fixed empty/minimal
  environment, and a private cwd outside checkout/evidence roots.
- Return only an opaque internally branded handle. SID, profile, folder, Job,
  roots, tokens, process handles, descriptors, and native records remain in a
  private identity map.

### `prepare(handle, request)`

- Hostile-detach the exact closed request and require the literal 5,000 ms
  timeout and normalized absolute candidate/RPC paths.
- Send one exact OPWB PREPARE frame containing the canonical OPWE five-path
  payload. PREPARE remains outside the coordinator interval.
- Strictly parse one bounded OPWR response and require exact magic/version/
  kind/operation/status/reserved bytes, canonical token/moniker/SID/folder/
  execution-root/binding fields, exact EOF for that frame, and no broker
  diagnostic/terminal ambiguity.
- Retain an independent exact request/path/byte binding. Return no preparation
  data.

### `launch(handle, request)`

- Require the same internal handle, PREPARED state, and exact detached request
  binding. Caller mutation, proxy/accessor/reflection, duplicate launch, and a
  second challenge refuse before writing.
- Write exactly one OPWB LAUNCH frame with the stable challenge of length
  `1..4,194,304`, honoring write callback/backpressure while retaining buffer
  ownership.
- Bound and drain broker stdout/stderr independently. Strictly parse exactly one
  LAUNCH response. Status 65/70 requires zero payload and throws. Status zero
  requires the native terminal payload: exact reserved bytes and lengths,
  `stdout`/`stderr` each at most 4 MiB, exact total payload, and no trailing or
  duplicate frame.
- Fatal-decode candidate streams as UTF-8. `EXITED` returns only an exact plain
  frozen `{exitCode:uint32, signal:null, stdout, stderr}`. Native `TIMEOUT`
  maps to the existing non-success terminal observation and can never normalize
  to PASS. Broker stderr is stable diagnostic/refusal data and is never mapped
  to candidate stderr.
- Do not parse candidate JSON, expected values, selected head, PASS, or timing.
  `isolated-walk.ts` performs semantic parse/validation after `launch` returns
  and before its captured monotonic stop, so those operations remain inside the
  trusted five-second interval.

An outer stable watchdog may hard-abort a nonresponsive broker only as a
fail-closed transition: retain terminal/control ambiguity, close/terminate the
stable broker, and force `teardownPrincipal` through native `RECOVER`. It may
not synthesize a terminal candidate response or claim timeout before native Job
terminal proof.

### `teardownPrincipal(handle)`

- For the live normal arm, send exactly one empty TEARDOWN, end stdin to provide
  exact EOF, parse exact zero-payload success, drain control pipes, and require
  root broker terminal exit with no signal/diagnostic/close ambiguity.
- For every failed/early-terminal arm, start exact authenticated `RECOVER` and
  require the same canonical recovery response/terminal facts.
- Recheck source/PE retained and pathname custody, close every owned resource,
  remove the opaque handle only after success, and retain fail-closed recovery
  state on ambiguity. Candidate semantic success is not returned by this
  method; the coordinator releases it only after teardown succeeds.

## Crash and parser ownership

The adapter adds no durable lifecycle phase. OPWJ/OPWX/OPWL remain solely owned
and recovered by the native broker. TypeScript owns only ephemeral process,
pipe, parser, buffer, and opaque-handle state. On parent crash, the native
kill-on-close Job and existing durable `RECOVER` chain remain authority; the
next stable adapter construction runs recovery before a new `SERVE`.

The parser must copy bytes before semantic reads, use data descriptors only,
reject extra/symbol/accessor/proxy-owned JS structure at its API boundary, and
never accept candidate or caller objects as native response authority. Native
binary lengths are unsigned with checked addition; no allocation occurs before
the relevant closed bound is proven.
