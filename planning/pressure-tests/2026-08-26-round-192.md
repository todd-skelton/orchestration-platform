## Finding 1: execution census close ambiguity is not latched

The following new/execution-critical helpers lack `ROOT_CUSTODY *` and simply
return false when `FindClose(find)` fails:

- `directory_empty` at the execution-parent/root boundaries;
- `directory_fixed_census` before CREATED and first COMPLETE DELETE;
- `exact_unnamed_stream` for parent/source/root/target/partial objects; and
- `execution_subset_census` on PARTIAL/COMPLETE retry.

Other authority-bearing journal census paths explicitly set
`root->resource_ambiguous` on the same returning-resource ambiguity. These
execution helpers do not. A `FindClose` failure after mkdir or target creation
causes construction to fail, but normal cleanup may then delete the root and
profile and return ordinary REFUSED. Likewise a close failure during cleanup
can be followed by successful retry work in the same process without an
ambiguity latch.

Round 175 and the landed profile custody require every close ambiguity to
produce RECOVERY_REQUIRED even if subsequent absence appears clean. Process
exit eventually closing the search handle does not let the current broker claim
an unambiguous mutation history.

### Smallest repair

Pass `ROOT_CUSTODY *` to the four helpers (or return a closed tri-state) and set
`resource_ambiguous` whenever `FindClose` fails. Preserve the attempt to close
on every early-return arm. Every caller after profile/execution mutation must
observe the latch when reducing REFUSED versus RECOVERY_REQUIRED.

Add compiled cases for `FindClose` returning failure in:

- initial parent emptiness and source stream census after profile creation;
- root emptiness/stream and fixed census after ATTEMPTED/mkdir;
- target stream census after a target create;
- PARTIAL and COMPLETE subset census during cleanup; and
- simultaneous census-close plus later handle/resource ambiguity.

The test must prove cleanup is attempted where safe, but the terminal result
cannot reduce below recovery required and no later profile success is reported
as ordinary refusal.

## Finding 2: publication faults do not exercise destructive ordering

`fault-execution-publication` calls `persist_execution_phase` directly. It
proves each publication failure returns false and leaves no pending file, but it
never calls `cleanup_execution`, counts `SetFileInformationByHandle` deletion,
or observes profile cleanup. Its DELETE/ABSENCE setup is the COMPLETE arm.

The actual execution fixture calls successful PARTIAL cleanup after post-mkdir
and short-write failures, but does not inject any of the 12 publication faults
into that cleanup. A mutant that begins deleting the partial root before a
durable PARTIAL DELETE record can therefore pass both suites: direct persist
still fails correctly, while unfaulted cleanup still succeeds. The same split
does not prove that profile deletion waits for execution ABSENCE when DELETE or
ABSENCE publication fails.

The root-ADS case also releases custody immediately after construction refusal;
it does not assert the product leaves the durable ATTEMPTED/root residue intact
without a child/root/profile delete.

### Smallest repair

Reuse the existing fault wrappers inside the production execution fixture:

1. construct one post-mkdir/partial-child ATTEMPTED root;
2. for each PARTIAL DELETE and ABSENCE publication fault, invoke
   `cleanup_execution` and assert zero child/root disposition calls before a
   durable DELETE, no profile-cleanup call before execution ABSENCE, retained
   exact state, and a successful clean retry/reparse;
3. repeat the ordering assertion for first COMPLETE DELETE and durable COMPLETE
   retry, including one target already deletion-proved;
4. for root ADS, assert zero product deletion and retained ATTEMPTED/root; remove
   only the test-injected ADS under fixture authority, then reconstruct and
   complete production PARTIAL recovery; and
5. count child-before-root and execution-before-profile calls rather than infer
   order from final emptiness.

The persist-only `4 x 12` matrix remains useful and need not be duplicated for
all phases. The added integration matrix may target the destructive PARTIAL
DELETE/ABSENCE and COMPLETE ordering boundaries only.
