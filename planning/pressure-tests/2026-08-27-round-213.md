## Production blocker: final terminal proof can cross the watchdog

At `packages/conformance/src/windows-isolation-broker.c:6046-6053`,
`terminal_wait_before_deadline` checks the clock before waiting but returns
success immediately for `WAIT_OBJECT_0`; it performs no post-wait monotonic
check.

More importantly, `terminal_job_zero_before` at lines 6083–6097 executes the
Job query before reading the clock:

```c
int state = terminal_job_zero_state(root, active);
if (state != 0) return state;
```

When the exact Job first reports zero, the function returns success without
checking whether that proof completed before, exactly at, or after 5,000 ms.
The caller then closes workers and can serialize `EXITED`.

This admits a real candidate-controlled timing schedule: root and worker waits
begin just before the boundary, their signals arrive at or after it, and the
first complete Job-zero observation is then accepted after the deadline. The
candidate cannot forge the stable clock, but it controls when its processes and
pipes become terminal. Round 208 requires termination at five seconds and
normal `EXITED` only when the complete root/workers/Job proof occurs within the
same fixed deadline.

The new tick cases do not kill this mutant. Fixture fault 3 returns 4,999 ms
and then freezes every later clock read at 4,999 ms. Faults 2 and 4 expose
5,000/5,001 ms at the initial process wait, before any successful final Job
proof. There is no schedule where earlier waits are in-bound and the final
successful Job proof crosses the boundary.

Smallest repair:

1. recheck the authenticated monotonic clock after each signalled wait;
2. check the clock both before and after a successful Job-zero observation;
3. perform one final monotonic check after every normal EXITED predicate,
   including the exit-code proof, and refuse/backward-clock fail closed;
4. treat elapsed time `>= 5,000` as TIMEOUT, never EXITED; and
5. add schedules where root/workers are observed at 4,999 but Job zero or the
   final exit-code proof completes at exactly 5,000 and at 5,001. Both must
   avoid EXITED, terminate/reprove as applicable, and emit no observation before
   complete terminal proof.

No new timer, thread, protocol field, or journal kind is needed.

## Remaining close/resource deletion gaps

The new close seam has only three role-specific arms:

- one transient failure for the stdin pipe;
- one persistent failure for the stdout pipe; and
- one persistent failure for the stderr thread handle.

`fixture_terminal_close_call` is incremented but never asserted. The case
oracle checks only result, hard-abort, free count, and resource ambiguity; it
does not assert the exact remaining/null pipe and thread owners or close order.
Consequently, role-specific mutants such as skipping the stdin thread, stdout
thread, stderr pipe, or the stdin retry after its one transient failure are not
all distinguished by exact owner census. Hard-abort fixture cleanup also closes
only retained thread handles and output buffers, not retained worker pipes, so
it cannot itself prove which pipe remained owned.

The buffer failure seam is invoked only for the stdout allocation. There is no
independent stderr-free failure. The advertised simultaneous case combines a
persistent stdout-pipe fault with the stdout-free fault, but hard abort skips
buffer release, so the configured free failure is never actually observed.

Complete the bounded evidence promised by Round 212:

- transient and persistent close failure for each of three pipes and each of
  three thread handles;
- exact per-case pointer/handle census and close-call order, proving successful
  retry clears only its exact owner and persistent failure retains it;
- independent stdout and stderr buffer-free failures with the failed pointer
  retained and every safe sibling cleanup attempted; and
- a genuinely simultaneous schedule whose asserted call census proves every
  configured fault was reached, followed by hard abort with no revoke, scratch,
  kind 6/7, OPWX, or OPWJ mutation.

This is deletion evidence for the existing owner model, not a request for a
new cleanup mechanism.
