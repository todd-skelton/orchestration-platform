## Common proposal rows and classification

`requireProposal`, and therefore public `parsePointerProposal`, now admits only
the two exact internally consistent rows:

```text
VALUE_PROPOSED     / SELECT
TOMBSTONE_PROPOSED / REMOVE
```

The existing individual closed enums remain unchanged, and the new pair check
removes their invalid Cartesian product. Both crossed rows,
`VALUE_PROPOSED/REMOVE` and `TOMBSTONE_PROPOSED/SELECT`, fail common parsing.
`classifyProposal` consumes the same `requireProposal` function inside its
total refusal boundary, so each crossed pending-shaped input returns `UNKNOWN`
rather than `PENDING`, `SELECTED`, or `LOST_CONFLICT`.

The focused positive VALUE row is the selected-epoch active-release fixture and
passes common parsing through successful locator validation. The focused
positive TOMBSTONE row uses `TOMBSTONE_PROPOSED/REMOVE`, a registry-derived
TOMBSTONE position domain, a recomputed outcome-only mutation ID, a recomputed
proposal receipt, and a tip that names that receipt; it also passes the generic
one-node locator. This is structural common-CAS success only. The locator still
does not claim that the supplied detached value has the family-specific
tombstone schema or that a family authorizes removal.

The common pair tightening is a fail-closed correction to pre-deployment v1,
not a schema or migration. Proposal members, canonical bytes for valid rows,
`Dr` framing, compatibility version, paths, and valid mutation identities are
unchanged.

## Trusted position-mode mapping

The locator first snapshots the exact four inputs and closed eight-member
expected identity, recomputes `Dp`, and validates the trusted position through
the registered pointer-kind route. It then derives the only allowed selected
proposal row from that already-validated mode:

```text
trusted VALUE     -> VALUE_PROPOSED / SELECT
trusted TOMBSTONE -> TOMBSTONE_PROPOSED / REMOVE
```

This check is distinct from common pair closure. A pair-consistent
`VALUE_PROPOSED/SELECT` proposal remains structurally valid in isolation but
refuses under independently trusted TOMBSTONE position evidence. The focused
attack recomputes the TOMBSTONE position digest, derives a new mutation ID from
that trusted tombstone identity and the attack's `SELECT` outcome, recomputes
the proposal receipt `Dr`, rebuilds the tip with that `Dr`, and therefore
changes the computed `Dt`. It still refuses specifically at
`proposal:position-mode-mismatch`.

Conversely, the valid TOMBSTONE row succeeds under trusted TOMBSTONE position,
and the normal VALUE row succeeds under trusted VALUE position. Crossed
intent/outcome rows never reach this comparison because the common parser has
already made them malformed. The common parser and locator therefore establish
separate boundaries without adding trusted position evidence to the generic
parser or duplicating a family validator.

## Outcome-only mutation identity and coordinated attack

The public `computeMutationId` implementation and its exact ordered frame are
unchanged by this commit. The preimage remains:

```text
pointer kind
canonical pointer path
Dp
transaction ID/null
source token
position digest
nullable prior Dt/Dv/Dr
successor Dv
outcome
```

There is no intent part. Intent is derived from trusted position mode plus the
closed two-row proposal invariant, so adding it would redundantly encode the
same choice and migrate every existing valid mutation identity.

The locator now calls the existing helper with only facts already trusted,
parsed, or recomputed at its four-input boundary:

- the exact closed trusted identity and registered position;
- the parsed proposal's complete-or-null prior `Dt/Dv/Dr`;
- the recomputed successor `Dv` under the trusted pointer kind and `Dp`; and
- the admitted proposal outcome.

It requires the resulting exact identity equal `proposal.mutationId`. No caller
expected mutation ID, fifth input, mutation-addressed lookup, index, or fallback
is introduced.

The coordinated Round 144 attack was executed in the focused suite. It replaces
the valid proposal mutation ID with an arbitrary lowercase SHA-256, recomputes
the exact proposal receipt `Dr`, puts that `Dr` in the supplied tip, and thereby
causes the locator to recompute the attacker's coherent `Dt`. Every other
trusted identity, position, prior, successor value, producer, and tip member
remains valid. The result is `{ ok:false }`; deleting only the new mutation-ID
equality changes that result to `{ ok:true }` and fails the focused assertion.
Thus refusal is not caused by a stale proposal receipt, stale tip, malformed
digest, partial prior, or wrong mode.

Valid existing mutation-ID goldens remain green, and the production diff does
not alter the helper input census, domain, part order, or final outcome-only
part. The fixture repair replaces its former arbitrary mutation ID with the
exact helper-derived value rather than changing an identity formula.

locator reads trusted position mode only after the registered common position

new comparisons remain inside the existing total refusal boundary.

Outer hostile input and hostile values independently placed in expected
