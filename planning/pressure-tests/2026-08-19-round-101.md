## The direct value is exact and minimal

The value has no nested proof or standalone digest family. Its canonical
members are:

1. `independentReviewReceiptDigest: sha256`;
2. `installedBytesDigest: sha256`;
3. `releaseDigest: sha256`;
4. `releaseManifestDigest: sha256`;
5. `releaseSubjectDigest: sha256`;
6. `reviewedInstallerDigest: sha256`; and
7. `schemaVersion: active-release/v1`.

That census is sufficient to connect the selected pointer value directly to
the already-reviewed release facts without introducing another record or
digest. `releaseDigest = releaseSubjectDigest` is an intentional semantic
equality, not two alternative identities. The former selects the immutable
directory `releases/<releaseDigest>/`; the latter directly names the reviewed
operation/core subject. The independent installed-tree read-back remains a
separate `installedBytesDigest`, so a matching directory/subject identity
cannot substitute staging bytes or a different installed tree.

For N0, E0 independently requires:

- release and subject to equal each other and the reviewed operation and
  successor core's reviewed subject;
- manifest to equal the reviewed operation and successor core manifest;
- installed bytes to equal the reviewed operation and successor core installed
  read-back;
- independent review to equal the reviewed operation and successor core
  review; and
- reviewed installer to equal the exact bootstrap operation's reviewed
  installer.

Because the operation is already required to be the anchor-bound
`BOOTSTRAP_INSTALL` arm and is recomposed into `Dsc`, moving all six value
members together does not create a caller-controlled island. Each comparison
has an independently parsed side already present in the E0 composition.

## Pointer identity, position, and persistence are stable

The active-release `Dp` is fixed by the existing common pointer formula over:

- kind `ACTIVE_RELEASE`;
- canonical path `installation/active-release.json`;
- the exact installation ID, project ID, and state-root digest;
- `transactionId` equal to the installation ID; and
- source token `none`.

Using the installation ID as the transaction component deliberately makes the
instance stable across bootstrap and promotions. Individual promotion
transactions therefore cannot split the authoritative pointer. Their mutation
identities still change through the common position/prior/successor inputs.

VALUE position evidence is exactly the closed record
`{ "mode": "VALUE", "parts": {} }` under
`active-release-position/v1`. The common mutation formula consequently derives
one exact mutation ID from the stable identity, empty position, prior triple,
successor `Dv`, and `SELECT`. The value and proposal use the common constructed
`Dp`/mutation paths; the only selected tip is
`installation/active-release.json`; immutable release bytes live only at
`releases/<releaseDigest>/`. The existing registry template and the new ledger
agree on all roots and paths.

## N0 and E0 remain acyclic

The required N0 dependency order is:

```text
reviewed BOOTSTRAP_INSTALL operation -> Dop -> Dsc
active-release value -> active-release Dv
Dsc + active-release Dv + null prior/epoch -> active-release proposal/Dr
active-release Dv/Dr -> active-release tip/Dt
selected active-release Dp/Dt/Dv/Dr -> E0 authority value/Dv
E0 authority Dv + existing upstream genesis facts -> Dbg
Dbg -> E0 authority proposal/Dr -> E0 authority tip/Dt -> Dgp
```

The active-release value does not contain `Dsc`, its own `Dv`, proposal, `Dr`,
tip, or `Dt`. Bootstrap `Dsc` does not contain the active-release graph. It can
therefore be the active-release proposal's reviewed-bootstrap producer without
a reverse edge. The E0 authority value contains only the already-selected
active-release quartet, while `Dbg` remains downstream of that value and
upstream of the E0 authority proposal. No digest requires itself, directly or
through the other pointer.

The implementation must derive rather than accept:

- the active-release `Dp` from the literal identity;
- `Dv` from the parsed seven-member value;
- the empty VALUE position digest;
- the mutation ID from the null prior and successor `Dv`;
- `Dr` from the actual proposal;
- `Dt` from the actual tip;
- N0's null prior and authority-epoch branches; and
- `producerDigest = Dsc` from the actual parsed operation and successor core.

It must then compare the authority value's four active-release members to that
derived selected graph. Retaining the old four-digest expectation as a second
authority source would violate the decision; replacing it with the actual
records is part of the authorized slice.

## Stable N still promotes N+1

The new bootstrap producer allowance is closed to exactly the initial
`ACTIVE_RELEASE` selection and the already-existing initial authority
selection. A later active-release mutation cannot reuse it: later proposals
require `SELECTED_EPOCH`, a complete prior selected triple at the same stable
active-release `Dp`, and a complete selected authority-epoch triple.

This preserves the established live-authority boundary. Structural records do
not grant mutation authority; ISS-004's lock-scoped private producer projection
comes from the selected stable predecessor epoch. Thus N+1's candidate bytes,
verdict, or self-reported review cannot select N+1. Stable N selects the
successor active-release graph first; the existing `STABLE_PROMOTION`
operation then binds predecessor and selected successor active-release
`Dp/Dt/Dv/Dr`, independent review, manifest, installed bytes, and release
subject before authority rotation grants N+1 an epoch.

The ledger intentionally does not authorize the cleanup gate, recovery fence,
cleanup archive, or full later-promotion lifecycle schemas. That explicit
boundary is not an ambiguity in this slice. The bounded implementation may
parse the common seven-member value and enforce the closed bootstrap-versus-
selected-epoch proposal branches, but it may not invent a later installer
receipt, operation field, producer digest meaning, lifecycle receipt, or
runtime capability. Those remain with their named later ledgers and producers.
