## Exclusive candidate materialization custody

The repaired order has one unambiguous authority direction:

```text
adapter-authenticated Dsubject
  -> stable opened-handle copy into a fresh external child
  -> stable handler consumes that child into an external execution artifact
  -> verified child cleanup
  -> candidate artifact launch
  -> untrusted observation only
```

This is constructible on Linux, macOS, and Windows. Before the final arrow,
the stable wrapper has started no candidate or other untrusted same-principal
process. It can therefore create a fresh external parent, retain and recheck
the parent/root identities, open only regular non-link candidate files, bind
the read handles and copied bytes to every `Dsubject` row, and let the stable
handler produce the external artifact. For the initial `ISS002_CONTRACTS`
handler, the already-present stable confined bundler demonstrates the credible
artifact shape: a stable-produced ESM bundle rather than execution from either
checkout or copied source tree.

The custody claim is temporal stable-runner exclusivity, not a false claim that
filesystem ACLs distinguish two processes running as the same OS principal.
That is why the child must be consumed and removed before the first untrusted
process exists. Candidate argv, environment, working directory, evidence, and
output expose only the consumed artifact, not either source materialization.
The source child no longer exists when candidate code starts.

Partial copy, a missing/extra/escaped destination, changed source/root/parent
identity, movement during a handle read, an unconsumed child, recursive cleanup
through an unverified ancestor, or cleanup failure all terminate before launch.
There is no useful best-effort cleanup arm: inability to prove removal is a
refusal. This is deletion-grade for the in-scope threat because the architecture
does not start an untrusted same-principal competitor until after successful
deletion; it does not pretend to provide hostile concurrent same-user isolation.

Executable mode remains portable and adapter-authoritative. `Dsubject` obtains
its boolean only from authenticated GitHub adapter tree rows using the closed
`100644 -> false` and `100755 -> true` projection. A checkout's POSIX mode or
Windows local-file attributes never re-authenticate or alter that value. The
initial Node handler launches the stable-produced artifact explicitly and does
not depend on a local executable bit. Any later reviewed stable handler that
needs executable semantics must derive them from the authenticated boolean;
unknown type/mode, symlink, submodule, local-mode substitution, or truncated
tree remains a refusal. Git and GitHub terms stay in the adapter; the core sees
only the portable boolean and opaque digest.
