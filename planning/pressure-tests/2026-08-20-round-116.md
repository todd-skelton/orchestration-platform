## Blocking findings

### 1. Root/head lookup and first-ever lineage are not constructible

The ledger says a full history is fetched by selected/common value digests and
walked from a supplied dense bounded array, without directory enumeration. The
common persistence contract instead stores values and proposals at
`installation/pointer-cas/<Dp>/values/<mutation-id>.json` and the corresponding
prior/genesis proposal bucket. The selected `pointer-current-tip/v1` exposes
`Dp`, `Dv`, and `Dr`; it does not expose the mutation ID, transaction ID,
`rootDigest`, ordinal, prior triple, or a value/proposal locator. `Dv` and `Dr`
are hashes and cannot be inverted into those missing path inputs.

This is especially visible at the canonical installation-scoped gate/fence
tips. The immutable roots are transaction-addressed, but the selected tip
contains only the hashed `Dp`; a cold reader cannot recover the transaction
component needed for the root path. Even if a caller independently supplies
the transaction and root, `recordedAt` is not deterministic, so it cannot
reconstruct the selected head bytes, `Dv`, or mutation ID to locate the
current value. A caller-supplied dense history is valid input to a pure
validator, but it is not a durable lookup rule and does not prove where the
actual selected bytes came from.

The BOOTSTRAP cleanup-archive null arm has the same unresolved recovery
boundary. It is allowed only when the canonical archive head has never been
selected; after a first selection, bare absence is permanently unavailable
and loss must be `UNKNOWN`. No named durable evidence in this ledger
distinguishes first-ever absence from a missing/corrupt FULL_REQUIRED selected
archive, and the deferred archive ledger does not yet supply that evidence.
The phrase “current selected cleanup-archive-head” also does not decide whether
a current archive-pointer tombstone is the required lineage arm. Accepting
filesystem absence, a caller Boolean, or a copied prior expectation would
silently weaken the fail-closed rule.

The smallest bounded remedy is to do one of the following before runtime
lookup is authorized:

1. decide one generic, verified common-CAS lookup from the selected tip to the
   exact value/proposal bytes and the transaction-addressed root, including
   deletion/loss handling and no enumeration; or
2. narrow this slice explicitly to pure validation of already-supplied closed
   bytes, remove the claim that `Dv` fetches persisted history, and defer all
   persistence/discoverability authority to that separately reviewed common
   lookup decision.

In either shape, the later archive ledger must name the exact selected-evidence
arm that proves first-ever versus prior archive/tombstone lineage. A second
authority tip, latest-file convention, unauthenticated index, directory scan,
or proof tree is not required.

### 2. Composed proof selection still requires undefined bytes

The decision explicitly defers the recovery-authorization and cleanup-archive
literal ledgers and their composed equality matrices. The current
`credential-broker.md` authorization core supplies conceptual field lists but
not literal JSON member names, mode-arm presence/absence, or a complete parser
ledger. The cleanup archive is likewise undecided. The new gate/fence section
nevertheless authorizes “pure relative composition,” the ISS-002 draft permits
composition validators, and compatibility requires branch-only proof absence
and independent/coordinated upstream substitutions.

Those validators cannot be implemented without choosing an input contract.
The root prose requires authorization core/CREATED, release, archive, fence,
admission, generation, and `Dsc` equalities, but does not give a closed
non-persisted composition census or an exhaustive proof matrix for the twelve
gate edges and ten admitted cells. Phrases such as “transition-specific
terminal/absence facts” and “exact branch terminal facts” do not select the
actual records required for each transition, or which branch-only records must
be absent. A coordinated attacker can rebuild a root and caller expectations
around the same substituted digest unless the validator is required to parse
and select a separately authenticated actual upstream graph; the deferred
schemas are the missing source of that fact.

Three boundary ambiguities make the implementation choice observable:

- `PUBLISHED` requires a PREPARED fence “before the gate head time,” but the
  ledger does not decide strict `<` versus non-strict `<=`; equal millisecond
  timestamps are possible under the global timestamp grammar.
- `ABORTING` says the active release still selects the predecessor, while a
  BOOTSTRAP root requires its predecessor active-release triple to be null. It
  does not state the exact bootstrap active-release absence/selection input
  for the pre-mutation abort arm.
- `COMPLETE` refers to exact branch terminal facts without assigning the
  bootstrap post-E0 completion, successor activation, and four abort
  publication paths their exact required and forbidden proof sets.

The smallest remedy is to remove composed root/gate/fence validation and its
upstream-substitution acceptance claims from this slice. Authorize only the
four structural parsers, two root digests, exact VALUE-position parsers, common
`Dv` head validation, and bounded relative history walking over supplied
records. Add the closed non-persisted composition input census, exhaustive
cell/edge proof matrix, equality sources, and exact `<`/`<=` rules alongside
the recovery-authorization and cleanup-archive literal ledgers. The strictly
larger alternative is to decide those composition inputs now; no proof bundle
needs to be restored inside a selected head.
