## 2. Bounded slice definitions

Recommended split, per Decision #282 Ruling 1: **two source packets plus one
closing census round**, sharing one sub-slice registration.

- **Slice C — fresh observed-protection typed parsing** (parse-phase only).
- **Slice D — the pure four-input binder** (relation phase + public surface).
- **Slice E — ISS-054 acceptance census and closure** (planning-only).

Rationale for the C/D split rather than one packet: it is the same phase gate
Decision #268 bound 2 made mandatory and Decision #272 re-affirmed — parse to
typed values first, relate only over typed values second. A single packet
would reintroduce exactly the interleaving that produced the five known
failure instances. It also keeps each artifact inside one reviewer's working
set: C is ~400-550 new parser lines plus vectors, D is ~350-450 relation lines
plus vectors; a combined packet would be ~900 source lines and ~2000 test
lines in one review.

## 3. The phase gate extends; the structural gaps and the deliberately open clause

### 3.1 The C/D split is the same Round-451 gate

Round 451's rule set is: (i) snapshot each root once with the
hostile-reflection primitive; (ii) every child record has its own parser
returning `ParseResult<SpecificRecord & ContractRecord>`; (iii) never
construct a parent whose child failed; (iv) no cross-record read, `.find`,
dereference, projection or digest before the gate; (v) in the relations
packet, no fragment parser, raw-object cast, non-null assertion over raw
input, or caller-asserted typed fast path (round-451:398-400, 246-247,
159-172). The fresh observation is structurally a receipt-shaped tree
(records, dense bounded arrays, union page branches), so (i)-(iv) apply
unchanged; the binder is pure cross-record relation work, so (v) applies
unchanged. Slice C is the phase-one analogue of Packet A and Slice D the
phase-two analogue of Packet B. Round 451 itself anticipates this: "Fresh
`observedProtection` and the four-input receipt/anchor binder remain
separate later slices with their own records after Packet B lands"
(round-451:101-103), and its attack list already names "closing ISS-054
before the later fresh-observation and binder records land"
(round-451:539).

### 3.2 Structural gap 1 — the anchor is typed by a whole-tree cast (Ruling 2 waives repair)

`packages/contracts/src/verifier-anchor.ts:168` returns
`{ ok: true, value: record as BootstrapVerifierAnchor }`, where `record` is
the `ContractRecord` (`Readonly<Record<string, JsonValue>>`,
`packages/contracts/src/runtime.ts:7`) produced by `snapshotClosedRecord`.
The nested `assets`, `signerWorkflow` and `operatorConfirmation` rows are
validated in place but are never returned as typed children — the declared
type is an assertion over raw `JsonValue` members.

Two facts bound the severity, both re-verified against this record's exact
head:

- **Detachment is sound.** `snapshotClosedRecord` delegates to
  `snapshotJson`, which recursively snapshots and freezes the whole tree and
  refuses proxies, accessors, non-enumerables and traps at every depth
  (`packages/contracts/src/runtime.ts:102-113, 157-178`). So the anchor's
  hostile-reflection posture is correct; the gap is type-level only.
- **Every field the binder reads is in fact validated before `ok: true`.**
  `repositoryId` (`verifier-anchor.ts:115`), `createdAt` (`:116`),
  `signerWorkflow.repositoryId` (`:146-148`, including the equality to the
  top-level ID), `operatorConfirmation.confirmedAt` (`:163-164`, including
  `confirmedAt <= createdAt`). The cast is justified in fact, but not by
  construction — precisely the defect class Decision #268 bound 2 names.

Decision #282 Ruling 2 resolves the question this raised (waive vs. repair
vs. separate slice) as **A: waive**. Slice D consumes the landed anchor
parser as-is; its review packet must state exactly which fields it reads and
where each is validated (the four citations above). If a Packet D reviewer
BLOCKs on the cast, a separate two-file repair slice with its own review is
the bounded follow-up — not footprint growth inside D.

The anchor implementation already exposes a parsed type usable today:
`VerifierAnchorAsset` and `BootstrapVerifierAnchor` are exported
(`verifier-anchor.ts:43, 53`) and `parseBootstrapVerifierAnchor` returns
`ParseResult<BootstrapVerifierAnchor>` (`:101`); it is produced by assertion
rather than by typed-child construction, which is exactly what Ruling 2
waives.

### 3.3 Structural gap 2 — reuse boundary in Packet A (favourable)

Packet A's row-level `parseHistoricalApiObservation`
(`repository-protection-parse.ts:1275`) is purpose-agnostic: it parses the
purpose, dispatches the request branch, parses pages, and requires
`triggeringBuild` non-null exactly when the purpose is `WORKFLOW_RUN` and
literal null otherwise (`:1290-1299`). It is therefore **directly reusable
for fresh rows with no edit**. Only the array-level census is
historical-specific: `parseHistoricalApiObservations` (`:1361-1377`) fixes
the length to `repositoryProtectionPurposes.length` (nine) and asserts the
ordered nine-purpose census. Slice C adds a sibling six-purpose array parser
and reuses the row parser. `parseEnvironmentBinding` (`:1419`) is reusable
verbatim — the fresh binding has the identical five-member census and the
identical literal names (6889-6890, 6788-6790). `parseRulesetSemantics`
(`:1494`) already covers the exact five-member semantic subset the fresh
observation carries. This is why Slice C is a four-file append rather than a
new module.

### 3.4 Structural gap 3 — is `apiTerminals` a parsed record or a derived projection?

The ledger states the `apiTerminals` row census (6896-6898) as part of the
terminal-evidence recipe, not as a member of `observedProtection`
(6879-6882). So the projection is **derived by the binder** from the fresh
observation's own rows, not supplied. **Not established** whether a public
helper analogous to `computeGitHubApiTerminalPaginationDigest` should also
accept a supplied `apiTerminals` array; if Slice D exports such a helper it
must, under the phase gate, own a typed parser for that row — which would
move the `apiTerminal` kind into Slice C. **Recommendation: do not export a
standalone terminal-evidence helper that accepts a supplied projection**;
derive it inside the binder only, and keep the `apiTerminal` kind out of
Slice C. If Todd or a reviewer wants the standalone helper, it moves to
Slice C's census and Slice D's export list.

### 3.5 The deliberately open clause D must pin with a positive

The ledger requires fresh page times to lie within
`observedProtection.startedAt..completedAt` and says explicitly "rather than
before receipt issue" (6887-6888). Combined with `issuedAt <= evaluatedAt`
(6927) and `evaluatedAt == completedAt` (6891-6892), a fresh window that
starts slightly before `receipt.issuedAt` and ends at or after it is
**admitted**. The ledger states no
`observedProtection.startedAt >= receipt.issuedAt` relation. Slice D must
not add one, and Slice D's vectors must include a positive that straddles
`issuedAt` so a later lane cannot silently tighten it. This straddle
positive is carried in §2.2's acceptance evidence above and remains
**not established** as a closed question beyond "do not invent the missing
relation" — the ledger simply does not require it, and D's job is to prove
that non-requirement with a passing vector, not to resolve it further.

### Flagged judgment calls

1. **The receipt's mapped parser is Packet B's public
   `parseRepositoryProtectionReceipt`, not Packet A's structure-only
   `parseRepositoryProtectionStructure`.** Section 2.2 names "Packet A for the
   receipt"; Packet B's parser invokes Packet A's first
   (`repository-protection.ts:616`) and then adds the receipt's own relations,
   so this is the strongest available typed parser and the phase gate holds a
   fortiori. Using the structural parser alone would let a receipt with an
   unbound `rulesetSemanticDigest` reach the binder and would force the binder
   to re-implement Packet B's relations.
2. **Fresh row times stay unbound to the root window (review observation O2).**
   6887-6888 scopes the fresh window to page times, and no ledger clause binds
   a fresh row's own `startedAt`/`completedAt` to it. The binder reads fresh
   row times for nothing and no digest frames them, so a row declaring times
   outside the root window is committed as a positive rather than refused by
   an unstated relation.
3. **The page-chain and derived-digest relations are re-expressed in this
   module rather than shared with Packet B.** Packet B's equivalents are module
   private and its public helpers throw on refusal, which the binder may not
   catch; `repository-protection.ts` is outside the six-file footprint. The
   duplication is therefore forced by the footprint, and a later extraction of
   the shared relations into a helper module is a bounded follow-up, not
   Packet D's work. It is the main reason the module is 743 lines rather than
   the 350-450 section 2.2 predicted.
4. **`completeReductionDigest` is recomputed for fresh rows.** Section 1.3
   does not list it explicitly, but 6884-6885 states that fresh rows use the
   identical formulas, and leaving it unchecked would let a fresh row enclose
   an unbound reduction. It is a within-row recomputation, not a
   historical/fresh equality, so it adds no over-binding.
