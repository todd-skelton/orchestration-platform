## Round 144 blocker removal verification

### OP-R144-1 — mutation ID is now derived and equal-bound

The repaired authority requires the locator to recompute
`proposal.mutationId` from only already-trusted or already-recomputed facts:

```text

```

It then requires exact equality to the selected proposal member. The result no
longer treats a well-formed SHA-256 supplied inside the proposal as its own
authority. The Round 144 coordinated attack—replace only `mutationId`, recompute
`Dr`, tip `proposalReceiptDigest`, and `Dt`—is named directly in acceptance item
11 and the deletion matrix.

No caller-supplied expected mutation ID, mutation-addressed lookup, fifth input,
producer proof, or current-tip reader was added. The existing four inputs
already contain every recomputation part. This is the smallest credible repair.

### OP-R144-2 — outcome-only framing and order are exact

The exact mutation-ID table now ends in one `outcome text` part. The adjacent
prose expressly says intent is not a second mutation-ID part. The complete
ordered preimage is therefore:

```text
pointer kind text
canonical path text
Dp raw32
```

That matches the current `computeMutationId` input census and framing order.
The former `outcome/intent` ambiguity is gone. The proposal `Dr` remains

proposal bytes. No digest domain or part changes for any valid existing
mutation, so no migration or golden rewrite is authorized.

Omitting intent from mutation ID is proportional. Trusted position mode derives
intent exactly, and the outcome text distinguishes SELECT from REMOVE. Hashing
intent again would duplicate the same operation choice and silently change all
valid mutation identities without closing an additional threat.

## OP-R145-1 — crossed proposal pairs remain valid to the public parser

The common proposal parser currently validates the two intent literals and the
two outcome literals independently. Except for the special reviewed-bootstrap
branch, it does not validate the exact two-row union. A cold selected-epoch
attack supplied a closed recovery-authorization proposal with:

```text
intent = VALUE_PROPOSED
outcome = REMOVE
```

All other fields were valid, including complete prior and selected-authority
epoch triples. Exact observed results were:

```text
parsePointerProposal(crossedProposal) -> { ok: true, ... }

classifyProposal({
  proposal: crossedProposal,
  selectedTip: null,
  selectedValue: null,
  selectedProposal: null,
  conflictReceipt: null
}) -> PENDING
```

The symmetric `TOMBSTONE_PROPOSED/SELECT` branch is admitted by the same parser
logic. These are not merely wrong for one caller's trusted position. The pair
itself is contradictory under the now-explicit common contract: VALUE intent
means ordinary selection and TOMBSTONE intent means removal.

This matters before a selected locator call. `parsePointerProposal` is a public
contract entry point, and `classifyProposal` is the common pre-CAS/recovery
classification API. The incorporated supervisor ledger says malformed,
contradictory, skipped, or fake-lost evidence is `UNKNOWN`. Reporting a crossed
record as `PENDING` may cause a lock holder to treat it as a resumable proposal
rather than refuse the invalid mutation.

Locator-only validation is necessary but insufficient:

- the common parser must reject `VALUE_PROPOSED/REMOVE` and
  `TOMBSTONE_PROPOSED/SELECT` without needing position evidence;
- the locator must separately bind the surviving pair to independently trusted
  VALUE/TOMBSTONE mode, rejecting even a pair-consistent tombstone proposal
  under trusted VALUE mode and vice versa.

The repaired authority states the second responsibility exactly. It does not
assign the first to the common parser, does not add parser/classifier evidence,
and does not widen the predicted locator footprint from "three constructors and
one validator." An implementation that changes only the locator therefore
satisfies the literal repair while leaving the public compatibility
contradiction intact.
