## Blocking production findings

### 1. Output-allocation failure loses live pipe ownership

At `windows-isolation-broker.c:6142-6152`, `create_terminal_workers` allocates
the stdout and stderr 4 MiB buffers before copying the three runtime pipe
handles into their worker owners. If either allocation returns null, it returns
with every `worker.pipe` still null.

`run_active_terminal` then calls `terminal_kill_and_join`, whose
`terminal_close_workers` at lines 6114–6127 closes only non-null worker pipes
but unconditionally sets:

```text
runtime.stdin_write = NULL
runtime.stdout_read = NULL
runtime.stderr_read = NULL
```

The original three handles were neither closed nor retained. Later runtime
cleanup cannot see them. A clean kill can therefore return ordinary refusal,
wait for TEARDOWN, and ultimately rely on process exit to close untracked
handles while claiming exact cleanup. This violates the single-owner handle
boundary and can also retain pipe ends across the response/teardown interval.

Required repair:

1. establish one explicit owner for every pipe before any fallible allocation/
   thread creation, or transfer ownership only after all allocations succeed;
2. never null a runtime handle unless that exact handle was transferred or
   successfully closed; and
3. on every partial allocation/creation prefix, close or retain all three
   pipes, free every successfully allocated buffer, and prove no duplicate or
   lost owner.

The fixture `HeapAlloc` seam currently cannot inject either terminal output
allocation failure, and `fixture_admission_terminal_matrix` does not cover it.

### 2. A nonterminal worker can race closed/freed context

At lines 6091–6139, `terminal_join_after_kill` records a failed/timeout wait but
returns to `terminal_kill_and_join`, which still calls
`terminal_close_workers`. `run_active_terminal` then calls
`release_terminal_buffers` even when the join failed.

Each worker context lives inside the stack-owned `ACTIVE_ADMISSION`; reader
threads retain pointers to their output buffer and worker fields. If a worker
wait is ambiguous or times out, the current code may close a pipe while that
thread uses it, free its output buffer, return through the stack frame, and
continue descriptor/profile reversal. That is a use-after-free/lost-custody
path in the stable native authority. Marking `resource_ambiguous` after doing so
does not make it fail closed.

Required repair:

1. no worker context, pipe, buffer, thread handle, `ACTIVE_ADMISSION`, DACL, or
   profile state may be released/mutated until every created worker thread is
   trusted-terminal;
2. after Job termination, actively unblock pipe I/O under a single-owner rule
   and join every worker; and
3. if root/worker/Job terminal proof remains ambiguous, take a fixed production
   hard-abort path that sends no success/refusal response, performs no DACL/
   execution/profile reversal, and exits the broker while durable OPWL phase 5
   plus kill-on-close preserve recovery authority. The OS may reclaim process
   memory/handles; normal C cleanup may not touch live worker state.

The hard-abort must be fixture-seamed only below production options, directly
exercised for each process/worker wait failure, simultaneous failures, Job kill
failure, and Job-zero query ambiguity, and must leave phase 5 for tracked
`RECOVER` to finish.

### 3. Live and recovery reversal ordering contradicts Round 208

`revoke_active_admission` at lines 5827–5867 persists
`ADMISSION_REVOKE_ATTEMPTED` before calling `terminate_admission_job`. In the
terminal arm it then restores root/files, proves 28 AccessCheck denials and 28
actual-open denials, proves scratch absence, and only afterward calls runtime
cleanup to close the retained impersonation/process tokens and process/
attribute handles.

The authorized terminal order is:

```text
trusted root/workers/Job terminal
-> terminate/reprove Job zero and named absence
-> durable kind 6
-> root-first then three-file restore
-> exact 28 AccessCheck + 28 actual-open denials
-> close/prove every token/process/thread/pipe/attribute handle
-> scratch absence
-> durable kind 7
-> OPWX cleanup
-> OPWJ cleanup
```

Current code is instead `kind6 -> Job -> restore -> denials -> scratch ->
handles -> kind7`. `recover_admission` at lines 7049–7089 likewise persists
kind 6 before `OP_ADMISSION_RECOVERY_JOB` for phase 1–5. OPWL phase 5 already
owns safe Job termination; a crash after Job zero but before kind 6 simply
repeats the phase-5 Job proof during recovery. No new journal kind is needed.

Required repair:

- apply the exact order above to live terminal teardown;
- for recovery from phases 1–5, authenticate the whole record set, terminate/
  prove the Job first, then append kind 6 before descriptor reversal; phase 6
  still rechecks Job absence before restore;
- retain old pre-resume refusal semantics only where their existing Round-198
  cleanup intent requires them; do not weaken the admitted terminal path; and
- make the compiled order log observe Job proof, both persistence barriers,
  root/file restore, all 56 denial calls, each runtime close, scratch, OPWX,
  and OPWJ. Counts alone are insufficient.

`fixture_admission_live_revoke_matrix` currently asserts two phase numbers,
28/28 counts, and one cleanup/restore count, but the fake cleanup/restore
functions do not append the decisive call order. It therefore approves the
inverted production sequence.

## Required executable evidence missing from the current tree

The current exact-source terminal matrix executes only a one-byte clean run, a
timeout, and `ResumeThread` returning zero. Its fake `WriteFile`, `ReadFile`,
`CreateThread`, `GetTickCount64`, and `HeapAlloc` paths mostly delegate to the
real APIs and provide no terminal fault schedule. It does not satisfy the
Round-208 deletion fence.

The repaired fixture must directly execute real production terminal functions
for at least:

- challenge length 0, 1, exact 4 MiB, and over-bound through parsing and worker
  write, with every chunk partition needed to distinguish partial progress;
- stdin partial writes, zero progress, early `ERROR_BROKEN_PIPE`, other write
  failure, complete write, and exact close result;
- stdout and stderr independently at 0, 1, exact 4 MiB, and 4 MiB + 1, with
  short reads, arbitrary chunks, true zero, broken-pipe EOF, other read error,
  overflow-latch-then-drain, and no truncation success;
- each output allocation failure, each of three thread-creation prefixes,
  thread-ID zero, wrong/duplicate handles, each pipe/thread close, each buffer
  free, and simultaneous resource failures under the repaired owner model;
- exact single `ResumeThread`, returns 0/1/>1/failure, wrong thread, and proof
  all three workers exist before the call;
- deadline before/at/after 5 seconds, backward clock, wait failure, root-first/
  pipe-first/Job-first terminal orders, `STILL_ACTIVE`, exit-query failure,
  Job accounting/list mismatch, incomplete/duplicate/overbound PID lists, and
  no TIMEOUT response before post-kill root/workers/Job zero;
- the nonterminal hard-abort path for every root/worker/Job ambiguity, proving
  no restore, scratch, kind 6/7, OPWX, or OPWJ mutation occurs before process
  exit and that subsequent RECOVER succeeds;
- exact EXITED and TIMEOUT response bytes, both stream lengths/order, all
  reserved bytes zero, each invalid kind/timeout-field/bound/length relation,
  candidate bytes beginning with `OPWB`, short/zero broker writes, and response
  buffer/free ambiguity; and
- outer PREPARE/LAUNCH/terminal-response/TEARDOWN sequencing: parent EOF,
  duplicate/reordered/nonzero/trailing frames, response-before-TEARDOWN, no
  result/status selected by candidate bytes, and cleanup on every control-loss
  point.

The real opt-in diagnostic encoded in the tree is useful but incomplete. It
contains canonical success, a root hang, a detached descendant with ignored

must additionally execute a descendant that retains an inherited output pipe,

RECOVER boundary. The opt-in run remains complementary; it cannot replace the
compiled allocation/resource/order mutants.

I did not rerun the mutating AppContainer diagnostic because the production
