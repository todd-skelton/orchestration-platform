## Context and evidence

Todd's adopted ruling #323 prioritizes a supervised useful run before release
certification. ISS-041 has exercised the journal and step boundaries using an
echo child and stub review; it deliberately excludes real worker dispatch.
ISS-026 and ISS-021 still own the production engine and worker-host contract.
This issue supplies the missing real-use learning outcome without pretending
those production capabilities or the M3 release are complete.

## Scope fence

In: a small portable pilot flow and explicit adapter to the existing launcher;
one controller-selected improvement to this orchestrator repository and confined
worktree; real author dispatch,
observation, distinct exact-head review, controller-published PR, exact-head
hosted CI observation, and restart without duplicate dispatch. Follow
`docs/planning/supervised-dogfood.md` for authority and handoff boundaries.

Out: promotion, merge authority, new credentials/provider protection, native
lock selection, automatic lease takeover, full production engine or broker,
general plugin system, copying/importing fixture code, and cross-host live
claims from a single-host trial. No task-specific policy belongs in the flow.

## Acceptance criteria and evidence

1. One real low-risk improvement to this orchestrator repository completes
   author -> independent reviewer ->
   hosted CI -> ready at the same exact head. The retained report links the
   issue, selected base/footprint, pilot revision, real attempt identities,
   reviewer disposition, PR head and checks. Echo workers or stub approvals
   may support tests, never the live acceptance evidence.
2. Restart while an attempt is being observed and again after readiness emits
   the same identities and no new author/reviewer launch or PR publication.
   A separately tested uncertain intent-to-launch interval blocks instead of
   retrying. Prove actual launch counts; do not infer them from status text.
3. Wrong-head review/CI, author-as-reviewer, missing terminal evidence, absent
   required checks, conflicting run ownership and out-of-footprint changes
   yield named blocked/failed results. Readiness cannot grant merge authority.
4. All runtime records and logs stay outside the source checkout. Only the
   supplied worktree may receive the selected work item's authorized edits.
   Existing launcher ownership and credential isolation remain authoritative.
5. Hosted macOS/Windows/Linux tests exercise the portable flow and adapter
   boundary. A live adapter preflight records availability and actual host;
   unavailable adapters refuse before launch. Windows launcher paths stay in
   the adapter configuration, never in the portable core.
6. One concise learning record identifies the next change justified by the
   run. No release/promotion or other issue completion is inferred.

## Verification plan

Run the four local gates: `pnpm typecheck`, `pnpm format:check`,
`pnpm planning:check`, `pnpm planning:board-check`. Independently review the
exact candidate including every changed assertion. Require intended tests to
execute in hosted three-OS bootstrap. Use targeted bare-Node reproductions only
for an identified uncertainty; no local test runner or native execution.

Tests use discovered `test/dogfood/*.test.ts` paths. Invoke the future pilot
directly with `node scripts/dogfood/run.mjs` and documented explicit arguments;
no root command is registered or activated by this planning change. Retain a
real trial transcript separately from fixture test output. Review is never
self-certification, and the existing controller publishes/merges independently.

## Predicted footprint and dependencies

Implementation: `scripts/dogfood/**` for the small flow and configured launcher
adapter, `test/dogfood/**` for discovered tests and bounded fixtures, this draft,
the supervised-dogfood plan's invocation section, and one pressure record.
No new workspace package or top-level `probes/` directory: #321 is not a hidden
dependency. No root-script, registry, schema or credential-store change.

ISS-041 is the completed prerequisite providing boundary/divergence evidence;
its code is not imported. There is no dependency on N0 certification, CF-2,
CF-8 or native mechanism selection. Existing launcher capability/ownership is
a runtime preflight, not a claim that the production ISS-021 adapter exists.
If its real API cannot support observation/restart, first name the smallest
concrete seam repair; do not quietly grow this into a replacement launcher.

## Operator actions

The existing controller explicitly selects the live issue, allowed diff,
worktree, launcher configuration and bounded attempts; it publishes the PR
and retains merge authority. No new credentials or provider settings. Any
additional privilege or irreversible operation requires a separate ruling.

## Independent review packet seed

Attack fake live evidence, wrong-head approval, hidden second dispatch after
crash, an empty CI check set treated as green, fixture imports, controller
replacement, local records used as public authority, and unavailable host
support misrepresented as portability. Check the real launcher seam before
building abstractions around assumed output.

## Falsifiable prediction and review-by horizon

One configured launcher adapter and one sequential pilot flow suffice to run
a useful issue without the capture/protection/promotion subsystem. Reassess at
the first live run or first concrete capability blocker. A requirement for
multiple new contract families or another controller falsifies this plan and
requires a smaller consumer-first replan, not silent scope expansion.

## Non-completion claims and glossary

No new public vocabulary or authority family. This plan is not implementation,
live execution, ISS-041 production adoption, ISS-026 completion, N0 certification
or ISS-015 self-promotion. ISS-064 through ISS-070 remain reserved backlog keys.
