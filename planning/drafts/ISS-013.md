## Context and evidence

The engine must not know how a consumer represents work, readiness, CI,
deployment, priorities, or operator actions. See the platform/project boundary
in `docs/architecture/vision.md` and contracts from `ISS-002`.

## Scope fence

In: typed adapter interfaces, capability negotiation, work frontier snapshot,
readiness result, workspace allocation, CI/deploy observation, mutation plan,
dry-run/apply separation, workspace reclaim, breaker policy facts, state-export
mapping/import plan hooks, fixture adapter, adapter conformance suite, and
`project snapshot/plan/apply` handlers with their public result schemas and
shared envelope/registry/census amendments.

Out: a specific code-host implementation, consumer policy, live credentials,
and first-consumer cutover.

## Decisions already made

Adapters return facts and explicit mutation plans; the engine owns lifecycle
mechanics. Every mutation has a dry-run observation and idempotency identity.

ISS-003 supplies the replaceable static handler interface and leaves `project`
as a handler-free placeholder. This slice owns project result schemas and
their exact supported-parser registrations, the corresponding
`orchestration-command-result/v1` command/result mappings, and replacement of
only that command-family placeholder. Success must parse under the command's
registered project result schema before serialization; config result bytes
cannot stand in for project behavior. Unknown/future schemas, mismatched
command/results, and malformed registrations still refuse. Shared scaffold
changes name ISS-013 and update each registration and every census table
restating it together in one reviewed amendment, as required by the work model.

## Acceptance criteria and evidence

1. The fixture adapter exercises every interface state, including unknown and
   unavailable authorities. Evidence: total state-enumeration test.
2. The adapter conformance harness runs unchanged against two behaviorally
   distinct fixtures, including one with no Git branch/worktree concept.
   Evidence: exact expected fact and mutation-plan transcripts.
3. Adapter mutation plans are inspectable, bounded, and idempotent before apply.
   Evidence: plan/apply negative controls.
4. Compatibility negotiation rejects unsupported engine/adapter pairs before
   external reads or writes. Evidence: canary adapter asserting zero calls.
5. `@orchestration-platform/adapter-sdk` replaces only the static `project`
   command-family placeholder and admits actual snapshot/plan/apply results
   through their public schemas and the shared closed envelope. Evidence:
   registry/census agreement, typed snapshot/plan/apply envelope goldens, and
   negative controls for unsupported schemas, config-result substitution,
   command/result mismatch, and missing or duplicate registrations. Other
   command-family registrations and supported config results remain unchanged.
6. Allocation/reclaim and export/import hooks use opaque identities and
   idempotent plans; ambiguous live resources or moved exports refuse. Evidence:
   two-adapter resource/import transition fixtures.
7. Adapters can supply different trip/recovery policies over the same generic
   breaker lifecycle without changing engine schemas. Evidence: contrasting
   policy fixtures and vocabulary scan.

## Verification plan

Include public-contract compatibility/golden and CLI envelope regression

## Predicted footprint and dependencies

Create implementation in predeclared `packages/adapter-sdk/`, its static CLI
handler registration, two fixture adapters, and conformance tests. Add the
project public result parsers, supported-schema registrations, closed envelope
command/result mappings, and compatibility/golden tests in
`packages/contracts/`; update the consuming CLI boundary and tests in
`packages/cli/` as needed for those results. Amend only the ISS-000-owned shared
manifests, static command registry/runner, and every census restating the
affected registrations needed to implement `project` and
`adapters:conformance`, together under ISS-013 ownership. Blocked by `ISS-002`
and `ISS-003`; blocks dispatch and portable modules. No glossary or roadmap
change.
