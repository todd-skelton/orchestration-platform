## Decision

The constraint is that current evidence cannot distinguish runner variation,
common real-Git cost, file order/reporting or a sharding-specific effect, so
the first deliverable is a bounded discriminator, not a repair. The simplest
viable alternative is to reconcile retained logs and available per-test JSON
first, without editing production behavior or making tests faster on a guess.
The chosen next step, only if that ledger does not discriminate, is test-only,
deterministic phase/process/Git timing capture for the two named cases so an
authorized host diagnostic can locate cost without changing their behavior;
the written conclusion must choose a supported narrow remedy for a **new,
separately reviewed** scope or a no-edit negative result with the missing
discriminator and one explicit follow-up decision. The accepted downside is
an inconclusive terminal result rather than repeated runs; a confirmed
coverage, aggregate, security or required-diagnostic defect goes straight to
prompt M1 containment and repair-versus-revert planning, while a latency miss
alone does not automatically revert ISS-210, and no timeout increase, skip,
retry policy, fixture split, runner increase, gate waiver or speculative
product/test optimization is authorized. A manifest-verified ledger that
already discriminates the cause would show that the observer step is
unnecessary.
