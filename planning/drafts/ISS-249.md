## Why

Three landed slices existed only to rewrite literal model selectors after a
model release: ISS-202 (#630), ISS-203 (#637) and ISS-218 (#700). They edited
`SELF_ROUTING` (`scripts/dogfood/routing.ts:16`) and the ladders in
`adapters/chase-sets-routing.json` (`docs/model-selection.md:21`, :28-45). The
host also writes literal models into every Chase Sets loop config's
`routingRows` (`queue.ts:943-947`). Todd's September 29 ruling (chase-sets #8403
comment 5900473741) treats a successor as a clean in-place swap, so each release
is a mechanical edit that still costs a slice, a landing and a host install.

The incumbent keeps model identity as data: the
`D:\Users\ToddS\AgentPools\state\model-registry.json` file, visible to the
executor at `/mnt/d/Users/ToddS/AgentPools/state/model-registry.json`. Probe on
2026-10-08: `format` is `model-registry/v2`, `generation` is 7,
`authorityDigest` is a string, and `families.<family>.current` names exact
models for astra, sol, luna, fable, opus, sonnet and haiku (for example, astra
is `gpt-6-astra` and sol is `gpt-6.1-sol`).

## Decision

Ladders may name a model family, resolved to the registry's current model when a launch intent is written.
The smaller alternative is to keep literal selectors and accept a slice per release. It is rejected because three slices already recorded that cost.
The larger alternative is to import the incumbent's routing-policy rows as well. It is rejected: that replaces ISS-203 placements, a separate decision.
Accept that ladder efforts stay platform-owned. Model-level `admittedEfforts` are not enforced here.
Revisit if the loop and the incumbent need different current models for one family.

Settled rules:
- **Entry shape.** A rung is `{family, effort}` or the existing `{model, effort}`.
  Literal entries need no registry, so every saved config and fingerprint stays
  valid and byte-identical.
- **Registry location.** The config field `modelRegistry` (absolute path) when
  present, otherwise the environment variable `DOGFOOD_MODEL_REGISTRY`, which
  `scripts/executor/run-loop.sh` exports. The family entries in `SELF_ROUTING`
  therefore work for saved self configs without editing them.
- **Retained compositions.** The fingerprint covers the whole step config, ladders included (`flow.ts:380-388`), and queue composition rebuilds that config from `SELF_ROUTING` (`queue.ts:2293`, :3098-3117). So when a stage directory already holds `config.json`, composition must take the author and reviewer ladders and rungs from that pinned `config.config` instead of the current routing table. Only directories with no `config.json` use family ladders. The effective model and effort of each role must also derive from the pinned rung, not only the ladder fields (round 3 reproduced `f7e93c7d...` only this way). No record is rewritten, and the fingerprint check is unchanged. Live control: the ISS-234 attempt-4 fingerprint `f7e93c7d...` must still match after `SELF_ROUTING` changes to families; round 2 measured that a naive swap changes it to `9ef11ebc...`.
- **Validation projection.** `format === "model-registry/v2"`, a safe-integer
  `generation`, a non-empty string `authorityDigest`, and `families` as an
  object whose used entries have `current` as a non-empty string or null.
  Anything else, or an unreadable file, stops with `model-registry-unavailable`
  (class `retry`, non-parking) before any intent is written. A null or absent
  `current` makes that rung unavailable: the existing ladder advance applies,
  and no launch is charged.
- **Resolution boundary.** One registry read per role selection, where
  `flow.ts:420-430` chooses the rung. The resolved exact model is persisted in
  the existing `${role}-intent` and attempt records (`flow.ts:560-565` intent, :583-588 attempt). A
  retained intent or attempt keeps its recorded model on resume and retry. A
  registry swap affects only intents written afterwards. The fingerprint
  continues to bind the ladder as configured (families), so a swap is not a
  changed ladder (`docs/loop.md:852`).
- **Independence.** `validateRoutingRow` (`routing.ts:75-86`) checks
  reviewer-author disjointness on resolved models from the same snapshot,
  across every author rung. Reviewer selection additionally excludes every
  model recorded for this attempt's authors. Two families resolving to one
  model count as duplicates.

## Done when

1. **AC1: family ladders.** `SELF_ROUTING` and every row in
   `adapters/chase-sets-routing.json` name families, with unchanged roles,
   efforts and rung order. Fresh Chase Sets configs may use family
   `routingRows`; `docs/model-selection.md` documents the host config shape.
2. **AC2: registry rules.** The validation projection above, implemented in
   `routing.ts`.
3. **AC3: identity and replay.** Intents and participant records carry the
   exact resolved model, family, `generation` and `authorityDigest`. Saved
   literal configs resume without any registry. Retained intents keep their
   recorded models after a registry swap. A retained self stage directory
   composed before this change resumes with an unchanged fingerprint and no
   registry access after `SELF_ROUTING` becomes families.
4. **AC4: regression.** Fixtures cover: a swap of `sol` to a synthetic
   successor changes the next new launch with no code or config edit; the swap
   leaves a retained intent unchanged; a swap that would make a reviewer equal
   an author refuses `routing-reviewer-not-independent`; a null family advances
   the ladder with no charge; a malformed registry stops before launch; and a
   literal saved config resumes. A mutant that reads the ladder literal must
   fail the swap fixture.
5. **AC5: docs.** `docs/model-selection.md` replaces its per-release selector
   tables with the family description and keeps its history section.
