## Why

Once the loop has delivered a Chase Sets milestone, routine delivery should
run on the platform and the `milestone-orchestrator` host loop should stop
being the default.

ISS-110's repeated manual status/recovery notes and ISS-135's scope incident
also expose the operator controls needed before that retirement. Deliver
ISS-136 status first, then ISS-137 pause/priority/resume and ISS-138 attention
alerts. These are M3 adoption work, not a reason to interrupt or widen the
current M2 validation.

## Done when

- Routine Chase Sets issues are delivered by the platform loop for one full
  milestone with the incumbent idle.
- A one-page rollback note in the Chase Sets repository says how to resume the
  incumbent skill if the platform stops.
- The skill's routine-delivery sections are marked superseded; its
  Todd-decision and operator-action sections remain.
- The operator can inspect a detached run, pause after current work, change
  next-work priority using existing policy, resume, and receive an actionable
  attention alert without keeping a host chat active. Record the actual
  commands and observations from the adoption run, including any manual recovery.

## Out of scope

Deleting the incumbent. Any second consumer. A dashboard or automatic restart
after crash, reboot, or idle: retain explicit operator resume, and admit a new
mechanism only if a real cycle records the blocker that requires it.
