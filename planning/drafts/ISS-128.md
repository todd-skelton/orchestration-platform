## Why

On 2026-09-12 the ISS-126 candidate failed its Windows and macOS jobs while
the ubuntu job was still running. `gh pr checks` reported the macOS check in
the `fail` bucket at once, delivery called `gh run view --log-failed`, and
the CLI refused with "run 34715149765 is still in progress; logs will be
available when it is complete". Delivery raised
`hosted-check-log-unavailable:Node 24 / macos-latest` and the loop parked
the issue. The ISS-124 repair path never ran, and the log existed two
minutes later.

## Done when

- When a required check is in the `fail` or `cancel` bucket but the run
  behind its link is not `completed` (`gh run view <id> --json status`),
  delivery returns `observing-hosted-checks` and polls again; it fetches the
  failed log only once the run is completed.
- `hosted-check-log-unavailable:<name>` is raised only when a completed run
  yields no failed log or the link carries no run id.
- `test/dogfood/delivery.test.ts` proves with fake `gh` output: a failed
  check on an in-progress run keeps observing, and the same check once the
  run completes returns the failed result with the log.

## Out of scope

Waiting for sibling checks that are still pending after the run completes;
the failed job's log is enough to start the repair.
