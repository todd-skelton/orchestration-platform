## Context and measured blocker

The authenticated ISS-022 result at decision core
`2e08babc6c141ef071eb26e1de399a603ec35f433473d3b60bcf7aa78da62a92`
is `BLOCK_REPLAN`: all three OS-profile slots and every selectable capability
slot, including `runtimeLock`, `destinationLock`, and `custody`, are null. The
original 21-vector probe established useful diagnostic facts, but it did not
select an unrelated-process lock. PR #192 landed the separately coordinated
native candidate, stable witness, build inputs, and refusal fixtures. The
remaining prerequisite is a registered and scheduled hosted native-compilation
path that can build those reviewed sources and run the already approved bounded
experiment on provider-fresh macOS, Windows, and Linux runners.

This issue registers that path. It neither changes the prior result nor grants
authority to the candidate, build, workflow, or diagnostic output.

## Decisions already made

Use Node 24 with `NAPI_VERSION=8` and the exact OS recipes, stable witness,
candidate interface, fixed lock file, lifecycle barriers, provider evidence,
and refusal semantics in the landed bounded native-lock ledger. Compile only
the two reviewed C sources in separate runner-temp directories with the hosted
image's unprivileged compiler/SDK and verified official Node distribution
inputs. Stable N builds and evaluates candidate N+1; candidate code never
loads in the stable parent, reducer, record job, or diagnostic verifier.

Run exactly, in order, `NATIVE_UNRELATED_EXCLUSION`,
`NATIVE_NORMAL_RELEASE`, `NATIVE_DEFAULT_NON_INHERITANCE`, and
`NATIVE_HOLDER_DEATH_ONCE`. Exercise all twelve frozen refusal controls and
perform one post-death acquisition attempt with no wait, retry, deletion, or
cleanup before that attempt. An unavailable compiler, SDK, header, import
library, or required provider fact is `UNSUPPORTED` or `UNKNOWN`; it never
authorizes installation, fallback, or a partial result.

The experiment emits diagnostic artifacts only. The stable reducer must keep
all selectable native capability/profile slots null and must not call an
existing capability receipt, decision-core, profile, or publication writer.
Only a later independently reviewed ISS-022 selection may consume a complete
three-OS result.

## Acceptance criteria and evidence

1. The protected ISS-006 workflow accepts only the literal experiment action
   and dispatches exactly one macOS, one Windows, and one Linux observation job
   plus the stable-only aggregate and record jobs. Workflow mutants reject a
   changed action, runner token, job census, input-selected matrix, optional OS,
   missing `if:always()` collection, candidate registry, or broader permission.
2. Each observation job materializes the exact reviewed stable and candidate
   sources through the authenticated candidate-file consume/delete boundary,
   verifies the actual Node distribution inputs, and compiles only those two C
   sources with the frozen argv on the hosted toolchain. The retained build
   census binds source/revision, stable fixture/build/loader bytes, Node
   headers/import library, compiler/SDK and Node identity, argv, outputs, and
   all lengths and SHA-256 values. Mutants reject source, revision, flag,
   header, output, architecture, ABI, loader-path, environment, or extra-file
   substitution.
3. Every OS runs the exact four cases in order and all twelve negative controls.
   Stable observations prove same-file identity, unrelated-process exclusion,
   explicit release while the holder lives, default non-inheritance, and the
   single immediate post-death witness attempt. Missing barriers, candidate-only
   claims, an inherited or wrong handle, wait/retry/delete behavior, a second
   post-death attempt, or an incomplete control census refuses the result.
4. Each OS uploads its one exact immutable diagnostic archive. The stable-only
   aggregate downloads exactly three same-attempt archives and retains the
   complete build, case, control, transcript, cleanup, and provider census.
   The record/verifier checks the exact protected revisions, jobs, conclusions,
   artifact bytes, protection state, and at least 30 days remaining retention.
5. The final disposition is diagnostic `PASS|FAIL|UNSUPPORTED|UNKNOWN` for each
   premise and the complete three-OS census. Collection success cannot upgrade
   a failed premise. Every existing ISS-022 selection/profile/capability slot
   remains null, the original 21-vector result remains byte-identical, and no
   release, production, or promotion receipt is produced.

## Predicted footprint and dependencies

Round 429 measured that the registered end state crosses four independently
attackable boundaries and cannot fit one review sitting. Delivery therefore has
three ordered implementation stages:

1. register the literal action, closed runner token, exact required three-OS
   registry/matrix, authenticated stable bundle, and case/control/prerequisite
   censuses in the existing hosted plan path; keep the workflow trigger absent;
2. implement one complete stable single-OS observation owner for official Node
   distribution/toolchain capture, authenticated candidate consume/delete,
   source-only build, four cases, twelve controls, and the retained archive;
3. activate the exact workflow trigger and add the stable-only three-OS
   aggregate, provider record, and terminal diagnostic verifier.

Each stage must leave the ordinary conformance action byte-stable and all
ISS-022 selection/profile/capability writers unreachable. Stage one may touch
only the conformance runner-token catalog, hosted plan implementation, one
private native-lock plan census module, their focused tests, and this planning
record. Later predicted footprints are bounded to their named owner layers.
No stage adds a public capability schema, package dependency, installed tool,
production consumer, or binary. A stage that crosses the next boundary is new
replan evidence.

This registration inserts `ISS-048` after `ISS-006` and before `ISS-022`.
`ISS-006` supplies the only admitted protected hosted harness. `ISS-022`
consumes a complete independently reviewed diagnostic result and remains the
only owner of lock selection; `ISS-004`, `ISS-005`, `ISS-020`, and `ISS-031`
remain blocked behind it. The edge replacement is the transitive reduction;
