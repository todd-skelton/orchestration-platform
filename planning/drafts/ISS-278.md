The nine validations come from `f.compose()` and `nextCycle` at `queue.test.ts:1977,3183,3185,3189,3229,3233,3236`.
Each call re-runs `validateLoopExecutor`. The supervisor validates once per cycle
(`scripts/dogfood/supervise.mjs:638`) and passes the result on (`:684`). The
existing seams are `queueConfigFromLoop(..., validatedExecutor)` (`queue.ts:2205,2234`)
and `nextCycle(..., validateExecutor)` (`scripts/dogfood/supervision.ts:418,556`). One run of
row `complete then retained item-stop` counted 463 children. One run of the sibling `pass` row counted 427.

Cause: each row runs several hundred sequential real Git children under one
fixed 30 s budget, so its wall time is child count times per-child latency.
Concurrent vitest processes and host load raised per-child latency until the
row crossed the limit. Nothing in the evidence shows a logic race.

## Decision

The constraint is that this row must stay under the unchanged 30,000 ms limit
even when the host is busy, and its failure must be attributable. The simplest
alternative is a per-test timeout or retry, which `docs/loop.md:1848-1850`
(ISS-160) and `:527-528` rule out because the existing timeouts stay and no
timeout increase or skip establishes attribution. The chosen option asserts an
exact per-row child-process count, which does not depend on host speed, and
removes the row's redundant executor re-validation through the existing seams,
matching the production supervisor. The accepted downside is a smaller margin
gain, about 64 of 357 children (18%), with no guarantee under arbitrary load.
The choice would be wrong if the census differs between two clean runs at the
same head, because then the count is not a deterministic signal.

## Simplest shape

1. A pass-through counter on `node:child_process` (`execFile`, its promisified form,
   and `spawn`), reusing the `vi.mock` precedent at `test/dogfood/delivery-adapter.test.ts:820-842`.
   It changes no arguments, results or errors, and is reset per row.
2. The row validates once and passes that result to every `f.compose` and `nextCycle` call.
3. Each row asserts its exact count.

   counter is pass-through: other tests in `queue.test.ts` pass with it present.
