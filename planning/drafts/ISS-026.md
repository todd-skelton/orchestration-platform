## Context and evidence

Portable primitives do not form a controller until one released component owns
the routine cycle. The composition lifecycle is defined in `Routine engine
cycle`; its exhaustive ordered step contract is
`docs/architecture/routine-cycle.md`; command/API ownership is declared in the
bootstrap manifest.

## Scope fence

In: cycle plan, run, resume, inspect; adapter frontier/policy ingestion; breaker
evaluation; typed selection/routing/module decision; dispatch; review reduction;
journal/restart composition; optional typed release action; terminal/no-work
receipt; one-cycle concurrency fence.

Out: consumer work policy, project vocabulary, provider implementation, direct
external API calls, bypassing owning packages, or a background daemon.

## Decisions already made

The engine composes typed package contracts and treats adapter/module outputs as
opaque plans. Only the exact session/cycle may advance. Crash recovery replays
the journal and resumes the exact incomplete step without repeating a terminal
external mutation.

## Acceptance criteria and evidence

1. Two behaviorally distinct adapters—including one without repository concepts—
   drive the unchanged engine through work, no-work, blocked, rejected, and
   release-assemble/certify, release-candidate-review, and promotion cycles.
   Evidence: complete golden cycle transcripts.
2. Crash injection before/after every step resumes exactly once or reaches a
   named refusal; moved plans, false prefixes, unknown authorities, and duplicate
   terminals never start a second mutation. Evidence: transition/fault matrix.
3. Restart under `WAITING_WORKER`, `WAITING_REVIEW`, and `WAITING_ACTION` observes
   the existing attempt instead of redispatching. Evidence: event/launch/action
   identity counts.
4. Engine package/schema/bundle scans contain no consumer labels, repository
   layout, provider names, or adapter policy fields. Evidence: generated
   vocabulary and dependency-boundary reports.
5. `@orchestration-platform/engine` replaces only the static `cycle` command
   placeholder and passes every canonical argv/envelope fixture. Evidence:
   handler census and parser matrix.
6. Every `routine-cycle/v1` ordinal has the published owner, typed input/output,
   fresh-authority point, skip receipt, terminal mapping, and resume identity;
   no implementation-selected step order is accepted. Evidence: generated
   protocol conformance and single-edge mutation tests.
7. A compile-time producer-consumer census proves exactly one producer for every
   step input: step 7 alone creates `dispatch-plan/v1`, and step 9 alone creates
   immutable `worker-result-subject/v1` or `review-attempt-result/v1` according
   to the bound role. A distinct later review cycle binds the closed target
   subject; disposition, mutation plan, and apply carry that identical target
   digest. Missing, substituted, reordered,
   rematerialized, stale, moved, or wrong-owner inputs refuse before mutation.
8. Every allocation/failure/rejection/apply path reaches owner-specific step-14
   reclaim exactly once or retains capacity for a live/unknown resource; repair
   is a typed later-cycle request, never an unplanned same-cycle mutation.
9. Every non-unknown exit at every ordinal produces a complete ordered census of
   terminal/skip receipts, a no-allocation or reclaim receipt, and a terminal
   cycle receipt; its next supervisor tick starts only after that proof.
   For promotion, step 13 persists a successor-verification follow-up, step 15
   writes predecessor N's terminal receipt and clears only the exact canonical
   activation fence after broker/active-record read-back, then the current tick
   exits. A crash between terminal write and clear safely retains the fence and
   exact-transaction recovery; no N1 cycle runs inline.
10. Multi-cycle conformance covers implementation-result review and landed
    `release-candidate-subject/v1` review. Neither subject kind can borrow the
    other's receipt, and implementation/assembly cycles cannot mutate where the
    published protocol requires a later review cycle.
11. Step 4 admits and invokes only a statically composed
    `orchestration-module/v1` registry entry whose source/emitted/descriptor/
    manifest digests equal the installed release manifest. Input and result are
    schema-validated around the single invocation. Missing, moved, duplicate,
    unlisted, dynamic, incompatible, extra-capability, effectful, candidate, or
    digest-mismatched modules refuse before invocation. Evidence: ABI call
    transcript and one mutant per refusal against both example adapters.

## Predicted footprint and dependencies

Create implementation in predeclared `packages/engine/`, its static CLI handler,
and cycle composition/fault fixtures. Blocked by the named public contracts for
CLI, sessions, dispatch, review, journal, routing/modules, adapters, release,
breakers, and credentials; blocks final N0 certification. Self-host and consumer composition roots
may contain adapter wiring only.
