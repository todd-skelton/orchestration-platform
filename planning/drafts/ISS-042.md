## Context and evidence

The proportionality review (pressure round 34) found no issue owns how the
operator observes what the controller is doing: `ISS-010` out-scopes analytics
dashboards, and the only status surface in the plan is the `ISS-015` N1
health-summary module, which exists as a change vehicle rather than a planned
capability. A controller that dispatches autonomous workers without a
first-class read-only status view forces the operator to read raw journals.

## Scope fence

In: an `orchestrate status` command family rendering current lease/session
state, the last cycle outcome and terminal receipts, active worker ownership,
breaker states, and pending operator actions from reduced journal state; a
closed `operator-status/v1` projection emitted as canonical JSON with a human
rendering derived from the same data; explicit `UNKNOWN` rendering for any
fact the reducers cannot establish.

Out: mutation of any kind, analytics dashboards, historical trend queries,
richer board projections (parked in the migration manifest), web UIs, and any
use of the projection as an authority input.

## Decisions already made

The projection is advisory-only and read-only: it consumes reducer output and
never blocks, extends, or interprets authority. Unknown state renders as
explicit `UNKNOWN`, never as invented health. The `status` family handler
lives in a new `@orchestration-platform/status` package, auto-membered by the
existing `packages/*` workspace glob and added by the same single
shared-scaffold amendment (per `docs/planning/work-model.md`) that adds the
family registration: the amendment adds command `status show` emitting
`operator-status/v1` to the CLI registry and every census table together. The
`ISS-015` health-summary module later projects the same `operator-status/v1`
shape; this issue owns the schema and the CLI surface.

## Acceptance criteria and evidence

1. `orchestrate status` renders lease, session, last-cycle outcome, active
   ownership, breaker, and pending-action facts from reduced state on a cold
   installation and during a live cycle without blocking the writer. Evidence:
   golden renderings for cold, mid-cycle, and post-crash fixtures.
2. The command is read-only: a run produces no filesystem delta anywhere.
   Evidence: before/after manifest comparison.
3. JSON and human renderings derive from one `operator-status/v1` instance;
   the human form contains no fact absent from the JSON. Evidence: rendering
   census test.
4. Reducer-unknown facts render explicit `UNKNOWN` with the owning receipt
   reference; no fixture renders invented or defaulted health. Evidence:
   seeded-unknown fixtures.
5. The `status` family lands through one reviewed shared-scaffold amendment
   updating the registration and every census table together. Evidence:
   `pnpm run verify:bootstrap` passing in the same change.
