## Question

Can a pinned supported Anthropic Claude Code CLI version provide the exact
executable, requested/reported model, launch, terminal, process-tree, and
per-role credential isolation evidence required for an authority-bearing
worker-host adapter on macOS, Windows, and Linux?

The first consumer's incumbent delivery loop routes implementation and review
across both Codex and Claude lanes. Restoring that routing surface under
platform authority requires a second concrete worker host proven to the same
contract as `ISS-023`, not assumed from the first host's evidence. Codex
receipts prove nothing about Claude Code; no evidence transfers between hosts.

The known open risk this probe must resolve, not assume away: Claude Code's
permission and tool-restriction model is enforced by the CLI process itself
rather than by an OS sandbox boundary equivalent to the Codex
`--sandbox read-only` contract. Cooperative in-process enforcement may or may
not satisfy the denied-capability contract; if it does not, the disposition
rule below narrows the host authority claim or requires external confinement
from the `ISS-031` custody topology.

## Pinned probe subject

The probe subject is the npm artifact `@anthropic-ai/claude-code`, installed
globally at one exact version. Pinning the exact version, registry tarball
identity (SRI and SHA-1), resolved launcher, and platform-native executable
hash is the first recorded probe step and a precondition for every run; no
run may start from an unpinned or floating install. Package identity alone is
insufficient; each target OS records its own resolved executable hash.

The requested model selector is exactly `claude-sonnet-5`, recorded against
the published Anthropic model catalog at pin time. A selector or alias is
routing input, not immutable model identity. The provider identity schema
from `ISS-012` is the authority contract for distinguishing selector, alias
movement, and provider-resolved snapshot; a provider-authenticated resolved
snapshot surface must be identified in the CLI's startup events before any
identity capability may pass. Selector equality alone never grants authority.

## Probe method and lifecycle timing

Before any run, author `docs/architecture/claude-probe-fixture.md` and
`docs/architecture/claude-tool-manifest.md` to the same closed-fixture
standard as the Codex pair: literal fixture tree bytes, prompts, environment
maps, effective-input admission, and the closed raw tool/schema/capability
surface. The fixture contract is reviewed before the first launch; the probe
may not invent or weaken it. The `ISS-023` fixture pattern, the trusted OS
harness, and the ISS-031-owned shared byte-hashed native-store attack suite
are reused; the fixture bytes, argv contract, and denied-capability canaries
are Claude-specific and independently reviewed.

Using the trusted OS harness, launch native argv arrays without a shell in
non-interactive print mode with machine-readable JSONL event output, closed
stdin, a 15-minute outer timeout, and a fresh initialized synthetic Git
repository with a recorded tree digest. Each role runs under an isolated
role-specific configuration home (`CLAUDE_CONFIG_DIR`), a fixture-only
`HOME`/`USERPROFILE`, an empty fixture temp root, and an environment
allowlist whose exact final key/value-name census (values redacted and
path-normalized) is part of each OS receipt; extra keys fail preflight. No
inherited secret except the role's bounded authentication capability,
installed only inside that role's isolated configuration home; no API token
environment variable is inherited.

The role matrix mirrors `ISS-023`: implementation receives workspace-scoped
write permission; review and observer receive read-only invocations and
adversarial prompts from the fixture contract. Exact flags, settings bytes,
and permission-mode encodings are fixed by the fixture contract, not chosen
per run. The launcher resolves and hashes the executable before constructing
argv; it does not use `PATH` lookup at child creation.

Capture executable hash/version before launch, startup events before
accepting liveness, reported model identity before accepting work,
process-tree observations while live/terminating, and terminal events after
exit. Probe absence, minimum-version refusal, alias/mismatch, stalled
startup, forced termination, author/reviewer environment crossover, and
moved subject. Negative fixtures remove the prompt, each isolation control,
or the clean role-specific home; mutate each effective-input source
enumerated by the fixture contract; and verify pre-launch or canary refusal
as applicable.

Against the exact backend/custody/IPC artifact selected by `ISS-031`, on
every OS and role execute every denied-capability canary in the fixture
contract: network, parent/sibling access, privilege, approval, write,
filesystem credential crossover, direct native-store extraction, and
interpreter/profile escape. Because permission enforcement is in-process,
each denied-capability canary must additionally distinguish CLI-cooperative
refusal from boundary enforcement, and the receipt records which produced
the refusal. Enforcement—not cooperative wording or incidental
unavailability—must produce an explicit refusal and unchanged external
census for the capability to pass.

The reported-model surface is a startup event, before the first work item,
that reports both the requested selector and a provider-authenticated
immutable snapshot/version. Missing or mismatched fields, selector equality
without a resolved snapshot, or a value supplied only by prompt/config is a
failed exact-identity capability—not something normalization may synthesize.

## Required durable evidence

Publish scrubbed raw JSONL/event fixtures, exact command/argument manifests,
prompt/workspace digests, environment allowlists, process receipts,
credential-canary results, and one normalized capability receipt per exact
OS image and CLI version, bound to probe source and test-bundle digests.
Include exact raw tool names, canonical schema bytes/digests, enforcement
capabilities, one refusal mutant for added, removed, renamed,
schema-expanded, or authority-expanded tools, and a per-canary
enforcement-versus-cooperation disposition. Include the ISS-031-owned shared
attack-suite fixture identity and argv plus a distinct refusal receipt for
every denied capability on every role and OS.

## Disposition rule

- If every required identity and isolation property is proven on all
  targets, `ISS-043` implements that exact contract and minimum CLI version.
- If denied capabilities are refused only cooperatively by the CLI process,
  file one bounded adapter-authority decision before `ISS-043` selecting
  external confinement from the `ISS-031` custody topology, a narrowed role
  surface (for example review/observer lanes only), or both.
- If exact reported identity, filesystem and native-store credential
  isolation, or process lifecycle cannot be proven on any required OS,
  return `BLOCK_REPLAN` and either narrow the second-host authority claim or
  record that first-consumer adoption proceeds Codex-only with Claude-lane
  parity explicitly fenced out of the `ISS-016` fixture census. Prompt text,
  private exports, or aliases cannot emulate missing authority.

## Scope fence

system as evidence for another, or accepting Codex-host evidence for any
Claude Code capability.
