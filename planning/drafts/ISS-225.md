At this base, whether a stop parks the issue is decided by
`isItemStopReason` (`scripts/dogfood/supervision.ts:71-101`): a hand-kept
list of 21 exact reasons and 4 prefixes. Every other reason is a non-parking
host stop. A regex scan of `scripts/dogfood` and `adapters` (estimated, not
exact) found about 525 throw or `demand`/`requireThat` sites with literal
reasons and about 300 distinct reason strings. About 250 of them are
integrity, drift or configuration refusals that all behave the same way. The
same scan showed a regex cannot reliably separate reason arguments from other
`demand` arguments, such as `exactKeys` key lists; the implementation must
not rely on one.

## Why

A stop reason today is a free-form string. Nothing ties a new reason to a
decision about who must act on it, so each incident adds a code, a recovery
sentence and, when the host is stuck, a new single-use mechanism. Later
slices can only shrink the system if every reason first has an explicit class
in one place that the running loop actually reads. This slice adds that
table and makes it the source of the existing park decision, with no
behavior change.

The five classes are named by who has to act next:

| Class | Who acts | Disposition at this slice |
| --- | --- | --- |
| `attempt` | the loop: the candidate or worker output was unacceptable | parks (unchanged) |
| `replan` | a person: the brief or authority must change first | parks (unchanged) |
| `retry` | nobody: external state was unavailable or unknown, and a same-run restart reconciles it | non-parking host stop (unchanged) |
| `wait` | a person, provider window or authority outside the loop | non-parking host stop (unchanged) |
| `halt` | the host: the loop's own records, config or executor disagree | non-parking host stop (unchanged) |

## Decision

The loop must keep today's park and host-stop behavior exactly while every stop reason gains an explicit class, because preserved runs and posted stop bodies are compared byte for byte. The simplest alternative is to keep the 21-code allowlist and go straight to an automatic retry list for the transient stops seen on 2026-09-30. This slice instead adds one five-class table that `isItemStopReason` reads, with halt-only family rules, an explicit legacy-parking list, and a test that fails when a thrown reason has no class. The accepted downside is that about 250 integrity and configuration reasons get classified even though they all behave identically today, and the `retry` and `wait` classes carry no behavior until a later slice uses them. If the follow-up slices land without deleting at least one legacy-parking entry, one per-site retry or one continuation instrument, the table was overhead and should be removed.

   `"prefix"`, `"family"` or `"unclassified"`, and

## Out of scope

| Not built here | Where it goes |
| --- | --- |
| Automatic bounded retry for `retry` reasons | Slice 2, separately planned. It needs a count and launch bound, reconcile-before-rerun at every external-effect step, and the 2026-09-30 restarts as its acceptance evidence. |
| Resolving legacy-parking entries | Slice 2 or later. Each entry moves only with its own evidence and review. |
| Retiring single-use continuation instruments | Slice 3, separately planned. Default is to replace them with re-filing a parked lineage as a fresh attempt from current main, with prior records as read-only evidence. A general grant record is built only if a second real lineage needs one. |
| A single budget ledger | Rejected. Implementation attempts and native launches bound different risks; per-mechanism allowances stay as bounded costs. |
| Classifying non-literal reasons beyond the named set, or retyping every throw site | Not needed for the ratchet; the runtime fallback stays `halt`. |
| Changing any posted body, record schema, prompt or `ACTIONABLE_STOP_REASONS` | Out of scope; ISS-216 shows the cost of two derivations of one body. |
