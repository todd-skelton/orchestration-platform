## Why

The fresh ISS-106 run published
[#388](https://github.com/todd-skelton/orchestration-platform/pull/388) at
head `65bdb7dd1b7670acedd50cbe2a9ccca4c20656e0`, then stopped before its first
hosted-check observation with `hosted-observation-unavailable`; the retained
evidence is summarized on
[#363](https://github.com/todd-skelton/orchestration-platform/issues/363#issuecomment-5636023941).
Publication was recorded at 14:29:31.720Z, GitHub created the workflow run at
14:29:33Z, and the stop was recorded at 14:29:33.904Z. GitHub CLI documents
this post-publication interval as a
[`gh pr checks` race](https://github.com/cli/cli/issues/7401), but the adapter
discarded the underlying CLI error, so this run cannot prove which failure it
observed. All three hosted jobs later passed.

## Done when

- The installed `gh pr checks --json name,bucket,link` response before the
  first check run is reproduced and distinguished from provider, JSON, and
  publication-identity failures.
- A confirmed just-published pull request with no check runs yet returns the
  existing `observing-hosted-checks` result, allowing the supervisor's normal
  observation interval to see the eventual named checks.
- Once checks appear, the existing exact required-name, head, pending,
  failure, cancellation, and skipping behavior is unchanged; no synthetic
  check is treated as evidence.
- Any other hosted-observation failure still stops, and its bounded underlying
  diagnostic appears in the existing learning-note paragraph without a new
  diagnostic artifact.
- No retry framework, timer, record, schema, authority, guard, preflight, or
  per-item file is added.
