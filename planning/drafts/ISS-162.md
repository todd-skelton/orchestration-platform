## Why

`m1-iss154-20260915T1004` attempt 1 (`cycle-1-complete.json`, ordinals
1-5) recorded five consecutive dead `gpt-6-astra/high` author launches.
Every trace ends the same way: `503 auth_unavailable: no auth available
(providers=codex, model=gpt-6-astra; last upstream error:
server_is_overloaded)`. Each launch first passed the ISS-129 models probe,
because the pool keeps a model listed while every credential for it is
cooling down (`internal/registry/model_registry.go`,
`modelRegistrationAvailability`). The URL in the message made the loop
classify each death as an outage, so the five launches spent native launch
budget and nothing waited.

A weekly quota block has the same shape: the model stays listed, the request
returns `429 model_cooldown`, which matches neither `modelRefused` nor
`providerFailure`, so the worker dies as a plain dead launch. Two of those
park the issue as `launcher-failed`. Measured on 2026-09-16 at 13:59: two
of three Codex accounts at 100% weekly (resets 09-19 and 09-20), the third at
63%; the three Claude accounts at 2%, 0% and 8% weekly. The pool's supervisor
already observes per-account, per-model routing status (`ready` or
`blocked` with `next_retry_after`) on `/api/status`; the loop never read it.

## Design

- `probePoolModel` in `dispatch-adapter.ts` reads
  `CODEX_POOL_STATUS_URL` inside the existing `waitForProvider` probe,
  after the models probe. A launch is admitted when any non-disabled account
  reports the model `ready`, or when no account mentions the model (the pool
  does not know it, or its observations are stale; the models probe alone
  decides). When every account blocks the model: a block that clears within
  `providerOutageCeilingMs` throws an ordinary error, so the launch waits
  with `waiting-provider` and the pool's reset time; a longer block (a
  weekly window) is `provider-model-refused`, so the worker advances its
  ISS-158 ladder (whose last rung is the other vendor) and an exhausted
  ladder stops the host with the reset time instead of after a wasted
  ceiling. Malformed or failing status waits like an outage;
  it is not a pass.
- `scripts/executor/run-loop.sh` exports `CODEX_POOL_STATUS_URL`;
  `pool-bridge.mjs` takes a port and `start-loop.ps1` starts one bridge
  per missing port (8317 inference, 8318 read-only status). The pool
  supervisor answers `GET /api/status` and `/api/health` for the bridge
  host; mutations keep the same-origin check.
- Pool side (`D:\Users\ToddS\AgentPools`, outside this repository):
  `projection.mjs` derives per-provider ordinal pace states (`exhausted`,
  `exhausts-before-reset`, `on-pace`, `expires-unused`) from the longest
  common window, published as `projection` on `/api/status`; on-change
  usage samples go to `logs/usage-samples.jsonl` and the steepest observed
  burn per provider caps what counts as realizable before a reset. The loop
  does not read the projection; it informs the operator's routing marker
  and ISS-158's ladders, whose last rung is the other vendor.

## Done when

- `probePoolModel` admits ready, admits unknown, waits on a block that
  clears inside the ceiling, refuses a longer block, ignores disabled
  accounts, and rejects malformed or failing status; tests in
  `test/dogfood/adapter.test.ts`. A refusal advances the launching role's
  ISS-158 ladder through the existing launch-time refusal path.
- `launch` composes the models probe and the pool probe under one
  `waitForProvider` call; without `CODEX_POOL_STATUS_URL` behavior is
  unchanged.
- The executor scripts export the status URL and bridge both ports.
- `docs/loop.md` records the incident and the admission rule.

## Out of scope

Reading the pace projection from the loop; choosing a row or rung from quota
state (ISS-158 owns ladders; the operator owns the marker); fast mode
(`service_tier`) automation before its quota multiplier is measured;
model-to-provider aliasing inside the proxy; reset-credit policy; migrating
records or the running loop config.
