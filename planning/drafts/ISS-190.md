## Why

ISS-182/#560 [stop 4](https://github.com/todd-skelton/orchestration-platform/issues/560#issuecomment-5728469560)
and PR #576's own [Windows job 105540420500](https://github.com/todd-skelton/orchestration-platform/actions/runs/35326425131/job/105540420500)
record two failures in `test/dogfood/setup-adapter.test.ts`:
`keeps fresh pilotRevision resolution ahead of plan persistence` and
`keeps fresh sourceBranch resolution ahead of plan persistence`. Both report
EBUSY removing their private `setup-git-fixture-*/portable repository`; neither
reports a test timeout. The same run's refresh timeout and source cleanup error
are a separate observation, not proof these setup failures are its aftermath.
The full run had 1079 passes, three failed tests and 17 existing platform skips.

At stable `2fae5debf1a70f93985e4ab73dd198c86ff1a859`, setup `assertExecutor`
launches seven concurrent Git reads in `Promise.all` at lines 453-461 and four
validation reads at lines 475-480. An invalid reference rejects the aggregate
before sibling subprocess promises necessarily settle. The catch returns
`setup-state-unverified`; the test then checks retained state and cleans up.
`observeWorktree` has the same fail-fast three-read batch at lines 509-513,
returning unknown on command failure. Setup's install-output pump lifecycle is
different and outside this repair.

A pure probe executes the unchanged exported `gitSetupAdapter` with fake
filesystem and child-process boundaries. For invalid pilotRevision and base,
the refusal is observed while two HEAD command promises remain pending; for
invalid sourceBranch, two status commands remain pending. Explicitly releasing
those siblings leaves zero pending. No Git executable, temp repository or live
provider is used. This proves the early-settlement defect, not that those exact
children held the hosted Windows locks. The failed hosted job did not retain
child-handle identities. Preserve that uncertainty; never claim a proven locker.

ISS-186 is saved-publication fixture-only and ISS-182 is closure-fixture-only.
Neither owns setup validation lifetime. ISS-189 owns delivery read reduction,
not cleanup. Do not hide this independent defect in any of those issues.

## Decision

Quality profile: `core-library`. G0: join the already-started Git validation
operations before their owning adapter method returns either success or refusal.
Keep the existing parallel reads and error classifications; retain the first
observed rejection while draining siblings if needed to preserve that behavior.
An existing local helper is acceptable only if it removes duplication in these
actual batches; do not export a new lifecycle abstraction.

Rejected: generic rm retries/sleeps, swallowed EBUSY, serialized whole suites,
larger timeouts or killing processes conceal ownership rather than fixing it.
Serializing all existing validation reads adds avoidable Windows work latency.
Accepted downside: failure waits for its own already-launched reads rather than
returning immediately; this adds no command, retry or new timeout. A hung child
remains an unresolved process failure under existing limits, not permission for
a cancellation framework. Revisit only if retained evidence shows another cause.
