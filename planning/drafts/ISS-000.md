## Context and evidence

Every later issue names pnpm verification commands, but the new repository does
not yet contain a workspace, lockfile, compiler, test runner, or runnable root
scripts. See `docs/architecture/vision.md`,
`docs/architecture/contract-decisions.md`, and `docs/planning/roadmap.md`.

## Scope fence

In: Node 24 and pnpm metadata, workspace layout, TypeScript configuration,
formatter, unit-test runner, package skeletons, root verification commands,
clean-checkout CI smoke, and placeholder commands that fail with a named
`CAPABILITY_NOT_IMPLEMENTED` result until their owning slice lands, including
the separate bootstrap CLI pnpm wrappers.

Out: implementation of runtime behavior, release publishing, consumer adapters,
or choosing contracts already settled in architecture documents.

## Decisions already made

Use Node.js 24, pnpm workspaces, TypeScript strict mode, Vitest, Prettier,
exactly pinned `esbuild@0.28.2`, and ES modules. Exact package names, exports,
CLI commands, root build targets/options, and contracts are
listed in `docs/architecture/bootstrap-manifests.md`. Package skeletons own
shared manifests so later parallel slices do not edit them.

## Acceptance criteria and evidence

1. A clean checkout installs with a frozen lockfile and runs format, typecheck,
   unit, build, and bootstrap checks on macOS, Windows, and Linux. Evidence:
   three-job smoke workflow.
2. Every verification command named by a planned issue resolves; unimplemented
   commands fail with the owning issue key rather than command-not-found.
   Evidence: command-census test generated from `planning/drafts`.
3. Workspace and package skeletons exactly match the authoritative package and
   export table. Evidence: manifest graph validation with missing/extra rows
   rejected.
4. No generated artifact or runtime state is written into tracked source paths.
   Evidence: clean-status check after the complete bootstrap suite.
5. The static CLI registry contains exactly one placeholder or implemented
   handler for every declared command family, with the declared owning package
   and issue. Evidence: machine-generated command census rejecting missing,
   duplicate, dynamically discovered, or extra handlers.
6. `planning/roadmap.json`, draft frontmatter, epic membership, milestones,
   direct blocked-by edges, acyclicity, and generated epic DAG blocks agree.
   Evidence: `pnpm run planning:check` plus one mutant fixture per mismatch.
7. The bootstrap executable commands and literal root wrappers are present as
   named `ISS-020` placeholders and included in the command census. Evidence:
   wrapper/owner rows reject missing, extra, or default-adding scripts.
8. The workspace includes predeclared `packages/*`, `modules/*`, and
   `adapters/*` globs. The first-consumer adapter manifest, exact package name,
   exports, scripts, empty static entrypoint, and three extension placeholders
   match the authoritative row. Evidence: frozen-install, filter, export, and
   manifest census without a later root-file edit.
9. The single root esbuild script/config pins the exact three private client-
   composition entries plus two non-alias broker-service entries and the
   ISS-003 non-alias CLI entry, all outputs/options, and the
   target-scoped `#broker-compose` resolver from the authoritative manifest;
   five placeholder entrypoints exist at the exact paths
   and fail with their owner keys; the CLI entry emits the ISS-003 canonical
   config results and failures. The root build sequentially builds the reviewed
   Windows native fact adapter before these six JavaScript outputs; the private
   builder never rebuilds native artifacts during tests. No package-local override or ordinary
   TypeScript/Node/package consumer can resolve the alias. Evidence: clean
   three-OS six-target build and byte comparison plus seventh-target, alternate-
   config/plugin, runtime/deep import, package export, externalization, emitted-
   specifier, tarball, installed-file, and source-map mutants.
10. Skeleton builds include the exact empty `modules/manifest.json`, a
    deterministic placeholder `modules/build/generate-registry.mjs`, and fixed
    empty generated registry. The placeholder accepts no module row and fails
    with owner `ISS-011` otherwise. Evidence: clean three-OS placeholder builds,
    repeated-byte equality, and non-empty/dynamic/edited-stub refusals; `ISS-011`
    replaces this predeclared surface without a root build/config edit.
11. Empty placeholders and wrappers exist for both `ISS-038` pre-N0 host-custody
    build entries and the exhaustive `host-custody:bootstrap` command surface.
    They fail with owner `ISS-038` until filled and are covered by target/command/
    alias censuses; only the host-custody client entry may resolve
    `#broker-compose`.
12. The exhaustive bootstrap placeholder registry and literal wrapper include
    `abort --input <file> --output <file>` owned by `ISS-020`, consuming the
    existing `bootstrap-install-input/v1` and emitting the named receipt with no
    defaults. Evidence: missing/extra/duplicate-
    flag and undeclared-command census.
