## Scope and observed need

Extract the repeated controller handoff across the accepted setup, native
author/reviewer flow, bounded review repair and delivery components for one
explicitly authorized finite queue. One invocation selects each bound item in
order, persists its cursor and stage intent, calls the existing component, waits
on exact identities, joins accepted review evidence and advances only after
confirmed delivery cleanup. Repository priority, scope, model/effort, provider
mutation and release decisions remain in the explicit adapter and authority.

ISS-078 is registered as #338 under EPIC-KERNEL/M2 and is blocked by
ISS-077/#337. The independently accepted executor is
`57d99a3b02142820e520fcf9e7e7f320e77b4765`; base
`bf7e66ead2f1a1800a19909cfbcd86e4552b0ba5` cannot certify or activate itself.
Initial admission is bounded to eight native launches; AUTHOR1 and REVIEWER2
are the first two reservations. This is implementation attempt one of four;
review and repair launches do not consume an implementation attempt, while
every participant and available usage observation remains in the queue lineage.

## G0 and smallest complete shape

G0: PASS. The smallest complete shape is one durable finite queue transition,
one explicit repository/execution adapter co-located with that engine and
directly composing the four accepted component entry points, and one thin
command. Queue authority binds a
closed ordered item set, stable executor, finite item and launch ceilings,
initial lineage and exact item policy. Runtime repair and delivery configs are
derived only from bound policy and exact durable review identities; guessing a
candidate head would be broader, not simpler.

Not built: unbounded scheduler; daemon/service; workflow language; generic
framework; duplicate launcher, setup, repair or delivery implementation; public
package API; read-only dashboard; per-item controller scripts; arbitrary model
router; candidate activation or production promotion; provider policy;
credential broker; existing-PR refresh; explicit setup Git selection; failed
native-launch adoption; global toolchain/compiler change. Each is unnecessary
for the seven criteria, duplicates accepted behavior, or needs later measured
authority.

## Non-goals

No credential invalidation/rotation, production promotion, arbitrary model
router, new native sandbox/launch policy, global environment or toolchain
changes, raw trace/private output ingestion, fabricated source failure,
arbitrary adoption/deletion, erased attempts/spend, manual-gate bypass, or
candidate self-certification. Operator actions remain explicit and do not
become automatic authority.

## Acceptance evidence

1. Explicit external authority binds a finite queue and its permitted work, repository adapters, stable executor, models/effort, source scope, admission and release boundaries. Malformed, unknown, drifted or exhausted authority fails closed before dependent mutation.
2. One invocation performs actual setup and dispatch, waits on exact known identities, handles a valid failed review through the accepted bounded repair path, and delivers accepted work using the existing four controller gates and actual hosted Windows/macOS/Linux proof. Merely calculating the next action is insufficient.
3. Durable stage/item intent and receipts precede effects. Restart resumes the current item or advances an already confirmed completion without duplicate workers, commits, PRs, merges, worktrees or dependency installation. Provider and filesystem observations corroborate uncertain receipts; absence of an observation is not proof of absence of an effect.
4. Preserve every real attempt, failed verdict, reserved/consumed admission and measured or unavailable usage through item and queue transitions. Distinguish implementation attempts from repair/review launches under current policy. Telemetry is advisory and never grants or blocks authority.
5. Queue completion is a statement about the finite authorized work only. Independently reviewed exact-head acceptance and stable external promotion remain necessary before a candidate may acquire executor authority. Do not silently switch the running engine to candidate code.
6. Retain actual evidence from multiple consecutive genuinely useful queue cycles without per-item controller scripts or routine corrective intervention. Include a real completed restart and a genuinely encountered, bounded failure/recovery path. Hosted fixtures alone and manually stitched partial feature runs do not satisfy this criterion. Never manufacture faulty code or a failed review to create evidence.
7. Every remaining recurring intervention discovered during real use receives a concrete recorded correction; a typed stop is safe behavior but is not proof that the full supervision-removal goal is complete. Preserve scope rather than redefining success around easy passing stages.
