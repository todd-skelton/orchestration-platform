## Why

M1 run `m1-accepted-replan-20260914T1416`, ISS-146 attempt 1, stopped twice at `planning:board-check`: #459 carried planning key ISS-147 absent from its saved candidate roadmap. The first stop occurred during the registration window; the second persisted after planning PR #460 merged and the executor clean-fast-forwarded to `7a105a4e232e75085066cef9f3d6d61d5d583465`. Gates still ran in source candidate `1310be46aa9eb686590a532b3a1312f15e228e66` based on `fc9ef1045834b2971521750188e7dcb6b16a23a6`, so current executor main was irrelevant. Both `cycle-2-stop-1.json` and `cycle-2-stop-2.json` and their completion records are preserved under `/root/orchestration-m1/runtime/m1-accepted-replan-20260914T1416`. Learning notes: #457, including https://github.com/todd-skelton/orchestration-platform/issues/457#issuecomment-5667056517. Register-first alone cannot protect an already-live candidate from a later registration.

## Done when

- Before gates run on a resumed or aged attempt, integrate its source worktree with actual current `refs/remotes/origin/main` through the existing native refresh/rebase path. Preserve candidate work, attempt/participant history and evidence. Incompatible or conflicting integration stops with a typed reason; once ISS-147's bounded conflict path exists, route there without duplicating it.
- At minimum, `planning:board-check` evaluates registrations from current main together with the candidate's own planning delta. It must neither reject a valid registration that landed after author start nor hide an invalid or omitted candidate planning change by checking main alone. No host copy into saved worktrees, temporary removal of live issues, synthetic gate receipt or global board-check exemption.
- The self adapter's `afterMirror` `planning:board-check` author gate is scoped to planning keys the candidate itself changes, or runs against current `origin/main` plus the candidate's planning delta, so global intake (a new registration or issue on main) can never fail a live attempt. Candidate-owned planning errors remain failures.
- Bind subsequent gate, delta review and publication authority to the actual resulting source head. Retain prior source review as inherited evidence but never treat changed semantic hunks as conflict-free equivalence. Do not reset implementation attempts, restart full authorship, lose failed history, or repeat a completed mutation on restart.
- Regress the actual sequence: attempt starts at an older roadmap; a separate valid registration lands on main and becomes a live issue; first gate and resumed gate consume current registrations plus candidate changes. Also cover candidate-owned invalid registration, no main movement, repeat resume, moving or unavailable main, and typed conflict/ISS-147 handoff. Exercise the genuine gate/refresh composition, not just a mocked board reader.
- Document native resume behavior and when source review or gate evidence must be renewed. No change to issue order, required hosted bootstrap, merge/deploy authority or worker mutation permissions.

## Out of scope

Hand-editing the preserved ISS-146 run, deleting attempts/worktrees, weakening board validation, new generic state or authority framework, restarting M2, JPEG/product repair, model changes, or milestone ownership changes. The host's separately authorized fresh M1 run and fresh worktreeRoot preserve the stopped run rather than repairing its records. Until this issue lands, platform intake is held while an M1 attempt is live; incumbent product delivery continues.
