## Why

Planning-only PR #584 (ISS-192) at head
`fdf7697a2900fa9cf2e41ca4cd64c05f242da8c8`, whose whole diff is
`planning/drafts/ISS-192.md` plus one `planning/roadmap.json` row, failed the
hosted Windows bootstrap of run `35460027988` attempt 2
([job 105949586706](https://github.com/todd-skelton/orchestration-platform/actions/runs/35460027988/job/105949586706))
with exactly one failure:
`test/dogfood/supervision.test.ts > selection authority failure refuses: incomplete census`
-> `Error: EBUSY: resource busy or locked, rmdir 'C:\Users\runneradmin\AppData\Local\Temp\planning-selection-ib2Hq6\executor'`.
The gate recorded 1 failed / 1152 passed / 17 existing platform skips, one file
failed and 19 passed, and 2720.31s total. That case itself measured 1554ms
against the unchanged 30000ms limit, so no case timed out. Ubuntu and macOS
passed the same head. A planning-only diff cannot have changed this behavior.

The failing identity is an `it.each` tuple at `supervision.test.ts:1064-1075`;
its assertions completed. The removed path is a `planning-selection-*` fixture
root, and the only recursive removal in that file is its `afterEach` at
`supervision.test.ts:846`, which calls
`rm(root, { recursive: true, force: true })` with no `maxRetries`. The captured
log carries no candidate source frame, so treat the `afterEach` attribution as
that identity comparison, not a recorded stack.

`test/dogfood/fixtures/planning-selection.ts` creates the root at line 19 and
clones the real remote into `<root>/executor` at line 73 through actual `git`
child processes; `executor` is the exact directory Windows refused to remove.
Node's `fs.rm` retries the transient `EBUSY`/`EMFILE`/`ENFILE`/`ENOTEMPTY`/
`EPERM` class with a linear backoff only when `maxRetries` is above zero, and it
defaults to zero. A Git child or a scanner still holding a handle for a moment
after the case completes is the ordinary Windows cause of this error. That is
the mechanism; which holder held `executor` at 2026-09-19T19:43 UTC is UNKNOWN
and is not asserted. Do not diagnose host load: nothing timed out.

`test/dogfood/supervise.test.ts:268` has cleaned with
`rm(root, { recursive: true, force: true, maxRetries: 3, retryDelay: 100 })`
since ISS-078/#344. Every other recursive fixture cleanup in `test/` omits it.

The same EBUSY-on-cleanup shape recurs in recent Windows jobs:
`105938379273` (run 35458651053, `native-refresh-*/source`), `105737602906`
(run 35387463735, `native-refresh-*/repo`), `105647841086` (run 35359761643,
`source-fail-native-*/repository`), and PR #556's `105194368074`. In those the
EBUSY followed a 30000ms case timeout, and #584 attempt 1 (job 105942106891)
likewise failed the registered ISS-182 refresh closure case at 30000ms and then
EBUSY on `native-refresh-*/source`. Attempt 2 is the first capture of this error
alone, so cleanup fragility is demonstrated independently of ISS-182's timing
failure. The last four main push runs (`35421912717`, `35383009633`,
`35366455190`, `35357444635`) were Windows-green; green history does not
exonerate a demonstrated failure, and one red job does not license a rerun.

ISS-182 owns the refresh closure-case timing and is NOT a dependency of this
issue: it reduces fixture work inside `refresh.test.ts`, while this issue makes
removal of an already-finished fixture root tolerate a briefly held handle.
Either can land first, so `blocked_by` is empty.

## Decision

Quality profile: core-library (test infrastructure only).

Constraint: a finished case must not fail because Windows briefly refused to
remove its own temporary root, and a root that genuinely cannot be removed must
still fail the case. Case assertions, fixture content, real Git work, the
30000ms test/hook limits, `fileParallelism: false`,
`sequence.concurrent: false`, existing platform skips and every runtime file
stay exactly as they are.

Chosen smallest shape: give each recursive fixture-root removal in `test/` the
bounded retry options already shipped at `supervise.test.ts:268` -
`maxRetries: 3, retryDelay: 100` - at the same call sites, changing nothing
else. No new module, hook, config key, wrapper or cleanup framework. The
worst-case added wait is the documented linear backoff on a root that is still
held, and zero on the ordinary path.

G0: a single-site fix at `supervision.test.ts:846` is smaller and insufficient.
Four other prefixes (`native-refresh-*`, `source-fail-native-*`) have already
produced the same error, and `planning-selection` roots are also pushed by
consumers in `queue.test.ts` and `queue-adapter.test.ts` whose own cleanups lack
retries. Deleting the fixtures' real clones would remove the proof the suites
exist for. A larger `retryDelay`, a swallowed cleanup error, a `try`/`catch`
around `rm`, extra serialization, a raised timeout, a skip, an OS-conditional
cleanup or a hosted rerun policy are all rejected: they weaken or repeat an
existing gate instead of tolerating a transient handle.

Accepted cost: the same four option bytes repeat at every cleanup site. That
repetition mirrors the shipped precedent and keeps each site independently
readable and revertable, which a shared helper imported by fifteen files -
including `test/executor.test.ts` and `test/format-eol.test.ts` outside
`test/dogfood/` - would not. If the implementer still judges the repetition a
finding, the only permitted alternative is one tiny helper in an existing
`test/dogfood/fixtures/` module with identical semantics and no other behavior;
a cleanup framework, global hook or `vitest.config.ts` change is not built.

Revisit only if a captured Windows job shows this error surviving the retry
budget; that would be a different, genuinely held-handle defect with its own
evidence, not a bigger budget. Do not assume `fs.rm` backoff semantics - confirm
them against the installed Node 24 before claiming the budget's worst case.
