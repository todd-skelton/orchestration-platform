## Why

ISS-129 (#421) records repeated provider outages; ISS-132 (#429) and ISS-134
(#433) record executor stops during hosted checks and queue admission. The
ISS-110 (#367) notes show the host detecting and explaining those stops, then
manually resuming. A detached run has issue stop notes, but no active host chat
to notice that it exited or that selected work requires Todd's decision.
Alerts should remove that repeated inspection burden, not become another
delivery controller.

## Done when

- Provide an opt-in lightweight host-side watcher of one configured run using
  ISS-136 status. It can detect supervisor disappearance as well as reported
  stops; it must not depend on the supervised process remaining alive. It
  never dispatches, changes priority, edits scheduling state, or restarts work.
- Use one explicitly configured existing GitHub tracking issue as the initial
  notification destination, with concise attention comments linking the run,
  affected issue/PR, existing learning note, last evidenced progress and age,
  and the action needed. Do not copy credentials or raw worker transcripts.
- Notify on unexpected supervisor exit, a host stop, or idle with outstanding
  operator-blocked work. Do not duplicate an existing learning note verbatim
  or post per-poll noise. Deduplicate an unchanged condition across watcher
  restarts using minimal notification state outside the checkout; report
  recovery once. Intentional pause and normal exhausted idle are not crashes.
- A configurable no-progress interval produces an attention warning, not a
  claim that a worker is dead. Include known provider/CI/deploy waits; do not
  kill slow work or alter existing phase timeouts and retry budgets.
- Notification failure is visible locally and retries on a later bounded
  observation, without affecting delivery or producing a tight retry loop.
  Document that GitHub notification delivery depends on subscription/settings
  and availability, and a watcher on this host cannot alert while the whole
  host is powered off. Do not claim remote uptime monitoring.
- Tests cover supervisor loss, repeated condition and watcher restart,
  recovery, intentional pause, blocked idle, slow but live work, unavailable
  observations, and GitHub failure. Demonstrate one opt-in alert and recovery
  on a test run, without disturbing the active M2 validation.
- Extend docs/loop.md with setup, destination, interval, stop/disable commands,
  and failure limitations. No watcher is installed or enabled merely by
  merging the implementation; operator activation is explicit.

## Out of scope

Automatic reboot/crash recovery, service-manager installation, new notification
providers, paging infrastructure, remote-host availability guarantees, dashboard,
or another scheduler/writer for delivery state.
