## Context and evidence

Planning and delivery guidance currently mixes reusable workflow with consumer
terminology and shell commands. See `docs/architecture/vision.md` and the
contract vocabulary from `ISS-002`.

## Scope fence

In: neutral planning, delivery, review, and repair modules; exact static
entrypoints; module manifest and `orchestration-module/v1` implementation;
capability declarations; adapter references; version compatibility; and
host-neutral bundle layout. The first concrete host is `ISS-021`.

Out: consumer labels, milestones, domain glossaries, model selection, and
runtime dispatch implementation.

## Decisions already made

Modules contain workflow and evidence standards. Project structure and policy
arrive only through `ISS-013`. Shell examples use the platform CLI. Repository-
local `docs/planning/work-model.md` and issue templates are excluded from shipped
bundles. The source-term map from `ISS-001` generates the package denylist. The
closed ABI, entrypoints, manifest fields, and static-admission rules are fixed in
`docs/architecture/module-abi.md`.

## Bounded optional disposition phase proposal

Round 401's two-family disposition/follow-up ledger explicitly proposes an
optional statically source-owned disposition export, allowed only with nonempty
descriptor dispositionCodes. Existing descriptor/plan exports and step-4
input/output byte contracts remain unchanged; inputSchemas/outputSchemas are
step-4 declarations. Plan-only modules remain valid partial ABI implementations.
Full-routine admission must prove the needed handler and code census before
worker or workerless action effects. The closed inline input contains actual
existing module/action/route/preflight/worker/review/skip records; no public
input family, resolver or arbitrary payload is added. Purity matches plan.

This is an explicit conditional-export/phase replan, not implemented behavior.
Code membership stays module-owned and cannot load a function; findings and
disposition use the exact current descriptor census. COMPLETE expressly means
nonmutating observer/review completion, while declined NO_ACTION is known
failure. Review-required ordinary results, including observer results, must
request later exact-target review. The ledger fixes full matrix/joins,
non-goals, acceptance vectors, verification, predicted footprint and attacks.
Later source requires ordinary independent review and existing source/manifest
admission; no module registry/code, tests, PASS or full-cycle completion is
claimed by this author packet. Root reconciles the draft/board after review.

## Consumer-backed manifest and planning definition

Round 434 closes the two definitions required before ISS-011 source can start:
the exact private manifest row/build order and the first neutral planning
module's descriptor and deterministic selection policy. This is grounded in
the landed ISS-013 branch/queue fixtures and the walking-skeleton module
consumer. It does not elaborate delivery, review, or repair ahead of their
runtime consumers.

The manifest remains one canonical ordered private array. Each row binds fixed
source/emitted paths, normalized tracked-source census, exact emitted bytes,
the existing descriptor identity, and direct ABI/schema/compatibility/
capability projections. The sole generator seals all inputs, denies ambient or
effect imports, emits serially with fixed options, rechecks identities, and
publishes each ignored output atomically with the registry last only after the
complete four-row verification. A final census gates the self-host build; build
output grants no installed or release authority.

The first implementation tranche is `planning` only. It supports the two
landed fixture adapter/policy tuples, declares one review-required
`planning.implement/work.read` implementation action, and deterministically
selects the first canonical READY `work.read` row only under an exact NO_TRIP
policy fact. It emits the existing closed action/brief structures or one exact
no-action/refusal cell. It never renders, routes, launches, mutates, reads a
provider, or infers current breaker/registry authority. The complete literal
definition and removal vectors are in `docs/architecture/module-abi.md`.

This packet changes definitions only. The following source packet may add only
the quarantined planning entrypoint and focused exact-byte, mutation,
effect-denial, two-adapter, and three-OS evidence. It keeps the empty manifest,
empty generator contract, and generated stub byte-stable. Final manifest and
generator activation waits until all four baseline source entrypoints have
consumer-backed semantics and executable evidence.

That source packet must exercise the new descriptor and plan through the
existing walking-skeleton preparation functions with actual ISS-013 branch and
queue snapshot/current-policy readers, retained parsed input, and post-await
binding validation. It pins branch TRIP to no action, queue NO_TRIP to the
implementation action, and an equivalent all-READY NO_TRIP decision projection
across both adapters. Hand-built module inputs are insufficient consumer
evidence. Inputs refused by the public parser produce no bound module result.

## Acceptance criteria and evidence

1. Fresh-context scenarios produce exact expected dispatch briefs, dependency
   plans, review packets, and mutation transcripts through two differently
   shaped adapters. Evidence: golden artifacts plus generated denylist scan.
2. Every module's exact `src/index.ts` exports `descriptor` and `plan`, with
   only the explicitly admitted optional `disposition` export from the bounded
   phase proposal, under `orchestration-module/v1` and declares engine, adapter,
   host, schema, action-kind, and capability compatibility. Evidence: compile-time ABI/export
   census, manifest validation, and incompatible-version refusals.
3. Planning artifacts require scope, decisions, acceptance evidence,
   verification, footprint, operator actions, and review attack surface.
   Evidence: positive and single-field-negative fixtures.
4. One host-neutral module artifact is byte-stable on all targets; concrete host
   discovery is tested by `ISS-021`. The `ISS-001` source-term map is test input
   only and is absent from the bundle. Evidence: packaging hashes, file census,
   and manifest/package inspection.
5. `modules/manifest.json` is the sole ordered module registry and binds source,
   emitted, descriptor, ABI, schema, compatibility, and capability digests for
   exactly the four baseline entrypoints. Missing, extra, duplicate, moved,
   dynamic-path, and digest-mutated rows refuse. Evidence: manifest/entrypoint
   matrix and clean three-OS packaging hashes.
6. Each `plan` is deterministic over canonical input and cannot access ambient
   filesystem, process, network, clock, random, credentials, host, adapter, or
   mutation APIs. Evidence: import/capability scan and effect-attempt mutants.
7. `modules/build/generate-registry.mjs` is the sole manifest-to-static-registry
   generator and emits only `modules/.generated/registry.ts` with literal imports
   and frozen digests in manifest order. Repeated three-OS generation is byte-
   identical; dirty, missing, stale, extra, dynamic-import, path-escape, changed-
   descriptor, and hand-edited output mutants fail before bundling.
8. Every module-emitted dispatch brief is a closed `dispatch-brief/v1`
   instance with no free-form prose field. Rendering is not this issue's
   scope: deterministic templates and rendering goldens belong to the selected
   host issues, beginning with `ISS-021`. Evidence: closed-schema census,
   goldens covering emitted structure, and one seeded prose-field mutant
   refusal.
9. Every descriptor emits a dense 1–256 closed `dispatchCatalog` whose exact
   `(actionKind,capabilityName,directiveKind,code)` resolver keys are unique and
   select one closed accessor/template pair. The descriptor's duplicate-free
   worker-required action/capability pair census exactly equals the catalog pair
   projection, and descriptor plus release-manifest digests bind every row.
   Evidence: accessor-only, template-only, and both-changed duplicate-key
   mutants; duplicate/missing/extra pair-census mutants; and descriptor/manifest
   substitution goldens.
