## Context and evidence

Planning and delivery guidance currently mixes reusable workflow with consumer
terminology and shell commands. See `docs/architecture/vision.md` and the
contract vocabulary from `ISS-002`.

## Scope fence

In: neutral planning, delivery, review, and repair modules; exact static
entrypoints; module manifest and `orchestration-module/v1` implementation;
capability declarations; adapter references; version compatibility; and
host-neutral bundle layout. The first concrete host is `ISS-021`.

Out: consumer labels, milestones, domain glossaries, model selection, and
runtime dispatch implementation.

## Decisions already made

Modules contain workflow and evidence standards. Project structure and policy
arrive only through `ISS-013`. Shell examples use the platform CLI. Repository-
local `docs/planning/work-model.md` and issue templates are excluded from shipped
bundles. The source-term map from `ISS-001` generates the package denylist. The
closed ABI, entrypoints, manifest fields, and static-admission rules are fixed in
`docs/architecture/module-abi.md`.

## Acceptance criteria and evidence

1. Fresh-context scenarios produce exact expected dispatch briefs, dependency
   plans, review packets, and mutation transcripts through two differently
   shaped adapters. Evidence: golden artifacts plus generated denylist scan.
2. Every module's exact `src/index.ts` exports only `descriptor` and `plan`
   under `orchestration-module/v1` and declares engine, adapter, host, schema,
   action-kind, and capability compatibility. Evidence: compile-time ABI/export
   census, manifest validation, and incompatible-version refusals.
3. Planning artifacts require scope, decisions, acceptance evidence,
   verification, footprint, operator actions, and review attack surface.
   Evidence: positive and single-field-negative fixtures.
4. One host-neutral module artifact is byte-stable on all targets; concrete host
   discovery is tested by `ISS-021`. The `ISS-001` source-term map is test input
   only and is absent from the bundle. Evidence: packaging hashes, file census,
   and manifest/package inspection.
5. `modules/manifest.json` is the sole ordered module registry and binds source,
   emitted, descriptor, ABI, schema, compatibility, and capability digests for
   exactly the four baseline entrypoints. Missing, extra, duplicate, moved,
   dynamic-path, and digest-mutated rows refuse. Evidence: manifest/entrypoint
   matrix and clean three-OS packaging hashes.
6. Each `plan` is deterministic over canonical input and cannot access ambient
   filesystem, process, network, clock, random, credentials, host, adapter, or
   mutation APIs. Evidence: import/capability scan and effect-attempt mutants.
7. `modules/build/generate-registry.mjs` is the sole manifest-to-static-registry
   generator and emits only `modules/.generated/registry.ts` with literal imports
   and frozen digests in manifest order. Repeated three-OS generation is byte-
   identical; dirty, missing, stale, extra, dynamic-import, path-escape, changed-
   descriptor, and hand-edited output mutants fail before bundling.
8. Every module-emitted dispatch brief is a closed `dispatch-brief/v1`
   instance with no free-form prose field. Rendering is not this issue's
   scope: the deterministic template and rendering goldens belong to
   `ISS-021`. Evidence: closed-schema census, goldens covering emitted
   structure, and one seeded prose-field mutant refusal.
