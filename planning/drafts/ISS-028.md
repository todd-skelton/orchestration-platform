## Context and evidence

Shadow and import slices need one concrete adapter package owner before they can
run in parallel without sharing manifests or composition files. The generic SDK
is defined by `ISS-013`.

## Scope fence

In: filling the predeclared concrete adapter skeleton, version/compatibility
implementation, configuration schema, and static shadow/import/mutation extension points,
empty conformance fixture, and package-boundary tests.

Out: live consumer reads/writes, shadow behavior, state mapping/import, policy
implementation, credentials, or platform package changes.

## Decisions already made

`ISS-000` owns package name `@orchestration-platform/adapter-first-consumer`, its
manifest, scripts, exact exports (`.`, `./shadow`, `./import`, `./mutation`),
workspace inclusion, empty `src/index.ts`, and static placeholder files. This
slice fills only predeclared adapter/configuration implementation. Later slices
own only their predeclared `src/shadow/`,
`src/import/`, and `src/mutation/` implementations; they replace their own
placeholder without editing shared scaffold files.

## Acceptance criteria and evidence

1. The scaffold loads against the exact SDK/engine compatibility versions and
   refuses mismatches before external access. Evidence: positive and version-
   mutation fixtures.
2. Shadow, import, and mutation placeholder registrations are static, unique, and owned by
   disjoint paths. Evidence: package/export/footprint census.
3. A clean checkout can apply representative shadow, import, and mutation patches in
   parallel without touching a common file. Evidence: collision simulation.
4. Packed platform artifacts exclude this consumer adapter; its package contains
   no secret, local path, or incumbent raw state. Evidence: package inspection.
5. `pnpm --filter @orchestration-platform/adapter-first-consumer test` resolves after
   frozen clean install without root/manifest/export edits. Evidence: exact
   filter and workspace census.
