## Context and evidence

This issue is the live-window half of what was a single eight-deliverable
draft. Decision #302's readiness audit found the draft in probe form
(`## Question`, `## Probe method and lifecycle timing`) under a `type:slice`
label, with no numbered acceptance criteria, no falsifiable prediction, and a
diff that could not clear one review sitting (audit §1, gates 1a-1c). Ruling
1A on Decision #302 (CF-0) repairs the form and moves every deliverable that
needs no live credential and no provider mutation into eight registered
sub-slices, `ISS-056` through `ISS-063`, each built and independently
reviewable against the ISS-054 public surface at the current head. What
remains here is exactly the live-window work: creating and tearing down the
synthetic GitHub resources, exercising the negative-control matrix against a
draft ruleset, authorizing the persistent ruleset and protected environment,
publishing the verifier anchor and running the producer, and the three-OS
credential-free public-bundle verification. `ISS-062` (CF-7) supplies the
offline verifier, runbook, and `:verify` implementation this issue exercises
live; `ISS-063` (CF-8) supplies the contract for the four post-upload
environment variables this issue's producer window depends on.

ISS-054 closed as completed at `60269e3` (Decision #297; Decision #302
comment thread), clearing the audit's Gate 3 blocker. The audit's remaining
findings are resolved as follows:

- **F1** (the four post-upload environment variables have no contract): moved
  to `ISS-063`; this issue's producer window (acceptance criterion 7) may not
  begin until `ISS-063` lands a ruling and, if the ruling requires it, a
  contract family.
- **F2** (`protectedPathPolicies` never enumerated): resolved below as an
  explicit, irreversible-at-ruleset-creation path list.
- **F3a/F3b** (two unprobed provider-capability facts): named below as
  explicit `BLOCK_REPLAN` triggers to be measured against a *draft* ruleset
  before the persistent ruleset is authorized.
- **F4** (two negative controls need `observedProtection`, which ISS-036 does
  not produce): resolved by `ISS-061` (CF-6) as an offline fixture-only
  harness; this issue exercises those two controls live only once ISS-038
  supplies a real read-back producer. `ISS-061`'s draft states, as a
  non-goal, that the fixture harness never becomes that producer.
- **F5** (the receipt cannot survive seven days to its ISS-038 consumer):
  the receipt is reclassified below as a re-issuable output; the ruleset
  (numeric ID and semantic digest) and the verifier anchor are this issue's
  durable outputs.
- **F6** (draft wording the schema does not support): "page counts" and
  "complete ETags" are removed as receipt claims below; "before-and-after
  ruleset" and "permission census" move to the probe's authenticated
  archive, which is required durable evidence but not a receipt member.

## Acceptance criteria and evidence

1. Every one of the nine `apiObservations` purposes
   (`repositoryProtectionPurposes`) is captured live during the producer run,
   each observation's `startedAt`/`observedAt`/`completedAt` bounded by
   `producer.startedAt` and `issuedAt`. Evidence: the producer's own captured
   transcript, replayed through `ISS-057`'s reducers to reproduce every
   receipt digest byte-for-byte, plus the probe's authenticated archive
   holding the before-and-after ruleset configuration and the app/token
   permission census — required durable evidence, never receipt members.
2. All twenty-eight negative controls named in the current `## Negative
   controls` list below, plus the ISS-054 closed-snapshot corpus at every
   protection and verifier-anchor entry point, are executed live and refuse.
   Evidence: one row per control naming the live mutation and the exact
   issue code, cross-checked against `ISS-058`'s offline matrix over the same
   controls.
3. Before any persistent ruleset is authorized, F3a and F3b are measured
   against a *draft* ruleset and recorded as explicit `BLOCK_REPLAN` triggers:
   (a) whether the least-privilege run-scoped `GITHUB_TOKEN` can read the
   Actions environment and environment-variable API rows the receipt's
   `ENVIRONMENT` and `ENVIRONMENT_VARIABLE` observations require with a
   non-null ETag captured during the producer run; (b) whether GitHub's
   ruleset API for this repository exposes each of the five `reviewPolicy`
   cells (`adminBypass`, `authorApproval`, `committerApproval`,
   `dismissalOnSourceChange`, `minimumApprovals:"1"`) as distinct readable,
   ETag-bearing fields. A negative answer to either is `BLOCK_REPLAN` for the
   persistent-ruleset and protected-environment branch of this issue, not a
   partial pass.
4. The persistent repository ruleset is created only after criteria 2 and 3
   pass; its numeric `rulesetId` and `rulesetSemanticDigest` are retained as
   this issue's durable output and are never weakened or bypassed for the
   enumerated paths.
5. The protected environment `host-custody-bootstrap-root` is created; the
   operator sets and reads back `VERIFIER_ANCHOR_SHA256` strictly before the
   producer run starts, chronology-locked per
   `docs/architecture/contract-decisions.md:7121`
   (`anchor.operatorConfirmation.confirmedAt <= anchor.createdAt <=
   receipt.environmentBinding.variableUpdatedAt <
   receipt.producer.startedAt <= receipt.issuedAt`); a rewrite or a
   retarget-then-restore of that variable after the producer run starts
   refuses.
6. The producer run emits `repository-protection-receipt/v1` and uploads it
   as the sole file in its named artifact; the receipt never carries its
   enclosing artifact ID or archive digest.
7. After GitHub finalizes upload, the operator independently reads back the
   artifact and sets the four post-upload values
   (`PROTECTION_RUN_ID`, `PROTECTION_ARTIFACT_ID`, `PROTECTION_RECEIPT_SHA256`,
   `PROTECTION_ARTIFACT_ARCHIVE_SHA256`) in the same environment, exactly as
   `ISS-063`'s ledger clause defines them; this criterion cannot be
   evidenced before `ISS-063` lands.
8. All three target operating systems (Windows, macOS, Linux) independently
   verify the downloaded public attestation bundle with pinned GitHub CLI
   2.93.0, no local GitHub login or token, and no target-repository API
   re-query. The verifier anchor predates and is independent of any kit
   candidate byte; combined anchor/root/verifier/bundle substitution refuses.
9. The two negative controls that only the binder can judge — a live ruleset
   change after receipt creation, and the anchor variable set or moved after
   the producer run — are exercised live only once `ISS-038` supplies a real
   `observedProtection` read-back producer; until then this issue's evidence
   for those two controls is `ISS-061`'s offline fixture harness, which does
   not itself satisfy this criterion.
10. Only the synthetic issue/branch/PR/workflow resources are removed after
    evidence capture; the persistent ruleset and the verifier anchor are not
    touched. The scrubbed teardown report is bound to the probe/test digests
    it reports on and leaks no token or private actor data.

**Falsifiable prediction.** The prediction is that the closed ISS-054
receipt and binder contracts, the `ISS-056`..`ISS-063` credential-free
scaffolding, and one supervised live-provider window per gated operator
action (O1-O11) are sufficient to produce an `ACCEPTED`
`repository-protection-receipt/v1` and a three-OS-verified public attestation
bundle, without any additional GitHub permission, workflow trigger, or
receipt member beyond those the ledger already closes. Review this prediction
before the first live window (L1): a need for a permission, observation
purpose, or receipt member the closed ledger does not already name is
`BLOCK_REPLAN`, not silent scope growth of this issue.

**Review-by horizon.** This issue is reviewed for readiness again once
`ISS-056`, `ISS-058`, `ISS-060`, and `ISS-061` land (the direct inputs to
`ISS-062`), and once more before any operator action in the O4/O5/O6/O8/O10/O11
class is authorized by its own Decision.

actor, pagination truncation, stale ETag, delayed/duplicate run, wrong

## Enumerated `protectedPathPolicies` path list

`docs/architecture/host-custody.md:34-46` is the only place in the repository
that names the host-custody source/build/review surface `ISS-038` produces:
the two review-producer workflow files, and (implicitly, through
`config/private-compositions.json:33` and `:38`) the two kit source entry
points `packages/host-custody/build/composition.ts` and
`packages/host-custody/build/broker-service-composition.ts`, both under
`packages/host-custody`. Directory-prefix interpretation of a
`protectedPathPolicies` row is a property of the supplied ruleset semantics,
not of the path's spelling: "A path denotes the exact path or directory
prefix interpreted by the supplied ruleset semantics; glob syntax, implicit
prefix broadening, and caller-selected matching are not part of this
contract" (`docs/architecture/contract-decisions.md:6702-6704`). Whether row
3 below is in fact read as a directory prefix remains subject to the same
draft-ruleset measurement this issue already requires before any persistent
ruleset is authorized (acceptance criterion 3). This issue enumerates
exactly three rows, ordered by UTF-8 `path`:

1. `.github/workflows/host-custody-bootstrap-build.yml`
2. `.github/workflows/host-custody-bootstrap-review.yml`
3. `packages/host-custody`

This list becomes an irreversible commitment inside the immutable
`rulesetSemanticDigest` the moment operator action O5 creates the persistent
ruleset — a commitment made over files that `ISS-038` has not yet written,
which is workable but binding. `ISS-038` is edited in this same change to
name this exact list as the paths its receipt's ruleset/path-policy semantics
govern.
