## Context and evidence

The first consumer's incumbent delivery loop dispatches implementation and
review across both Codex and Claude lanes. A platform that can only launch
the Codex host cannot reproduce that routing surface, so Claude-lane parity
at adoption requires a second concrete worker host implementing exactly the
contract admitted by `ISS-044`. The engine and routing contracts are already
provider-neutral (`ISS-012`, `ISS-013`); this slice adds one integration
package and changes no engine contract field.

## Scope fence

In: CLI discovery, exact executable and version identity, exact requested
and reported model identity, native launch, role-specific rendered
`dispatch-brief/v1` bytes and credentials, role-isolated configuration
homes, transcript/artifact binding, startup liveness, terminal receipt,
independent review attempt isolation, and any external confinement required
by the `ISS-044` disposition decision.

Out: other providers or additional hosts, remote workers, model-quality
calibration, multi-model planning experiments, automatic credential
installation, prompt tuning, or vendor-specific behavior in the core engine.

## Decisions already made

The adapter is an optional integration package and implements only the exact
minimum version, invocation, event, identity, isolation, and confinement
contract admitted by `ISS-044`. Aliases never satisfy exact identity. No
Codex-host evidence, threshold, or capability claim transfers to this host.
If `ISS-044` narrowed the authority claim (for example cooperative-only
enforcement for some capability), this adapter exposes exactly the narrowed
role surface and refuses the rest; prose cannot widen it. Whether `ISS-017`
shadow parity requires this host or explicitly fences Claude-lane parity out
is recorded in the `ISS-016` fixture census, not decided silently here.

## Acceptance criteria and evidence

1. Dispatch binds executable hash/path identity, CLI version, requested
   model, reported model, role, launch identity, and subject revision.
   Evidence: terminal worker-host receipt.
2. Missing CLI, version mismatch, model mismatch, alias-only identity,
   startup silence, or moved subject yields a named refusal without
   ownership leakage. Evidence: lifecycle mutation matrix.
3. Review attempts cannot access implementation mutation credentials and
   cannot reuse author attempt identity; role-specific configuration homes
   never share authentication state. Evidence: credential canaries and
   negative attempt tests.
4. Every claimed capability/OS row passes the exact host contract on macOS,
   Windows, and Linux. An absent or unsupported CLI/OS is never a pass: it
   follows the ISS-044 disposition by narrowing the declared role/capability
   surface or returning `BLOCK_REPLAN`. Evidence: complete three-OS probe
   receipts with explicit unsupported-row negatives.
5. Missing, malformed, or unknown worker role refuses before launch; only
   explicit implementation attempts receive mutation-scoped credentials, and
   every capability the `ISS-044` disposition marked cooperative-only is
   wrapped in the decided external confinement or refused. Evidence: role
   omission, confinement, and credential-canary matrix.
6. Per-attempt temporary homes and artifacts remain owned through forced
   launcher termination/restart and are reclaimed only after the exact
   process tree exits. Evidence: host-resource lifecycle and orphan negative
   tests.
7. The installed adapter reruns the ISS-031-owned shared native-store attack
   suite as extended by the `ISS-044` filesystem matrix for implementation,
   review, and observer roles on all three OSes. A successful shared-suite,
   other-role-home, broker-endpoint, or process-memory read refuses
   certification; omission or incidental backend failure is not denial.
8. This host renders `dispatch-brief/v1` through its own versioned
   deterministic template: rendering the same brief is byte-identical across
   all three OSes, the rendered digest equals the dispatch-plan binding, and
   a seeded free-form prose injection into the template inputs refuses.
   Evidence: three-OS rendering goldens, digest-equality checks, and the
   injection mutant.
9. Routing (`ISS-012`) can select between the Codex and Claude hosts for the
   same declared capability from evidence snapshots alone, and neither
   host's evidence satisfies a route requiring the other. Evidence: golden
   two-host routing cases with host-mismatch negatives.

## Predicted footprint and dependencies

Requires one reviewed `ISS-000`-owned amendment before implementation
starts: the `packages/host-claude/` skeleton, its bootstrap-manifest row,
and a `claude.authenticated-preflight/v1` broker-operation registration
mirroring the Codex preflight shape. This slice then fills only
implementation/test files in that predeclared skeleton and adds scrubbed
lifecycle fixtures. Blocked by the Claude Code authority probe `ISS-044`,
which transitively supplies dispatch, routing, custody, and the first-host
pattern. It blocks nothing on the self-host critical path.

## Operator actions

Install and authenticate the pinned Claude Code CLI on designated test
runners and approve a bounded live probe. Credentials must not be committed
or included in receipts.

## External authority probe and evidence timing

Capture CLI/executable identity immediately before launch and reported
model identity during startup before accepting worker liveness.

## Glossary impact

## Independent review packet seed

mismatch, credential crossover between role homes, shell launch, stale
subject, transcript confusion, Codex evidence or thresholds credited to
this host, cooperative refusal counted as confinement, and a CLI absent on
one OS being counted as pass. Use the lifecycle/identity matrix, the
two-host routing goldens, and the credential canary report.
