## Why

When the attached child exits after a nonterminal status, the parent currently
returns only the child exit code. The host must then infer whether the run was
lost, and can discover it long after the lifecycle moment. The smallest useful
repair is a bounded Windows-side record at the existing EOF/exit join, without
inventing a worker verdict or changing the supervisor protocol.

The lifecycle probe is the exact moment the implementation needs: status
`observing-author` was the last emitted line at `17:06:45.171Z`, then the WSL
child disappeared during the update window. The implementation must capture
`observedAt` when the parent has observed EOF and `WaitForExit`, not infer it
from a child timestamp, log mtime, or a later host poll. The child exit code is
read at that same join; if unavailable the note says so explicitly.

### Note location and closed schema

The note location is `<config-directory>\supervisor-loss\<run>.json`, where
`<config-directory>` is the directory containing the absolute `-Config` path
already supplied to `start-loop.ps1`, and `<run>` is the validated run identity
from that config. This is a Windows-side host path adjacent to the host-owned
config, outside the checkout and WSL runtime; no new parameter or runtime
directory is introduced. One run gets one deterministic note: write it once
with a temporary sibling and atomic rename, and never append or overwrite an
existing note.

The JSON object is closed (no unknown keys) and UTF-8 encoded:

```json
{
  "schemaVersion": "supervisor-loss/v1",
  "kind": "supervisor-loss",
  "classification": "supervisor loss/unknown outcome",
  "run": "<run identity>",
  "config": "<absolute config path>",
  "observedAt": "<UTC RFC3339 instant ending Z>",
  "lastObservedStatus": "<nonterminal status or null>",
  "childExitCode": 0,
  "childExitCodeAvailable": true
}
```

`childExitCode` is `null` and `childExitCodeAvailable` is `false` when the
code cannot be read. The only status value that permits omission is one of
the existing terminal controls: `idle`, `complete`, `stop`, `cancel`, or
`pause`. A note is never a native stop, worker verdict, retry permission, or
GitHub instruction. The serialized UTF-8 object is at most 4096 bytes;
`run` and `lastObservedStatus` are 1-128 ASCII characters (or `null` for the
status), `config` is an absolute path of at most 1024 characters, and
`observedAt` is one UTC RFC3339 instant. The parent refuses a value outside
these bounds rather than writing an unbounded note.

## Done when

1. **One bounded parent-side record.** In `scripts/executor/start-loop.ps1`,
   retain the last accepted status while reading the existing attached child's
   stdout. Preserve every existing echoed line, native-db request/reply
   exchange, concurrent stderr drain, `WaitForExit` handling and child exit
   code propagation. After EOF and child exit, if no terminal status was
   observed, write exactly one closed `supervisor-loss/v1` record to
   `<config-directory>\supervisor-loss\<run>.json` using a temporary sibling
   and atomic rename. The record contains only the keys and bounded values in
   the schema above, labels `supervisor loss/unknown outcome`, records the
   parent observation instant, and records the child code or explicit
   unavailable. Do not write under the checkout, WSL runtime, or a second
   process-owned directory; do not rewrite an existing note.
2. **Normal paths are unchanged.** Idle, complete, stop, cancel and pause
   terminal statuses retain their current stdout, stderr, child exit code and
   parent return behavior and write no note. A child that ends after a
   terminal status is not classified as loss. A nonterminal status followed by
   EOF is loss even for child exit code zero; a nonzero child code is recorded
   as data, never converted into a native worker verdict. Note-write failure
   reports a bounded host diagnostic without changing the propagated child
   code. No watcher, auto-restart, Linux signal, runtime backfill, retry-budget
   change, or GitHub write is added, and no note is promised when Windows or
   the parent also dies.
3. **Red-before at the real attached boundary.** In
   `test/executor.test.ts`, before the candidate change, run the existing
   attached-parent harness with an unmistakably synthetic child that emits one
   nonterminal status and exits without a terminal status. Capture the missing
   note as red for child exit code zero and for a nonzero code. After the
   change, the same real `Start-AttachedSupervisor` boundary is green: each
   case writes one durable note with the exact run/config identity, an
   observation-time assertion, the last status, and code/explicit-unavailable.
   Exercise `idle`, `pause`, `cancel` and terminal `stop` controls and assert
   that no note is written and their existing output/exit behavior remains

4. **Fail-closed and bounded controls.** Freeze all other inputs and vary one

5. **Author-local handoff.** Planned files are
