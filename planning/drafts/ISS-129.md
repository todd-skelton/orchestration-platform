## Why

On 2026-09-12 the first M2 author on chase-sets#7821 (run `m2-payout-fees`)
had finished three of its four steps when the subscription pool proxy on the
Windows host restarted under it: the trace ends with five `Reconnecting`
errors against `http://172.23.240.1:8317/v1/responses`, then `turn.failed`
with `stream disconnected before completion`; the proxy's new process start
time is three minutes after the worker's exit receipt. `observe` in
`scripts/dogfood/dispatch-adapter.ts` raised `launcher-failed` and the loop
parked the issue with `status:needs-replan` after one attempt of four. Every
stop the loop took that day was the same shape: the ISS-126 author died on a
503 while the pool's upstream TLS handshake timed out, and two ISS-122
launches died on a revoked pool token.

ISS-127 relaunches a dead worker once. That covers a single dropped stream,
but not an outage: when the provider is down for minutes, the relaunch dies
at once, the second death is `launcher-failed`, and the issue is parked for
a condition that has nothing to do with the work. The loop treats the pool
as always up; `run-loop.sh` probes `/v1/models` exactly once, at launch, and
never again.

## Done when

- The loop knows the provider it launches workers against. `run-loop.sh`
  already rewrites the pool address into the executor's Codex home; the
  simplest shape is exporting that base URL to the supervisor it starts, and
  the dispatch adapter probing `<base>/models` with the same auth the
  workers use.
- Before every launch, including the ISS-127 relaunch and the repair launch,
  the loop waits until the probe answers. While waiting it prints one
  `waiting-provider` status line per poll, like the `observing-*` lines, and
  the wait is bounded by a `providerOutageCeilingMs` in the loop config
  (default thirty minutes). Past the ceiling the stop is `provider-unavailable`
  with the last probe error as diagnostics. It is caused by the host: the note
  is posted, the issue is not parked, and the supervisor exits (Rule 7).
- A dead launch is caused by the outage, not the work, when the trace's last
  `error` or `turn.failed` message names the provider base URL, a 5xx, or a
  stream disconnect. Such a launch does not consume the single ISS-127
  relaunch and does not count as an implementation attempt; the loop waits
  for the probe and launches again. Each launch still counts one native launch
  against `nativeLaunchCeiling`, which is the only bound on a flapping
  provider.
- A dead launch whose trace names anything else keeps ISS-127's behaviour:
  one relaunch, then `launcher-failed`, parked.
- `test/dogfood/flow.test.ts` proves with a fake adapter and a fake probe:
  a provider-dead author launch waits, relaunches when the probe answers, and
  lands with the attempt count unchanged; a probe that never answers stops
  with `provider-unavailable` without parking; a dead launch whose trace does
  not name the provider still follows ISS-127.

## Out of scope

Fixing the pool proxy or the bridge. Raising `request_max_retries` in the
worker's Codex home. Provider fallback. Retrying hosted-check or GitHub API
outages; those keep their own reasons.
