## Why

The M2 run `m2-iss184-20260924T1135`, ISS-184 candidate 1, PR
[#645](https://github.com/todd-skelton/orchestration-platform/pull/645) at
`a9f94cc95163182e50c72fbe4aa10671848d87c2` exposed a platform gap.
Bootstrap run [36001909891](https://github.com/todd-skelton/orchestration-platform/actions/runs/36001909891)
passed Ubuntu in 7 minutes, failed macOS in 14 minutes, and left Windows in
`pnpm run verify:bootstrap` at `tsc --noEmit -p tsconfig.json` from
12:53:36Z until the host cancelled it at 13:41:50Z. The captured
`job-107640372535-windows-cancelled.log:166-168` has no intervening output.
The captured `bootstrap.yml.at-89934753:11-27` has a three-OS matrix and no
`timeout-minutes`; absent intervention, the supervisor would remain in
`observing-hosted-checks` until GitHub's 360-minute default job timeout.
The host's [#368 intervention receipt](https://github.com/todd-skelton/orchestration-platform/issues/368#issuecomment-5815275381)
records the manual cancellation. The captured supervisor snapshot orders
`observing-hosted-checks`, `advancing-attempt`, then observation of ISS-184:2;
it has no timestamps establishing a five-minute interval. This was an
intervention, not unattended success, and the macOS failure supplied the
repair evidence in that run.

Successful Windows jobs took 45m33s in main run
[35992311472](https://github.com/todd-skelton/orchestration-platform/actions/runs/35992311472/job/107609051531)
and 35m07s in ISS-205 run
[35988875619](https://github.com/todd-skelton/orchestration-platform/actions/runs/35988875619/job/107597924010).
Twice the slower successful duration is 91m06s. A 100-minute job limit
provides 8m54s beyond that doubled baseline while bounding an otherwise
six-hour wait. These are whole-job timings, not a diagnosis of the Windows
`tsc` hang or permission to change local test timeouts.

## Scope

Add `timeout-minutes: 100` to the single `smoke` job in
`.github/workflows/bootstrap.yml`. It applies to each matrix job, including
Windows, without changing the matrix, `fail-fast: false`, steps, required
contexts or `pnpm run verify:bootstrap`. A single job-level limit is sufficient;
there is no measured need for per-OS values. Add a focused workflow config
test/check that rejects removal or drift of the limit at the job level.

No executor-side hosted-observation deadline is in scope. GitHub owns the job
clock and reports an authoritative terminal conclusion without a second loop
clock. On current `origin/main` `89934753f69e92320e57f8f60178031a52988136`,
`scripts/dogfood/delivery-adapter.ts:298-325` maps completed `timed_out` to
`fail` and `cancelled` to `cancel`. A job-level `timeout-minutes` expiry actually
concludes `cancelled` (probe 1 below). `failedCheckLog` at
`scripts/dogfood/delivery-adapter.ts:1435-1461` currently fetches only
`gh run view <run> --attempt <n> --log-failed`, which omits cancelled jobs.
`scripts/dogfood/delivery.ts:864-880` dedupes both buckets by run. A sole
Windows timeout therefore reaches `hosted-check-log-unavailable:<name>` at
`:875`, an item stop at `supervision.ts:93`, and parks rather than repairing.
When macOS also fails, `hosted-failure.log` contains macOS but not the cancelled
Windows log. The bucket mapping and `:1259-1293` hosted-failure route remain;
log acquisition, not classification, is the missing link.

For a `cancel`-bucket check, make `failedCheckLog` fetch its own job log with
`gh run view --job <check.actions.job> --log`, retaining its before/after
`verify()` checks and completed-run gate. `fail` checks retain the existing
one `--log-failed` fetch per run. In `hostedFailureEvidence`, dedupe cancel
checks by job link and fail checks by run, so a mixed run contributes both
logs. A completed cancelled job with an empty log still raises
`hosted-check-log-unavailable`. Do not alter buckets, park reasons, the
ISS-128 completed-run gate, or any observation clock.

   three-OS matrix, `fail-fast: false`, steps and full verification command
   remain unchanged. No check, assertion or OS is skipped or weakened.
2. A focused Vitest config check fails when `bootstrap.yml` loses or changes
   `timeout-minutes: 100` at the `smoke` job level, as a sibling of `runs-on`,
   not inside a step. SYNTHETIC delivery tests use a fake `gh` whose
   `--log-failed` returns only `failure`, `timed_out`, `startup_failure`, or
   `action_required` job logs, and returns empty when the sole non-pass job
   is `cancelled`. With only Windows `cancel`, the current main rejects with
   `hosted-check-log-unavailable:Node 24 / windows-latest`; the fix returns
   `status: "failed"` and retains the Windows job log in `hosted-failure.log`.
   With macOS `fail` and Windows `cancel` in one run, that file contains both
   logs, with exactly one `--log-failed` call and one `--job ... --log` call.
   Update the exact-argument assertion and cancel fakes in
   `test/dogfood/delivery.test.ts:272-285,1314-1320,1356-1395` without dropping
   assertions; retain completed-run gating, genuine empty-log parking and
   resume idempotence. Add a `timed_out` -> `fail` row to the conclusion table
   at `test/dogfood/delivery-adapter.test.ts:178-215`, retaining the
   `cancelled` -> `cancel` row.
3. Run focused checks and `pnpm typecheck`, `pnpm format:check`,
   `pnpm planning:check`, and `pnpm test` at the candidate head. Independent

   required before landing. At the final-head hosted lifecycle moment, capture
   the run/job IDs, exact head, observed UTC instant, job conclusions and
