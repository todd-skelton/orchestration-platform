## Why

This is the M1 exit evidence. Source changes and fixtures prove nothing about
unattended operation; three real consecutive issues do.

[Run 4 exited 0 after automatically merging ISS-115, ISS-116 and ISS-117 as
PRs #394, #395 and #396, with no manual step between launch and the third
merge.](https://github.com/todd-skelton/orchestration-platform/issues/363#issuecomment-5638356108)

## Done when

- One `supervise` invocation with one `loop.json` lands three consecutive
  `ready` issues on this repository as merged PRs with green three-OS CI.
- No per-item host script, hand-edited state file or manual `gh` call is used
  between the first launch and the third merge.
- The evidence reports whether an automatic transient retry or supervisor
  restart occurred. Run 4 used zero of each; ISS-115 and ISS-116 each used an
  ordinary review repair, and a separate planned restart in run 2 resumed
  successfully.
- The run records (state directories, worker identities, PR numbers, spend as
  reported by the CLI) are retained outside the checkout and linked from this
  issue.

## Out of scope

Any new capability. If a cycle needs a manual recovery step, the learning note
becomes a new `ready` issue and this one waits.
