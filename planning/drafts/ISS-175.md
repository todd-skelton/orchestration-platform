## Why

Rule 3 says the hosted three-OS `bootstrap` workflow is the only required
check on a PR, and the loop's delivery stage enforces that itself
(`adapters/self.mjs` `REQUIRED_CHECKS`, observed before merge). GitHub
does not. Measured on 2026-09-16 with
`gh api repos/todd-skelton/orchestration-platform/rules/branches/main`:
the ruleset carries `deletion`, `non_fast_forward` and `pull_request`
rules and no `required_status_checks` rule. So `gh pr merge --auto`
from a person or an agent merges immediately.

That is how PR #526 (`322fcba`) landed at 23:17:42Z with no job of
PR-head run `35161647660` concluded and main run `35161658257` not yet
created (it started at 23:17:44Z; the first ubuntu job finished at
23:20:54Z). The change was planning-only and all six jobs later passed,
but the landing was not gated, and the supervisor reconciling PR #519 had
to treat main publication as unverified. The loop's own
authority model (rule 6) was never at risk; the gap is outside the loop,
where everyone else merges.

## Decision

Constraint: the loop's delivery path must keep observing the same three
contexts, and no receipt, verifier anchor or protection audit program
returns (parked 2026-09-10 under "Not carried forward"). Simplest
alternative: a written rule that humans wait for green, which is what rule
3 already is and what just failed. Chosen: one additive
`required_status_checks` rule on ruleset `21694457`
(`protected-main-conformance`) naming the three bootstrap contexts with the
strict up-to-date policy off, applied by the author with the `gh` sign-in
the executor already holds (`todd-skelton`). Todd's authorization on
2026-09-17, verbatim: "Part of this issue would be for the agent to change
the rules with my github sign in. I only need to approve the change," and
readying #531 is that approval. The ruleset id, the strict-off policy and
the script shape are scoped implementation choices under that
authorization, not words Todd wrote. The live `apply` is a one-time
exception to rule 6's worker-publishing prohibition, limited to this one
mutation; rule 9 is untouched, since no runtime state is edited and no
second loop writer is introduced. Accepted downside: a hosted outage blocks
every landing, including planning-only ones, until an operator bypasses it
explicitly. Revisit when: the required contexts are renamed, or a run
records a merge blocked by a check the loop does not observe.

## Done when

- A tracked script, `scripts/planning/require-bootstrap-checks.mjs`, reads
  ruleset `21694457` with `gh api`, and in `check` mode exits non-zero
  unless a `required_status_checks` rule exists whose contexts equal
  `REQUIRED_CHECKS` in `adapters/self.mjs` (`Node 24 / ubuntu-latest`,
  `Node 24 / windows-latest`, `Node 24 / macos-latest`) with
  `strict_required_status_checks_policy` false. In `apply` mode it adds
  that one rule when absent and is otherwise a no-op; the existing
  `deletion`, `non_fast_forward` and `pull_request` rules, conditions,
  bypass actors and enforcement are sent back unchanged from what was read.
  It never removes or rewrites another rule. A test with an injected `gh`
  double covers absent, present and foreign-rule cases.
- The author runs `apply` once against the live repository during the
  attempt, then `check`, and pastes both outputs and the resulting
  `gh api repos/todd-skelton/orchestration-platform/rules/branches/main`
  output in the PR description. The independent reviewer reruns `check`
  and reads the live rules; the reviewer never runs `apply`.
- Rule 3 in `docs/loop.md` states that GitHub enforces the same three
  contexts on `main` and names the `check` command that proves it.
- The loop's own delivery path is unchanged: `REQUIRED_CHECKS`,
  `observePublication` and the merge path in `delivery-adapter.ts` pass
  their existing tests without modification.
- Run typecheck, format:check, planning:check and test.

## Simplest shape and not built

| Not built                                     | Reason                                                       |
| --------------------------------------------- | ------------------------------------------------------------ |
| A loop-side check that the ruleset exists     | Rule 9: the loop guards its own authority, not GitHub's       |
| A pre-apply approval comment or ruling packet | Todd's approval is the ready label on #531; one mutation only |
| Protection receipts or verifier anchors       | Parked 2026-09-10; nothing recorded a need for them          |
| Requiring reviews or linear history on main   | Not what failed; keeps the change to the observed gap        |

## Out of scope

Changing which checks the loop observes, adding checks to the workflow,
altering merge method or queue settings, or rolling back PR #526.
