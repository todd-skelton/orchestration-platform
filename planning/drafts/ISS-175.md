## Why

Rule 3 says the hosted three-OS `bootstrap` workflow is the only required
check on a PR, and the loop's delivery stage enforces that itself
(`adapters/self.mjs` `REQUIRED_CHECKS`, observed before merge). GitHub
does not. Measured on 2026-09-16 with
`gh api repos/todd-skelton/orchestration-platform/rules/branches/main`:
the ruleset carries `deletion`, `non_fast_forward` and `pull_request`
rules and no `required_status_checks` rule. So `gh pr merge --auto`
from a person or an agent merges immediately.

That is how PR #526 (`322fcba`) landed at 23:17:42Z while PR-head run
`35161647660` and main run `35161658257` still had Windows and macOS
jobs in progress. The change was planning-only and both ubuntu jobs had
passed, but the landing was not gated, and the supervisor reconciling
PR #519 had to treat main publication as unverified. The loop's own
authority model (rule 6) was never at risk; the gap is outside the loop,
where everyone else merges.

## Decision

Constraint: the loop's delivery path must keep observing the same three
contexts, and no receipt, verifier anchor or protection audit program
returns (parked 2026-09-10 under "Not carried forward"). Simplest
alternative: a written rule that humans wait for green, which is what rule
3 already is and what just failed. Chosen: one `required_status_checks`
rule on the `main` ruleset naming the three bootstrap contexts with strict
up-to-date policy off, so hosted CI blocks the merge button and
`gh pr merge --auto` waits as it is designed to. Accepted downside: a
hosted outage blocks every landing, including planning-only ones, until an
operator bypasses it explicitly. Revisit when: the required contexts are
renamed, or a run records a merge blocked by a check the loop does not
observe.

## Done when

- The `main` ruleset requires exactly the contexts in
  `adapters/self.mjs` `REQUIRED_CHECKS`: `Node 24 / ubuntu-latest`,
  `Node 24 / windows-latest`, `Node 24 / macos-latest`. This is an
  operator change on GitHub, not a worker change; the closing comment
  pastes the `gh api .../rules/branches/main` output showing the rule.
- Rule 3 in `docs/loop.md` states that GitHub enforces the same three
  contexts on `main` and gives the one `gh api` command that proves it.
- Merge queue behavior is unchanged: the loop's `enqueuePullRequest` path
  and `observePublication` checks in `delivery-adapter.ts` still pass
  the existing tests without modification, and a landing through the loop
  after the rule is added is recorded in the closing comment.
- Run typecheck, format:check, planning:check and test for the docs edit.

## Simplest shape and not built

| Not built                                     | Reason                                                       |
| --------------------------------------------- | ------------------------------------------------------------ |
| A loop-side check that the ruleset exists     | Rule 9: the loop guards its own authority, not GitHub's       |
| Protection receipts or verifier anchors       | Parked 2026-09-10; nothing recorded a need for them          |
| Requiring reviews or linear history on main   | Not what failed; keeps the change to the observed gap        |

## Out of scope

Changing which checks the loop observes, adding checks to the workflow,
altering merge method or queue settings, or rolling back PR #526.
