## Why

A retained `delivery`-phase attempt whose refresh DELTA review failed is never
projected to `phase: "failed"`, so the next selection of the same key in the same
run stops `malformed-attempt-record` before any worker launches. The loop halts
with no attempt consumed, no failed receipt, and the reviewer's prescribed fix
stranded in a terminal no successor reads.

Run `m1-author-parser-recovery-20260917T0546`, read-only under
`/root/orchestration-m1/runtime/m1-author-parser-recovery-20260917T0546/`,
records the whole sequence. Cycle 1 selected ISS-174 (#529) at base
`804e9357a88868daab31b211966f645baeca6c02`. Its source author
`01a0ade7-0cfa-70b1-8c75-a212d82f51db` passed and its source reviewer
`01a0adec-b4cf-7441-8350-4918864f89ef` passed at candidate
`a0ffac88e8ad1cff0db47659f37d14fc46662ef0`. Two gate stops
(`cycle-1-stop-1.json` and `cycle-1-stop-2.json`, both
`gate-attribution-unknown:planning:board-check` naming six
BOARD_CONTRACT_MISMATCH siblings) were admitted as an ISS-157 gate-stop
continuation: `iss-174-attempt-1/source/gate-stop-continuation.json` reserves the
grant (`repairSha 6666cec7d55242902e4f866a00db2c23c726a514`, authority
[#529 comment 5748812816](https://github.com/todd-skelton/orchestration-platform/issues/529#issuecomment-5748812816)).
The continuation refreshed onto main `af3bcd2fe58700c8459445168dc5d0943e51a1e2`

`804e935... !== af3bcd2...` and throws `"malformed-attempt-record"`
(`queue.ts:1696`) before setup, worktrees or any launch.

No failed receipt is written at stop time either. `finalStep`
(`queue.ts:1944-2025`) lists `refresh-review-failed` among the reasons it
converts into `attemptFailureRecord`, but only when
`item.acceptedReplan || item.conflictContinuation` (`queue.ts:1949`); a gate-stop
continuation is neither, so nothing runs. The defect is therefore a missing
projection, not a missing stop handler.

**The same defect applies to an ordinary ISS-148 refresh DELTA FAIL outside a
continuation.** `scripts/dogfood/refresh.ts` throws `refresh-review-failed` from
three places, and this brief generalizes over exactly the two whose retained
record carries a `native-refresh.head`: `refresh.ts:311` (`reviewRefresh`
`reviewer-failed`) and `refresh.ts:325` (the terminal non-PASS verdict, parsed at
`refresh.ts:324` and thrown at `refresh.ts:325`). For those two the retained
record shape is identical in both cases: `phase: "delivery"`, an accepted stage,
the pre-refresh head, and a latest same-item participant that is a failed
`stage: "refresh"` reviewer. The third site, `refresh.ts:259`
conflict-resolution `reviewer-failed`, is **excluded**: it is reached only under
`if (active.conflict && !active.head)` (`refresh.ts:225`) and `active.head` is
first assigned at `refresh.ts:264`, after the try/catch that throws, so its
retained `native-refresh.json` has **no** `head` and instead carries
`resolutionUsed: true` and a `conflict` object (`refresh.ts:186-188`,
`refresh.ts:217-220`). That shape cannot satisfy this projection's head binding,
and ISS-160's `failedConflict` does not own it either, because `failedConflict`
demands a failed **author** terminal at the pinned conflict seed
(`queue.ts:1351-1358`) while this site raises on a passed author and a FAILing
conflict-resolution reviewer. It keeps refusing at `queue.ts:915` exactly as it
does today. Two structural differences matter for the two generalized sites and
the implementation must absorb both. First, an ordinary refresh writes
`native-refresh.json` in the accepted stage directory (`refresh.ts:85-88`,
`origin = delivery.stateDirectory`), while the ISS-157 continuation writes it in
the `gate-stop-continuation/` sibling and an ISS-152 gate correction writes it in
the `gate-correction/` sibling - the same three origins
`repositoryQueueAdapter.delivery` already resolves (`queue.ts:3058-3065`
and `queue.ts:3199-3205`). Second, an ordinary refresh leaves
**no** item-local `gate-stop.json`: `stopGate` is reached from the refresh catch
only when `recovering` (`queue.ts:3329-3336`), which is why this run has
`source/gate-stop-continuation/gate-stop.json` with
`reason: "refresh-review-failed"` while an ordinary refresh would have none. A
refresh only runs after main moved, so the retained base practically never equals
the new selection base and `malformed-attempt-record` is the outcome; in the
theoretical equal-base case the loop instead re-enters delivery and re-parks at
`refresh.ts:325` without ever advancing, which is the same stall under a
different reason.

`docs/loop.md:132-133` promises that a failed delta review "follows the ordinary
work-caused stop and parking policy", and `docs/loop.md:366-367` promises that
explicit planning unpark "can admit it again". Neither promise holds today for
any issue parked this way, so the defect is generic to the delivery phase, not
specific to ISS-174 or to #529.

## Decision

Constraint: keep the three existing projections, `validateFailedAttempt`'s exact
key set, `validateAttempt`'s base demand for every other record shape, ISS-157's
single-writer continuation reservation, ISS-148's refresh records, the
four-attempt ceiling and every retained byte unchanged, and derive the advance
only from persisted worker records, never from an invented review. Simplest
alternative: have the delivery adapter write `phase: "failed"` when
`refresh-review-failed` is thrown, rejected because that stop is raised from
inside an in-flight delivery whose replay is the documented reconciliation for a
lost integration response (`queue.ts:3319-3328`), so a park-time rewrite would
leave an ordinary same-cycle resume unable to re-enter delivery at all and would
change ISS-148's steady state for every refresh rather than only failed ones.
Chosen: beside the ISS-160, ISS-179 and ISS-181 observations, composition
observes a retained `delivery`-phase record for the selected key whose latest
same-item history participant is a `stage: "refresh"`, `role: "reviewer"`,
`outcome: "failed"` entry, whose `reviewer-attempt` and `reviewer-terminal` pair
at the resolved refresh directory carries that same identity with
`status: "failed"` at the refresh head, whose refresh origin is resolved exactly
as `repositoryQueueAdapter.delivery` resolves it, which holds no `publication` or
`publication-intent` at either the accepted stage or the refresh directory, whose
item-local `gate-stop.json` reads `refresh-review-failed` when one exists at that
origin, and whose run-scope completed item-stop pair records
`refresh-review-failed` for this key at this `candidateAttempt`; it then advances
that record once to `phase: "failed"` with `head` set to the reviewed refresh
head, `findings` set to the reviewer's prescribed findings parsed from the same
terminal the `refresh.ts:324` parse reads before `refresh.ts:325` throws,
`reviewId` set to that refresh reviewer's identity, `history` recovered through
`readQueueHistory` and `authorFailures`
retained verbatim, and `acceptedStage` and `stateDirectory` cleared to `null`, so
the existing tail of the scan composes `iss-<key>-attempt-N+1` at the rebased
refresh head and refuses with `implementation-attempt-ceiling-exhausted` at the
ceiling; the reviewed refresh head is chosen over the retained head because
`finalStep` already prefers `refreshed.head` for exactly this phase
(`queue.ts:1983-1991`), because the prescribed findings' `file:line` coordinates
and the "Start from rejected candidate" prescription (`queue.ts:1034-1035`) are
coherent only at the head the reviewer actually read, and because
`attemptBase = attempt.rebasedBase ?? attempt.head` feeding `pendingRebase`
(`queue.ts:924` and `queue.ts:956-976`) then rebases a head that already
integrates the refresh main, where the pre-refresh head would replay the
integration the refresh performed and would attribute that delta to the next
author against `mainBase`. Accepted downside: attempt 1 is consumed by a review
it never got a repair stage for, because a DELTA FAIL has no repair path, so each
refresh rejection spends one implementation attempt and hands its prescription
forward as findings rather than as a repair, which this brief accepts as the
already-published ISS-148 parking cost. What would show this wrong: a recorded
run in which a `delivery`-phase record carrying a failed refresh reviewer should
have resumed rather than advanced - an in-flight reviewer with no terminal, a
later PASS after further main movement, or a publication already open at the
refresh head - which is why each of those shapes must keep breaking at
`queue.ts:915` exactly as it does today.
