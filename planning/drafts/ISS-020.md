## Context and evidence

Final N0 certification must include the bootstrap workflow, executable,
installer, schemas, and tests in the same immutable source it certifies. The
generic release protocol comes from `ISS-014`; trusted harness rules come from
`ISS-006`; authenticated workflow/grant authority comes from `ISS-029`.

## Scope fence

In: pinned production `.github/workflows/bootstrap-build.yml`,
`.github/workflows/bootstrap-review.yml`, and
`.github/workflows/bootstrap-authorize.yml`, `orchestration-bootstrap`
executable, exact argv/envelope/parser contract, source-subject generation,
minimal transactional installer/recovery command, native-broker recovery
capability custody, N0 schemas, wrappers, fault fixtures, and
canonical idempotent pre-mutation `abort` command/request/receipt,
source/package census registration; reviewed broker plan/install/verify/remove
commands that invoke only the `ISS-032` lifecycle transaction library.

Out: selecting the final N0 revision, final OS certification, semantic review,
human grant, installation, active authority, or N0 orchestrating N1.

## Decisions already made

The bootstrap CLI surface in `docs/architecture/bootstrap-manifests.md` is
exhaustive. Root scripts are literal wrappers. Pinned workflow context emits an
exact lowercase-hex source subject; symbolic revisions such as `HEAD` refuse.
Candidate runtime code cannot select tests, aggregate receipts, review, grant,
or install itself.
Production workflows implement the exact passed `ISS-029` claim/trigger/
attestation contract but are distinct bytes and paths from the probe-only
workflows; final certification binds and tests both the correspondence and the
fact that probe workflows cannot target production commands/state.

## Acceptance criteria and evidence

1. The tracked source/package census includes every bootstrap workflow,
   executable, installer, schema, wrapper, and test byte that final certification
   must bind. Evidence: manifest coverage report.
   This includes `bootstrap-review.yml`, its closed semantic-review prompt/result
   schema, distinct-role launcher, and candidate-substitution canaries.
2. Each bootstrap command has one canonical positive argv and missing,
   duplicate, unknown, positional, wrong-schema, actor, and symbolic-revision
   negative fixtures. Evidence: generated parser/authority matrix.
3. Pnpm wrappers forward byte-equivalent argv and produce byte-identical records
   to the bootstrap executable; they add no defaults. Evidence: wrapper parity.
4. Crash injection at every installer boundary reaches predecessor, installed
   successor, or same reviewed recovery transaction. Evidence: fixture fault
   matrix; no real authority grant occurs.
5. Candidate-controlled workflow/test selection, aggregation, review, grant, or
   installer substitution is impossible through the bootstrap capability set.
   Evidence: environment/filesystem capability canaries.
6. Before first mutation the installer stores a one-use raw recovery capability
   only in the admitted native broker and durably binds its non-secret reference,
   generation, digest, target host/user, transaction, installer, candidate, and
   state root, then executes exact authorization-created → cleanup-gate
   PENDING/read-back → consume/read-back `CONSUMED_BOUND` → first-destination-
   mutation ordering. The canonical `recover`
   command proves and reuses only that existing bound record after process and
   host restart; it never consumes again. Missing, unconsumed, locked, copied,
   replayed, substituted, or wrong-host/user
   capability refuses. Evidence: kill/reboot at every mutation boundary plus
   pre-bound consume/read-back, recovery reuse, second-consume/replay, and
   terminal broker-internal revocation canaries.
   Before gate creation, abort may invoke the existing narrowed recovery-admin
   revoke method only for unconsumed state after authoritative gate/destination
   absence. After gate creation, abort CASes the gate to `ABORTING`; only the
   broker reconciler revokes unconsumed/consumed state from destination absence,
   and the exact resumed bootstrap command commits archive/head/gate removal.
   After any destination mutation abort/client revoke refuse. Evidence: crash/
   restart at every create/gate/consume/mutation and abort revoke/head boundary
   plus false-absence/race controls.
   `abort --input <file> --output <file>` is the sole cancellation surface. It
   consumes the existing immutable `bootstrap-install-input/v1`, derives the
   deterministic transaction/authorization/gate paths, and reads the
   authoritative destination census itself; no separate abort request exists.
   Authorization-absent input refuses, pre-gate unconsumed state revokes, and
   post-gate state records/resumes `ABORTING`; post-mutation input refuses.
   Repeated exact invocation returns the same receipt; moved transaction/input/
   destination census refuses.
7. The canonical `bind-credentials` command accepts only non-secret native
   references plus the exact accepted review/candidate/target-host/user/state-
   root bindings and emits `bootstrap-credential-set-receipt/v1`. Under only
   `bootstrap.credential-verify`, it may request the broker's static certified
   read-only canaries and receive their non-secret capability proofs. It runs from
   the attested reviewed bootstrap bundle, never source-tree runtime code, and
   cannot install, lease, dispatch, receive referenced secrets, choose callbacks/
   endpoints, or request mutation capabilities. Evidence:
   exhaustive argv/actor/capability and source-tree/candidate substitution tests.
8. The reviewed bootstrap bundle statically imports the exact canary descriptors
   owned by `ISS-021` and `ISS-033`, plus the broker-client manifest/factory from
   `ISS-032`; it exposes no runtime registration. Evidence: source/bundle/export/
   descriptor digest census and missing/extra/duplicate/moved/callback/deep-
   import mutants, all included in final certification and semantic review.
9. `bootstrap/build/composition.ts` is the sole bootstrap composition entrypoint.
   Through the predeclared build-only alias it emits one closed installer/binder
   bundle with only the bootstrap grantees/methods in the broker-client manifest.
   Evidence: bundle/method/manifest census and alternate-entrypoint, runtime
   deep-import, dynamic registration, source-map, and shipped-generator mutants.
10. The canonical broker commands bind the accepted candidate/review, exact
    `ISS-031` topology, broker executable/service-definition digests, host,
    custody/runtime principals, endpoint, and transaction. Production
    `broker-plan` requires the exact `host-custody-retention-receipt/v1` and CAS-
    binds reduced profile/manifest/executable/key generation to the final
    production profile/operation-manifest/executable. `broker-install` emits
    `broker-upgrade-receipt/v1`; `broker-verify` proves the same non-exportable
    host key reference/public key/generation, new production authority, and old-
    byte denial. Install/upgrade/restart/remove require explicit OS
    administration and fresh plan/read-back; interruption resumes or removes
    only that transaction. Evidence: complete argv/actor/profile/key/fault
    matrix and three-OS principal/service/endpoint/binary census.
11. `bootstrap/build/broker-service-composition.ts` is the sole broker executable
    entrypoint. It statically injects into the `ISS-032` core exactly the Codex
    descriptor/implementation from `ISS-021` and ten GitHub descriptors/
    implementations from `ISS-033` listed in
    `broker-operation-manifest/v1`, then emits the exact service output named in
    the build contract. Real synthetic-provider canaries pass through the
    installed service on all OSes. Evidence: operation/descriptor/method/bundle
    census plus missing/extra/duplicate/moved/callback/endpoint/capability,
    direct-import, source-map, tarball, and provider-secret-output mutants.
