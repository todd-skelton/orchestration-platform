## Why

`verifyWorkspace` in `scripts/dogfood/delivery-adapter.ts:696-722` spawns 17 Git
processes on every call at current main
`817d07532375283c2ee1115e7c0460f3f8630b11`, and it is called once per draft
observation and once per gate across three real `deliver()` passes. In the owning
dogfood closure cases that is about 32 calls, about 544 of the roughly 638
built-in Git processes a single case spawns - about 85% of all Git work in a case
that has 2187ms of headroom under a 30000ms limit.

The failure that demonstrates the cost is ISS-182. Its attempt 2 stopped
`author-failed` at `465f1beb2f16c6d77a8b3e79bfac247884976f08` on branch
`codex/iss-182`, open as draft PR #576, whose whole diff is
`test/dogfood/refresh.test.ts`, +20/-14. At that head
[Windows job 105540420500](https://github.com/todd-skelton/orchestration-platform/actions/runs/35326425131/job/105540420500)
ran `refresh.test.ts` for 1504596ms and recorded 3 failed, 1079 passed and 17
skipped; the six-deletion sibling case `mirrors the exact six ISS-174 deletions
(autocrlf: true)` timed out at 30017ms against the unchanged 30000ms limit. No
base control ran on that runner, so the candidate is not attributed as the cause
of that timeout - and equally, the candidate did not carry the owning file under
the unchanged gate.

The attempt-2 author measured the dominant cost with `GIT_TRACE` over three
repeated samples per arm, retained read-only at
`\\wsl.localhost\Ubuntu\root\orchestration-m1\runtime\m1-sibling-mirror-recovery-20260917T0848\iss-182-attempt-2\source\author-temp`.
Those traces are **pre-ISS-189**: each base run of the partial-mirror-true
closure case spawned 670 Git processes, of which 581 (86.7%) are the five
`verifyWorkspace` command shapes and 576 are the 32 `verifyWorkspace` cycles
themselves at that runtime's 18 spawns per call. The residual 89 spawns are the
fixture construction - `init`, `clone --bare`, three `worktree add`, `fetch`,
`commit`/`add`/`reset`, `ls-tree`, eight `merge-base` and the plan's draft `show`
reads - every one of which ISS-182 AC1 requires the fixture to keep. `601f79d`
(ISS-189, PR #583) has since removed one `rev-parse --git-common-dir` per call,
so current main is 17 spawns per call and about 638 per closure-true case. The
shape of the cost is unchanged: it is runtime Git process volume on the
`verifyWorkspace` path, not fixture work.

Two green Windows logs at current main measure how little room is left. At
`490fe76` the closure cases took 27565ms and 27813ms and the six-deletion cases
22865ms and 21655ms over a 1358391ms file; at `2e04eb5` they took 23932ms and
26201ms, and 22275ms and 22366ms, over 1344928ms. Worst-case headroom is
30000 - 27813 = **2187ms, 7.3%**, while #576's runner was **10.8-11.9%** slower
on the same file (1504596ms against 1358391ms and 1344928ms). 27813ms at that
observed slower rate is about 31114ms - over the limit. A runner no slower than
one already observed this month puts the closure-true case over the gate with no
product defect present.

The independent planning review of the ISS-182 replan
(`ROOT/.orchestrator/platform-iss182-replan-review-r2.report.md`, verdict
BLOCK_FIXABLE, its F2 and its "Recommendation to the host") recommended
registering exactly this issue and confirmed ISS-189 as proof the work is
reachable and bounded: 3 changed runtime lines plus 389 lines of coverage.

**ISS-182 stays parked and is NOT a dependency of this issue.** ISS-182 owns the
fixture fence inside `test/dogfood/refresh.test.ts`; it has spent its named
fixture candidate for -7 of 670 spawns and reported this runtime volume as its
blocker. Its un-park condition names this issue's landing *plus* a measured
threshold: at this issue's final head both closure variants measured on a hosted
Windows runner under the unchanged 30000ms test/hook limits,
`fileParallelism: false` and the existing platform skips, with worst-case

alone is not the threshold: ISS-189 landed, reduced this very volume, was never
measured against these cases, and left them at 2187ms. This issue owns the
reduction and its measurement; it does not un-park ISS-182 and does not amend it.
`blocked_by` is therefore `[]`.

## Decision

Quality profile: core-library (one runtime script function and its coverage).

Constraint: every fact `verifyWorkspace` establishes today must still be
established, live, on every call, from the same working directories, with the
same refusal outcomes and the same fail-fast ordering. No retained record shape,
persisted artifact, state-directory file, `DeliveryConfig` field, adapter
interface, test timeout, worker setting, `vitest.config.ts` key, fixture body or
platform skip changes. No runtime Git behavior changes except how many processes
deliver the same reads.

### Which of the 17 may be derived once, and why the answer is none

The named reducible shape - the `remote get-url` / `--push` pair per root (6 of
17) as "immutable remote configuration" and `--git-common-dir` per worktree (3 of
17) as "worktree family membership" - **does not survive contact with the
coverage ISS-189 landed**, and this brief rejects it explicitly so that no
implementer re-proposes it:

- Within one `verifyWorkspace` call exactly one duplicate `(command, cwd)` pair
  remains, and this brief takes it. The nine `assertWorktreeRepository` reads are
  three distinct commands at three distinct working directories, so nothing is
  available there. The authority reads are different: `status --porcelain` is
  issued at `config.controllerRoot` (`delivery-adapter.ts:705`) and again at
  `config.repositoryRoot` (`:711`), and those two fields hold the **same path** in
  every configuration this issue is measured against.
  `test/dogfood/refresh.test.ts:790-791` sets `repositoryRoot: f.repo` and
  `controllerRoot: f.repo`, and that `DeliveryConfig` drives both closure cases
  and both six-deletion cases; `test/dogfood/delivery-adapter.test.ts:527-528`
  sets both fields to `resolve(root, "controller")`, so ten of the eleven AC2
  matrix variants run with coincident roots and only `root-dirty` separates them,
  explicitly, at `:823`. That duplicate is call-local, crosses no call boundary,
  and is taken in `### Chosen shape` below by serving both directories' facts from
  one live process. It is not a cache: every fact is still established live, on
  every call, from the working directory that owns it.
- Across calls, the remote URLs are not immutable and are proven not to be.
  `test/dogfood/delivery-adapter.test.ts:968` ("rechecks real worktree-local
  %s-controller %s %s URLs after %s target drift") verifies a workspace, then
  sets a **worktree-local** `remote.origin.url` or `pushurl` through
  `extensions.worktreeConfig`, then requires the next call to refuse. Any cache
  spanning two calls returns the stale URL and that case fails.
- Across calls, worktree family membership is not immutable either.
  `test/dogfood/delivery-adapter.test.ts:1043` ("canonicalizes a real repository
  alias while retaining fresh worktree-family checks") rewrites the review
  worktree's `.git` gitfile to a foreign clone between two calls and requires the
  second to refuse.
- Across one `deliver()` pass, `test/dogfood/delivery-adapter.test.ts:1120`
  ("refuses intervening real workspace drift between %s") drifts
  `remote.origin.pushurl` between two draft mutations and between a gate and
  publication, inside a single `deliveryStep`, and requires the next
  `verifyWorkspace` to refuse with `candidate-workspace-drift`. A per-pass cache
  is precisely what that case exists to reject.
- Independently of any test: `assertGitTarget` is the anti-exfiltration
  authority. Caching it across calls means a mid-pass repoint of `origin` to a
  foreign remote is not seen before the next push. That is a security regression,
  not an optimisation.

Combining the pair into one process was also checked and rejected on measured Git
behavior. `git remote -v` reports **all** push URLs but only the **first** fetch
URL: with two `remote.origin.url` entries configured,
`remote get-url --all origin` printed both and `git remote -v` printed one. The
`["same", "reviewWorktree", "fetch", "multiple"]` tuple at
`delivery-adapter.test.ts:968` adds a second fetch URL exactly so that
`urls.length !== 1` refuses; under `remote -v` it would be accepted.
`git config --get-all` is not a substitute either: `remote get-url` applies
`url.<base>.insteadOf` rewriting, which that same test depends on. The six
`remote get-url` spawns are therefore irreducible, and `assertGitTarget`
(`:505-521`) must not change at all - four other call sites (`:585`, `:605`,
`:1485`, `:1517`) depend on its exact two-spawn behavior and its
`delivery-repository-mismatch` / `delivery-repository-unverified` codes.

Replacing the three per-worktree `rev-parse --git-common-dir` with one
`git worktree list --porcelain` at the repository root is rejected for the same
reason: that asks the root which worktrees it has registered, while the shipped
check asks each worktree which common directory *it* resolves to. The
administrative entry survives a rewritten gitfile, so the root-side question
cannot see the drift `:1043` demands be seen.

**Conclusion: none of the 17 may be carried across calls, derived once per
verification pass, or derived once per `deliver()` pass. All 17 facts stay live
and per call, read from the working directory that owns them at the moment they
are used.** The answer to the spawn volume is not a cache; it is fetching more
than one live fact per process - including, where two configured roots are one
directory, fetching four of them.

### Chosen shape

Leave `assertGitTarget` and `assertWorktreeRepository` (`:523-538`, nine spawns)
exactly as ISS-189 landed them, and replace the eight authority reads inside
`verifyWorkspace` (`:700-716`) with one `git status --porcelain=v2 --branch` per
**distinct** working directory. That command reports the resolved HEAD object id,
the current branch and the working-tree state in a single process, so each
`(rev-parse HEAD, status --porcelain)` pair and the
`(branch --show-current, status --porcelain)` pair at the repository root collapse
to one spawn each, at the same working directory, in the same order, comparing the
same values.

When `controllerRoot` and `repositoryRoot` canonicalise to the same directory -
decided by `realpath` + `samePath`, exactly the canonicalisation
`assertControllerExecutor` (`:636-640`) already performs on those two fields -
rows 10-13 are served by **one** live `status --porcelain=v2 --branch` at that
directory, whose single output is evaluated against the controller revision, then
the `main` predicate, then cleanliness, in the current order and with the current
refusal outcomes. When the two roots differ, two reads are issued at two
directories exactly as today.

**17 spawns per call become 12 when the two roots coincide and 13 when they do
not.** The coincident case is what every case this issue is measured against runs:
a 29.4% per-call reduction, about 160 fewer spawns per closure case (544 -> 384 of
about 638, about 25% of all Git work in the case). The distinct-roots case is a
23.5% reduction and about 128 fewer spawns. Both numbers are normative: AC1 and
AC2 below bind the per-call count **per configuration**, not one fixed number.

What the count reduction does and does not buy. Every shape removed is a ref read
- three `rev-parse HEAD` and one `branch --show-current` per call - while every
shape retained at those same working directories is a `status` worktree walk. The
per-call count reduction is therefore an **upper bound** on the reduction in Git
work, which is what the wall-clock threshold actually measures. The implied
requirement is stated here rather than assumed: closing the worst observed closure
case from 27813ms to 26785ms needs **1028ms** across the removed spawns - about
**8.0ms per spawn** at 128 removed (distinct roots), about **6.4ms per spawn** at
160 removed (coincident roots). No figure in this lineage underwrites that number.
ISS-182's 42-53ms per spawn is whole-case wall-clock divided by total spawn count,
an upper bound that assumes all case time is spawn cost, so it cannot be spent on
*marginal* saving on the cheapest shapes. Windows `git.exe` process-creation
overhead plausibly clears it; this brief does not assume it. That is why the
coincident-root reuse is taken rather than left: it is the only remaining reduction
on the expensive `status` shape available inside this footprint.

`assertControllerExecutor` (`:630-669`) carries the same coincident-root duplicate
- `rev-parse HEAD` and `status --porcelain` at the executing root (`:649`,
`:653`) and `branch --show-current` and `status --porcelain` at `repositoryRoot`
(`:661`, `:662`) - and is **out of scope** here. It is a separate exported
function with its own call sites (`scripts/dogfood/queue.ts:2394`,
`delivery-adapter.test.ts:2217`, `:2830`, `:3480`, `:3484`, `:3490`), it is not
on the `verifyWorkspace` per-call path, and this issue's footprint is the body of
`verifyWorkspace`. Leave it byte-unchanged; the remedy does not spread to it.

Per call, the disposition of each invocation is:

| #     | Invocation                             | Working directory | Fact                       | Disposition                                                                     |
| ----- | -------------------------------------- | ----------------- | -------------------------- | ------------------------------------------------------------------------------- |
| 1     | `rev-parse --git-common-dir`           | `repositoryRoot`  | root common directory      | keep live, own spawn                                                            |
| 2     | `remote get-url --all origin`          | `repositoryRoot`  | effective fetch URL set    | keep live, own spawn                                                            |
| 3     | `remote get-url --push --all origin`   | `repositoryRoot`  | effective push URL set     | keep live, own spawn                                                            |
| 4     | `rev-parse --git-common-dir`           | `worktree`        | worktree family membership | keep live, own spawn                                                            |
| 5     | `remote get-url --all origin`          | `worktree`        | effective fetch URL set    | keep live, own spawn                                                            |
| 6     | `remote get-url --push --all origin`   | `worktree`        | effective push URL set     | keep live, own spawn                                                            |
| 7     | `rev-parse --git-common-dir`           | `reviewWorktree`  | worktree family membership | keep live, own spawn                                                            |
| 8     | `remote get-url --all origin`          | `reviewWorktree`  | effective fetch URL set    | keep live, own spawn                                                            |
| 9     | `remote get-url --push --all origin`   | `reviewWorktree`  | effective push URL set     | keep live, own spawn                                                            |
| 10-11 | `rev-parse HEAD` + `status`            | `controllerRoot`  | revision, cleanliness      | one `status --porcelain=v2 --branch`; also serves 12-13 when the roots coincide |
| 12-13 | `branch --show-current` + `status`     | `repositoryRoot`  | branch is main, cleanliness| the same process as 10-11 when the roots coincide; its own one when they differ  |
| 14-15 | `rev-parse HEAD` + `status`            | `worktree`        | candidate head, cleanliness| one `status --porcelain=v2 --branch`                                            |
| 16-17 | `rev-parse HEAD` + `status`            | `reviewWorktree`  | candidate head, cleanliness| one `status --porcelain=v2 --branch`                                            |

No row is derived once per pass or per `deliver()`; every row is read live on
every call. Rows 1-9 keep their own process for the reasons above. Rows 10-17 are
served by **three** `status --porcelain=v2 --branch` processes when
`controllerRoot` and `repositoryRoot` canonicalise to one directory - the
configuration every measured case runs - and by four when they differ.

The whole runtime footprint is the body of one function;
`assertWorktreeRepository`, `assertGitTarget`, `DeliveryConfig`, the adapter
interface and every `delivery.ts` call site are untouched.

Confirmed against a real Git before this brief was written, and to be
re-confirmed against the executable resolved at implementation time:

- `git status --porcelain=v2 --branch` on a clean tree with no upstream prints
  exactly `# branch.oid <sha>` and `# branch.head <name>`.
- With an upstream configured it also prints `# branch.upstream <ref>` and
  `# branch.ab +N -M`. **A clean tree that is ahead of its upstream still prints
  `# branch.ab +1 -0`.** "Clean" therefore means "no line outside the
  `# branch.*` headers", never "exactly two lines" and never "empty output".
  Today's `status --porcelain` returns `""` for an ahead-but-clean tree and the
  replacement must agree.
- `# branch.head` is `(detached)` on a detached HEAD, where
  `branch --show-current` returns `""`. Both fail the `!== "main"` comparison, so
  the repository-root predicate is preserved; state the equivalence rather than
  assuming it.
- `# branch.oid` is `(initial)` on an unborn HEAD, where `rev-parse HEAD` exits
  non-zero. Today that throw is caught by `verifyWorkspace` and becomes `false`;
  `(initial)` compares unequal to any 40-character head and also becomes `false`.
  Same outcome, different path - say so and cover it.
- Output is split on `/\r?\n/`, consistent with the rest of this file, and
  `git()` trims.

G0, the smaller alternatives, all rejected: a call-local *cache* of a parsed value
is refused like any other - the one duplicate `(command, cwd)` pair that exists
when the two roots coincide is taken by issuing one live process for both facts,
not by remembering one; a pass-scoped or `deliver()`-scoped cache of any of the 17
is refused above; `remote -v` and `worktree list --porcelain` lose demonstrated
refusals; `rev-parse --git-common-dir HEAD` in one spawn is a real further -2 but
requires `assertWorktreeRepository` to return heads across the function boundary,
disturbing ISS-189's landed lines for two spawns, so it is not taken here;
`rev-parse --abbrev-ref HEAD` instead of `branch --show-current` prints `HEAD`
when detached and buys nothing the v2 header does not already give. Deleting the
orchestrator's own `verifyWorkspace` demand at `delivery.ts:1161` because
`runGate` re-verifies at `delivery-adapter.ts:822` would remove a whole redundant
call, but it moves the guarantee from the adapter-agnostic orchestrator into one
adapter that the `DeliveryAdapter` interface does not require to self-guard, and
gates are a small minority of the 32 calls. Not built here.

Accepted cost: the repository-root branch read and the three cleanliness reads now
share a parser with the head reads, so a single output-shape mistake affects four
predicates instead of one - and at coincident roots four of those facts arrive
from a single process. That is bought back by AC2's preserved eleven-variant
drift matrix, which fails if any one of those predicates stops discriminating.

If measurement at the implementation head shows the reduced per-call count does not
put the worst observed **closure** case at or below about 26785ms, that is an
**AC7 failure**, not a finding discharged by reporting it: the issue stops and
escalates to the host with the measured numbers and the actual remaining dominant
cost named. Reporting the residual cost is required in that case; it does not
satisfy AC7. Nothing else becomes available either way - do not raise a timeout,
add a skip, change worker or file-parallelism settings, stub `verifyWorkspace`, or
weaken a refusal to pass a gate.

## Done when

- **AC1 Twelve spawns per call at coincident roots, thirteen when they differ,
  every fact still live.** `verifyWorkspace` spawns exactly 12 Git processes per
  call when `controllerRoot` and `repositoryRoot` canonicalise to the same
  directory - the configuration every case this issue is measured against runs -
  and exactly 13 when they do not, and still establishes all 17 facts on every
  call: the root common directory and both effective remote URL sets at
  `repositoryRoot`, `worktree` and `reviewWorktree`; the controller revision and
  controller cleanliness at `controllerRoot`; the `main` branch and cleanliness at
  `repositoryRoot`; and the candidate head and cleanliness at `worktree` and
  `reviewWorktree`. `assertGitTarget` (`:505-521`) and `assertWorktreeRepository`
  (`:523-538`) are byte-unchanged and their nine spawns remain, and
  `assertControllerExecutor` (`:630-669`) is byte-unchanged. The remaining
  authority spawns are one `status --porcelain=v2 --branch` per **distinct**
  working directory, issued in the current order - controller, repository root,
  worktree, review worktree - after `assertWorktreeRepository`, so a family or
  target mismatch still refuses before any authority read. Coincidence of the two
  roots is decided by `realpath` + `samePath`, the canonicalisation
  `assertControllerExecutor` (`:636-640`) already performs; when they coincide the
  one output at that directory is evaluated against the controller revision, then
  the `main` predicate, then cleanliness, in that order. Cleanliness is decided by
  "no line outside the `# branch.*` headers", proven against a fixture whose branch
  is ahead of a configured upstream and therefore reports `# branch.ab +1 -0` while
  clean. Detached HEAD and unborn HEAD still refuse. No `DeliveryConfig` field,
  adapter interface member, exported signature, state-directory record, retained
  artifact, `delivery.ts` call site, timeout, worker setting, `vitest.config.ts`
  key, fixture body or platform skip changes. No fact outlives the single
  `verifyWorkspace` call that reads it: no cache, memo, module-level map,
  `WeakMap`, request-scoped object or lazily-initialised promise may carry any of
  the 17 facts across calls, across a verification pass or across a `deliver()`
  pass, and none may survive the call that issued it. Serving several facts of one
  call from one live process issued during that call is not retention, and is what
  this criterion requires.
- **AC2 Fresh authority and intervening drift are still caught.** The
  eleven-variant matrix at `test/dogfood/delivery-adapter.test.ts:805` stays
  eleven distinct cases and still asserts the exact call sequence. The count
  assertion at `:873` becomes **variant-aware**: the ten variants that run the
  shipped config (`:527-528`, where `controllerRoot` and `repositoryRoot` are the
  same path) assert 12, and `root-dirty` - which separates the two roots at
  `:823` precisely so it can isolate - asserts 13. A single fixed number there
  fails one way or the other; the expected argument vectors are updated per
  variant to match. Because `root-dirty` and `root-branch`, and each
  `%s-HEAD`/`%s-dirty` pair, now arrive through one command per distinct working
  directory, each must drift a different field of that command's output and each
  must still refuse on its own; a matrix that collapses to seven cases is a
  weakened gate, not a simplification. The membership assertion at `:892` no
  longer identifies *which* fact drifted, because the authority variants now share
  a command; discrimination is retained by each variant's own
  `resolves.toBe(false)` at `:878` and by AC3, and that is the intended reading,
  not a silently weakened assertion. The real-Git cases at `:912`
  (`foreign-fetch`, `foreign-push`, `extra-push`), `:968` (worktree-local
  fetch/push URL drift including the `multiple` tuples), `:1043` (repository alias
  with a rewritten review gitfile) and `:1120` (drift between drafts and between
  gate and publication inside one `deliveryStep`) keep their current assertions
  and still refuse; the command allow-lists those cases enumerate must not be
  broadened to accept any command, and are expected to need no change at all,
  because those cases refuse inside `assertWorktreeRepository` before any
  authority read is issued. Add a fresh-workspace case proving the first call on a
  newly constructed workspace reads the full per-call set for its configuration
  and accepts.
- **AC3 Negative control: nothing derived survives a single read.** Add one
  focused case that verifies a workspace, mutates a fact of each kind - a head, a
