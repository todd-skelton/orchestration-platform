## Context and evidence

Runtime slices require real macOS, Windows, and Linux evidence before their
implementation choices can be trusted. The repository bootstrap supplies the
runner skeleton. Round 165 found that the former packet named receipts and a
trusted default-branch harness without fixing their bytes, provenance join,
writer topology, registry ownership, diagnostics, retention, or timing rules.
The approved repair uses a protected `repository_dispatch` provider record as
bounded pre-ISS-029 evidence; status-check names are presentation, not
authority.

Round 234 found the same-host OS-principal isolation stack disproportionate to
this issue's threat model and replanned it out: candidates are always
independently reviewed revisions of this repository admitted through
protected-main dispatch, and each hosted job runs on a provider-fresh virtual
machine, so the per-job runner VM plus that admission boundary is the isolation
authority for ISS-006. Same-host principal isolation is parked with a named
unpark condition, not refused.

Evidence: `docs/architecture/contract-decisions.md`,
`docs/architecture/state-machines.md`, `ISS-000`,
`planning/pressure-tests/2026-08-24-round-165.md`, and
`planning/pressure-tests/2026-08-27-round-234.md`, plus the live-provider
recovery in `planning/pressure-tests/2026-08-27-round-235.md`.

## Scope fence

environment/raw-artifact/job-receipt/aggregate contracts, the adapter-only

aggregation, 30-day evidence retention, local advisory entrypoint, exact

allowing candidate code to select required tests or write receipts/aggregates,
OIDC/artifact attestation, status-check authority, live capabilities, review,
installation, state mutation, promotion, and any same-host OS-principal
isolation machinery (transient UIDs, AppContainer SIDs, Job Objects, privileged
setup/teardown helpers, isolation brokers, or compiled artifacts committed to
the repository). That machinery's unpark condition is a slice that must execute
candidate bytes which are not an independently reviewed revision of this
repository; the condition is owned by the self-host promotion path and is
revisited no later than `ISS-019`. Final release certification belongs to
`ISS-019`; authenticated bootstrap provenance belongs to `ISS-029`.

## Decisions already made

The literal ISS-006 ledger in `contract-decisions.md` is sole authority. It
defines nine portable closed records, the adapter-only direct protected-ref,
full protection, and provisional-provider records, their exact
members/enums/domains/bounds, and the derived aggregate
reducer. `Dsubject` is the complete canonical regular-file candidate tree with
the sole Git projection `100644 -> executable:false` and
`100755 -> executable:true`; every other mode/type or truncated tree refuses.
`Dcontracts` is the stable ISS-002 schema-version census; fixture bytes and
stable generator source/parameters have separate exact domains. The core sees
only opaque SHA-256 identities; GitHub/repository/workflow/run/job/artifact
terms remain in the GitHub Actions adapter.

The sole hosted entry is `repository_dispatch` type
`conformance_candidate`. GitHub supplies default-branch `GITHUB_REF` and
`GITHUB_SHA`; the plan job additionally requires protected `main`, exact
workflow ref/path, and `GITHUB_WORKFLOW_SHA = GITHUB_SHA`. The closed payload
has the sole member `candidateRevision`, naming one lowercase 40-hex commit in
this repository. Stable and candidate bytes use separate credential-free
roots. The stable registry alone derives the matrix. Before any candidate
process starts, the stable wrapper copies opened-handle-verified candidate
bytes into a fresh child of an exclusively stable-owned external parent,
consumes that child into the external execution artifact, and deletes the
child. Candidate code receives only the consumed artifact, never either
materialization path. Partial copy, parent/root movement, cleanup failure, or
unconsumed paths refuse; local filesystem mode is not cross-platform authority
and the executable bit remains bound by the authenticated adapter projection.

The plan and record jobs bind only the distinct direct
`github-conformance-protected-ref/v1` projection of literal
`GITHUB_REF_PROTECTED=true`; it proves that GitHub reported some protection for
the triggering ref and is never interpreted as a zero-bypass policy snapshot.
The full classic/ruleset projection is terminal-only because the read-only
workflow token cannot authenticate branch-protection administration data and
GitHub hides `bypass_actors` from callers without ruleset write access.

The isolation boundary for this issue is the provider-fresh per-job runner VM
plus protected-main admission of the reviewed candidate revision. Candidate
vectors execute in fresh child Node processes started by the stable parent in
a separate temporary tree outside either checkout. The stable parent alone
owns expected values, selected-head equality, output parsing, timing, result
normalization, raw observations, and receipts; candidate stdout is hostile
data and cannot be a receipt or PASS assertion. Its monotonic five-second
interval includes launch, module load, IPC, parse, full validation, response,
and terminal exit; candidate duration/PASS claims are ignored. Candidate
processes receive no stable path, secret, provider metadata, write token,
OIDC, cache, ambient environment, or aggregate authority, and no candidate job
performs a privileged operating-system operation. The repository contains no
compiled executable; everything executed builds from reviewed source. Every
remote workflow action is pinned to a reviewed full commit SHA; mutable
tags/branches/short hashes and installs outside the frozen integrity graph
refuse.

Candidate jobs upload only attempt-qualified untrusted observation artifacts.
A fresh stable-only job recomputes manifests and provider metadata, creates
portable receipts, and derives at most one aggregate. A later stable-only job
queries the exact run-attempt jobs/artifacts and writes the provisional
provider record. It binds `Daggregate`; the aggregate does not bind its
downstream record, so there is no digest cycle. No run artifact is hosted
authority or grants a capability/promotion verdict before the terminal
verifier returns PASS. After the run is terminal, the
administrator-authenticated independent verifier requires the exact
successful record job and attempt-qualified provider-record artifact through
live API digest/length/time/expiry checks. Observation and aggregate provider
identities are their explicit ZIP archive bytes plus exact extracted layouts;
the single provisional provider record uses pinned `archive:false`, so its API
digest/length bind canonical JSON written to exact attempt-qualified filename
`conformance-<runId>-<runAttempt>-provider-record.json`; the upload has no
ignored/competing `name` input. `recordedAt` is the provider `Date` header of
the last pre-upload jobs query, and the inclusive provider-time order is exact.
The verifier also reads full classic protection, terminally paginates ruleset
summaries, fetches every ruleset detail, and requires visible empty
`bypass_actors` plus the complete restriction union. Hidden/omitted bypass data
refuses. That post-job observation terminates the chain without asking the
record to attest itself.

The stable registry contains one `iss002-contracts` suite and exactly Linux,
macOS, and Windows required jobs. Future suites land through reviewed stable
registry/handler/vector/requirement rows without changing workflow logic. Each
receipt matches its own suite's `Dvector`; `Dregistry` commits the mapping and
the aggregate does not repeat one false global vector digest. Suite rows also
close helper/custody `REQUIRED|UNUSED` and `NONE|WALK_1000` arms, including
nullable timing. Candidate package discovery never changes the required
census. The stable 22-row vector census covers the exact ISS-002 domains,
ledgers, reflection cases, crash prefixes, and 1,000-record walk named by the
authority ledger.

The raw manifest has exact environment/report JSON and stderr/stdout text rows;
the environment row digest must equal the portable environment's
`osImageDigest`. Bytes are hashed without newline, encoding, locale, path, or
diagnostic normalization. Normalized result is only
`PASS|FAIL|UNSUPPORTED`; missing, duplicate, skipped, cancelled, timed-out,
unreadable, expired, mixed-run, or non-PASS evidence cannot produce an
aggregate. Local mode creates no record: it starts diagnostics with exact
`ADVISORY CONFORMANCE RESULT`, returns 0 only for all-PASS and 1 otherwise, and
cannot invoke a hosted serializer.

The 1,000-record vector runs exactly once in each of three fresh child Node
processes per OS. The stable parent's `process.hrtime.bigint()` measures the
complete launch-to-terminal-response interval, including startup, module load,
IPC, JSON parse, full genesis-to-head validation, selected-head response, and
exit. Every interval must be at most 5,000,000,000 nanoseconds; there is no
candidate time, warmup, averaging, best-of, or retry. Provider-verified
artifacts and metadata retain at least 30 days.

GitHub check names do not establish provenance because required checks do not
bind one event or workflow. The independently reviewed provisional provider
record, terminal-verifier PASS, and full protected-main policy snapshot are the
bounded pre-ISS-029 evidence. The
harness never promotes a candidate or routes the candidate's verdict into its
own authority. Actor identity is retained only in raw provider diagnostics; it
is not an authority member or part of `DproviderRun`.

## Operator actions

After the workflow lands on `main`, an administrator must:

1. verify the active default-branch ruleset requires pull requests, blocks
   deletion and force-push, and has no bypass that would let candidate bytes
   replace the reviewed workflow revision;
2. configure Actions artifact retention to permit at least 30 days; and
3. dispatch the exact independently reviewed candidate revision, retain the
   run/provider record, then run the post-terminal verifier over the successful
   record job, unique provider-record artifact, all three required jobs, and
   aggregate.

Do not configure a status-check name as conformance authority. Check names may
be displayed for convenience, but the provider record and independent review
remain required.
