## Why

Rule 4 makes the reviewer answer G0, "is there a simpler way?". The answer
is validated as a bounded string (`repair-policy.ts` `parseReview`) and
then lives only in `reviewer-terminal.json` under the WSL runtime root.
Measured on 2026-09-16: 63 self-run reviewer terminals under
`/root/orchestration-m1/runtime`, every one with a substantive G0, none
visible anywhere the operator reads. Several name concrete deletions ("remove
the now-unused queue digest helper", "queue.ts delivery() is now very long")
that no one saw.

The question is also unconstrained. One recorded answer proposed dropping the
cross-run lineage scan (`queue.ts` `accepted-replan-required`) in favour of
the accepted-replan claim file alone; the scan runs before any claim exists,
so that "simpler" shape changes behavior. A simplification that drops a
stated constraint is a regression, not elegance.

The PR body already carries measured line changes (`adapters/self.mjs`
`publication`, `adapters/chase-sets.mjs` `publication`), and delivery
already reads `reviewer-attempt` from `config.stateDirectory`. The
accepted review's terminal is beside it.

## Decision

Constraint: the verdict stays a bounded JSON object with the same keys, the
G0 string, and the 2000-character cap (ISS-150), so recorded verdicts keep
parsing and resume is unaffected. Simplest alternative: leave G0 as is and
read terminals by hand. Chosen: reword the launch-time G0 question to require
the same constraints, and print the accepted G0 in the PR body from the
existing terminal record. Accepted downside: the body grows by one paragraph
and a missing terminal now stops publication. Revisit when: a run records a
G0 answer that the PR body could not carry within the cap, or a refresh
comparison fails on the G0 line.

## Done when

- Every reviewer launch (initial, DELTA and gate-correction: `flow.ts`
  `workerPrompt` report line, `repair-adapter.ts`
  `sourceReviewerReportPrompt` and `reviewerReportPrompt`) phrases G0 as:
  "Is there a simpler shape that still satisfies every acceptance criterion
  and every stated not-built reason? Answer No with one reason, or name the
  shape and the constraint you checked it against." The wording is applied at
  launch, outside the saved source/reviewer prompt fingerprint
  (`flow.ts` `conflicting-run-configuration`). Verdict keys, the string
  type of `g0`, findings shape and the length cap are unchanged; the
  ISS-150 fixtures still parse.
- Self and Chase Sets `pullRequest` append `Review G0:` followed by the
  accepted review's `g0` after the line-change block. The text comes from
  `reviewer-terminal.json` in `config.stateDirectory`, parsed with
  `parseReview` against `config.run` and `config.candidateHead`. An
  absent, unparsable or wrong-head terminal is a `DeliveryBlocked` reason
  named in the draft, never a silent omission or an empty line.
- The body stays a pure function of the accepted candidate, so
  `delivery-adapter.ts` `publication` and refresh body comparison
  (`normalizeBody`) still match, and a forward-only refresh re-edits the body
  as it does today. A delivery whose `delivery-plan` was recorded by the
  previous executor either resumes with its recorded body or stops with the
  existing plan-drift reason; a test shows which, and the draft's evidence
  says so.
- Tests cover the three prompt sites, both adapters' bodies, the blocked
  terminal cases, and the resume case. Run typecheck, format:check,
  planning:check and test. Rule 4 in `docs/loop.md` states the new question
  and that the PR body carries the answer.

## Simplest shape and not built

| Not built                                   | Reason                                                                 |
| ------------------------------------------- | ---------------------------------------------------------------------- |
| Structured `g0` object or a G1 delete list | Recorded terminals show no malformed final G0; more keys fight the cap |
| Posting G0 as an issue comment              | The note path reconciles external mutation; the PR body is already ours |
| Automatic issue creation from G0            | Rule 7 intake stays with the operator                                  |

## Evidence

`missing-reviewer-terminal` blocks an absent, unreadable or non-JSON terminal;
`unreviewed-delivery-source` blocks an unparsable summary, wrong run/head,
invalid or over-cap G0, or a non-PASS review. Both are `DeliveryBlocked`
reasons; neither adapter omits the paragraph on failure.

The pre-G0 resume fixture in `test/dogfood/delivery.test.ts` covers both saved
plan states: an authorized plan resumes with its recorded body unchanged;
a plan without authorization stops with the existing
`unauthorized-delivery-plan` reason when the new G0 paragraph changes its
digest. No saved plan or prompt fingerprint is migrated. Adapter tests cover
both bodies, replay and terminal failures; the forward-only refresh fixture
checks that the edited body file carries the current G0 answer.

## Out of scope

Changing what blocks (notes never block), reviewer ladders, the verdict
schema, learning-note intake, any Chase Sets Quality Packet key, or reading
G0 back into a later attempt's prompt.
