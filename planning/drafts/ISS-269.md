## Why

On 2026-10-24, retained planning recovery for [ISS-267 Prevent worker self-interrupts during silent heavy verification](https://github.com/todd-skelton/orchestration-platform/issues/846) selected the self author ladder's rung 2 (`family: fable`, `effort: high`). Both planning authors were launched with `-m null` and stopped before provider reservation with `model_not_found: unknown provider for model null`. The host-owned registry was healthy: `D:/Users/ToddS/AgentPools/state/model-registry.json` is `model-registry/v2`, generation 7, authority digest `f2b3d2c923541196`, and `families.fable.current` is `claude-fable-5-1` (the captured registry lines are 2, 54-56 and 1963-1964). The planning path selects and stores a family placement in `scripts/dogfood/planning-repair.ts`, then calls the native launcher without the `routing.ts` `resolveRole` materialization used by `flow.ts`; `dispatch-adapter.ts` consequently serializes a null model. This is a platform code defect, not a registry correction or a new recovery allowance.

The retained incident is a non-execution: no provider reservation, attempt, charge, retry, parking, or verdict authority is changed. The implementation must make newly selected planning author and reviewer placements concrete through the same resolver and registry snapshot contract as ordinary flow, while retaining already recorded placements byte-for-byte and preserving every ladder and ceiling.

## Scope fence

In scope are the planning author and planning reviewer launch/configuration path, the shared resolver/config composition needed to call it safely, and focused tests under `test/dogfood`. The implementation may add a narrow shared `dispatch-adapter.ts` assertion that a native request never receives a null model. It must not change ordinary ladders, rung advancement, retained intents, retry or native-launch ceilings, reservations, charges, participants, parking, review/verdict authority, registry policy, provider policy, heavy-verifier behavior, executor/runtime state, or the retained ISS-267 records.

## Simplest shape

Before a new planning native launch or reservation, call the existing `routing.ts` `resolveRole` with the selected role and rung, carry its concrete model plus family, generation, and authority digest into the launch config, and use the resulting config for the existing launch. Add one shared fail-closed null-model assertion at request composition and focused planning/flow/dispatch coverage; do not create a second resolver or a planning-only registry format.

## Done when

1. Every newly selected planning author or reviewer family placement is materialized through the same `resolveRole` and model-registry snapshot path as `flow.ts` before native launch or reservation. The launch config and saved intent carry a concrete model, effort, family, generation and authority digest; retained intents and retained placements are reused without re-resolution or rewriting. A focused regression is red at implementation head `445b98b772edb4d66326cf6e47fc1ad1c44c4755` and green after the fix.
2. The retained ISS-267 rung-2 fable case uses the checked-in generation-7 registry fixture and emits `claude-fable-5-1` in the native request rather than `null`. The regression covers both planning author and planning reviewer selection, and a shared dispatch-adapter check proves no request argument contains `-m null` or an undefined model.
3. Missing, unreadable, malformed, stale, null, or absent family-current registry states refuse before reservation and before native launch with the existing named `model-registry-unavailable` or `provider-model-refused` contract as applicable. Each negative records zero reservation/launch records and is discriminating: with all non-governing inputs frozen, deleting or bypassing the named guard makes the candidate control fail.
4. Literal placements and ordinary source, repair, reviewer, retry, refusal, rung-advancement, and retained-intent paths remain unchanged. Tests cover the planning author sibling and planning reviewer sibling, not only the normal `flow.ts` path, and prove that a registry generation change affects only a new intent rather than a retained placement.
5. The implementation preserves all existing authority and budget semantics: no attempt/native-launch ceiling, retry, reservation, participant, charge, parking, review or verdict rule changes; the retained ISS-267 count and null-worker evidence remain untouched. An exact-head reviewer directly reruns changed tests and inspects the full diff, never through ControllerBattery or ControllerPrecursor.
6. Planning/review/documentation lanes inspect bounded evidence and run only cheap focused checks. Any heavy command refuses with exit 73 before reservation and is non-execution, not PASS and not a consumed attempt; heavy reproduction is returned to the host for an attributed implementation/verifier lane. The host, not this issue, owns full `pnpm test` and hosted bootstrap verification.

## Defect-class constraints

- `missing-fail-closed-regression-evidence`: freeze all non-governing inputs for each registry refusal, run the candidate and a named guard-deletion/bypass mutant, and require candidate-green plus mutant-red; a refusal reached through another guard is not evidence.
- `validation-misses-sibling-seed-path` and `lifecycle-repair-misses-sibling-retained-state-entrypoint`: enumerate and exercise both planning roles and the ordinary flow sibling, including fresh selection, retained intent and retry, while preserving destructive/reset-free paths.
- `state-machine-steady-state-missing`: name the retained placement as the steady state and prove a second observation/step is inert with no re-resolution, new launch or changed saved bytes.
- `retained-artifact-schema-ratchet` and `retry-events-double-count-terminal-outcome`: old planning records remain readable and unchanged; do not fabricate missing model provenance, append a worker, refund a non-execution, or count a retry twice.
- `provider-fixture-diverges-from-executable-mapper`: derive or validate the generation-7 fixture through the existing registry schema/resolver and prove fixture-to-launch equivalence; do not hand-spoof a desired model.
- `presence-evidence-treated-as-completeness` and `canonical-artifact-directory-masks-missing-payload`: inspect bounded request arguments, terminal status and reservation records, not merely artifact-directory presence.
- `mandated-external-assertion-contradicts-authority`: carry the fresh host registry probe at the exact resolver lifecycle moment; stop on contradiction and label synthetic controls unmistakably.
- `parallel-node-verifiers-exhaust-host-memory`, `format-check-not-run` and `unrunnable-verification-command`: use only bounded cheap commands in this lane, resolve each declared script against the exact trusted manifest, run the formatter check on the committed planning diff, and leave heavy/full-suite verification to the host.
