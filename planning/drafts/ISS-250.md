**UNREADY: decision `platform-self-install-decision-r1` is FINAL (APPROVE_WITH_AMENDMENTS, folded in below); `ready` waits for an independent COMPLETE planning review of this body.**

## Why

A landed platform fix takes effect only after the host installs it. The Chase
Sets container holds eleven host scripts as of 2026-10-09,
`.orchestrator/m1-executor-upgrade-<sha>.sh` (4c1287e, 4d52bec, 484d911,
e7d270c, 18bddd3, d9d0455, 2d1e3a1, ce7debe, a1ab41d, 2a53b7b, a3b4407), with execution logs under
`.orchestrator/logs/m1-executor-upgrade-*.out`. Each script refuses when a
supervisor is live (`m1-executor-upgrade-ce7debe.sh:6`), fast-forwards
`/root/orchestration-m1/repo` to an exact `origin/main`, runs
`pnpm install --frozen-lockfile`, and checks porcelain. The host then resumes
the run through `scripts/executor/start-loop.ps1 -Resume`. That is one host
script and one restart per landing, against M1's exit evidence of "no per-item
host script or manual step" (`docs/loop.md`, Milestones). M1 and M2 share this
executor (handoff section 1, executor row).

## Decision (FINAL `platform-self-install-decision-r1`, claude-fable-5-1/high, 2026-10-09: APPROVE_WITH_AMENDMENTS)

1. **Authority.** `docs/loop.md` Running (:1026-1028) requires independent
   exact-head PASS plus three-OS green before a host install. Equivalent: let
   `S` be `origin/main` after fetch. `S` must be a fast-forward of
   `executorHead` (`git merge-base --is-ancestor`); otherwise record
   `upgrade-deferred:not-fast-forward`. Walk
   `git rev-list --first-parent executorHead..S`. Each step `C` is admitted if
   (a) some `merge.json` under `config.stateRoot` written by this executor's
   self runs has `mergeCommit == C` (regardless of C's parent count; native
   landings are squashes, `delivery-adapter.ts:2069-2076`, and the record
   implies the native exact-head PASS and observed `REQUIRED_CHECKS` on the PR
   head), or (b) `git diff --name-only C^1 C` is confined to `planning/`.
   Branch-side commits of a merge are not evaluated; the merge's first-parent
   diff is the complete change. Additionally the push-event `bootstrap` run on
   `S` must have `success` for every `REQUIRED_CHECKS` context
   (`adapters/self.mjs:27`; `Node 24 / windows-latest` aggregates the three
   Windows jobs, `bootstrap.yml:90-93`). Any unadmitted step, missing witness,
   or incomplete or non-green context defers to the host with
   `upgrade-deferred:<step>:<reason>`. The wrapper installs exactly `S`;
   `origin/main` having moved past `S` by install time is neither a failure
   nor a deferral. Checked against history: all 23 first-parent steps
   `4c1287e..a3b4407` (the 11 host installs) are admitted by this rule.
2. **Exclusion.** Every attached wrapper body holds a shared `flock` on
   `$TASK_ROOT/executor.lock` for its supervisor's lifetime. The installer
   releases its own shared lock only after its supervisor exits, then takes
   `flock -xn`. If any other run, M1 or M2, holds the lock, the install is
   deferred and the wrapper restarts the supervisor on the current head. A
   wrapper that cannot take its shared lock, because an install holds the
   exclusive lock, waits up to 10 minutes and then exits `executor-busy`.
   The lock descriptor is opened by the body and closed for the supervisor
   pipeline (`9>&-`), so no supervisor or worker inherits it. Wrapper-emitted
   stops (`executor-busy`, `executor-install-failed`,
   `upgrade-requires-restart`) are JSON protocol lines
   `{status, run, observedAt}` on stdout, and `start-loop.ps1` adds them to
   `$terminalStatuses` (:222); this Windows-side change takes effect on the
   host's next start.
3. **Failure steady state.** Before the fast-forward, the installer writes
   `$TASK_ROOT/executor-install.json`
   (`{state:"installing", from, to, at}`). On success it removes the file.
   On any failure it rewrites the file with state `failed` and the failed
   step, and every wrapper refuses to start a supervisor while that file
   exists (`executor-install-failed`, class `halt`) until the host repairs
   and removes it. Wrapper order: shared lock, then state-file check, then
   supervisor start. A file in state `installing` blocks the same as `failed`.
4. **Self adapter only.** Only runs whose config has `adapter: "self"` may emit
   `upgrade-ready`. A replaced supervisor restarts its native-DB correlation
   counter at zero (`supervise.mjs:252`), and the attached Windows parent
   rejects non-increasing correlations (`start-loop.ps1:111`), so a re-executed
   Chase Sets supervisor would break its native-DB channel. Self runs do not
   use that channel. Chase Sets (M2) runs still take the shared lock, so they
   defer self installs while they run, and they never install.
5. **M1 exit wording.** Rewrite the M1 row (`docs/loop.md:2146`) to "through
   one attached `start-loop.ps1` invocation (one ISS-219 wrapper binding) with
   no per-item host script or manual step". A self-install re-exec of the
   supervisor inside that binding counts as one invocation; the report lists
   each re-exec with `from`/`to` SHAs, separately from automatic retries and
   host restarts.

Rejected alternatives: keeping the host scripts (a manual step per landing);
a fresh clone per issue (duplicates worktree and saved-run paths); an install
daemon (a second writer).
Accept a host restart when S touches `scripts/executor/`,
`scripts/dogfood/process-ownership.mjs`, `package.json` or `pnpm-lock.yaml`,
by choice for the package files, and because the wrapper body and the Windows-side
`scripts/executor/` files (`start-loop.ps1` runs from the Windows checkout) cannot be replaced by a WSL install.

## Done when

1. **AC1: boundary.** Only after a completed cycle and before the next
   selection does the supervisor exit with `{status:"upgrade-ready", sha}`,
   and only if decision point 1 holds for S. Otherwise it continues and
   records `upgrade-deferred:<reason>` once per S. Controls exercise the real
   first-parent walk: admit a #774-shaped squash and a #779-shaped planning merge
   with branch commits; refuse an unwitnessed implementation step, a witness for a
   different SHA, and a missing or failed required context.
2. **AC2: exclusive install.** The wrapper performs decision point 2 and
   then `git merge --ff-only S`, the frozen install, and a porcelain check. A
   restart-only diff stops `upgrade-requires-restart` (class `wait`, non-parking)
   before any mutation.
3. **AC3: durable failure.** Decision point 3. A failure injected after the
   merge stays blocked across a new `start-loop.ps1` start, and an `installing`
   file left by an interrupted installer blocks a new start.
4. **AC4: re-entry.** After a successful install the wrapper re-executes the
   supervisor with the same config. The run resumes through ISS-133 with
   records, reservations and allowances unchanged. The Windows parent stays
   attached, and the ISS-219 cgroup membership and invocation binding are
   unchanged.
5. **AC5: tests.** `test/executor.test.ts`: green install; peer holding the
   shared lock defers; an M2 start that races the install waits; restart-only
   diff; failure persisted across restart. `test/dogfood/supervise.test.ts`:
   the `upgrade-ready` boundary, the deferral reasons, and a Chase Sets adapter
   config that never emits `upgrade-ready`. A mutant that drops
   the exclusive lock must fail the race control. A child holding fd 9 must not
   block `flock -xn` (descriptor closure). `start-loop.ps1` accepts the three
   wrapper statuses as terminal, tested through its dot-source path (:316-317). The new stop reasons are added
   to `fault-class.ts` and pass its inventory ratchet.
6. **AC6: docs.** Update `docs/loop.md` rules 6 and 9, Running, and rewrite the
   M1 row per decision point 5.
