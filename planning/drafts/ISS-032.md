## Context and evidence

Supervisor, adapters, and worker hosts need credentials after a user-session
restart without ambient inheritance or durable secret records. Implement only
the exact backend matrix passed by `ISS-031` under the credential contract.

## Scope fence

In: credential reference schemas/parsers, bind/inspect/revoke commands,
the exact probe-admitted custody-principal/backend adapters, role/capability
checks, statically named broker-side bounded operations,
Codex-home reference, lock/expiry/revocation health, zeroization, receipts,
internal one-use recovery and host-evidence key APIs, and the closed bootstrap
capability-verification path; closed prepare/activate/abort successor-client API
and installation-scoped active-client generations; private broker core/factory, exact probe-selected
IPC/service definitions and pinned Windows service-wrapper asset,
install/upgrade/restart/remove transaction library, and
one-use operator provisioning channel.

Out: secret prompts/files/argv, cloud vaults, unattended pre-login unlock,
credential rotation policy, project-specific scopes, or storing raw secrets in
platform state.

## Decisions already made

The broker implements only the probe-admitted OS/backend/version/custody matrix.
Same-user secrecy is never inferred from a private API or clean environment. Locked,
missing, revoked, expired, wrong-user, or unknown reference refuses before
external access. Durable outputs are non-secret and redacted by schema.

## Acceptance criteria and evidence

1. Bind validates a provisioned native reference and exact role/capability set
   without accepting or persisting secret material. Evidence: filesystem/state/
   argv/environment delta and secret canary scans.
2. Statically registered broker-side operations and Codex-home launch expose
   only the requested admitted capability to the exact role/attempt, then
   zero/release it. Direct `CredReadW`, `SecItemCopyMatching`, Secret Service,
   filesystem, process-memory, and broker-endpoint attacks from every other role
   and unlisted process fail before secret return. Evidence: three-OS attack,
   concurrency, and cross-role canaries bound to the passed probe topology.
3. Cold user-session, locked, missing, moved, wrong-user, expired, revoked, and
   extra-capability states reduce exactly per the lifecycle on all admitted OSes.
   Evidence: state/restart matrix.
4. Revoke increments generation before future access and cannot race into a new
   callback/launch. Evidence: barrier-controlled revoke/read tests.
5. `@orchestration-platform/credentials` replaces only the static `credential`
   CLI placeholder and passes the canonical argv/envelope matrix.
6. Only a caller holding `release.recovery-admin` may ask the broker to create a
   one-use recovery capability. The broker generates it with the OS CSPRNG,
   writes raw bytes directly to the native store, returns only the bound
   reference/digest, and atomically consumes/revokes it without exposing bytes.
   Evidence: caller-bound API/schema tests, OS entropy/store receipts, crash at
   every create/consume boundary, concurrent consume, replay, wrong-binding, and
   secret-canary scans on all admitted OSes.
7. Closed `host.evidence-admin`/`host.evidence-sign` APIs generate, store, sign,
   and revoke host Ed25519 keys without raw-key egress; every call binds exact
   host/user/state/collector/enrollment identity. Evidence: three-OS caller-
   capability, creation/sign/revoke/restart, wrong-binding, copied-reference,
   concurrent-sign/revoke, and private-key canaries.
8. `createCredentialBrokerService({ operationRegistry })` validates the exact
   closed operation descriptor/schema/capability/digest shape and stamps
   `production/v1`. The separate
   `createHostCustodyBootstrapBrokerService({ hostMethodManifest })` accepts
   only the exhaustive three-method `host-method-manifest/v1`, stamps
   `host-custody-bootstrap/v1`, and has no operation registry or downstream
   dispatch path. Core tests use fixed synthetic production operations;
   arbitrary callbacks/endpoints, dynamic registration, missing/extra/
   duplicate/moved rows, secret-return schemas, capability expansion,
   cross-profile client/reference/request substitution, and every downstream
   operation against the reduced factory refuse before native-store/network
   access. Real production descriptor composition belongs to `ISS-020`.
9. The exact `broker-client-manifest/v1` is compiled by the internal non-exported
   build-only `packages/credentials/build/compose.ts` generator into narrowed
   private-`WeakSet` object clients for only
   the listed package/executable compositions. No generic constructor or
   registration export exists. Evidence: export/deep-import/bundle census and
   forged/lookalike/serialized/replayed/unlisted/cross-caller capability tests
   that refuse before native-store access on all OSes. The generator is consumed
   only by the three predeclared client-composition aliases and is absent from runtime exports,
   tarballs, installed source maps, and emitted module specifiers. These object
   clients authorize broker operations but do not substitute for OS custody;
   the `ISS-031` direct-store denial suite is rerun against installed bytes.
10. The broker core plus lifecycle library implements the exact passed Windows
    WinSW-hosted SCM, macOS LaunchDaemon,
    and Linux systemd identity/service/IPC contract. The transaction library can
    plan, install, read back, upgrade same-authority bytes, restart, recover, and
    remove one exact digest without leaving duplicate principals/endpoints or a
    writable binary. The Windows package contains the exact probe-hashed WinSW
    2.12.0 asset/license/config generator and binds the absolute Node/broker
    digests. Evidence: three-OS clean-host/reboot/fault matrix plus
    worker connect, endpoint discovery, handle duplication, impersonation,
    replay, copied executable, wrong principal, and service-definition mutants.
11. Only `release.successor-admin` may prepare one inactive successor admission
    bound to an exact reviewed candidate/promotion transaction, activate it after
    matching atomic `active-release/v1`, or abort it only while the cleanup gate
    remains `PENDING`. Reference
    secrets remain installation-scoped; activation atomically advances broker-
    client generation to N+1 and revokes N ordinary authority without
    reprovisioning. Crash/replay/concurrent/wrong-candidate, executable,
    operation-manifest, active-record, installation, generation, N1-self-call,
    and skipped/reordered handoff mutants follow pre-activation rollback or post-
    activation forward recovery exactly. Evidence: three-OS barrier matrix and
    secret/process/endpoint census.
    Recovery uses that same closed `activateSuccessorClient` method—no fourth
    client method. A newly launched predecessor reconstructs the private client,
    re-reads durable arguments, and authenticates the current launch generation;
    one-use capability consumption creates a durable transaction-bound
    `recovery-authorization/v1` at the canonical transaction path with exact
    `CREATED_UNCONSUMED`→`CONSUMED_BOUND`→`REVOKED` CAS semantics, current
    immutable launch-state/pointer bindings where applicable, and terminal native-item cleanup. Its
    discriminated `bootstrap-n0`/`successor` modes require their own exact fields
    and canonical nulls: N0 never invents predecessor/successor/fence/cycle/
    launch values; successor requires them. Mode-specific terminal predicates
    distinguish N0, uninterrupted successor with authoritative launch absence,
    and attached successor with `TERMINAL_COMPLETE`;
    pre-consumption expiry refuses, but the binding must be consumed before the
    irreversible boundary and then cannot expire until terminal broker-internal
    revocation. Its successor pre-launch form has canonical null launch binding;
    only the launched predecessor's broker-authenticated LIVE channel may CAS-
    attach the immutable source/generation/attempt/READY/initial-LIVE and gate/
    fence-root identity—not a mutable current-pointer digest. Every broker call
    verifies that the canonical pointer descends from that initial LIVE through
    the same-source immutable chain. Adjacent `AUTHORITY_REBIND` records advance
    head digests without updating or repeating attachment. First attachment after N
    pre-handshake failures may target N only when every prior immutable attempt
    is terminal-retryable and the binding remained null. Later attached
    generations require terminal-to-adjacent READY→LIVE chains. The shim has no attachment
    client. Same-target
    activation is byte-idempotent. Evidence:
    crash before/after capability consume and broker CAS, multiple sequential
    launch generations, adjacent/nonadjacent authority-head rebinds, and process/broker restarts, already-activated read-back,
    broker-internal terminal revoke cleanup with no fourth client method,
    canonical cleanup-gate blocking until its receipt for N0, null-launch, and
    attached successor paths, N0/successor mixed-mode/null mutants,
    uninterrupted null-launch revocation, and cross-transaction/wrong-target
    refusal, including failure before handshake, first attachment at generation
    two, duplicate/concurrent first attachment, and skipped attached-generation
    mutants.
    A pre-fence continuation may use only the consume method while gate
    `PENDING`; it never attaches recovery authorization. Consumed state CASes
    `NOT_PUBLISHED` → `PUBLISHING` before fence creation/read-back and then
    `PUBLISHING` → `PUBLISHED`. After fence publication
    it terminalizes/archives/exits before a fresh fence-backed generation-zero
    LIVE chain performs first attachment. Before gate creation, the existing revoke method handles only exact
    `CREATED_UNCONSUMED` abort with gate/irreversible-state absence. After gate
    creation it always refuses; gate `ABORTING` makes the broker reconciler sole
    revoker for unconsumed/consumed state, and `ABORTING` admits no broker client
    or attachment. After shim-proven staging absence, the reconciler compare-
    removes and reads back the exact pending admission before native-item removal
    and authorization revocation. Successor `NOT_PUBLISHED` requires fence
    absence; `PUBLISHING` accepts only fence absence or the exact precomputed
    fence and the shim completes exact publication even under abort;
    `PUBLISHED` requires the matching fence retained through revoke. Abort terminalizes/removes any pre-fence launch before final
    gate cleanup. Successor activation CASes gate `PENDING` → `ACTIVATING` before
    active-release CAS; abort CASes `PENDING` → `ABORTING`, and exactly one wins.
    If abort wins with a fence-backed READY/LIVE/attached launch, its channel is
    denied and broker cleanup requires source-specific `TERMINAL_ABORTED`
    archive/pointer removal. If `ACTIVATING` wins, abort refuses even while the
    active record still names N.
    Evidence: N0 and successor abort/restart/race matrices before/after every
    staging, admission, native-item, revoke, and fence boundary, plus moved-
    admission and false-absence controls.
12. Both closed service factories share only the native-custody and lifecycle
    primitives; factory/profile/manifest identity is carried through service,
    endpoint, client brand, reference, request, receipt, and upgrade records.
    Neither factory accepts the other's manifest argument or can be widened by
    omission/defaults. Evidence: exhaustive compile-time/API/bundle census and
    cross-profile substitution matrix on all three OSes.
