## Why

This is the M2 exit evidence: the loop delivers real Chase Sets work while the
incumbent controller is still available as the fallback.

Operator prerequisites on the WSL Ubuntu executor, done by Todd or Claude
before this issue is labeled `ready`:

- `/root/orchestration-m2/repo` is a clean clone of `chase-sets/chase-sets` on
  `main`, and its pnpm store has been warmed once online with
  `pnpm install --frozen-lockfile --ignore-scripts` so the loop's offline
  setup install succeeds.
- `/root/orchestration-m2/loop.json` names `"adapter": "chase-sets"`,
  `"repository": "chase-sets/chase-sets"`, that executor root, its own state
  and worktree roots, and the same tools as the M1 config.
- Todd names the target milestone by making it the first pull-window entry
  under the product's outcome policy. It should be small and low-risk.
- `gh` on the executor is authenticated as an account with push access to
  the repository (verified 2026-09-11).

## Done when

- One `loop:supervise` invocation with that config lands at least one Chase
  Sets issue end to end: selection by the adapter, author, independent
  review, `PR Required` green, landing through the merge queue, and deploy
  verification, with the loop closing the issue.
- The invocation continues until the milestone's runnable set is empty or a
  typed stop. Every stop posts its learning note on the Chase Sets issue.
- The incumbent controller was not used for those issues; any manual step is
  recorded on this issue and becomes a new `ready` issue here.
- Run records stay outside both checkouts and are linked from this issue.

## Out of scope

Routine delivery of all Chase Sets work (ISS-111). Repairing a failed staging
deploy; that stays a learning note for a person.
