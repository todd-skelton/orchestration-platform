## Why

Chase Sets is the first real consumer. Its repository is `chase-sets/chase-sets`.
Its incumbent controller (the `milestone-orchestrator` skill and
`chase-sets/.orchestrator`) already encodes readiness, branch naming, landing
and deploy verification. The adapter translates those rules; it does not
rebuild them. The facts below were read from the repository on 2026-09-11.

Facts the adapter must match:

- Readiness is defined by the product repository itself:
  `scripts/dispatch-window.mjs` (`derivePullWindow`, `isRunnableRefined`),
  `scripts/milestone-policy.mjs` and `scripts/backlog-classify.mjs` on `main`.
  A milestone is executable when its description carries the
  `<!-- outcome: {...,"status":"committed"} -->` marker; an issue is runnable
  when open, refined, in an executable milestone, and all native blocked-by
  issues are closed. Never infer order from titles or dates.
- `main` has a ruleset with one required check, `PR Required` (the
  `pr-required` job in `.github/workflows/platform-pr.yml`), and a merge queue
  (squash, all-green, two entries). Landing means adding the PR to the queue;
  the queue merges it.
- Deploy verification: the newest `platform-production.yml` run for the
  merged commit whose `Deploy Staging` job actually executed (not skipped)
  succeeded, including its "Verified immutable active release" digest step.
- Branches are `codex/<issue>-<slug>-g<attempt>`. Local pre-push gates per the
  product `AGENTS.md` are the `verify:static:scoped` and `typecheck` scripts;
  hosted CI owns the full suite. Issue bodies have a Context heading and an
  acceptance section; the author works from the body, not a draft.

## Done when

- The seam gains `issueContext({ repository, key, number, executorRoot })`
  returning `{ title, body, acceptanceCriteria, rules }`, and
  `queueConfigFromLoop` in `scripts/dogfood/queue.ts` stops reading
  `planning/roadmap.json`, the draft file and `docs/loop.md` itself. The self
  adapter returns the draft title, its "Done when" bullets and `docs/loop.md`;
  behavior on this repository is unchanged. Issue keys become opaque
  `[a-z0-9-]+` strings everywhere the loop currently requires `ISS-\d{3}`.
- `adapters/chase-sets.mjs` implements the seam:
  - `selectCandidates` fetches milestones (id, number, title, description,
    state) and open issues (number, title, labels, issue type, milestone,
    blocked-by states) with `gh api graphql`, imports the three product
    readers from `<executorRoot>/scripts/`, takes the first pull-window
    milestone, and returns its runnable refined issues ordered by
    `priority:p0..p3` then number, keyed `cs-<number>`.
  - `issueContext` returns the issue title, body, the list items under the
    body's acceptance heading (the whole body as one criterion if none), and
    the product `AGENTS.md` as rules.
  - `branchName` returns `codex/<number>-<slug>-g<attempt>`.
  - `pullRequest` returns title = issue title, body = `Closes #<number>` plus
    the existing line-count block, draft first.
  - `requiredChecks` returns `["PR Required"]`.
  - `mergeMethod` returns `{ method: "queue" }`; the delivery adapter enqueues
    with `gh pr merge <n> --squash`, then observes until the PR is merged or
    the queue removes it, which is a typed stop.
  - `afterMerge` verifies the deploy as described above within a bounded
    window; failure is a typed stop `deploy-not-verified` with a learning
    note, never an automatic repair.
  - Local gates before publish are `verify:static:scoped` and `typecheck`;
    there is no planning mirror.
- The adapter carries no platform logic and `scripts/dogfood/` carries no
  Chase Sets vocabulary.
- `node adapters/chase-sets.mjs --dry-run` with `CHASE_SETS_ROOT` set to a
  checkout prints the pull-window milestone, the selected issue, its branch
  name and PR title without launching a worker. Its output against the live
  repository is posted on this issue as the learning note.

## Out of scope

Running a Chase Sets issue through the loop (ISS-110). The Claude worker host
(ISS-109). Changing the product readiness scripts or the merge queue.
