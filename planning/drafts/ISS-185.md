## Why

The host's 2026-09-17 observation on platform #367 records native ISS-183
attempt 3 failing a new publication on another PR's hosted failure. In run
`m1-malformed-author-recovery-20260917T1635`, PR #566 published unchanged head
`ab2fdadac4404814ccf0090b7b144ef80000ac3b`. Its saved `hosted-failure.log`
identifies publication 566 but names PR #565's run `35270001390`, Windows job
`105366636997`, which had failed at 21:01:33Z. PR #566's own run `35276352971`
began at 21:23:05Z and was still active in the host's observation. Attempt 3
was already failed with six participants; attempt 4 started at 21:23:14Z.
Do not spend another attempt or mutate that history to reproduce the defect.

At 21:31Z, `gh pr checks 566` instead exposed its own pending jobs. The host
also observed six old/new rows in `statusCheckRollup`. The actual run API
identifies both runs as `pull_request`, `.github/workflows/bootstrap.yml`,
attempt 1, at the same SHA, but binds the older run to PR 565/source branch
`codex/iss-183-attempt-2` and the newer to PR 566/`codex/iss-183-attempt-3`.
Same SHA and a matching required-check name are not current-publication proof.

At executor `5929b9dfa917a4acec6db0ab2cd0dcba87885431`, `checks` in
`scripts/dogfood/delivery-adapter.ts` trusts the `gh pr checks` projection and
only reads workflow identities when required names are missing. `failedCheckLog`
checks run completion and SHA, not publication attribution. The delivery consumer
therefore turns stale failure into repair work; stale green can symmetrically
authorize early landing. Stale green is a required negative control, not an
observed landing in this incident. ISS-132/143 addressed absent required jobs
and startup visibility, not this present-but-foreign check set. ISS-141 owns
complete diagnostics, ISS-175 external branch protection, and ISS-182/183/184
different defects. None owns this attribution correction.

## Decision

Constraint: only the current publication's authoritative hosted results may
fail its work or authorize landing. Simplest alternative: delay a new PR's
first check read, rejected because elapsed time neither proves attribution nor
prevents stale green. Chosen: use the existing GitHub adapter's run/job evidence
to attribute required results before projecting pass, pending or failure, and
use that same attribution when collecting failure logs. Reuse existing delivery
observation, bounded startup wait and non-parking host-stop paths. No independent
provenance service, persisted observation protocol or new attempt budget.

Accepted downside: extra read-only GitHub requests and waiting when GitHub cannot
establish ownership. Revisit if a recorded non-Actions required context or changed
GitHub rerun contract cannot be expressed by the existing adapter. Do not build
general provider support preemptively or copy the product's CI classifier.
