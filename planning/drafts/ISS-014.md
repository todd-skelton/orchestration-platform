## Context and evidence

Self-hosting is safe only if the candidate cannot authorize or install itself.
See the trust model in `docs/architecture/vision.md`, state primitives from
`ISS-004`, review authority from `ISS-009`, and journal from `ISS-010`.

## Scope fence

In: separate `release-operation-plan/v1` assemble-certify/promote kinds,
candidate manifest, build provenance, conformance packet, independent review
packet, stable preflight, transactional install, installed-byte verification,
promotion receipt, N1+ pre-activation staging/abort, and post-activation forward
recovery. The promotion transaction owns the atomic active-release switch,
creation/update of the supervisor-shim recovery fence, two-phase broker
successor-client handoff, and successor-verification follow-up request; engine
terminalization owns the final fence clear.

Out: release scheduling, package-registry publishing, consumer auto-update, and
policy deciding whether a behavior change is desirable.

## Decisions already made

One immutable candidate identity binds all evidence. Release layout, recovery
issuer, and authority rules come from `docs/architecture/contract-decisions.md`;
states come from `docs/architecture/state-machines.md`. Stable code performs
every authority-bearing preflight and mutation. Bootstrap N0 remains forward-
only after its first destination mutation. For N1+, staged bytes and pending
broker admission remain explicitly non-authoritative and removable by only the
same transaction until the cleanup gate CASes `ACTIVATING`; after that decision
CAS, rollback is refused and only forward recovery is allowed, even before the
active-release pointer CAS.
Recovery uses only the exact injected `RecoveryAdminClientV1` and
`SuccessorAdminClientV1` fixed in
`docs/architecture/broker-client-manifest.md`; release code cannot construct or
discover a broker client.

## Acceptance criteria and evidence

1. Moved, self-reviewed, partially tested, or contradictory candidates refuse
   before mutation. Evidence: one negative fixture per authority field.
2. Crash injection at every install boundary ends in predecessor, successor, or
   resumable reviewed transaction, never an unclassified state. Evidence:
   complete transaction state matrix.
3. Installed bytes and manifest match the reviewed candidate before authority
   transfers. Evidence: read-back hashes and tamper negative control.
4. Recovery capability cannot be replayed or borrowed across transactions.
   Evidence: identity and revocation tests.
5. `@orchestration-platform/release` replaces only the static `release`
   command-family placeholder. Evidence: registry census and complete release
   command-envelope tests.
6. `assemble-certify` binds a fresh landed SHA/tree and stable-selected suite to
   `release-candidate-subject/v1` plus complete target receipts but cannot
   promote. `promote` requires a distinct accepted review of that exact candidate
   subject; worker-result review, pre-merge review, moved landed tree, or
   candidate-authored aggregation refuses. Evidence: operation-kind/subject-
   union matrix and five-cycle self-host fixture.
7. `createReleaseService({ recoveryAdminClient, successorAdminClient })` accepts
   only the privately branded narrowed clients injected by an authorized
   composition and invokes
   exactly create authorization → create/read back `PENDING` cleanup gate with
   created/expected-consumed digests → consume/read back `CONSUMED_BOUND` →
   publish/read back recovery fence,
   and broker-internal terminal revoke around the published transaction
   boundaries. Recovery proves/reuses the existing binding and never consumes
   again.
   Missing, forged, serialized, replayed, broad, or cross-client values refuse
   before installation mutation. Evidence: compile-time surface census and
   broker/release composition fault matrix.
8. Promotion stages verified successor bytes and broker admission, verifies
   `supervisor-shim/v1`, consumes/read-backs recovery authorization, durably
   raises the recovery fence only afterward, CASes the cleanup gate from
   `PENDING` to `ACTIVATING`, and atomically replaces `active-release/v1` as the
   sole active-identity point. Abort races activation only on `PENDING` →
   `ABORTING` versus `PENDING` → `ACTIVATING`; before either N remains active,
   while after `ACTIVATING` only the same N
   transaction may activate the broker's N+1 client generation, revoke N
   ordinary authority, emit terminal read-back, and record the mandatory
   successor-verification follow-up. Engine step 15 clears the fence only after
   exact promotion/broker/resource read-back. Evidence:
   barrier crash/replay/wrong-candidate matrix at every handoff boundary.
   Abort before gate creation uses client revoke plus authoritative gate absence.
   After gate creation it first records `ABORTING`; the shim/predecessor removes
   and proves exact staging absence, then the broker internally compare-removes
   and reads back the bound pending admission while
   applying the gate's fence-publication discriminator: `NOT_PUBLISHED` proves
   canonical fence absence; `PUBLISHING` accepts only fence absence or the exact
   precomputed fence and deterministically completes exact publication even if
   abort wins; `PUBLISHED` retains the exact
   fence through broker-internal revoke, then clears it. `ABORTING` never attaches recovery authority
   or receives any broker client. A gate-bound exact predecessor continuation
   resumes `PENDING` after caller death before consume or publication;
   only `PENDING` plus matching unconsumed authority receives the narrowed
   consume method. It must read back consumed state, CAS `PUBLISHING`, create/
   read back the exact fence, then CAS `PUBLISHED`. It writes terminal handoff
   evidence, exits, and leaves the shim to
   archive/remove the pre-fence launch before fresh fence-backed generation zero.
   Abort separately commits cleanup archive/head/removal. No visible fence may coexist
   with `CREATED_UNCONSUMED`. Evidence: create/gate/consume/fence ordering and
   crashes after each staging/admission/revoke/fence/head write.
   Crash specifically after gate creation before consume, after consume, after
   `PUBLISHING`, fence creation, `PUBLISHED`, and on both sides of pre-fence terminal handoff/archive/
   pointer removal; the shim must finish the immutable pre-fence source before
   creating fresh fence-backed generation zero and reject simultaneous,
   mismatched, or cross-source transitions. If abort wins any publication race,
   the child loses all clients, exits as `TERMINAL_ABORTED`, and the shim
   archives/removes its pointer before broker-internal abort completion. Abort
   winning at `NOT_PUBLISHED` creates no fence; a previously won `PUBLISHING`
   always reaches exact `PUBLISHED` before revocation. Both initial absent and
   exact-present `PUBLISHING` variants are crash-tested. If abort wins after a
   fresh fence-backed `READY`/`LIVE` chain exists, the broker denies its channel
   and the shim terminalizes it as `TERMINAL_ABORTED`, proves exit, archives,
   and removes the pointer before broker-internal admission/revoke/fence/gate
   cleanup. If `ACTIVATING` wins, abort refuses and recovery is forward-only.
   Evidence: races/faults at fence-backed READY, LIVE before/after attachment,
   both decision CAS outcomes, exit/archive/pointer removal, active-release CAS,
   revoke, and fence clear. Every gate/fence transition first writes immutable
   adjacent head history and CASes its current pointer; a live child pauses until
   the shim appends/CASes same-source `AUTHORITY_REBIND`. Faults cover old-launch/
   new-head after `PUBLISHING`, `PUBLISHED`, `ACTIVATING`, `ABORTING`, and fence
   `PREPARED` → `POST_ACTIVATION`; no rebind launches, reattaches, skips a head,
   or changes roots/process identity. Publication, abort, and activation writers
   must wait whenever the launch pointer has not acknowledged the current head;
   racing second-head writes refuse.
   Gate and fence initialization kills after deterministic root, ordinal-zero
   head, and current-pointer CAS; exact same-transaction root-only and root-plus-
   head prefixes resume one suffix, while head-without-root, current-without-
   both, multiple/mismatched bytes, and non-null initial predecessor refuse.
   Kill every recovery process in turn at steps 13, 14, and 15; the canonical
   current pointer must advance through create-once immutable transition records
   and one adjacent generation only after terminal proof,
   reuse the exact transaction/capability, forbid concurrent attempts, and
   eventually complete by a later scheduler invocation. Evidence: multi-crash
   launch/channel/fence transcript including shim death before/after child
   creation, single-child adoption, proven absence, ambiguity-to-unknown, stale
   channel, terminal archival/CAS cleanup, and a second recovered promotion.
