## Why

ISS-226 can determine whether interrupted work is safe to continue; it cannot
invoke itself after a VM loss. The existing attached Windows parent is already
the sole canonical launch path; its survival across the demonstrated class of
WSL update is unproven and must be captured before readiness.
Extend it with explicit bounded arming rather than installing a watcher.
Detection is at its child's EOF/exit, not a later chat or process-name poll.

### Existing-owner check

ISS-164 owns this parent, protocol, native-db bridge and child exit handling;
ISS-224 owns loss recording there. ISS-226 owns vacancy and interrupted-item
reconciliation. ISS-219 ownership and ISS-222 grace remain native, not
PowerShell copies. ISS-137 owns pause/explicit resume; ISS-138 owns attention
comments but stays observation-only in WSL. ISS-225's five classes are read
through native admission and grant no generic restart. ISS-133 permits a
separately authorized stopped-executor upgrade, not automatic fast-forward.
No existing roadmap owner supplies a Windows automatic recovery parent.

## Decision

Automatic recovery must survive WSL loss without acquiring a second delivery
writer or bypassing native fences. The simplest alternative is native startup
reconciliation invoked by a separate scheduled trigger. Select the selected
attached-parent architecture, an explicitly armed existing attached Windows parent calling
native admission and ordinary start within a fixed bound. Accept that recovery
ends when this parent dies and that unknown outcomes need host attention. If
the parent cannot survive the demonstrated WSL child loss with the private
stream intact, this architecture fails its acceptance rather than silently
expanding into a service.

### Guarantee boundary

The guarantee is deliberately limited to involuntary supervisor/Ubuntu VM
loss while this Windows parent remains alive and its armed inputs remain
unchanged. Windows reboot, parent death, legacy unbound runs, and automatic
service resurrection are not promised. A loss before the first attributable
run/invocation is attention, not a fresh run guess. The r6 incident predates
ISS-219 bindings and is not itself authorized for automatic re-entry.

## Done when

1. **Explicit arming at the existing entry.** Add opt-in `-RecoverLoss` to
   `scripts/executor/start-loop.ps1`; absent means today's one attachment
   and unchanged exit behavior. It is mutually exclusive with `-Resume`
   and `-PauseAfterCurrent`. Arming retains the exact config bytes/hash,
   run/state root, material verifier context, installed executor identity and initial invocation in a
   single small host-side recovery-session record under
   `%LOCALAPPDATA%\orchestration-platform\recovery`, outside both checkout
   and Linux runtime. No broad config framework. A separate manually
   authorized invocation is a new session, not a reset of native attempts.
   Existing sessions and their consumed reservations remain history. Test
   canonical script parameter composition and unarmed byte-equivalent
   protocol/exit behavior with the existing `startLoopHarness`.
2. **Detect, then reconcile before every restart.** After attached EOF and
   actual child exit, preserve ISS-224's note and exit facts. Only loss
   after an attributable nonterminal run can enter recovery. Invoke
   ISS-226 native admission in the configured host namespace; re-read it
   immediately before launch, after any wait, with pause, vacancy, durable
   phase, external intents and armed identities current. Use the same
   `Start-AttachedSupervisor`/`run-loop.sh` path, never `-Resume`, never an
   independent supervisor. No launch occurs on attention, changed
   config/executor, live descendant, unknown outcome, legacy ownership or
   terminal fence. All interrupted phases in ISS-226's table remain native:
   author/reviewer completion or remaining retry, exact hosted observation,
   and queue/merge/post-merge reconciliation before further effects.
   A synthetic attached-child loss followed by eligible admission launches
   exactly one continuation of the same run, not a new config or issue.
3. **Fixed durable bound, including ambiguous launch.** At most two
   automatic supervisor starts in one armed parent session, across all
   losses and successful intermediate progress. Before each start, persist
   its reservation in the session record; missing acknowledgement is an
   uncertain launch that consumes that reservation and requires fresh
   native vacancy/outcome reconciliation, never an immediate duplicate.
   Acknowledgement means the first protocol status line carrying the same run
   from the new child; its absence is missing acknowledgement.
   Do not reset the count on `observing-*`, success, changed note, new boot
   or resumed cycle. For each loss, at most six readiness observations,
   separated by delays of 10, 30, 60, 120 and 300 seconds (about nine minutes
   after EOF before exhaustion). Each native observation has a 30-second
   deadline. The window is derived from the September 30 System log: WSL
   service disabled 17:06:47.460Z, VM network detached 17:06:53-55Z, new WSL
   Service installed 17:07:20.902Z, VM network restored 17:07:39.8Z, about 53 s
   unavailable after the last 17:06:45.171Z status. F4's measured re-availability
   time must fit inside it. A deadline or WSL-unavailable read is unknown and
   creates no supervisor; only transport unavailability uses those bounded
   observation retries. A native safety refusal ends the session at once.
   Do not kill Linux or live run processes on a deadline; retain the exact
   probe identity and return attention if its exit is uncertain. Before
   launching, prove all owned probe commands ended. The fixed observation
   and two-start bounds are local recovery costs, not a new worker retry,
   attempt or provider-outage allowance. Tests crash the synthetic parent
   at reserve/launch/ack boundaries and prove retained state cannot produce
   a third start or replay an uncertain start. The parent's admission and
   probe `wsl.exe` invocations redirect or close stdin, so package-update
   prompts cannot wait for interactive input.
4. **Intentional endings win.** `idle`, `paused` and `blocked` terminate
   recovery, including `blocked` for a nominal `retry` reason; `complete`
   alone remains nonterminal. Pending pause also prohibits another start,
   rather than clearing it or continuing toward a boundary automatically.
   Handle Ctrl-C/cancellation before any cleanup in the recovery wrapper:
   durably disarm first, then preserve existing attached-child cleanup.
   Catch cancellation separately from child EOF or command failure. A
   cancellation before first status, while waiting, during admission or
   while attached must never schedule another start. If the parent is

   Synthetic tests keep all five ending/cancellation positions green and

## Out of scope

### Scope fence

Only the attached Windows parent's opt-in loss loop and its small durable
session outcome. Non-goals: a replacement controller, generic stop retry,
scheduled watcher, cross-host recovery or new delivery authority. Reuse the
ISS-226 phase table in full, not a partial PowerShell interpretation. All
preexisting attempts, verdicts, reviews, retries and external intents remain
unchanged except ordinary native continuation writes.

### Simplest shape

One surviving attached Windows parent calls native admission and the existing start path at most twice; no second scheduler or autonomous watcher.

## Defect-class constraints

- `state-machine-steady-state-missing`: enumerate unarmed, armed-attached,
  loss, observing, reserved, reattached, disarmed and attention states;
  retained terminal replay is inert.
- `steady-state-fast-path-skips-required-reconciliation`: reattachment or
  prior eligibility never skips fresh native admission after a wait.
- `fixture-only-health-integration`: exercise the actual PowerShell parent,
  native CLI composition, stdio and durable writer, not only a loop helper.
- `retained-artifact-schema-ratchet`: keep ISS-224's eight-key loss note and
  old runtime/config bytes; new session state lives separately outside them.
- `temporal-join-ignores-causality`: exact armed session, config, invocation
  and observed loss must agree; historical notes never trigger a new run.
- `retry-events-double-count-terminal-outcome`: persist reservation before
  each start and retain it on ambiguity; native attempts are neither reset
  nor charged merely for a preflight/readiness observation.
- `workflow-terminalizer-missing-early-cancellation`: disarm before cleanup,
  including pre-status cancel; forced parent death cannot self-resurrect.
- `missing-fail-closed-regression-evidence`: execute named bypass mutants
  with isolated governing inputs; unrelated refusal does not prove a fence.
- `mandated-external-assertion-contradicts-authority`: actual host evidence
  proves the lifecycle it observes; synthetic boot/PR facts stay synthetic.
- `unrunnable-verification-command`: present future activation parameters as
  a pending packet, not as a runnable current command or readiness PASS.
- `lifecycle-repair-misses-sibling-retained-state-entrypoint`: cover canonical
  entry, dot-sourced harness, native-db and cancellation paths together.
- `effective-configuration-fingerprint-omits-overrides`: bind verifier context
  and effective arguments as well as the file hash; drift refuses.
- `presence-evidence-treated-as-completeness`: a session/ack file merely
  existing is not an observed attachment or reconciled outcome.
- `stale-review-bound-to-wrong-head`: activation uses only the independently
  reviewed installed head; arming never upgrades or extends review authority.
- `raw-exception-message-in-structured-log`: emit bounded categories and safe
  pointers, with a synthetic secret-bearing-error negative control.
- `vitest-wall-clock-timeout-under-parallel-host-load`: recovery delays,
  deadlines and crash fixtures use an injected clock/sleep and synthetic
  transports. No test sleeps in real time and no test timeout is raised;
  open #716/ISS-221 tracks this Windows 30 s class.
- `future-capability-documented-as-current`: mark activation-gated behavior
  as not current until installed; reviewed planning does not activate recovery.
- `worker-tool-ceiling-kills-heavy-verifier-wrapper`: resolve the named
  commands at the implementation head; later full gates use the foreground
  exclusive verifier, and no timeout/load claim is accepted without the
